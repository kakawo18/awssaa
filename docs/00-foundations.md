# 第0章 設計の基礎と問題の読み方

> **この章の使い方**：サービス名を暗記する前に必ず目を通してください。AWS SAAの設問では、単なるサービス名ではなく「**どのような条件のもとで、なぜその構成を選択するのか**」という論理的な判断力が問われます。この章では、以降の全章で繰り返し活用する**6つの判断軸**、**可用性・耐久性・RTO/RPO**の正確な定義、そして**設問を正しく読み解く手順**の基礎を整理します。

---

## 0.1 サービス名の前に確認すべき6つの判断軸

**困りごと**：サービス名とキーワードを1対1で丸暗記していると、設問の前提条件が少し変わっただけで判断に迷ってしまいます。たとえば「S3へのプライベート接続＝VPCエンドポイント」と機械的に覚えていても、接続元がオンプレミス環境であれば適切な答えは変わります。

**仕組み**：設問で提示される条件は、大半が次の6つの軸のいずれかに分類できます。各章に掲載されている比較表も、これらの軸に基づいて設計されています。

| 軸 | 理解すべき本質 | 典型的な誤解・見落とし |
|---|---|---|
| **通信** | 名前解決（DNS）、ルーティング（経路）、通信許可（SG/NACL）、アクセス権限（IAM/リソースポリシー）は**それぞれ独立した階層**です。1つでも遮断されていれば通信や操作は成立しません | 「VPCエンドポイントを設定したのにS3にアクセスできない」→ ルーティングは通っているが、**バケットポリシーの明示的拒否でブロック**されている |
| **障害** | インスタンス障害、AZ障害、リージョン障害、**誤操作・誤削除**では対策が根本から異なります。レプリケーション（複製）は機器障害には有効ですが、誤削除の防止には役立ちません | 「マルチAZ配置にしたから安全」→ **誤って実行したDELETEクエリもスタンバイ側へ同期複製される** |
| **データ** | オブジェクト（HTTP/S経由で取得）、ブロック（単一インスタンス専用ディスク）、共有ファイル（複数台から同時アクセス）、構造化レコード（キーやSQLで検索）など、データの性質によって最適な保存先が決まります | 「複数台のEC2で共有する」要件であるにもかかわらず、単一インスタンス用のEBSを選択してしまう |
| **処理** | 同期処理か非同期処理か、セッションなどの状態をどこに保持するか、**同一処理のリクエストが重複して届いた場合にどう対処するか（冪等性）**を考慮します | キューを導入すれば重複処理がすべて解消されると誤認する → **分散システムでは再配信が起こり得る前提で設計する必要がある** |
| **性能** | レイテンシ（応答時間）、スループット（単位時間あたりの処理量）、同時接続数は**それぞれ異なる課題**であり、講じるべき解決策も異なります | 「DBの応答が遅い」という問題に対して常にリードレプリカを提案してしまう → **接続数の枯渇が原因であればRDS Proxyが必要** |
| **費用** | 課金体系を確認します：容量（GB）、稼働時間、リクエスト回数、処理キャパシティ（ACU/RCU/WCU）、データ転送量（データ送信料など）。「サーバーレス＝常に最も安価」とは限りません | Fargateはリクエストの有無にかかわらず、**タスクが稼働している時間分だけ課金が発生する** |

**選ぶ条件**：設問を読んだら、まず「この問題はどの軸の課題を扱っているのか」を見極めます。判断軸を特定できれば、比較検討すべき選択肢を2〜3個に素早く絞り込めます。

**理解確認**：「複数のEC2から同時に読み書きする共有ストレージ」は、6軸のどれに該当するか。
→ **データ**軸（共有ファイルストレージ → EFSまたはFSx）。なお「Windows環境・SMBプロトコル」という追加条件があれば、同じデータ軸の中でFSx for Windows File Serverが適切な選択肢となります。

## 0.2 可用性と耐久性、冗長化・レプリケーション・バックアップの区別

**困りごと**：「高可用性」「耐久性」「冗長化」「バックアップ」といった用語を曖昧に捉えていると、誤削除への対策を問う設問で誤ってマルチAZ構成を選んでしまうといったミスが発生します。

**用語の整理**

| 用語 | 本来の意味 | 何から保護できるか | 何から保護できないか |
|---|---|---|---|
| **可用性** | 必要なときに**システムが利用可能な状態にある**割合（稼働率。例：99.99%など） | ハードウェア障害やAZ障害によるサービス停止 | データの論理的な破損や消失そのもの |
| **耐久性** | 保存されたデータが**失われずに維持される**確率（例：S3の99.999999999%［11ナイン］など） | 物理ディスクの故障、データセンター規模の障害 | 利用者の誤操作による削除や不正な上書き |
| **冗長化** | 同一の役割を果たすコンポーネントを複数用意すること（Auto Scalingによる複数台運用、マルチAZ配置など） | 単一コンポーネントや1つのAZの障害 | アプリケーションのバグや誤操作によるデータ不整合 |
| **レプリケーション** | データの**現在の状態**を別の場所へ継続的に複製すること（同期／非同期） | 障害発生時の迅速な切り替え、読み取り負荷の分散 | **誤ったデータ更新や誤削除もそのまま複製先へ反映される** |
| **バックアップ** | ある特定時点のデータ状態を**別の媒体や領域に退避・保存**すること（スナップショット、PITRなど） | データの誤削除、ランサムウェア被害、論理破壊 | 復元作業に一定の時間を要する（RTOが長くなる） |

**選ぶ条件**
- 「サービスを中断させずに稼働させ続けたい」→ 冗長化・レプリケーション（マルチAZ配置、Auto Scaling、グローバルデータベースなど）。
- 「**過去の特定の時点の状態に復旧したい**」→ バックアップ、バージョニング、PITR（ポイントインタイムリカバリ）。レプリケーション単体では過去の状態には戻せません。
- 「可用性とデータ保護の両立」が要件の場合 → マルチAZ配置と自動バックアップのように、**目的の異なる複数の仕組みを適切に組み合わせます**。

**条件違いの例**

| 設問の前提条件 | 適切な判断 | 他の選択肢を除外する理由 |
|---|---|---|
| AZ障害が発生してもRDSを停止させたくない | マルチAZ DBインスタンス配置 | リードレプリカ：非同期レプリケーションであり手動昇格が必要なため、自動フェイルオーバーによる高可用性担保が主目的ではない |
| 誤って全データをDELETEしてしまったため、1時間前の状態に復旧したい | 自動バックアップからのPITR（ポイントインタイムリカバリ） | マルチAZ配置：DELETE操作そのものがスタンバイ側にも同期複製されてしまっているため |
| 同一データを別リージョンでも低遅延で読み取り、障害時にはそちらへ切り替えたい | クロスリージョンリードレプリカ／Aurora グローバルデータベース | 単一リージョンのバックアップ：切り替え先リージョンに即座に稼働するインスタンスが存在しないため |

**理解確認**：「データを2台のインスタンスへ即時同期複製している。誤って全件削除を実行してしまった場合、もう1台からデータを復旧できるか。その理由は？」
→ **復旧できない**。更新操作が即座に複製される構成では、2台目も削除後の状態になってしまいます。過去のデータを取り戻すには、バックアップ、PITR、バージョニングのように「過去の特定時点の状態を保持する仕組み」を個別に用意する必要があります。

## 0.3 RTOとRPOの指標

**困りごと**：「数分以内に復旧」「データの損失は許されない」といった設問の要件がどちらの指標に対応しているかを混同していると、ディザスタリカバリ（DR）戦略の選択肢を正しく判断できません。

**仕組み**
- **RTO（Recovery Time Objective：目標復旧時間）**：障害発生から**サービスが復旧するまでに許容される時間**。復旧手順の自動化度合いや速度によって決まります（スタンバイへの自動フェイルオーバーなら短く、バックアップから新規構築する場合は長くなります）。
- **RPO（Recovery Point Objective：目標復旧時点）**：障害発生時に**失われることが許容されるデータの時間幅（過去どの時点まで戻せれば許容されるか）**。バックアップの取得頻度や、レプリケーションの方式（同期か非同期か）および遅延時間によって決まります。

**具体例**：14:00に障害が発生し、13:55時点のバックアップデータを用いて14:20にシステムを復旧した場合、実績値は**データ損失5分（RPO実績）・復旧所要時間20分（RTO実績）**となります。設問の要件が「RPO 15分以内、RTO 30分以内」であれば、この構成は要件を満たしています。一方、「RPO 1分以内」が求められる場合は5分間隔のバックアップでは不十分であり、同期レプリケーションや遅延の極めて小さい非同期レプリケーションが必要になります。

**選ぶ条件**
- RTOを短縮したい場合 → **あらかじめ起動済みの待機系リソース**を用意する（ウォームスタンバイ、マルチサイト／アクティブ-アクティブなど）。
- RPOを短縮したい場合 → **データ複製の頻度を高める、または同期レプリケーションを採用する**（マルチAZ同期レプリケーション、Aurora グローバルデータベース、継続的バックアップなど）。
- いずれの指標も短縮するほどコストが増加します。試験では「提示されたRTO/RPOを満たす中で、最もコスト効率の高い構成」が問われます。

**注意点**：目標値（Objective）と実際の運用実績値は別物です。単に戦略の名称（パイロットライトなど）を当てはめるだけで数値が保証されるわけではなく、実際の値は具体的な復旧手順とデータ複製方式によって決まります（→第12章）。

**理解確認**：「1時間ごとにスナップショットを取得し、障害時はそこから新しいDBを起動する構成」において、RPOとRTOはそれぞれ何によって決まるか。
→ RPOは**スナップショットの取得間隔（最大約1時間分のデータ損失）**で決まり、RTOは**スナップショットから新規DBを起動して接続先を切り替えるまでの手順所要時間**で決まります。RPOを縮めるにはPITR（継続的バックアップ）や同期レプリケーション、RTOを縮めるには事前起動された待機系リソースが必要です。

## 0.4 通信経路の疎通と、操作の認可の区別

**困りごと**：「VPCエンドポイントを作成したのにS3に書き込めない」「セキュリティグループのポートを開放したのにDBに接続できない」といった設問に対し、原因を特定しないまま不要なルーティング設定ばかりを追加してしまう誤りが散見されます。

**仕組み**：1回のリクエストは、以下のすべての階層を正常に通過して初めて成功します。どの階層で処理が停止しているかによって、見直すべき設定箇所が異なります。

| 階層 | 検証すべき設定・サービス | 通信が遮断されている場合の主な症状 |
|---|---|---|
| 名前解決 | Route 53、プライベートホストゾーン、Resolver | ホスト名が名前解決できない、古いIPアドレスが返される |
| ルーティング（経路） | ルートテーブル、IGW、NAT Gateway、VPCエンドポイント、VPCピアリング、Transit Gateway | **接続タイムアウト**（宛先にパケットが到達しない） |
| パケットフィルタリング | セキュリティグループ（ステートフル）、ネットワークACL（ステートレス、戻り通信の許可も必須） | **接続タイムアウト**または接続拒否 |
| 認証・認可 | IAMポリシー、リソースポリシー（S3バケットポリシー、KMSキーポリシー等）、SCP | **403 AccessDenied**（通信は到達しているが操作が拒否される） |
| 暗号化キーの権限 | KMSキーポリシー、グラント | データの復号に失敗する（オブジェクト一覧は取得できるが中身を読み取れない） |

**選ぶ条件**
- 発生している症状が**タイムアウト**であればルーティング（経路）またはパケットフィルタリング（SG/NACL）を疑います。一方、**403 AccessDenied**であれば認証・認可（IAMや各種ポリシー）を確認します。設問に記載されたエラー内容から、対象とすべき階層を正しく特定します。
- AWSのポリシー評価論理では、**「明示的な拒否（Explicit Deny）」がすべての「許可（Allow）」よりも優先**されます（SCP、バケットポリシー、IAMポリシーなど）。

**理解確認**：「プライベートサブネット内のEC2からS3に対し、ゲートウェイ型VPCエンドポイント経由でPutObjectを実行したところ、403エラーが返された。ルートテーブルにはエンドポイント宛ての経路が正しく登録されている」。次に見直すべき設定は何か？
→ ネットワーク経路は疎通しているため、**EC2に割り当てられたIAMロールのポリシー、S3バケットポリシー（`aws:sourceVpce`条件の記述内容など）、VPCエンドポイントポリシー**、およびSSE-KMS暗号化を使用している場合は**KMSキーポリシー**を確認します。NAT Gatewayやインターネットゲートウェイを追加しても解決にはなりません。

## 0.5 設問を解く論理的な手順

**推奨される解答ステップ**
1. **必須条件を正確に抽出する**：高可用性の要件（マルチAZが必須か）、目標復旧指標（RTO/RPO）、データの保持期間、コンプライアンス・規制要件（暗号化、改変防止など）、プロトコルやエンジンの互換性、実行時間制限などの制約条件を整理します。
2. **条件を満たせない選択肢を除外する**：制約に抵触する選択肢を論理的な理由とともに除外します（例：「Lambdaは最大実行時間15分の制限を超えるため除外」「単一AZ構成のためAZ障害に耐えられず除外」など）。多くの場合、この段階で有力な選択肢が2つ程度に絞られます。
3. **設問の優先基準に従って最適解を選択する**：残った候補の中から、設問が最も重視している方針（「最もコスト効率が高い」「運用のオーバーヘッドが最小」「最高のスループット」など）に従って正解を決定します。

**避けるべき誤った思考パターン**
- **キーワードのみでの安易な判断**：「サーバーレス」という単語が含まれていても、実行時間の上限、OSレベルの制御要件、常時稼働時のコスト比較などにより、Lambdaが最適解とならないケースがあります。
- **要件を満たさない低コスト構成の選択**：どれほど安価であっても、可用性要件やRTO/RPOを満たさない構成は誤答となります。
- **特定の構成を一律に不正解とみなすこと**：「単一AZ」構成であっても、設問が高可用性を求めておらずコスト最小化を優先している場合（検証環境や再生成可能なデータ処理など）は正解になり得ます。

**この教材の読み進め方**
1. この第0章で、設計の判断軸と基礎用語を正確に把握します。
2. 第1部（第1〜10章）で、各サービスの**動作の仕組みと、選定すべき条件・選定してはならない条件**を読み込みます。比較表を見る際は「どの軸による違いか」を意識します。
3. 第2部（第11〜14章）の**分野別設計ケース**を通じて、条件が1つ変化した際に解答がどう変化するかを演習します。
4. 付録A・Bは**総復習用**として活用します。候補サービスを思い浮かべたあと、右端の「確認する条件」と照合して記憶を定着させます。
