# 第0章 設計の基礎と問題の読み方

> **この章の使い方**：サービス名を覚える前に読む。SAAの設問は「どのサービスか」ではなく「**どの条件で、なぜそれを選ぶか**」を問う。この章では、以降の全章で繰り返し使う**6つの判断軸**と、**可用性・耐久性・RTO/RPO**の意味、そして**設問を読む順序**を先に固める。

---

## 0.1 サービス名の前に見る6つの判断軸

**困りごと**：サービス名を並べて覚えると、設問の条件が1つ変わっただけで手が止まる。「S3にプライベート接続＝VPCエンドポイント」と覚えていても、接続元がオンプレなら答えは変わる。

**仕組み**：設問の条件は、ほぼ次の6軸のどれかに分類できる。各章の比較表は、この軸のどれで分かれているかを示している。

| 軸 | 理解すること | 典型的な取り違え |
|---|---|---|
| **通信** | 名前解決（DNS）・経路（ルート）・通信許可（SG/NACL）・操作権限（IAM/リソースポリシー）は**別の層**。1つ通っても他が塞がっていれば届かない | 「エンドポイントを作ったのにS3にアクセスできない」→経路は通っているが**バケットポリシーで拒否**されている |
| **障害** | インスタンス障害／AZ障害／リージョン障害／**誤削除**では対策が違う。複製は障害には効くが誤削除には効かない | マルチAZにしたから安全→**誤更新もスタンバイに複製される** |
| **データ** | オブジェクト（HTTPで取得）／ブロック（1台のディスク）／共有ファイル（複数台から同時）／レコード（キーやSQLで引く）で置き場所が決まる | 「複数EC2で共有」なのにEBSを選ぶ |
| **処理** | 同期か非同期か。状態をどこに保存するか。**同じ処理が2回来たとき**どう扱うか（冪等性） | キューを置けば重複が消えると思う→**再配信は起こる前提で設計** |
| **性能** | レイテンシ（1回の応答時間）／スループット（単位時間の処理量）／同時接続数は**別の問題**。効く対策も別 | 「DBが遅い」に対して常にリードレプリカ→**接続数枯渇ならRDS Proxy** |
| **費用** | 課金単位を見る：容量（GB）／時間（稼働時間）／リクエスト数／処理量（ACU・RCU）／転送量（GB out）。「サーバーレス＝安い」ではない | Fargateはリクエストがなくても**タスクが起動中なら課金** |

**選ぶ条件**：設問を読んだら、まず「この問題はどの軸の話か」を決める。軸が決まれば、比較すべき候補が2〜3個に絞れる。

**理解確認**：「複数のEC2から同時に読み書きする共有ストレージ」は6軸のどれで決まるか。→ **データ**軸（共有ファイル→EFS/FSx）。ただし「Windows・SMB」なら同じデータ軸の中でFSx for Windowsに変わる。

## 0.2 可用性と耐久性、冗長化・レプリケーション・バックアップ

**困りごと**：「高可用性」「耐久性」「冗長化」「バックアップ」を同じ意味で読むと、誤削除への備えを問う設問でマルチAZを選んでしまう。

**用語の整理**

| 用語 | 意味 | 何から守るか | 何から守れないか |
|---|---|---|---|
| **可用性** | 必要なときに**使える**割合（99.99%など） | サービス停止 | データの消失そのもの |
| **耐久性** | データを**失わずに保持**できる確率（S3の11ナインなど） | ディスク故障・AZ障害 | 利用者自身の削除・上書き |
| **冗長化** | 同じ役割の部品を複数持つ（ASGの複数台、マルチAZ） | 1台／1AZの障害 | 論理的な誤り（バグ、誤操作） |
| **レプリケーション** | データの**現在の状態**を別の場所へ複製し続ける（同期／非同期） | 障害時の切り替え、読み取り分散 | **誤更新・誤削除も複製される** |
| **バックアップ** | ある時点の状態を**別に保存**する（スナップショット、PITR） | 誤削除・ランサムウェア・論理破壊 | 復元に時間がかかる（RTOが長い） |

**選ぶ条件**
- 「止まらないようにしたい」→冗長化・レプリケーション（マルチAZ、ASG、グローバルデータベース）。
- 「**過去の状態に戻したい**」→バックアップ・バージョニング・PITR。複製では戻れない。
- 「両方」が設問の要件なら、マルチAZ＋バックアップのように**役割の違う2つを組み合わせる**。

**条件違いの例**

| 条件 | 判断 | 外す候補と理由 |
|---|---|---|
| AZ障害でもRDSを止めたくない | マルチAZ配置 | リードレプリカ：非同期・手動昇格で、可用性の主目的ではない |
| 誤って全件DELETEした。1時間前に戻したい | 自動バックアップからのPITR | マルチAZ：DELETEも同期複製されている |
| 同じデータを別リージョンで読みたい、障害時はそちらへ切替 | クロスリージョンレプリカ／グローバルデータベース | 単一リージョンのバックアップ：切替先で動く実体がない |

**理解確認**：「同じデータを2台へ即時複製している。誤って全件削除した場合も、もう1台があれば必ず復旧できるか。理由は？」
→ **できない**。削除も複製される構成では、2台目も削除後の状態になる。過去の時点に戻すには、バックアップ／PITR／バージョニングのように「時点を保存する仕組み」を別に持つ必要がある。

## 0.3 RTOとRPO

**困りごと**：「数分以内に復旧」「データ損失は許されない」という設問の文を、どちらの指標に結びつけるかが曖昧だと、DR戦略の表を暗記しても使えない。

**仕組み**
- **RTO（Recovery Time Objective）**＝障害発生から**復旧までに許容できる時間**。復旧手順の速さで決まる（自動フェイルオーバーは短く、バックアップから構築し直すと長い）。
- **RPO（Recovery Point Objective）**＝**失ってよいデータの時間幅**。バックアップの頻度、または複製方式（同期／非同期）とその遅延で決まる。

**例**：14:00に障害が起き、13:55時点のデータまで復元して14:20に再開した場合、実績は**データ損失5分・復旧20分**。設問で「RPO 15分、RTO 30分」が要件なら、この結果は両方満たしている。「RPO 1分」が要件なら、5分ごとのバックアップでは足りず、同期または遅延の小さい非同期レプリケーションが必要になる。

**選ぶ条件**
- RTOを短くしたい→**すでに動いている待機系**を持つ（ウォームスタンバイ、マルチサイト）。
- RPOを短くしたい→**複製の頻度を上げる／同期にする**（マルチAZ同期、グローバルデータベース、継続的バックアップ）。
- 両方短くすると費用が上がる。設問は「要件を満たす中で最も安い構成」を聞くことが多い。

**注意**：目標値（Objective）と実績値は別。戦略名（パイロットライトなど）だけでRTO/RPOの数値が保証されるわけではない。実際の値は復旧手順と複製方式で決まる（→第12章）。

**理解確認**：「1時間ごとにスナップショットを取り、障害時はそこから新しいDBを起動する構成」のRPOとRTOはそれぞれ何で決まるか。→ RPOは**スナップショット間隔（最大約1時間の損失）**、RTOは**スナップショットからDBを起動して接続先を切り替えるまでの手順時間**。RPOを縮めるにはPITR（継続的バックアップ）や同期レプリケーション、RTOを縮めるには起動済みの待機系が必要。

## 0.4 通信できることと、操作が許可されることは別

**困りごと**：「VPCエンドポイントを作ったのにS3に書けない」「SGを開けたのにDBに繋がらない」という設問で、経路の追加を選び続けてしまう。

**仕組み**：1回のアクセスは、次の層をすべて通って初めて成功する。どこで止まっているかで、直す場所が変わる。

| 層 | 見るもの | 止まっているときの症状 |
|---|---|---|
| 名前解決 | Route 53、プライベートホストゾーン、Resolver | 名前が引けない、古いIPが返る |
| 経路 | ルートテーブル、IGW/NAT、エンドポイント、ピアリング/TGW | タイムアウト（到達しない） |
| 通信許可 | セキュリティグループ（ステートフル）、NACL（ステートレス、戻りも要許可） | タイムアウトまたは拒否 |
| 認証・認可 | IAMポリシー、リソースポリシー（バケットポリシー、キーポリシー）、SCP | **403 AccessDenied**（到達はしている） |
| 暗号鍵の権限 | KMSキーポリシー | 復号できない（オブジェクトは見えるが読めない） |

**選ぶ条件**
- 症状が**タイムアウト**なら経路か通信許可。**AccessDenied**なら認可。設問の症状の書き方で層を特定する。
- 「明示的Deny」はどの層のAllowよりも強い（SCP、バケットポリシー、IAM）。

**理解確認**：「プライベートサブネットのEC2からS3へ、ゲートウェイエンドポイント経由でPutObjectすると403になる。ルートテーブルにはエンドポイントへの経路がある」。次に見るべきものは？→ 経路は通っているので、**IAMロールのポリシー、バケットポリシー（`aws:sourceVpce`条件など）、エンドポイントポリシー**、SSE-KMSなら**キーポリシー**。NATやIGWの追加は解決にならない。

## 0.5 問題を解く順序

**手順**
1. **絶対に満たす条件を拾う**：可用性（マルチAZ必須か）、RTO/RPO、データの保持期間、規制（暗号化・改変不可）、互換性（既存プロトコル・エンジン）、実行時間の上限。
2. **その条件を満たせない選択肢を外す**：ここで2択に絞れることが多い。外すときは理由を言葉にする（「Lambdaは15分を超えるから」「単一AZだからAZ障害で止まるから」）。
3. **残った候補を、設問の優先事項で比較する**：「最もコスト効率が高い」「運用負荷が最小」「最も高性能」のどれを聞かれているかで決める。

**やってはいけないこと**
- キーワードだけで決める：「サーバーレス」と書いてあってもLambdaが常に正解ではない（実行時間、OS制御、常時稼働のコストで外れる）。
- 「最も安い」を要件より優先する：可用性やRTOを満たさない構成は、安くても不正解。
- 単語の有無で不正解を決める：「単一AZ」でも、設問が可用性を要件にしていなければ不正解とは限らない（開発環境、再作成可能なデータなど）。

**この教材の読み方**
1. この章（第0章）で軸と用語を固める。
2. 第1部（第1〜10章）で各サービスの**仕組みと選ぶ／選ばない条件**を読む。比較表は「どの軸で分かれているか」を意識する。
3. 第2部（第11〜14章）の**設計ケース**で、条件を1つ変えたときに答えがどう変わるかを練習する。
4. 付録A・Bは**復習用**。候補を思い出したら、最後の列の「確認する条件」に戻る。
