# 第1章 コンピューティング

> **章の一言**：EC2は「自由だが運用責任も自分持ち」、Lambdaは「運用ゼロだが15分・ステートレス」。試験は常に**「運用負荷」と「制約」のどちらを取るか**で正解を決める。

---

## 1.1 Amazon EC2

**一言で**：OSレベルから自由に触れる仮想サーバー。他の選択肢が使えない理由がある時の答え。

**試験の核心**
- **購入オプション**が最頻出。ワークロードの性質（中断可否・期間・ライセンス）で一意に決まる。
- **インスタンスストア**は物理サーバー直結の一時ディスク。**停止・終了で消える**（再起動では消えない）。永続化が必要ならEBS。
- **ステータスチェック**は2種類。システム（AWS側のハード/ネットワーク障害）とインスタンス（OS側の問題）。前者は**自動復旧（auto recovery）**で別ハードに移す。
- **IMDSv2**（トークン必須）はSSRF対策。「メタデータ経由で認証情報が盗まれた」→IMDSv2を強制。
- EC2にはアクセスキーを置かず、**IAMロール**をアタッチする（キーは自動ローテーション）。

**購入オプションの見分け**
| 問題文のキーワード | 答え |
|---|---|
| 中断されても良い／バッチ・CI・ステートレス／最大90%安く | スポットインスタンス |
| 1〜3年使い続ける／柔軟にインスタンスタイプを変えたい | Savings Plans（Compute SP） |
| 1〜3年／特定リージョンの特定ファミリー固定でさらに安く | EC2 Instance SP／リザーブドインスタンス |
| 特定AZの**キャパシティを確保**したい | ゾーンRI／オンデマンドキャパシティ予約 |
| 短期・予測不能・検証 | オンデマンド |
| **ソケット/コア単位のライセンス持ち込み（BYOL）** | Dedicated **Host** |
| ハードウェア専有だけしたい（コンプライアンス） | Dedicated **Instance** |

**プレイスメントグループの見分け**
| 要件 | 種類 |
|---|---|
| ノード間の低レイテンシ・高スループット（HPC、単一AZ） | クラスター |
| 少数の重要インスタンスを**別々のハードウェア**に分散（AZあたり7台まで） | スプレッド |
| HDFS/Cassandra/Kafkaなど**大規模分散システム**をラック単位で分離 | パーティション |

**ひっかけ**：「高可用性のためにEC2を冗長化」だけでは不十分。**マルチAZ配置＋ELB＋Auto Scaling**の3点セットが正解の型。

## 1.2 Amazon EC2 Auto Scaling

**一言で**：台数を需要に合わせて増減し、壊れたインスタンスを自動で入れ替える仕組み。

**試験の核心**
- 定義は**起動テンプレート**（起動設定はレガシー。バージョン管理・スポット混在ができるのはテンプレート側）。
- **ヘルスチェックタイプが最重要ひっかけ**。既定はEC2ステータスチェックのみ＝「OSは生きているがアプリが500を返す」状態を検知できない。**ELBヘルスチェックを有効化**して初めて入れ替わる。
- **ライフサイクルフック**＝起動完了前／終了前に一時停止してカスタム処理（ログ退避、設定投入、ウォームアップ）。
- 既定の終了ポリシー：台数が最も多いAZ → 最も古い起動テンプレート → 次の課金時間に最も近いもの。
- ウォームプール＝起動に時間がかかるアプリの待機インスタンス群（コールドスタート対策）。

**スケーリングポリシーの見分け**
| 問題文のキーワード | 答え |
|---|---|
| 「CPU平均40%を維持」など**指標を一定に保つ** | ターゲット追跡（まず疑う既定解） |
| 指標の超過幅に応じて段階的に台数を変える | ステップスケーリング |
| **毎週月曜9時**など時刻が分かっている | スケジュールされたスケーリング |
| **周期的な傾向**を機械学習で先読みし、事前に増やす | 予測スケーリング |
| キュー滞留に応じて増減 | ターゲット追跡＋カスタム指標（`ApproximateNumberOfMessages` / インスタンス数） |

**ひっかけ**：「スケールアウトは速く、スケールインは慎重に」→ クールダウン／インスタンスウォームアップの調整。スケールインで処理中リクエストを切らない → **接続ドレイニング（登録解除の遅延）**。

## 1.3 AWS Elastic Beanstalk

**一言で**：コードを上げるだけでEC2・ELB・ASGを自動構築するPaaS。**裏側のリソースは自分のアカウントに見える**のが特徴。

**試験の核心**
- 追加料金なし（作られたEC2等の料金のみ）。インフラの細部を自分で設計したくない開発者向け。
- **DBは環境内に作らない**。環境を削除するとDBも消えるため、RDSは環境外に分離するのが定石。
- 環境タイプ：**Webサーバー環境**（HTTPを受ける）／**ワーカー環境**（SQSキューを自動ポーリング）。
- `.ebextensions` でカスタム設定を投入。

**デプロイポリシーの見分け**
| 要件 | ポリシー |
|---|---|
| 最速・ダウンタイム許容（開発環境） | All at once |
| 追加コストなし、少しずつ入れ替え（一時的に容量低下） | Rolling |
| **容量を落とさず**入れ替え（一時的に追加インスタンス） | Rolling with additional batch |
| **ダウンタイムなし＋失敗時に即ロールバック** | Immutable（新インスタンス群を並行作成） |
| **新旧環境を並行稼働しURLを入れ替え**、即座に切り戻し | Blue/Green（CNAMEスワップ） |
| 一部トラフィックだけ新版へ（カナリア） | Traffic splitting |

**似たサービスとの違い**：CloudFormation＝インフラをコードで完全制御／Beanstalk＝アプリ中心で自動構築／App Runner＝コンテナをURLまで全自動（インフラは見えない）。

## 1.4 AWS Outposts

**一言で**：AWSのラックを自社データセンターに置き、同じAPIでオンプレを操作する。

**試験の核心**
- 選ばれる理由は2つだけ：**データレジデンシー（データを国内/施設内から出せない）**と、**オンプレ既存システムとの超低レイテンシ**。
- 管理はAWSリージョンから行うため、リージョンへの接続は必要。

**エッジ系サービスの見分け**
| 要件 | 答え |
|---|---|
| 自社データセンター内にAWSを置く／法規制でデータを出せない | Outposts |
| 大都市圏のユーザーへ**一桁ミリ秒**（ゲーム、映像編集） | Local Zones |
| **5Gモバイル端末**に対して超低遅延 | Wavelength |
| ネットワークが無い現場（船・工場）で一時的に処理してから転送 | Snowball Edge（コンピューティング最適化） |

## 1.5 AWS Batch

**一言で**：大量のバッチジョブをキューに積み、必要なだけEC2/Fargateを自動起動して処理する。

**試験の核心**
- 構成要素：**ジョブ定義**（何を動かすか）＋**ジョブキュー**（優先度）＋**コンピューティング環境**（どこで動かすか）。
- コンピューティング環境で**スポット**を選べる＝バッチ処理のコスト最適解として頻出。
- **配列ジョブ**で数千の並列実行、ジョブ間の依存関係も定義可。

**見分けポイント**
| 問題文のキーワード | 答え |
|---|---|
| 数時間かかる計算ジョブ、**Lambdaの15分を超える** | AWS Batch |
| 常時稼働するAPI/サービス | ECS/EKS/EC2 |
| 複数サービスをまたぐ**手順・分岐・リトライの制御** | Step Functions |
| 単発の軽量処理をイベントで起動 | Lambda |

## 1.6 AWS Lambda

**一言で**：サーバー管理なしでコードを実行。イベント駆動・疎結合アーキテクチャの中心。

**試験の核心（数字は付録Bに出典付きで集約）**
- 最大実行時間 **15分**／メモリ 128MB〜10GB（**メモリを増やすとCPUも比例して増える**＝遅い処理はメモリ増で解決することがある）（→付録B）。
- `/tmp` は 512MB〜10GB。デプロイパッケージは zip 50MB（直接）、解凍後250MB、**コンテナイメージなら10GB**。
- リージョンあたり同時実行 **1,000**（既定、引き上げ可。新規アカウントはこれより低いことがある）。
  - **予約済み同時実行**＝その関数の上限を固定し、他の関数を枯渇させない（**スロットリング対策**）。
  - **プロビジョニング済み同時実行**＝事前にウォーム状態を確保（**コールドスタート対策**）。SnapStart（Java）も同様の目的。
- VPC接続のLambdaは**そのままではインターネットに出られない**。**パブリックサブネットに置いても出られない**（ENIにパブリックIPが付かない）。外に出すならプライベートサブネット＋NAT Gateway、S3/DynamoDBだけならゲートウェイVPCエンドポイント（→第3章 3.1）。

**呼び出しモデルの見分け**
| 呼び出し元 | モデル | 失敗時の挙動 |
|---|---|---|
| API Gateway、ALB | 同期 | 呼び出し元にエラーを返す |
| S3、SNS、EventBridge | 非同期 | 自動で2回リトライ → DLQ／Lambda Destinations |
| SQS、Kinesis、DynamoDB Streams | ポーリング（イベントソースマッピング） | キュー/シャードに残る。SQSはDLQ、Kinesisはシャードがブロックし得る |

**エッジでの実行の見分け**
| 要件 | 答え |
|---|---|
| ヘッダー操作・URL書き換え・簡易トークン検証、**1ms未満・超高頻度・安価** | CloudFront Functions（JS、ビューア側のみ） |
| オリジンへのリクエスト改変、外部APIやS3アクセス、重い処理 | Lambda@Edge（Node/Python、オリジン側でも動く） |

**ひっかけ**：「状態を保持したい」→Lambdaはステートレス。DynamoDB/S3/ElastiCacheへ外出しする。

## 1.7 その他のコンピューティングサービス

| サービス | 一言で | 試験での決め手 |
|---|---|---|
| Amazon Lightsail | 固定月額のかんたんVPS | 「シンプルな小規模サイトを最小の手間と**予測可能な料金**で」 |
| AWS App Runner | コンテナ/ソースをURLまで全自動デプロイ | 「コンテナ化済みWebアプリをインフラ管理なしで」（ECS/EKSより手間が少ない） |
| EC2 Image Builder | AMI/コンテナイメージ作成の自動化 | 「パッチ適用済みの標準AMIを定期的に自動生成・配布」 |
| Elastic Fabric Adapter (EFA) | HPC向け低遅延ネットワーク | MPI・機械学習の分散学習＋クラスタープレイスメントグループ |
| AWS Nitro Enclaves | 同一インスタンス内の隔離実行環境 | 「極秘データをOSからも隔離して処理」 |
| VMware Cloud on AWS | オンプレVMware環境をAWSへ | 「既存のVMware資産を書き換えず移行」 |
