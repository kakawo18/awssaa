# 第1章 コンピューティング

> **章の一言**：EC2は「OSから自由に制御できる反面、運用の責任も自身で負う」、Lambdaは「サーバー運用が不要な反面、最大実行時間15分やステートレスといった制約がある」。試験では常に**「運用のオーバーヘッド削減」と「アーキテクチャ上の制約」のトレードオフ**から最適解を導きます。

---

## 1.1 Amazon EC2

**概要**：OSレベルから自由に管理・カスタマイズできる仮想サーバー。マネージドサービスの制約により他の選択肢が適用できない場合や、既存環境の移行における標準的な選択肢となります。

**試験での要点**
- **購入オプション**の選び分けが頻出。ワークロードの特性（中断の可否、稼働期間、既存ライセンス要件など）に応じて最適なオプションを判断します。
- **インスタンスストア**は物理ホストに直結された一時ディスクであり、**インスタンスの停止や終了によってデータが消失**します（OSの再起動では保持されます）。永続的なデータ保管が必要な場合はEBSを使用します。
- **ステータスチェック**は2種類あります。システムステータスチェック（基盤側のハードウェアやネットワーク障害）と、インスタンスステータスチェック（OSの破損やカーネルパニックなど）。前者のハードウェア障害に対しては、**CloudWatchアラームによる自動復旧（Auto Recovery）**を設定して健全なホストへ自動移行させます。
- **IMDSv2（インスタンスメタデータサービス v2）**はセッショントークンを必須とすることでSSRF（サーバーサイドリクエストフォージェリ）攻撃を防ぎます。問題文で「インスタンスメタデータを経由した認証情報の不正取得を防ぐ」とあれば、IMDSv2の利用を強制します。
- EC2インスタンス内に長期的なアクセスキーを配置せず、**IAMロール**を割り当てて一時的な認証情報を自動ローテーションさせます。

**購入オプションの選び分け**
| 設問の要件・特徴 | 最適な選択肢 |
|---|---|
| 中断が許容される／バッチ処理・CI/CD・ステートレス環境／最大90%のコスト削減 | スポットインスタンス |
| 1年または3年の継続利用／インスタンスファミリーやOSを柔軟に変更したい | Savings Plans（Compute Savings Plans） |
| 1年または3年／特定リージョンの特定インスタンスファミリーに固定して最大の割引率を得る | EC2 Instance Savings Plans ／ スタンダードリザーブドインスタンス |
| 特定のアベイラビリティゾーン（AZ）で**確実にコンピュート容量を確保**したい | ゾーンリザーブドインスタンス ／ オンデマンドキャパシティ予約 |
| 短期運用・急激な負荷変動・検証用途 | オンデマンドインスタンス |
| **ソケット単位や物理コア単位の既存ライセンス持ち込み（BYOL）** | Dedicated Host（Dedicated ホスト） |
| ライセンス制約はなく、コンプライアンス要件等でハードウェア専有のみが必要 | Dedicated Instance（ハードウェア専有インスタンス） |

**プレイスメントグループの選び分け**
| 要件 | 種類 |
|---|---|
| ノード間の低レイテンシ・高スループット通信が必須（HPC、単一AZ配置） | クラスタープレイスメントグループ |
| 少数の重要なインスタンスを**互いに異なるハードウェアラック**に分散配置（AZあたり最大7台まで） | スプレッドプレイスメントグループ |
| HDFS、Apache Cassandra、Kafkaなど**大規模分散システム**において、ラック単位で耐障害性を確保 | パーティションプレイスメントグループ |

**注意すべき落とし穴**：「高可用性を実現するためにEC2インスタンスを複数台配置する」だけでは不十分です。**マルチAZ配置＋ELB（Elastic Load Balancing）＋Auto Scaling**を組み合わせる構成が基本パターンとなります。

## 1.2 Amazon EC2 Auto Scaling

**概要**：需要の変動に応じてインスタンス数を自動でスケールイン/アウトさせ、異常が発生したインスタンスを自動的に正常なインスタンスへと置き換える仕組み。

**試験での要点**
- インスタンスの設定定義には**起動テンプレート**を使用します（起動設定［Launch Configuration］は旧世代の機能であり、バージョン管理やスポットインスタンスとオンデマンドの混在運用に対応しているのは起動テンプレートです）。
- **ヘルスチェックのタイプ**：既定では「EC2ステータスチェック」のみが有効となっており、「OSは起動しているがWebアプリケーションがHTTP 500エラーを返している」といった障害を検知できません。アプリケーションの正常性に基づいて自動置換を行うには、**ELBヘルスチェックを有効化**する必要があります。
- **ライフサイクルフック**：インスタンスの起動完了前または終了前に処理を一時停止し、ログの退避、初期設定スクリプトの実行、キャッシュのウォームアップなどのカスタム処理を完了させてから進行させます。
- 既定の終了ポリシー：インスタンス数が最も多いAZを選択 → 最も古い起動テンプレートを使用しているインスタンスを選択 → 次の課金時間に最も近いインスタンスを選択。
- ウォームプール：起動に長時間を要するアプリケーション向けに、事前初期化済みの停止・待機インスタンス群を保持しておく仕組み（コールドスタートの緩和）。

**スケーリングポリシーの選び分け**
| 設問の要件・特徴 | 最適な選択肢 |
|---|---|
| 「CPU使用率の平均を40%に維持する」など、**特定メトリクスを目標値に保つ** | ターゲット追跡スケーリングポリシー（第一候補となる標準構成） |
| メトリクスの超過幅に応じて段階的に台数を増減させたい | ステップスケーリングポリシー |
| **毎週月曜朝9時**など、負荷上昇のタイミングが事前に確定している | スケジュールされたスケーリング |
| **周期的な負荷の波**を機械学習で分析し、ピーク前に自動で事前スケールさせる | 予測スケーリング |
| キューの滞留メッセージ数に応じてインスタンス数を増減させる | ターゲット追跡スケーリング ＋ カスタムメトリクス（`ApproximateNumberOfMessagesVisible` / インスタンス台数） |

**注意すべき落とし穴**：「急なスパイクには素早くスケールアウトし、スケールインは慎重に行いたい」という要件では、クールダウン期間やインスタンスウォームアップ期間の調整を行います。また、スケールイン時に処理中のリクエストを強制切断しないためには、**コネクションドレイニング（登録解除の遅延）**を適切に設定します。

## 1.3 AWS Elastic Beanstalk

**概要**：アプリケーションコードをアップロードするだけで、EC2、ELB、Auto Scalingなどの基盤リソースを自動構築するPaaS。**作成された基盤リソースが自身のアカウント内にそのまま表示され、自由に直接カスタマイズできる**点が特徴です。

**試験での要点**
- Beanstalk自体の利用料は無料で、自動構築されたEC2やELB等のインフラ料金のみが課金されます。インフラ構築の詳細に工数をかけたくない開発者向けのサービスです。
- **データベースはBeanstalk環境内に作成しない**のが原則です。環境を削除した際にデータベースまで同時に削除されてしまうため、本番環境のRDSインスタンスはBeanstalk環境の外部に独立して構築し、接続文字列を環境変数で渡す設計とします。
- 環境タイプ：**Webサーバー環境**（HTTP/HTTPSトラフィックを直接受ける）／**ワーカー環境**（SQSキューからメッセージを自動ポーリングしてバックグラウンド処理を行う）。
- `.ebextensions` ディレクトリ内の設定ファイルにより、OSレベルの詳細なカスタム設定やミドルウェアの導入を自動化できます。

**デプロイポリシーの選び分け**
| 要件 | 最適なポリシー |
|---|---|
| 最も迅速にデプロイを完了させたい、一時的なダウンタイムは許容（検証環境向け） | 一括（All at once） |
| 追加コストをかけず、インスタンスを少しずつ順次更新（更新中は一時的にキャパシティが低下） | ローリング（Rolling） |
| **処理キャパシティを低下させずに**順次更新（一時的に追加インスタンスを起動） | 追加バッチによるローリング（Rolling with additional batch） |
| **ダウンタイムなし＋更新失敗時に即座にロールバック**したい | イミュータブル（Immutable：新バージョンのインスタンス群を並行して別グループとして構築） |
| **新旧環境を並行稼働させて動作検証し、DNSを切り替えて即座にリリース**（即時切り戻しも可能） | Blue/Greenデプロイ（CNAMEスワップ） |
| 新バージョンの影響を小規模なトラフィックで検証したい（カナリアリリース） | トラフィックスプリッティング（Traffic splitting） |

**類似サービスとの比較**：CloudFormation＝インフラ全体の構成をコードで完全定義・制御／Beanstalk＝アプリ中心で一般的なWeb/ワーカー構成を自動生成／App Runner＝コンテナをURL発行まで全自動で運用（基盤インフラはユーザー側には非公開）。

## 1.4 AWS Outposts

**概要**：AWSが設計した専用ハードウェアラックをオンプレミスの自社データセンターに設置し、クラウドと同じAWS APIやサービス群をローカル環境で利用できるようにするサービス。

**試験での要点**
- 採用理由は主に2つに絞られます：**データレジデンシー（法規制や機密性によりデータを物理的に施設外へ出せない）**、および**既存のオンプレミス機器との超低レイテンシ通信（ミリ秒未満の連携）**。
- コントロールプレーンはAWSリージョン側で管理されるため、指定したAWSリージョンへの安定したネットワーク接続が前提となります。

**エッジコンピューティングサービスの選び分け**
| 要件 | 最適な選択肢 |
|---|---|
| 自社データセンター内にAWSハードウェアを配置／厳格なデータ保管規制への対応 | Outposts |
| 特定の大都市圏のエンドユーザーに対して**一桁ミリ秒台**の低遅延を提供（ゲーム、リアルタイム映像処理など） | Local Zones |
| **5Gモバイル通信網のキャリア網内**にアプリケーションを配置し、端末に対して超低遅延通信を実現 | Wavelength |
| ネットワーク接続のない極限環境（船舶、工場、災害現場など）でデータを現地処理してからAWSへ転送 | Snowball Edge（コンピュート最適化）※2025年11月7日以降は既存顧客のみ。新規のエッジ用途はOutpostsが案内されている |

## 1.5 AWS Batch

**概要**：大量のバッチ処理ジョブをキューで管理し、ジョブの規模や要件に応じて最適なEC2インスタンスやFargateタスクを自動的にプロビジョニングして効率よく並列処理するフルマネージドサービス。

**試験での要点**
- 主要な構成要素：**ジョブ定義**（実行するコンテナイメージやコマンド、メモリ/CPU要件）＋**ジョブキュー**（ジョブの優先度制御）＋**コンピューティング環境**（インスタンスタイプやFargate、最大vCPU数などのリソース指定）。
- コンピューティング環境に**スポットインスタンス**を指定可能であり、バッチ処理のコストを劇的に削減する構成として頻出です。
- **配列ジョブ**を利用することで、単一のジョブ定義から数千件の並列タスクを効率的に投入・実行でき、ジョブ間の依存関係（前段の完了後に後段を実行）も制御可能です。

**見分けポイント**
| 設問の要件・特徴 | 最適な選択肢 |
|---|---|
| 数時間に及ぶ計算・レンダリング処理、**Lambdaの最大実行時間15分を超える処理** | AWS Batch |
| 常時稼働して外部リクエストを受け続けるWeb APIやマイクロサービス | ECS ／ EKS ／ EC2 |
| 複数のAWSサービスをまたぐ**一連のワークフロー、分岐処理、待機、再試行の制御** | Step Functions |
| 単発で軽量な処理を、S3等のイベント発生をトリガーとして実行 | Lambda |

## 1.6 AWS Lambda

**概要**：サーバーの管理やプロビジョニングを一切行わずにコードを実行できるサーバーレスコンピューティングサービス。イベント駆動型・疎結合アーキテクチャの中核を担います。

**試験での要点（具体的な数値は付録Bに出典付きで集約）**
- 最大実行時間は **15分**。割り当てメモリは 128MB〜10GB（**メモリを増やすとCPUコア数やネットワーク帯域も比例して増加**するため、CPUバウンドな低速処理はメモリ割り当てを増やすことで高速化できる場合があります）（→付録B）。
- 一時ストレージ `/tmp` は 512MB〜10GB。デプロイパッケージの上限は、直接アップロードのZIP形式で50MB、展開後250MB、**コンテナイメージ形式であれば最大10GB**まで対応可能です。
- リージョンあたりの同時実行数の初期クォータは **1,000**（引き上げ申請が可能。新規アカウントではこれより低く設定されている場合があります）。
  - **予約済み同時実行数**：対象の関数が使用できる同時実行数の上限を固定・予約し、急激なスパイクによる同一アカウント内の他関数のスロットリングを防止します。
  - **プロビジョニング済み同時実行数**：指定した数の実行環境を事前に初期化・ウォーム状態で待機させ、**コールドスタートによるレイテンシの遅延を解消**します。Java実行環境における SnapStart も同様にコールドスタート対策として有効です。
- VPCに接続したLambda関数は、**既定の状態ではインターネットと通信できません**。また、**パブリックサブネットに配置した場合でもインターネットには出られません**（Lambda用のENIにはパブリックIPアドレスが割り当てられないため、直接インターネットゲートウェイを経由できない）。外部のインターネットへ接続させるには**プライベートサブネットに配置し、NAT Gatewayを経由**させます。なお、S3やDynamoDBへのアクセスのみであれば、NAT Gatewayではなく**ゲートウェイ型VPCエンドポイント**を利用することでコストを抑えられます（→第3章 3.1）。

**呼び出しモデルの分類**
| 呼び出し元サービス | 呼び出し方式 | 処理失敗時の動作 |
|---|---|---|
| API Gateway、Application Load Balancer | 同期呼び出し | 呼び出し元へ即座にエラーレスポンスが返される |
| Amazon S3、Amazon SNS、EventBridge | 非同期呼び出し | 自動的に最大2回のリトライが実行され、その後DLQ（デッドレターキュー）またはLambda送信先（Destinations）へルーティング |
| Amazon SQS、Kinesis Data Streams、DynamoDB Streams | ポーリング（イベントソースマッピング） | メッセージやレコードは元のキュー／ストリームに保持される。SQSではDLQへ退避、Kinesisでは障害レコードにより該当シャードの処理がブロックされる可能性がある |

**エッジ環境でのコード実行の選び分け**
| 要件 | 最適な選択肢 |
|---|---|
| HTTPヘッダーの付与・変更、URLのリライト・リダイレクト、簡易なJWT検証など、**1ミリ秒未満の超低遅延・高頻度・低コスト**が求められる軽量処理 | CloudFront Functions（JavaScript限定、ビューアリクエスト／レスポンスのみ） |
| オリジンへのリクエスト改変、外部APIの呼び出しやS3/DynamoDBへのアクセス、実行時間が比較的長い複雑な処理 | Lambda@Edge（Node.js / Python対応、オリジンリクエスト／レスポンスでも動作可能） |

**注意すべき落とし穴**：「処理の途中で状態（ステート）を保持したい」という要件に対し、Lambda単体でメモリ内に状態を持ち続けることはできません（実行環境は破棄・再利用されるため）。状態の管理は DynamoDB、S3、ElastiCache などの外部データストアに切り離して設計します。

## 1.7 その他のコンピューティングサービス

| サービス | 概要 | 試験での判断ポイント |
|---|---|---|
| Amazon Lightsail | 定額制のシンプルな仮想プライベートサーバー（VPS） | 「小規模なWebサイトや開発環境を、最小限の手間と**予測可能な月額固定料金**で運用したい」 |
| AWS App Runner | コンテナやソースコードからWebアプリを全自動デプロイ | 「インフラの設計・管理を行うことなく、コンテナ化されたWebアプリケーションをURL発行まで迅速に公開したい」（ECS/EKSよりも運用負荷が低い） |
| EC2 Image Builder | AMIやコンテナイメージの作成・テストを自動化 | 「最新のセキュリティパッチが適用された標準ゴールデンAMIを定期的に自動ビルド・検証・配布したい」 |
| Elastic Fabric Adapter (EFA) | HPC向けの高帯域・低レイテンシネットワークインターフェース | MPI（Message Passing Interface）を用いた機械学習の分散学習、クラスタープレイスメントグループと併用 |
| AWS Nitro Enclaves | EC2インスタンス内に構築される独立した隔離実行環境 | 「機密性の高い暗号鍵や個人情報を、OSの管理者権限からも完全に隔離してセキュアに処理したい」 |
| VMware Cloud on AWS | VMwareのSDDC環境をAWSの専用ベアメタルインフラ上で稼働 | 「既存のVMwareベースの仮想化資産を、アーキテクチャや運用ツールを変更することなくAWSへ移行したい」 |
