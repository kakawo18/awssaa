# 第2章 ストレージ

> **章の一言**：ストレージの選定はデータのアクセス形態によって大別されます。**オブジェクトストレージ（S3）／ブロックストレージ（EBS）／共有ファイルストレージ（EFS・FSx）**の3つの分類を軸に、「複数サーバーから同時に共有」「単一インスタンスにマウント」「HTTP/S経由で直接配信」といった要件に着目して判断します。

---

## 2.1 Amazon S3

**概要**：容量無制限で99.999999999%（11ナイン）の高い耐久性を持つオブジェクトストレージ。既定で同一リージョン内の少なくとも3つのアベイラビリティゾーン（AZ）にデータが分散複製されます。

**試験での要点**
- **強い読み取り整合性（Strong Read-After-Write Consistency）**を提供します（書き込み成功直後のGETリクエストで常に最新のデータが取得できます。過去仕様であった「結果整合性」の記述は現在の仕様では誤りとなります）。
- 1オブジェクトの最大サイズは **48.8 TiB**（マルチパートアップロード利用時：最大10,000パート×各パート最大5 GiB）。単一のPUT操作でアップロードできる上限は **5 GiB** のため、これを超えるファイルはマルチパートアップロードが**必須**となります（なお、**100 MBを超えるデータ**ではマルチパートアップロードの利用が公式に推奨されています。※従来の上限は5 TBであり、古い過去問等ではこの数値を前提とした設問も見られます［→付録B］）。
- プレフィックス（フォルダ構造のパス）あたり、**毎秒 3,500 PUT/POST/DELETE、毎秒 5,500 GET/HEAD リクエスト**の処理性能が目安となります。性能がボトルネックとなる場合は、プレフィックスを分散させて並列度を高めます（→付録B）。
- バージョニングは**一度有効化すると完全に無効化（Disabled）することはできず、中断（Suspended）のみ可能**です。通常の削除操作では「削除マーカー」が付与されるだけであり、過去バージョンを指定して明示的に削除しない限りデータは失われません。
- **MFA削除**を有効化することで、バージョンの完全削除やバージョニング設定の変更時にMFA認証を必須化し、誤削除を防ぎます（設定にはルートユーザーが必要です）。

**ストレージクラスの選び分け**
| 設問の要件・アクセス特性 | 最適なクラス | 最低保持期間 |
|---|---|---|
| 頻繁にアクセスされるデータ、標準的なWebコンテンツ | S3 Standard | なし |
| **アクセス頻度やパターンが不明・変動する**、運用の手間をかけずにコストを最適化したい | S3 Intelligent-Tiering | なし |
| アクセス頻度は低いが、必要な際は**即座に（ミリ秒単位で）**取得したい、高い可用性を維持したい | S3 Standard-IA | 30日 |
| アクセス頻度が低く、**再生成が容易なデータ（サムネイル画像など）**でコストを最優先したい | S3 One Zone-IA（単一AZ配置のためAZ障害で消失するリスクあり） | 30日 |
| 四半期に1回程度の低頻度アクセスだが、取り出し時に**ミリ秒単位の即時アクセス**が必要なアーカイブ | S3 Glacier Instant Retrieval | 90日 |
| 通常のアーカイブ保管、データの取り出しに**数分〜数時間**の猶予がある | S3 Glacier Flexible Retrieval | 90日 |
| **年1回以下**のアクセス、7年保管等の長期コンプライアンス保管、ストレージ費用を最安に抑えたい | S3 Glacier Deep Archive（取り出し所要時間12〜48時間） | 180日 |

Glacier Flexible Retrieval の取り出しオプション：**迅速（Expedited：1〜5分）／標準（Standard：3〜5時間）／大容量（Bulk：5〜12時間）**。「緊急で数分以内に取得」という要件では迅速取り出し（Expedited）を選択します。

**データ保護・管理機能の選び分け**
| 要件 | 最適な機能・設定 |
|---|---|
| 誤った上書きや削除からデータを保護したい | バージョニング（＋MFA削除） |
| **法的規制やコンプライアンス要件により、一定期間は管理者（ルートユーザー含む）でも削除・改変できないようにしたい** | S3 オブジェクトロック **コンプライアンスモード** |
| 組織内の誤削除防止策として保護しつつ、権限を持つ特権ユーザーであれば解除できるようにしたい | S3 オブジェクトロック **ガバナンスモード** ／ リーガルホールド |
| ディザスタリカバリ（DR）やアクセス遅延改善のため、別リージョンへ自動複製したい | クロスリージョンレプリケーション（CRR：**バージョニングの有効化が必須**） |
| 同一リージョン内でアカウント間でのログ集約や環境分離を行いたい | 同一リージョンレプリケーション（SRR） |
| 15分以内のデータ複製完了をSLAとして担保したい | S3 Replication Time Control（RTC） |

**暗号化方式の選び分け**
| 要件 | 最適な方式 |
|---|---|
| 追加設定や管理の手間なく、標準で保管時暗号化を適用したい | SSE-S3（既定で有効） |
| **暗号化キーのライフサイクル管理、アクセス制御の分離、CloudTrailによる利用ログの監査**が必要 | SSE-KMS（CloudTrailにキーの使用履歴が記録される） |
| SSE-KMS利用に伴うKMSのAPIリクエスト費用やスロットリングを抑制したい | **S3 バケットキー**の有効化 |
| 暗号化キーを自社内で完全に管理し、AWS側にはキーを保持させたくない | SSE-C（HTTPS通信が必須） ／ クライアントサイド暗号化 |

**アクセス制御の選び分け**
| 要件 | 最適な機能・設定 |
|---|---|
| バケットやオブジェクトの意図しないパブリック公開を組織全体で確実に防ぎたい | ブロックパブリックアクセス（＋OrganizationsのSCP） |
| 特定のクライアントに対して、**一時的な有効期限付き**で安全にアップロード／ダウンロードさせたい | 事前署名URL（Presigned URL） |
| S3バケットをパブリック公開せず、CDN（CloudFront）経由のアクセスのみに限定したい | CloudFront ＋ **オリジンアクセス制御（OAC）**（※OAIの後継機能） |
| 大規模な共有データセットに対し、多数の異なるアプリケーションごとに個別のアクセス権限を付与したい | S3 アクセスポイント |
| 異なるAWSアカウントからのアクセスをクロスアカウントで安全に許可したい | バケットポリシー（＋アクセス元アカウントのIAMポリシー） |

**その他の重要な機能**：イベント通知（S3へのオブジェクト作成・削除を契機にSNS/SQS/Lambda/EventBridgeへ通知）、S3 Transfer Acceleration（遠隔地からの大容量アップロードをCloudFrontエッジ経由で高速化）、S3 バッチオペレーション（既存の大量オブジェクトに対して一括でタグ付けやコピーを実行）、S3 Storage Lens（ストレージ使用状況や最適化の推奨事項を組織横断で可視化）、リクエスタ支払い（データ取得にかかる転送料金をダウンロード側に負担させる）。

## 2.2 Amazon EBS

**概要**：単一のEC2インスタンスにアタッチして使用する、アベイラビリティゾーン（AZ）限定の永続ブロックストレージ。

**試験での要点**
- **同一AZ内のインスタンスにのみ直接アタッチ可能**です。別AZや別リージョンに展開する場合は、**EBSスナップショット（データの実体はS3に保存）**を作成し、それをコピー・復元してボリュームを再作成します。
- スナップショットは**増分バックアップ**として保存されます。途中の世代を削除しても、他の世代のスナップショットから完全に復元できる整合性が維持されます。
- 暗号化：暗号化されたボリュームのスナップショットは自動的に暗号化され、暗号化スナップショットから作成されるボリュームも自動で暗号化されます。**未暗号化の既存ボリュームを暗号化**するには、「スナップショット取得 → 暗号化を有効にしてスナップショットをコピー → コピーからボリュームを復元」の手順を踏みます。
- Amazon Data Lifecycle Manager（DLM）を用いることで、EBSスナップショットの自動取得・世代管理・ライフサイクル移行をポリシーベースで自動化できます。
- 高速スナップショット復元（FSR）：スナップショットからのボリューム作成直後における初回アクセス時の遅延（ストレージブロックの遅延読み込み）を解消します。

**ボリュームタイプの選び分け**
| 設問の要件・特徴 | ボリュームタイプ |
|---|---|
| 汎用的なワークロード。容量と独立してIOPSやスループットを個別に設計・プロビジョニングしたい | **gp3**（推奨される汎用SSD） |
| 旧世代のgp2からコストを削減しつつ、ストレージ性能をベースラインに固定したい | gp3（gp2はIOPSが容量に比例し、ベースラインは3 IOPS/GB） |
| 高いIOPSが要求される基幹データベース、**最大99.999%の優れた耐久性**、複数EC2からの同時接続（Multi-Attach） | io2 ／ io2 Block Express |
| ビッグデータ解析、ログ処理など**大容量シーケンシャルI/O**を低コストで処理したい | st1（スループット最適化HDD、**ブートボリューム不可**） |
| アクセス頻度が極めて低いコールドデータ向けの最安ストレージ | sc1（コールドHDD、ブートボリューム不可） |

**注意すべき落とし穴**：「複数のEC2インスタンスから同時に読み書きを行いたい」という要件に対し、EBS Multi-Attach は **io1/io2ボリュームかつ同一AZ内限定、さらにクラスタ対応共有ファイルシステム（GFS2等）の導入が前提**となります。一般的な複数サーバーでのファイル共有要件では **Amazon EFS** が正解となります。

## 2.3 Amazon EFS

**概要**：複数のEC2インスタンスからネットワーク経由で同時マウント可能な、Linux向け（NFSv4）のフルマネージド共有ファイルストレージ。マルチAZに分散配置され、容量は自動的に拡張されます。

**試験での要点**
- 「複数インスタンスによる同一ファイルの共有」「WordPress等のWebコンテンツやCMSの共有データ領域」といった要件において第一候補となります。
- ストレージクラス：Standard（マルチAZ配置による高可用性）／**One Zone**（単一AZ配置による約半額の低コスト運用）。ライフサイクル管理を有効化することで、アクセス頻度の低いファイルを**低頻度アクセス（IA）ストレージクラスへ自動移行**できます。
- スループットモード：**Elastic**（推奨設定：使用量に応じて自動的にスケール）／バースト（容量に応じてスループットが決定）／プロビジョンド（容量が小さくても高いスループットを事前に確保したい場合）。
- パフォーマンスモード：汎用（汎用的なWebサーバー等向け、最小のレイテンシ）／最大I/O（数千台のクライアントから同時接続、集約スループットを最優先）。
- アクセス制御はPOSIXパーミッション＋セキュリティグループ＋IAMポリシーの組み合わせ、保存データの暗号化にはAWS KMSを使用します。

**注意すべき落とし穴**：Windows環境（SMBプロトコル）にはネイティブ対応していません。Windows環境での共有ファイルストレージには **FSx for Windows File Server** を選択します。

## 2.4 Amazon FSx

**概要**：既存の主要なサードパーティ製ファイルシステムを、AWS上でフルマネージドサービスとして提供するサービス群。プロトコルやOS要件に応じた選び分けが明確です。

| 設問の要件・特徴 | 最適なサービス |
|---|---|
| **Windows環境**、SMBプロトコル、Active Directory統合、NTFSアクセス制御、分散ファイルシステム（DFS） | FSx for **Windows File Server** |
| **ハイパフォーマンスコンピューティング（HPC）**、機械学習、数百GB/sの高スループット・サブミリ秒の低遅延、**S3と直接連携**した高速データロード | FSx for **Lustre** |
| オンプレミスの**NetApp ONTAP**資産の移行、NFS/SMB/iSCSIのマルチプロトコル対応、高度なスナップショットや重複排除機能 | FSx for **NetApp ONTAP** |
| 既存の**ZFSファイルシステム**の移行、Linux/Unix向けNFS低遅延アクセス、効率的なスナップショット機能 | FSx for **OpenZFS** |

**FSx for Lustreの補足**：S3バケットをデータリポジトリとしてリンクし、必要なデータのみをオンデマンドで高速ロード（Lazy load）して処理し、計算結果をS3へ書き戻す運用が一般的です。デプロイタイプにはスクラッチ（一時処理向け・非冗長・超高速）とパーシステント（永続保管向け・高可用性）の2種類があります。

## 2.5 AWS Backup

**概要**：複数のAWSサービスにまたがるデータバックアップを、一元化されたバックアップポリシーに基づいて自動管理・監査する統合サービス。

**試験での要点**
- 対応サービス：Amazon EC2、Amazon EBS、Amazon RDS、Amazon Aurora、Amazon DynamoDB、Amazon EFS、Amazon FSx、AWS Storage Gateway、Amazon S3、VMwareワークロードなど。
- **バックアッププラン**（取得スケジュール、保持期間、コールドストレージへのライフサイクル移行）を定義し、**リソースタグやリソースIDベース**でバックアップ対象を自動割り当てします。
- **クロスリージョンコピーおよびクロスアカウントコピー**をサポートしており、災害対策（DR）やランサムウェア対策として隔離されたセキュリティアカウントへバックアップを自動退避できます。
- **AWS Backup Vault Lock**：WORM（Write Once, Read Many）モデルを適用し、コンプライアンスモードでは**管理者やルートユーザーであっても指定期間内のバックアップ削除や保持期間短縮を完全に防止**します。
- AWS Backup Audit Manager により、組織全体のバックアップポリシーの遵守状況やコンプライアンス適合性を継続的に監査・レポートできます。

**選び分け**：「複数サービス・複数アカウントにまたがるバックアップ運用を一元化し、コンプライアンス監査を行いたい」場合は AWS Backup を選択します。単一サービス内でのスナップショット自動化のみであれば、EBS用の Amazon Data Lifecycle Manager（DLM）や RDS の自動バックアップ機能で十分なケースもあります。

## 2.6 AWS Storage Gateway

**概要**：オンプレミスのサーバー環境から標準的なストレージプロトコル（NFS/SMB/iSCSI/VTL）でアクセスでき、バックエンドの実体としてS3やS3 Glacierを利用するハイブリッドクラウドストレージサービス。

| オンプレミス側のプロトコル／要件 | ゲートウェイの種類 | バックエンドの保存先 |
|---|---|---|
| NFS／SMBでファイル共有し、**保存データがそのままS3オブジェクトとして格納**される | **S3 File Gateway** | Amazon S3 |
| SMBプロトコルでWindowsファイル共有をクラウドへシームレスに拡張 | **FSx File Gateway** | FSx for Windows File Server |
| iSCSIブロックストレージ、**頻繁にアクセスするデータのみをローカルにキャッシュ**し、残りはクラウドに退避（ストレージ容量削減） | Volume Gateway **キャッシュ型** | Amazon S3（全データ） |
| iSCSIブロックストレージ、**全データをオンプレミスに保持**しつつ、非同期でポイントインタイムバックアップを取得（低遅延を最優先） | Volume Gateway **保管型** | オンプレミス ＋ EBSスナップショット（S3） |
| 既存の**バックアップソフトウェアが利用しているテープライブラリ装置**をクラウドで置き換えたい | **Tape Gateway**（VTL） | Amazon S3 ／ S3 Glacier |

**類似サービスとの比較**：Storage Gateway＝**既存アプリを変更せず継続的にハイブリッド連携する運用**／AWS DataSync＝**オンプレミスとAWS間での大規模データの一括・定期的転送**／AWS Snowball＝**ネットワーク帯域の制約がある環境からの大容量データの物理移送**。
