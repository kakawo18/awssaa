# 第2章 ストレージ

> **章の一言**：ストレージ問題は3語で決まる。**オブジェクト（S3）／ブロック（EBS）／ファイル共有（EFS・FSx）**。問題文の「複数サーバーから同時に」「単一EC2に」「HTTPで取得」を拾えば9割決まる。

---

## 2.1 Amazon S3

**一言で**：容量無制限・11ナインの耐久性を持つオブジェクトストレージ。既定でリージョン内の複数AZに複製される。

**試験の核心**
- **強い読み取り整合性**（書き込み直後のGETで最新が読める）。古い「結果整合性」の記述は誤り。
- 1オブジェクト最大5TB。**100MB超はマルチパートアップロード推奨、5GB超は必須**。
- プレフィックスあたり **3,500 PUT / 5,500 GET per秒**。性能不足はプレフィックス分散で解決。
- バージョニングは**有効化したら無効に戻せない**（停止のみ）。削除は「削除マーカー」が付くだけ。
- **MFA削除**はバージョンの完全削除を防ぐ。設定はルートユーザーのみ。

**ストレージクラスの見分け**
| 問題文のキーワード | クラス | 最低保存期間 |
|---|---|---|
| 頻繁にアクセス | Standard | なし |
| **アクセスパターンが不明・変動する**、運用の手間なしに最適化 | Intelligent-Tiering | なし |
| 低頻度だが**即座に**必要、可用性は落としたくない | Standard-IA | 30日 |
| 低頻度・**再作成可能**（サムネイル等）でコスト最優先 | One Zone-IA（単一AZ＝AZ障害で消える） | 30日 |
| 四半期に1回程度・**ミリ秒で取り出したい**アーカイブ | Glacier Instant Retrieval | 90日 |
| アーカイブ、取り出しは**数分〜数時間**で良い | Glacier Flexible Retrieval | 90日 |
| **年1回以下**・7年保管などの長期保全、最安 | Glacier Deep Archive（取り出し12〜48時間） | 180日 |

Glacier Flexible の取り出し速度：**迅速1〜5分／標準3〜5時間／大容量5〜12時間**。「緊急で数分」＝Expedited。

**データ保護の見分け**
| 要件 | 答え |
|---|---|
| 誤削除・上書きから守る | バージョニング（＋MFA削除） |
| **規制対応で一定期間、誰も（ルートでも）消せない** | オブジェクトロック **コンプライアンスモード** |
| 運用上の保護だが、権限者は解除可 | オブジェクトロック **ガバナンスモード**／リーガルホールド |
| 別リージョンにコピー（DR・レイテンシ改善） | クロスリージョンレプリケーション（**バージョニング必須**） |
| 同一リージョンでログ集約・アカウント分離 | 同一リージョンレプリケーション |
| 15分以内の複製をSLAで保証 | Replication Time Control (RTC) |

**暗号化の見分け**
| 要件 | 答え |
|---|---|
| とりあえず暗号化（既定で有効） | SSE-S3 |
| **キーの管理・監査・ローテーション・利用者制限**が必要 | SSE-KMS（CloudTrailにキー利用が残る） |
| KMSのリクエストコスト／スロットリングが問題 | **S3バケットキー**を有効化 |
| キーは自社で持ちAWSに保管させない | SSE-C（HTTPS必須）／クライアントサイド暗号化 |

**アクセス制御の見分け**
| 要件 | 答え |
|---|---|
| 誤公開を組織的に防ぐ | ブロックパブリックアクセス（＋SCP） |
| 特定ユーザーに**期限付き**でアップロード/ダウンロードさせる | 事前署名URL |
| S3を非公開のままCDN配信 | CloudFront＋**OAC**（旧OAI） |
| 多数のアプリごとに異なるアクセス制御を与えたい | S3 アクセスポイント |
| クロスアカウントでのアクセス許可 | バケットポリシー（＋相手側IAM） |

**その他の頻出**：イベント通知（S3→SNS/SQS/Lambda/EventBridge）、Transfer Acceleration（遠距離からの大容量アップロードをエッジ経由で高速化）、S3 Select（オブジェクト内をSQLで部分取得）、バッチオペレーション（既存オブジェクトの一括処理）、Storage Lens（利用状況の可視化）、リクエスタ支払い。

## 2.2 Amazon EBS

**一言で**：EC2に接続する**単一AZ**のブロックストレージ。

**試験の核心**
- **AZをまたげない**。別AZ／別リージョンで使うには**スナップショット（実体はS3に保存）**経由でコピー。
- スナップショットは**増分**。世代を消しても他世代の復元性は保たれる。
- 暗号化：スナップショットも復元ボリュームも自動的に暗号化。**未暗号化ボリュームを後から暗号化**するにはスナップショット→暗号化コピー→復元。
- Data Lifecycle Manager（DLM）でスナップショットを自動取得・世代管理。
- 高速スナップショット復元（FSR）＝復元直後の初回アクセス遅延をなくす。

**ボリュームタイプの見分け**
| 問題文のキーワード | タイプ |
|---|---|
| 汎用・迷ったらこれ。IOPSとスループットを容量と独立に設定 | **gp3** |
| gp2からのコスト削減・性能固定 | gp3（gp2はIOPSが容量比例＝3 IOPS/GB） |
| 高IOPSが必要なDB、**最大99.999%の耐久性**、Multi-Attach | io2 / io2 Block Express |
| ビッグデータ、ログ処理など**シーケンシャルな大量スループット** | st1（HDD、**ブート不可**） |
| 滅多にアクセスしない最安HDD | sc1（ブート不可） |

**ひっかけ**：「複数のEC2から同時に書き込みたい」→ Multi-Attach は **io1/io2かつ同一AZ、クラスター対応ファイルシステム必須**。通常は **EFS** が正解。

## 2.3 Amazon EFS

**一言で**：複数のEC2から同時マウントできる**Linux（NFS）**の共有ファイルストレージ。マルチAZで自動拡張。

**試験の核心**
- 「複数インスタンスが同じファイルを共有」「Webコンテンツ・CMSの共有領域」＝EFSの合図。
- ストレージクラス：Standard（複数AZ）／**One Zone**（単一AZ・約半額）。ライフサイクル管理で**IAへ自動移行**。
- スループットモード：**Elastic**（迷ったらこれ、使用量に応じ自動）／バースト／プロビジョンド（容量は小さいが高スループットが必要）。
- パフォーマンスモード：汎用（既定、低レイテンシ）／最大I/O（数千クライアント、レイテンシ犠牲）。
- アクセス制御はPOSIX権限＋セキュリティグループ＋IAM、保存時暗号化はKMS。

**ひっかけ**：Windows（SMB）では使えない。→ FSx for Windows File Server。

## 2.4 Amazon FSx

**一言で**：特定のファイルシステムをそのままマネージドで使うサービス群。**キーワードが露骨に出る**ので取りこぼさない。

| 問題文のキーワード | 答え |
|---|---|
| **Windows**、SMB、Active Directory統合、NTFS ACL、DFS | FSx for **Windows File Server** |
| **HPC**、機械学習、数百GB/s、サブミリ秒、**S3と連携**して処理 | FSx for **Lustre** |
| 既存の**NetApp ONTAP**資産、NFS/SMB/iSCSIのマルチプロトコル、スナップショット・重複排除 | FSx for **NetApp ONTAP** |
| 既存の**ZFS**、NFSで低レイテンシ、スナップショット | FSx for **OpenZFS** |

**Lustreの補足**：S3バケットをリンクしてデータをlazy loadし、結果を書き戻せる。スクラッチ（一時・高速・非冗長）と永続の2デプロイタイプ。

## 2.5 AWS Backup

**一言で**：複数サービスのバックアップを**ポリシーで一元管理**するサービス。

**試験の核心**
- 対象：EC2/EBS、RDS/Aurora、DynamoDB、EFS、FSx、Storage Gateway、S3、VMware など。
- **バックアッププラン**（頻度・保持期間・ライフサイクル）＋**タグベース**で対象を自動選択。
- **クロスリージョン／クロスアカウント**コピーでDR・ランサム対策。
- **Vault Lock**＝WORM。コンプライアンスモードでは**誰も保持期間を短縮・削除できない**。
- Backup Audit Manager でバックアップ準拠状況を監査。

**見分け**：「複数サービス・複数アカウントのバックアップ要件を統一し、監査したい」＝AWS Backup。単一サービスのスナップショット自動化だけなら DLM／RDS自動バックアップでも可。

## 2.6 AWS Storage Gateway

**一言で**：オンプレのサーバーから見ると普通のファイル/ディスク/テープ、実体はS3やGlacierというハイブリッド用ゲートウェイ。

| オンプレ側のプロトコル／要件 | 種類 | 保存先 |
|---|---|---|
| NFS/SMBでファイル共有、**そのままS3オブジェクトになる** | **S3 File Gateway** | S3 |
| SMBでWindows共有をクラウドへ | **FSx File Gateway** | FSx for Windows |
| iSCSIブロック、**よく使うデータだけ手元にキャッシュ**（容量削減が目的） | Volume Gateway **キャッシュ型** | S3（全データ） |
| iSCSIブロック、**全データをオンプレに保持**しつつ非同期バックアップ（低レイテンシが目的） | Volume Gateway **保管型** | オンプレ＋S3スナップショット |
| 既存の**バックアップソフトのテープ装置**を置き換えたい | **Tape Gateway**（VTL） | S3／Glacier |

**似たサービスとの違い**：Storage Gateway＝**継続的なハイブリッド運用**／DataSync＝**一度きり〜定期の大量転送**／Snowball＝**ネットワークが細い/大容量の物理移送**。
