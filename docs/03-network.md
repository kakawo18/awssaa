# 第3章 ネットワークおよびコンテンツ配信

> **章の一言**：ネットワークの設問は「**1回の通信がどこを通り、どこで止まるか**」を追えれば解ける。順番は **所属範囲（CIDR）→ 経路（ルート）→ 通信許可（SG/NACL）→ 外への出口（IGW/NAT/エンドポイント）→ 名前解決（DNS）**。この順で1回追ってから、ELB・CloudFront・接続方式の比較に進む。届かない原因が「経路」なのか「許可」なのか「認可（IAM/バケットポリシー）」なのかを分けるのが最重要（→第0章 0.4）。

---

## 3.1 VPCの基礎：所属範囲と経路

**困りごと**：「パブリックサブネットに置いたのに外に出られない」「NATを追加したのにS3に書けない」。どれも、通信が通る層の順序を追わずに部品を足しているのが原因。

**仕組み：1回の通信が通る順序**

| 順 | 層 | 決めるもの | 試験で問われる形 |
|---|---|---|---|
| 1 | **IP/CIDR/サブネット** | 送信元がどの範囲に所属するか | /28 なら使えるIPは11個（**先頭4つ＋末尾1つの5個が予約**） |
| 2 | **ルートテーブル** | 宛先に対する**次の転送先**（最長一致で1本だけ選ばれる） | 0.0.0.0/0 の向き先が IGW か NAT か何もないか |
| 3 | **SG／NACL** | その通信を**許可するか**（往路と戻りの両方） | 3.2で詳述 |
| 4 | **IGW／NAT／エンドポイント** | VPCの**外へどう出るか**（方向と相手） | 3.3で詳述 |
| 5 | **DNS** | 宛先の**名前をどのIPに解決するか**（経路とは別） | 3.4で詳述 |

**サブネットの種類は「名前」ではなく「ルート」で決まる**
- **パブリックサブネット＝ルートテーブルに IGW への経路（0.0.0.0/0 → igw-xxx）があるサブネット**。名前に public と付いていても、経路がなければ外に出られない。
- パブリックサブネットに置いたインスタンスでも、**パブリックIP（またはElastic IP）がなければインターネットと通信できない**。経路とIPの両方が要る。
- **プライベートサブネット**からのアウトバウンド（パッチ取得、外部API）は **NAT Gateway**。NAT自体は**パブリックサブネットに置き**、**AZごとに1つ**置かないとそのAZのNAT障害で他AZのインスタンスまで巻き込む。
- **IPv6**のアウトバウンド専用は **Egress-Only インターネットゲートウェイ**。IPv4のNATと混同しない（IPv6にNATは要らない）。

**VPC接続Lambda（1.6と共通の落とし穴）**
- LambdaをVPCに接続すると、関数はVPC内のENI経由で通信する。**パブリックサブネットに置いてもインターネットには出られない**。LambdaのENIにはパブリックIPが付かないため、経路があってもIGWを通れない。
- 外に出すなら**プライベートサブネット＋NAT Gateway**。S3/DynamoDBだけなら**ゲートウェイエンドポイント**（NAT料金がかからない）。

**選ぶ条件／選ばない条件**
- 「プライベートサブネットのEC2からOSのパッチを取得したい」→NAT Gateway。**Session ManagerはSSHの代替であって、インスタンスからの外向き通信の経路にはならない**。
- 「S3へだけ出たい、NAT料金を避けたい」→ゲートウェイエンドポイント（3.3）。NATを追加するのは、要件に対して過剰でコストもかかる。

**条件違いの例**

| 条件 | 判断 | 外す候補と理由 |
|---|---|---|
| EC2はパブリックサブネットにあるが、外部と通信できない。ルートに 0.0.0.0/0 → IGW はある | パブリックIP／EIPの有無、SG/NACLのアウトバウンドと戻りを確認 | NATの追加：パブリックサブネットには不要。ルート追加：既にある |
| プライベートサブネットのEC2からS3へ、NATなしで通信したい | S3のゲートウェイエンドポイント | NAT：動くがNAT処理料と転送料がかかる。IGW：プライベートサブネットの定義に反する |
| VPC接続Lambdaから外部APIを呼びたい | プライベートサブネット＋NAT Gateway | パブリックサブネットに置く：LambdaのENIにパブリックIPが付かないので出られない |

**理解確認**：「パブリックサブネットとは何か」を、名前を使わずに説明せよ。→ **ルートテーブルにインターネットゲートウェイへの経路があるサブネット**。さらに、そこにあるインスタンスが実際に通信するにはパブリックIPと、SG/NACLの許可が要る。

**監視・その他**：VPCフローログ（**許可/拒否の記録は取れるがパケットの中身は見えない**→中身が要るならTraffic Mirroring）、Reachability Analyzer（到達性の原因特定＝どの層で止まっているかを調べる道具）、AWS Network Firewall（ステートフルなL3〜L7フィルタ・ドメイン制限）。

## 3.2 通信制御：セキュリティグループとネットワークACL

**困りごと**：「特定IPを遮断＝NACL」と覚えると、WAFやSGで解くべき設問で間違える。往路と戻りを別に考えないと、NACLで戻りのポートを塞いでしまう。

**仕組み**

| | セキュリティグループ | ネットワークACL |
|---|---|---|
| 適用先 | ENI（インスタンス単位） | サブネット単位（サブネット内の全ENIに効く） |
| 状態 | **ステートフル**：往路を許可すれば**戻りは自動で許可** | **ステートレス**：往路と戻りを**別々に許可**（戻りは**エフェメラルポート 1024〜65535**の許可が要る） |
| ルール | **許可のみ**（書いていないものは拒否） | 許可と**拒否**。**番号の小さい順**に評価し、最初に一致したルールで決まる |
| 参照 | 送信元に**別のSGを指定できる**（CIDRを書かずに「ALBのSGから」と書ける） | CIDRのみ |

**選ぶ条件／選ばない条件**
- 通常のアクセス制御（Web層はALBのSGからだけ、DB層はApp層のSGからだけ）→**SG**。SGをチェーンで参照するのが定石。
- **特定のIPアドレス／CIDRからの通信を拒否したい**→NACLは候補の1つ。ただし条件を見る：
  - **L3/L4で、サブネット単位で**遮断したい→NACL（拒否ルールが書ける唯一のVPC内機能）。
  - 対象が**HTTP/HTTPSで、ALB/CloudFront/API Gatewayの手前**なら→**WAFのIPセット**（レート制限やパターン検知も一緒にできる）。
  - **CloudFrontで国単位**に制限したい→**地理的制限**（NACLには国という概念がない）。
  - SGでは拒否が書けないので、「SGで特定IPを拒否」は成立しない。
- 「戻りの通信だけ通らない」→NACLのアウトバウンドでエフェメラルポートを許可していない可能性。SGなら起こらない症状。

**通信許可と認可は別**：SGもNACLも通しているのに403が返るなら、それはIAM・バケットポリシー・エンドポイントポリシー・KMSキーポリシーの層（→第0章 0.4）。ポートを開けても解決しない。

**条件違いの例**

| 条件 | 判断 | 外す候補と理由 |
|---|---|---|
| 特定IPからのSSH総当たりをサブネットごと止めたい | NACLで拒否ルール（番号を小さく） | SG：拒否が書けない。WAF：SSHはL7のHTTPではないので対象外 |
| 特定IPからのHTTPリクエストをALBの手前で止め、あわせてレート制限もしたい | WAF（IPセット＋レートベースルール） | NACL：レート制限はできない。サブネット単位なので他の用途に副作用 |
| Web層にはALBからだけ、DBにはWeb層からだけ通したい | SGを送信元に指定してチェーン | NACL：CIDRでしか書けず、ALBのIPは変わる |

**理解確認**：「NACLでインバウンド80を許可したのにWebサーバーに応答が返らない」原因は？→ NACLはステートレスなので、**アウトバウンドでエフェメラルポート（1024〜65535）への許可**がないと戻りが出ていけない。SGなら戻りは自動許可されるためこの症状は出ない。

## 3.3 VPCの外との接続：エンドポイント・PrivateLink・ピアリング・TGW・VPN/DX

**困りごと**：「S3/DynamoDB＝ゲートウェイ型、それ以外＝インターフェース型」と暗記すると、オンプレからS3へプライベート接続する設問で間違える。接続方式は「**接続元がどこか**」と「**経路をどこまで延ばせるか**」で決まる。

**仕組み：VPCエンドポイントの2種類**

| | ゲートウェイエンドポイント | インターフェースエンドポイント（PrivateLink） |
|---|---|---|
| 実体 | **ルートテーブルのエントリ**（プレフィックスリスト → vpce） | **サブネット内のENI**（プライベートIPを持つ） |
| 対象 | **S3 と DynamoDB** | ほとんどのAWSサービス、**S3も可**、他アカウントのサービス、SaaS |
| 料金 | **追加料金なし** | **時間課金＋処理データ量**（有料） |
| 使える接続元 | **同じVPC内**からのみ（ルートテーブルを見るのはVPC内のリソースだけ） | VPC内に加え、**ピアリング・TGW・VPN・DX越し**（オンプレ）からもENIのIPへ届く |
| SG | 付けられない（エンドポイントポリシーで制御） | ENIにSGを付けられる |
| DNS | 不要（ルートで振り分け） | プライベートDNSでサービス名をENIのIPに解決 |

**S3へのプライベート接続は2択で、接続元で決まる**
- **VPC内から同一リージョンのS3**へ、インターネットとNATを避けたい→**ゲートウェイ型**を先に検討（無料）。
- **オンプレからVPN/DX越しにS3**へプライベート接続→**ゲートウェイ型は延長できない**（オンプレ側のルートには乗らない）ので**インターフェース型**。**Direct Connect Gateway経由でもS3のゲートウェイ型は使えない**。
- 「S3以外＝インターフェース」ではなく、「**S3でも接続元がVPCの外ならインターフェース**」。

**エンドポイントがあるのに拒否される**：経路は通っている。**バケットポリシー・エンドポイントポリシー・IAM**の認可を見る（`aws:sourceVpce` 条件で「このエンドポイント経由だけ許可」にしているとき、別経路からは403）。経路の追加では解決しない。

**VPC同士・オンプレとの接続**

| 要件 | 答え | 選ばない条件 |
|---|---|---|
| 自社のサービスを他アカウントのVPCに公開（相手にVPC全体を見せない） | **PrivateLink**（NLB＋エンドポイントサービス） | ピアリング：相手に自VPCのCIDRが見え、CIDR重複不可 |
| VPCを2つだけ、単純に接続 | VPCピアリング（**推移的ルーティング不可・CIDR重複不可**） | 3つ以上を相互に繋ぐならメッシュになり管理が破綻→TGW |
| VPCが多数／オンプレも含めハブ＆スポークで集約 | **Transit Gateway** | 2つだけならピアリングの方が安い |
| オンプレ接続を**すぐ・安く**始めたい、暗号化必須 | Site-to-Site VPN（インターネット経由、2トンネル） | 帯域と遅延の一貫性が要件ならDX |
| **一貫した帯域・低レイテンシ**の専用線（開通に数週間〜） | Direct Connect（**既定では暗号化されない**→IPsec VPNやMACsecを併用） | 「今週中に」なら間に合わない |
| DXの冗長化 | DX 2本（最高）／DX＋VPNバックアップ（安価な現実解） | |
| 複数リージョンのVPCへ1本のDXから | Direct Connect Gateway | |

**条件違いの例**

| 条件 | 判断 | 外す候補と理由 |
|---|---|---|
| VPC内EC2→同一リージョンS3、NATなし・低コスト | **ゲートウェイ型**を検討 | インターフェース型：動くが有料。NAT：処理料と転送料 |
| オンプレ→VPN経由→S3のプライベート接続 | **インターフェース型**を検討 | ゲートウェイ型：オンプレのルートから到達できない |
| エンドポイントはあるがバケットポリシーで拒否される | 経路の追加では解決しない。**認可（バケットポリシー／エンドポイントポリシー／IAM）**を確認 | NAT/IGW追加：経路の問題ではない |
| 他社SaaSに自VPCのCIDRを知られずに接続したい | PrivateLink（インターフェース型） | ピアリング：CIDRを相互に公開する |

**理解確認**：「S3にはゲートウェイ型があるのに、なぜオンプレからはインターフェース型を使うのか」→ ゲートウェイ型は**VPCのルートテーブルのエントリ**であり、VPNやDXで繋いだオンプレ側のルーティングには現れない。インターフェース型は**ENI（プライベートIP）**なので、VPCに到達できる経路があればオンプレからも届く。

## 3.4 名前解決：Route 53 と Resolver

**困りごと**：「DNSで振り分ける」と「HTTPリクエストを制御する」を混同すると、Route 53で認証やパスルーティングをしようとする設問で間違える。DNSが返すのは**IP（または別名）だけ**で、リクエストの中身は見ない。

**仕組み**：DNSは通信の**前**に行われる名前→IPの解決。経路（3.1）や通信許可（3.2）とは独立している。名前が引けても経路がなければ届かず、経路があっても名前が引けなければ始まらない。

**ルーティングポリシー（何を基準にどのIPを返すか）**

| 基準 | ポリシー | 補足 |
|---|---|---|
| 常に同じ答え | シンプル | |
| **正常なほうを返す**（アクティブ/スタンバイ、DR） | フェイルオーバー（**ヘルスチェック必須**） | 切替は**TTL分遅れる** |
| **最も遅延が小さい**リージョン | レイテンシーベース | 距離ではなく計測された遅延 |
| **ユーザーの国・地域** | 位置情報（Geolocation） | 言語別サイト、法規制、地域ブロック |
| リソースの位置と**バイアス**で範囲を調整 | 地理的近接性（Geoproximity、Traffic Flow必要） | |
| **重み**で割合を変える（A/Bテスト、段階移行） | 加重（Weighted） | 20%だけ新環境へ、など |
| **複数のIP**を返す（簡易な負荷分散） | 複数値回答 | ヘルスチェック付き |

**DNSでできること／できないこと**
- できる：リージョン間の振り分け、障害時の切替、段階的な移行。
- **できない**：パスやヘッダーでの振り分け（→ALB）、認証（→ALB＋Cognito、API Gateway）、IPでの遮断（→WAF/NACL）、レート制限（→WAF）。

**選ぶ条件／選ばない条件**
- **エイリアスレコード**：ALB・CloudFront・S3・API Gatewayなどへ向け、**Zone Apex（example.com）に設定でき、クエリ料金が無料**。CNAMEはApexに設定できない。
- ヘルスチェックは**エンドポイント／他のヘルスチェックの計算（親子）／CloudWatchアラーム**の3種。プライベートリソースは外から見えないので**CloudWatchアラーム経由**で監視。
- プライベートホストゾーン＝VPC内だけで有効な名前解決。
- **Resolver エンドポイント**：**インバウンド**＝オンプレからAWSの名前を引く／**アウトバウンド**＝AWSからオンプレの名前を引く。これは名前解決の話で、経路（VPN/DX）は別に必要。
- TTLを短くすると切替が速いが、クエリ料金と負荷は増える。**DNSでのフェイルオーバーはTTL分の遅れが出る**。TTLを待てない要件なら Global Accelerator（3.6）。

**条件違いの例**

| 条件 | 判断 | 外す候補と理由 |
|---|---|---|
| 東京とバージニアの両方で稼働、ユーザーを速いほうへ | レイテンシーベース | 位置情報：国で決めるので遅延最小とは限らない |
| EUのユーザーだけEU内のサイトへ（法規制） | 位置情報（Geolocation） | レイテンシーベース：遅延が小さければEU外へ送る可能性がある |
| /api はコンテナ、/static はS3へ振り分けたい | ALB（パスルーティング）またはCloudFront（ビヘイビア） | Route 53：パスを見られない |
| オンプレのサーバーがVPC内のプライベート名を引きたい | Resolver インバウンドエンドポイント（＋VPN/DX） | アウトバウンド：向きが逆 |

**理解確認**：「Route 53のフェイルオーバーで切り替えたのに、一部ユーザーが古い側に行き続ける」理由は？→ クライアントやリゾルバが**TTLの間キャッシュ**しているため。即時に切り替えたいなら、TTLを短くするか、DNSに依存しないGlobal Acceleratorを使う。

## 3.5 負荷分散：ELB

**困りごと**：「ALBかNLBか」を機能表で覚えると、固定IPと静的IPの違いや、WAFを付けられる先の違いで迷う。**L7（HTTPの中身を見る）かL4（TCP/UDPの接続だけ見る）か**で分け、そのうえで固定IPの要否を見る。

**仕組み**：ELBはDNS名で公開され、複数AZのノードがトラフィックをターゲット（EC2、IP、Lambda、コンテナ）へ分散する。ヘルスチェックに失敗したターゲットには送らない。ASGとセットで「台数の増減」と「振り分け」を分担する。

**種類の見分け**

| 問題文の条件 | 答え | 補足 |
|---|---|---|
| HTTP/HTTPS、**パス・ホスト名・ヘッダーでルーティング**、コンテナ、Lambdaをターゲット、Cognito認証、WAF | **ALB**（L7） | DNS名のみで**固定IPは持たない** |
| **TCP/UDP**、**静的IP／Elastic IP**、超低レイテンシ、数百万リクエスト/秒、**送信元IPを保持**、PrivateLinkの受け口 | **NLB**（L4） | WAFは付けられない |
| **サードパーティ製のファイアウォール/IDS/IPSアプライアンス**を透過的に通す | **GWLB**（GENEVE） | |
| 古い環境、EC2-Classic | CLB（レガシー、新規は選ばない） | |

**選ぶ条件／選ばない条件**
- 固定IPが要件（顧客のファイアウォールに登録）→**NLB**か**Global Accelerator**。ALBの前にNLBを置く構成もある。
- クロスゾーン負荷分散：**ALBは既定で有効（無料）／NLB・GWLBは既定で無効**（有効化するとAZ間転送料）。
- スティッキーセッション：ALBはCookieベース、NLBはソースIPベース。**セッションは外部化（ElastiCache/DynamoDB）するのが設計としての正解**で、スティッキーは応急処置。
- 登録解除の遅延（接続ドレイニング、既定300秒）＝スケールイン時に処理中のリクエストを切らない（→付録B）。
- ACM証明書で**SSL/TLSを終端**、SNIで1つのALBに複数ドメインの証明書。ALBでHTTP→HTTPSリダイレクト。
- クライアントIPはALBでは **X-Forwarded-For** ヘッダーで取得（NLBはそのまま見える）。
- ターゲットのヘルスチェックに失敗したインスタンスには振り分けない＝**ASGのヘルスチェックタイプをELBにする**とセットで効く（EC2ステータスだけだとアプリが死んでいても入れ替わらない）。

**条件違いの例**

| 条件 | 判断 | 外す候補と理由 |
|---|---|---|
| HTTPS、/api と /web でターゲットを分けたい | ALB | NLB：パスを見られない |
| 顧客が送信元IPを固定してほしいと言っている（TCP） | NLB（EIP割当） | ALB：固定IPなし |
| HTTPSでパス分けもしたいが固定IPも必要 | NLB → ALB の2段、または Global Accelerator → ALB | ALB単体：固定IPなし |
| ゲームのUDPトラフィック | NLB | ALB：HTTP/HTTPSのみ |

**理解確認**：「ALBの前にWAFを付けた。NLBにも付けたい」は可能か？→ **不可**。WAFはHTTPの中身を見るのでL7のALB・CloudFront・API Gatewayにしか付かない。NLBの前で守るならNACL/SG、またはCloudFront＋WAFを前段に置く。

---

## 3.6 配信と高速化：CloudFront と Global Accelerator

**困りごと**：どちらも「エッジ」「高速化」と説明されるので混同する。違いは**キャッシュするか（HTTP）**と**固定IPでTCP/UDPを引き込むか**。

### CloudFront

**仕組み**：世界中のエッジロケーションでコンテンツを**キャッシュ**し、ユーザーに近い場所から返すCDN。オリジンはS3・ALB・EC2・オンプレいずれも可。キャッシュできない動的コンテンツも、エッジからAWSバックボーンを通ることで速くなる。

**選ぶ条件／選ばない条件**
- S3を**非公開のまま**配信するなら **OAC（旧OAI）**。バケットポリシーでCloudFrontのみ許可。
- コンテンツ保護：**署名付きURL＝個別ファイル／署名付きCookie＝複数ファイルをまとめて**。地理的制限で国単位のブロック。
- **WAFを付けられる**（ALB/CloudFront/API Gatewayが対象。NLBには付かない）。
- CloudFront用のACM証明書は**バージニア北部（us-east-1）で発行**する。
- オリジン障害に備える**オリジングループ（オリジンフェイルオーバー）**。
- コスト削減は**価格クラス**（100/200/All）で配信範囲を絞る。
- キャッシュの即時更新は**無効化（Invalidation）**だが、**ファイル名にバージョンを付ける方が推奨**。
- **混同注意**：S3 Transfer Acceleration＝**アップロード**の高速化／CloudFront＝**配信（ダウンロード）**の高速化。

### Global Accelerator

**仕組み**：2つの**固定Anycast IP**でユーザーを最寄りのAWSエッジに引き込み、AWSバックボーン経由で最適なリージョンのエンドポイント（ALB/NLB/EIP）へ送る。キャッシュはしない。エンドポイントのヘルスに応じて**数十秒でリージョンを切り替える**（DNSのTTLに依存しない）。

**CloudFrontとの見分け**

| 条件 | 答え | 外す理由 |
|---|---|---|
| 静的/動的コンテンツを**キャッシュ**して配信、HTTP/HTTPS | CloudFront | GA：キャッシュしない |
| **TCP/UDP**（ゲーム、IoT、VoIP、SIP）、キャッシュ不要 | Global Accelerator | CloudFront：HTTP/HTTPSのみ |
| **静的IPアドレスが必要**（ファイアウォールのホワイトリスト登録） | Global Accelerator | CloudFront：IPは変わる |
| **リージョン障害時に数十秒で切り替えたい**（DNS TTLに依存したくない） | Global Accelerator | Route 53：TTL分遅れる |
| 段階的にリージョンへ流量を振る | Global Accelerator（トラフィックダイヤル） | |

**理解確認**：「動画配信サイトの表示を速くしたい」と「対戦ゲームのUDP通信を安定させたい」で答えが分かれる理由は？→ 前者は**同じコンテンツを多数が取る**のでキャッシュが効く＝CloudFront。後者は**キャッシュできない双方向のTCP/UDP**を近いエッジから安定した経路で送る＝Global Accelerator。
