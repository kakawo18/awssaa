# 第3章 ネットワークおよびコンテンツ配信

> **章の一言**：ネットワーク関連の設問は、「**1つのパケットがどの経路を通り、どのレイヤーで遮断されているか**」を論理的に追跡することで解きほぐせます。確認の基本順序は、**所属範囲（CIDR/サブネット）→ ルーティング（ルートテーブル）→ パケットフィルタリング（SG/NACL）→ 外部への接続経路（IGW/NAT Gateway/VPCエンドポイント）→ 名前解決（DNS）**です。通信が失敗する原因が「ルーティング（経路）」なのか「ネットワーク制御（SG/NACL）」なのか「リソースへのアクセス認可（IAM/バケットポリシー）」なのかを正確に見極めることが最も重要です（→第0章 0.4）。

---

## 3.1 VPCの基礎：所属範囲とルーティング

**困りごと**：「パブリックサブネットにEC2を配置したのにインターネットに出られない」「NAT Gatewayを追加したのにS3への書き込みがエラーになる」といった問題は、通信が通過する階層の順序を整理せずにコンポーネントを闇雲に追加してしまうことが原因です。

**仕組み：1つの通信パケットが通過する階層**

| 順序 | 評価レイヤー | 決定される事項 | 試験での主な問われ方 |
|---|---|---|---|
| 1 | **IPアドレス／CIDR／サブネット** | 送信元や宛先がどのネットワーク範囲に所属するか | サブネットサイズ（例：`/28` であれば利用可能なIPは11個。**ネットワークアドレス、ブロードキャスト、AWS予約の計5個が予約済み**） |
| 2 | **ルートテーブル** | 宛先IPに対する**次のホップ（転送先ターゲット）**。最長プレフィックス一致で1つのルートが選択される | デフォルトルート `0.0.0.0/0` のターゲットが IGW なのか、NAT Gateway なのか、未設定なのか |
| 3 | **セキュリティグループ／ネットワークACL** | パケットの送受信を**許可するかどうか**（往路と復路の双方） | 3.2で詳述 |
| 4 | **IGW／NAT Gateway／VPCエンドポイント** | VPCの**境界の外へどのような手段で抜けるか**（方向性と接続先） | 3.3で詳述 |
| 5 | **DNS（名前解決）** | 宛先の**ホスト名をどのIPアドレスに解決するか**（ルーティング経路とは独立） | 3.4で詳述 |

**サブネットの種類は「名前」ではなく「ルートテーブル」で決まる**
- **パブリックサブネットの本質**：ルートテーブルにインターネットゲートウェイ宛てのデフォルトルート（`0.0.0.0/0 → igw-xxxx`）が関連付けられているサブネットを指します。名前に「public」と付いていても、ルートテーブルにIGWへの経路がなければ外部通信は成立しません。
- パブリックサブネット内に配置したEC2インスタンスであっても、**パブリックIPv4アドレス（またはElastic IP）が割り当てられていなければインターネットとの双方向通信はできません**。ルーティング経路とパブリックIPの双方が必要です。
- **プライベートサブネット**からのアウトバウンド専用通信（OSパッチ取得や外部API呼び出しなど）には **NAT Gateway** を使用します。NAT Gateway自体は**パブリックサブネット内に配置**し、単一障害点を回避するために**AZごとに1台ずつ冗長配置**します（同一AZのNAT Gatewayが停止しても、他AZのインスタンスに影響を波及させないため）。
- **IPv6環境**におけるアウトバウンド専用の出口には、**Egress-Only インターネットゲートウェイ（EIGW）**を使用します（IPv6にはNATという概念がなく、ステートフルなアウトバウンド限定ゲートウェイとして機能します）。

**VPC接続Lambda関数の通信における注意点**
- Lambda関数をVPCに接続すると、関数実行環境はVPC内のHyperplane ENI経由で通信します。この際、**たとえパブリックサブネットを指定して配置しても、直接インターネットには出られません**。LambdaのENIにはパブリックIPアドレスが付与されないため、IGWを経由したインターネットアクセスが成立しないためです。
- 外部インターネットへ接続させる場合は、**プライベートサブネットに配置し、パブリックサブネットに置いたNAT Gatewayを経由**させます。なお、宛先がS3やDynamoDBのみであれば、NAT Gatewayではなく**ゲートウェイ型VPCエンドポイント**を利用する方がコストとスループットの面で優れています。

**選ぶ条件／選ばない条件**
- 「プライベートサブネット内のEC2からOSパッチをダウンロードしたい」→ NAT Gateway を配置。**AWS Systems Manager Session Manager はSSHのセキュアな代替手段であり、インスタンスからの任意のアウトバウンド通信経路にはなりません**。
- 「S3へのみ通信を行いたい、NAT Gatewayの通信処理コストを削減したい」→ ゲートウェイ型VPCエンドポイント（3.3）。S3専用のアクセスに対してNAT Gatewayを追加するのはコスト過剰となります。

**条件違いの例**

| 前提条件 | 適切な判断 | 他の選択肢を除外する理由 |
|---|---|---|
| EC2をパブリックサブネットに配置したが外部と通信できない。ルートテーブルには `0.0.0.0/0 → IGW` が存在する | パブリックIP／EIPの割り当て有無、およびSG/NACLの通信許可設定を確認する | NAT Gatewayの追加：パブリックサブネットでは不要。ルートの追加：すでにIGW宛てが存在するため不要 |
| プライベートサブネットのEC2からS3に対して、NAT料金をかけずに通信させたい | S3用のゲートウェイ型VPCエンドポイントを導入する | NAT Gateway：動作はするが処理料金とデータ転送料金が発生する。IGW直結：プライベートサブネットの定義に反する |
| VPC接続のLambda関数から外部サードパーティAPIを呼び出したい | プライベートサブネットに配置し、パブリックサブネットのNAT Gatewayを経由させる | パブリックサブネットへの直接配置：LambdaのENIにパブリックIPが付与されないため通信不可 |

**理解確認**：「パブリックサブネットとは何か」を、設定の観点から説明せよ。
→ **ルートテーブルにインターネットゲートウェイ（IGW）へのデフォルトルート（`0.0.0.0/0`）が設定されているサブネット**。さらに、配置されたインスタンスが実際にインターネットと通信するには、パブリックIPアドレスの割り当てと、SG/NACLによる双方向の通信許可が必要です。

**ネットワークの監視・分析ツール**：VPCフローログ（**パケットのメタデータ［送信元/宛先IP・ポート・プロトコル・許可/拒否］は記録できるが、ペイロード［パケットの中身］は見えない**。ペイロードのキャプチャが必要な場合はトラフィックミラーリングを使用）、VPC Reachability Analyzer（設定に基づいて通信経路の疎通可否をシミュレーションし、どのレイヤーで遮断されているかを特定するツール）、AWS Network Firewall（ステートフルなL3〜L7インスペクションやFQDNドメインフィルタリングを提供するフルマネージドファイアウォール）。

## 3.2 通信制御：セキュリティグループとネットワークACL

**困りごと**：「特定IPアドレスを遮断したい＝ネットワークACL」と単純暗記していると、WAFやセキュリティグループで対処すべき設問を見誤ります。また、往路（インバウンド）と復路（アウトバウンド）の通信特性を正しく把握していないと、ネットワークACLで戻りパケットを誤って遮断してしまいます。

**仕組みの対比**

| 比較項目 | セキュリティグループ（SG） | ネットワークACL（NACL） |
|---|---|---|
| 適用対象 | ENI（インスタンス／リソース単位） | サブネット単位。**サブネットの境界を出入りするトラフィック**に適用され、**同一サブネット内のインスタンス間通信には関与しない**（サブネット内の通信制御はSGで行う） |
| 動作状態 | **ステートフル**：インバウンドを許可すれば、対応する**戻りのアウトバウンド通信は自動的に許可**される | **ステートレス**：インバウンドとアウトバウンドを**それぞれ明示的に許可**する必要がある（戻り通信用に**エフェメラルポート 1024〜65535**の開放が必須） |
| 評価ルール | **許可ルールのみ**定義可能（定義されていない通信は暗黙的に拒否） | **許可および拒否ルール**を定義可能。**ルール番号の若い順**に評価され、最初に一致したルールが適用される |
| 送信元／宛先の指定 | IPアドレス（CIDR）に加え、**他のセキュリティグループIDを指定可能**（IP変動に依存しないチェーン設定が可能） | IPアドレス（CIDR）のみ指定可能 |

**選ぶ条件／選ばない条件**
- 一般的な多層アーキテクチャのアクセス制御（Web層はALBのSGからのみ許可、DB層はApp層のSGからのみ許可）→ **セキュリティグループ**。SG同士を相互参照させるチェーン構成がベストプラクティスです。
- **特定の発信元IPアドレス／CIDRブロックからの通信を明示的に拒否したい** → 状況に応じて以下のサービスを使い分けます：
  - **L3/L4レベルで、サブネット全体への到達を拒否したい** → **ネットワークACL**（VPC内で拒否ルールを直接記述できる標準機能）。
  - 通信プロトコルが**HTTP/HTTPSであり、ALB／CloudFront／API Gatewayの前段で遮断したい** → **AWS WAF の IPセット**（レートベースの制限やSQLインジェクション対策なども一元管理可能）。
  - **CloudFront配信において国・地域単位で遮断したい** → **CloudFrontの地理的制限（Geo Restriction）**（ネットワークACLには地理情報の概念はありません）。
  - セキュリティグループには「拒否ルール」が存在しないため、「SGで特定IPを明示的に拒否する」という選択肢は誤りとなります。
- 「リクエストは届くがレスポンスがクライアントに返らない」→ ネットワークACLのアウトバウンドでエフェメラルポート（1024〜65535）が許可されていないケースが典型です。ステートフルなセキュリティグループではこの問題は発生しません。

**条件違いの例**

| 前提条件 | 適切な判断 | 他の選択肢を除外する理由 |
|---|---|---|
| 特定の悪意あるIPからのSSH攻撃をサブネット単位で即座に遮断したい | ネットワークACLで若い番号の拒否（DENY）ルールを追加する | セキュリティグループ：拒否ルールを記述できない。WAF：SSHはL4プロトコルのためL7対象のWAFでは検査不可 |
| 特定IPからの大量HTTPアクセスを遮断し、あわせてリクエスト頻度のレート制限も行いたい | AWS WAF（IPマッチ条件＋レートベースルール） | ネットワークACL：レート制限や動的な頻度制御には対応できない。サブネット全体に影響が及ぶ |
| Web層へのアクセスはALB経由のみに限定し、DB層へのアクセスはWeb層からのみに限定したい | セキュリティグループの送信元に相手のSG IDを指定してチェーン化する | ネットワークACL：IP（CIDR）しか指定できず、ALBのように動的にIPが変わるリソースを正確に制御できない |

**理解確認**：「ネットワークACLのインバウンドでポート80を許可したのに、Webサーバーからのレスポンスが外部クライアントに戻らない」原因は何か？
→ ネットワークACLはステートレスであるため、**アウトバウンドルールでクライアント側の一時ポート（エフェメラルポート：1024〜65535）への送信が許可されていない**ことが原因です。セキュリティグループであれば戻りの通信は自動的に追跡・許可されます。

## 3.3 VPCの外部接続：エンドポイント・PrivateLink・ピアリング・Transit Gateway・Direct Connect

**困りごと**：「S3/DynamoDB＝ゲートウェイ型、それ以外＝インターフェース型」と単純暗記していると、オンプレミス環境から専用線経由でS3へプライベート接続する設問で判断を誤ります。エンドポイントの選定は、「**接続元のクライアントがどこに存在するか**」および「**ルーティング経路が伝播可能か**」によって決まります。

**仕組み：VPCエンドポイントの2つのタイプ**

| 比較項目 | ゲートウェイ型エンドポイント | インターフェース型エンドポイント（AWS PrivateLink） |
|---|---|---|
| 実装形態 | **ルートテーブルのエントリ**（プレフィックスリスト → `vpce-xxxx`） | **サブネット内に配置されるENI**（プライベートIPアドレスを持つ） |
| 対応サービス | **Amazon S3 および DynamoDB のみ** | ほとんどのAWSマネージドサービス、**Amazon S3（対応）**、他アカウントのサービス、サードパーティSaaS |
| 料金体系 | **追加料金なし（無料）** | **エンドポイントごとの時間課金 ＋ 処理データ量課金（有料）** |
| 利用可能な接続元 | **同一VPC内のリソースからのみ**（ルートテーブルを参照できる同一VPC内のコンポーネントに限定） | 同一VPC内に加え、**VPCピアリング、Transit Gateway、Site-to-Site VPN、Direct Connect経由のオンプレミス環境**からも到達可能 |
| セキュリティグループ | 適用不可（エンドポイントポリシーで制御） | ENIに対してセキュリティグループを適用可能 |
| 名前解決 | 不要（ルートテーブルのプレフィックスリストで自動ルーティング） | プライベートDNSを有効化することで、標準のサービスFQDNをENIのプライベートIPに自動解決 |

**S3へのプライベートアクセスの選び分け**
- **同一VPC内からS3へ接続し、インターネット経由やNAT Gatewayの費用を回避したい** → まず**ゲートウェイ型エンドポイント**を検討（追加料金なしで利用可能）。
- **オンプレミス環境からDirect ConnectやVPN経由でS3へプライベート接続したい** → **インターフェース型エンドポイント**を採用。ゲートウェイ型エンドポイントはVPCのルートテーブルにのみ存在するため、オンプレミス側へ経路を拡張・伝播させることができません。**Direct Connect Gatewayを経由した場合でも、S3のゲートウェイ型エンドポイントへは到達できません**。
- 「S3＝ゲートウェイ型」と決めつけるのではなく、「**S3であっても接続元がVPCの外部であればインターフェース型が必要**」と整理します。

**エンドポイントを経由しているのにアクセスが拒否される場合**：ネットワーク経路は開通しています。**S3バケットポリシー、VPCエンドポイントポリシー、IAMポリシー**の認可設定を確認します（バケットポリシーで `aws:sourceVpce` 条件を用いて特定のエンドポイントからのみアクセスを許可している場合、異なる経路や別のエンドポイントからのリクエストは403エラーとなります）。新たなゲートウェイやルーティングを追加しても解決しません。

**VPC間およびオンプレミスとの接続方式の選び分け**

| 要件 | 最適な選択肢 | 選ばない理由・制約事項 |
|---|---|---|
| 自社の特定サービスのみを他アカウントのVPCに安全に公開したい（自社VPCの全体ネットワークは見せない） | **AWS PrivateLink**（NLB＋VPCエンドポイントサービス） | VPCピアリング：相手側に自社VPC全体のCIDRが公開され、CIDRの重複が許容されない |
| 2つのVPC間のみをシンプルかつ安価に直接接続したい | **VPCピアリング** | 3つ以上のVPCを相互接続する場合、推移的ルーティング（A-B間とB-C間からA-C間の通信）が不可能なためフルメッシュ接続が必要になり管理が複雑化する |
| 多数のVPC間、およびオンプレミス環境をハブ＆スポーク型で一元的に統合接続したい | **AWS Transit Gateway** | 2つのVPC間だけの接続であれば、Transit Gatewayは時間料金や処理料金が発生するためVPCピアリングの方が安価 |
| オンプレミスとの安全な通信を**低コストかつ迅速に**開設したい | **AWS Site-to-Site VPN**（インターネット経由、冗長2トンネル） | 帯域の安定性や一貫した低遅延が必須要件である場合はDirect Connectが必要 |
| **一貫した高帯域・極めて低いレイテンシ**の専用物理接続が必要 | **AWS Direct Connect**（物理回線手配のため開通に数週間〜数ヶ月要する） | **既定では暗号化されない**（通信の暗号化が必須要件の場合は、Direct Connect上でIPsec VPNを構成するか、MACsec対応ポートを利用する） |
| Direct Connect接続の耐障害性・冗長構成 | Direct Connect回線の2重化（最高可用性）／ Direct Connect ＋ バックアップとしてのSite-to-Site VPN（現実的な高可用性構成） | 単一のDirect Connect接続では回線障害やメンテナンスに対応できない |
| 1本のDirect Connect接続から複数リージョンの複数VPCへアクセスしたい | **Direct Connect Gateway** | 各リージョンごとに個別の物理回線を敷設するのは非効率 |

## 3.4 名前解決：Route 53 と Resolver

**困りごと**：「DNSによる名前解決での振り分け」と「リクエスト内容に基づくルーティング」を混同すると、URLパスによる振り分けやユーザー認証をRoute 53で処理しようとして誤答に至ります。DNSがクライアントに返すのは**IPアドレス（またはエイリアス名）のみ**であり、HTTPリクエストのヘッダーやパス情報の内容を見ることはできません。

**ルーティングポリシーの選び分け**

| ルーティングポリシー | 動作と特徴 | 主な用途 |
|---|---|---|
| **シンプル** | 単一のリソースまたは静的なIPアドレスを返す | 特別な制御が不要な標準的な単一構成 |
| **フェイルオーバー** | プライマリのヘルスチェックが異常となった場合にスタンバイへ切り替え（**ヘルスチェックの設定が必須**） | アクティブ／パッシブ構成のディザスタリカバリ（切り替えには**DNS TTL分の遅延**が生じる） |
| **レイテンシーベース** | エンドユーザーに対して最も通信遅延が小さいAWSリージョンのリソースを返す | 世界各地に分散配置された複数リージョン環境でのパフォーマンス最適化 |
| **位置情報（Geolocation）** | クライアントのアクセス元国や地域に基づいてリソースを返す | 地域ごとの言語別サイト誘導、コンテンツ配信権の法規制順守、特定地域からのアクセス制御 |
| **地理的近接性（Geoproximity）** | ユーザーとリソースの物理的な位置関係に基づき、**バイアス値**を調整してトラフィックの配分領域を柔軟に変更 | Route 53 Traffic Flow を用いた高度な地域間トラフィック制御 |
| **加重（Weighted）** | 指定した数値の比率（パーセンテージ）に従ってリソースへトラフィックを配分 | 新機能の段階的リリース、カナリアリリース、A/Bテスト |
| **複数値回答** | ヘルスチェックを通過した最大8つの正常なIPアドレスをランダムに返す | クライアント側での簡易なロードバランシング |

**DNSレベルで実現できること／できないことの明確化**
- **可能なこと**：リージョン間でのトラフィック振り分け、障害時のスタンバイ系への切り替え、段階的な加重移行。
- **不可能なこと**：URLパスやHTTPヘッダーによる振り分け（→ ALBで処理）、認証・認可（→ ALB＋Amazon Cognito、API Gateway）、送信元IPによるアクセス遮断（→ AWS WAF、ネットワークACL）、レート制限（→ AWS WAF）。

**Route 53の重要仕様**
- **エイリアスレコード**：Route 53固有の仮想レコード。ALB、CloudFront、S3静的ウェブサイトホスティング、API Gateway等のAWSリソースを直接指定でき、**Zone Apex（ネイキッドドメイン：`example.com` など）にも設定可能**です。さらに、エイリアスレコードに対する名前解決クエリには**DNSクエリ料金が発生しない**というメリットがあります（CNAMEレコードはZone Apexには設定できません）。
- **Route 53 Resolver エンドポイント**：
  - **インバウンドエンドポイント**：オンプレミスのDNSサーバーから、VPC内のプライベートホストゾーンの名前解決を転送・問い合わせる際に使用。
  - **アウトバウンドエンドポイント**：VPC内のリソースから、オンプレミス環境の社内ドメインを名前解決するためにオンプレミスDNSサーバーへ転送する際に使用。
  - （※これらはDNSクエリの受け渡し機能であり、VPCとオンプレミス間のネットワーク経路［Site-to-Site VPNやDirect Connect］が別途疎通している必要があります）。
- **フェイルオーバーの即時性**：DNSによる切り替えはクライアントやローカルリゾルバのDNSキャッシュに依存するため、**TTLが切れるまで古い宛先へアクセスが継続**します。数秒〜数十秒での即時フェイルオーバーが必須要件である場合は、DNSに依存しない **AWS Global Accelerator** を検討します。

## 3.5 負荷分散：Elastic Load Balancing（ELB）

**困りごと**：「ALBかNLBか」を機能一覧の丸暗記で判断しようとすると、固定IPの要否やAWS WAFとの連携可否で混乱します。基本は「**L7（HTTP/HTTPSの中身を解析して振り分けるか）**」または「**L4（TCP/UDPの接続を高速に中継するか）**」を軸に判断します。

**ロードバランサーの種類の選び分け**

| 種類 | レイヤー | 主な特徴と適した要件 | 注意点・制約事項 |
|---|---|---|---|
| **Application Load Balancer（ALB）** | レイヤー7（HTTP/HTTPS） | **URLパス、ホスト名、HTTPヘッダーに基づく詳細なルーティング**。ターゲットとしてEC2、ECSコンテナ、Lambda関数をサポート。**AWS WAFの直接統合**、Cognitoによるユーザー認証統合 | ロードバランサー自体はDNS名で提供され、**固定の静的IPアドレスは持たない** |
| **Network Load Balancer（NLB）** | レイヤー4（TCP/UDP/TLS） | 超高スループット、**極めて低いレイテンシ**、毎秒数百万リクエストの急激なスパイク対応。**固定の静的IPアドレス（Elastic IP）**を各AZに割り当て可能。送信元IPアドレスを保持。AWS PrivateLinkのエンドポイントサービス受け口 | HTTPレベルのルーティングは不可。**AWS WAFを直接アタッチすることはできない** |
| **Gateway Load Balancer（GWLB）** | レイヤー3/4 ＋ 透過ゲートウェイ | サードパーティ製の**次世代ファイアウォール（NGFW）、IDS/IPSアプライアンス**の仮想マシン群を水平スケールさせ、透過的にトラフィックを中継・検査 | GENEVEプロトコル（ポート6081）によるカプセル化を使用 |

**設計上の重要ポイント**
- **固定IPアドレスの要件**：クライアント側のファイアウォールで送信先IPをホワイトリスト登録する必要がある場合 → **NLB** または **AWS Global Accelerator** を採用します。ALBの高度なL7ルーティングと固定IPを両立させたい場合は、「NLBを前段に置きターゲットとしてALBを指定する構成」または「Global Acceleratorの後段にALBを配置する構成」をとります。
- **クロスゾーン負荷分散**：ALBでは既定で有効（追加料金なし）。NLBおよびGWLBでは既定で無効（有効化するとAZをまたぐ通信に対してリージョン内データ転送料金が発生します）。
- **セッションの維持（スティッキーセッション）**：同一クライアントからのリクエストを同一インスタンスに固定する機能（ALBはCookieベース、NLBは送信元IPベース）。ただし、ステートレス設計の観点からは、**セッション情報を外部データストア（Amazon DynamoDB や ElastiCache）へ分離・集約するのがアーキテクチャとしてのベストプラクティス**です。
- **登録解除の遅延（コネクションドレイニング）**：インスタンスが登録解除される際、処理中のリクエストが切断されないよう、指定した期間（既定300秒）新規リクエストの割り振りを停止しつつ既存接続の完了を待機します。

## 3.6 コンテンツ配信と高速化：CloudFront と Global Accelerator

**困りごと**：どちらも「AWSエッジロケーションの活用」「通信の高速化」という説明がなされるため混同されがちです。判断の分かれ目は、「**コンテンツをエッジでキャッシュするか（HTTP/HTTPS専用）**」か、「**固定Anycast IPを用いてTCP/UDP通信をAWSバックボーンへ引き込むか**」にあります。

### Amazon CloudFront
- **仕組み**：世界各地のエッジロケーションで静的・動的コンテンツを**キャッシュ**し、ユーザーに物理的に最も近い場所から高速に応答するCDN（コンテンツ配信ネットワーク）サービス。
- オリジンとしては S3バケット、ALB、EC2、オンプレミスのWebサーバーなどを柔軟に設定可能。キャッシュできない動的APIリクエストであっても、最寄りのエッジからAWSの最適化された専用バックボーンを経由することでレイテンシが大幅に低減されます。
- **オリジンアクセス制御（OAC）**：S3バケットをパブリック公開せず、CloudFrontからのみ安全にアクセスさせるための最新機能（従来のOAIの後継）。
- **セキュリティと暗号化**：AWS WAF をエッジに直接統合可能。カスタムドメインのSSL/TLS証明書（ACM）は、必ず**バージニア北部リージョン（us-east-1）**で発行する必要があります。
- 署名付きURL（単一ファイルへのアクセス保護）／署名付きCookie（会員制サイト等で複数コンテンツへのアクセスを一括保護）。

### AWS Global Accelerator
- **仕組み**：ユーザーに対して**2つの静的Anycast IPv4アドレス**を提供し、世界中のエッジロケーションでトラフィックを受け入れて即座にAWSプライベートバックボーンネットワークへ引き込みます。
- **キャッシュ機能は持たず**、TCPおよびUDPトラフィックを最適化された経路で最も健全かつ近接したリージョンのエンドポイント（ALB、NLB、EC2、Elastic IP）へ高速転送します。
- エンドポイントの正常性を継続的に監視し、**障害発生時は数十秒以内で健全な別リージョンへ自動フェイルオーバー**します（クライアント側のDNSキャッシュやTTLの制約を受けません）。

**CloudFront と Global Accelerator の選び分け**

| 設問の要件・特徴 | 最適な選択肢 | 他方を除外する理由 |
|---|---|---|
| 静的・動的なWebコンテンツを**エッジでキャッシュ**して配信負荷とレイテンシを下げたい（HTTP/HTTPS） | **CloudFront** | Global Accelerator：キャッシュ機能を持たない |
| **TCP／UDPプロトコル**（オンライン対戦ゲーム、IoT通信、VoIP/SIP音声通信など）の通信遅延を低減したい | **Global Accelerator** | CloudFront：HTTP/HTTPSプロトコルのみに対応 |
| クライアント側のファイアウォールで許可するため、**固定の静的IPアドレス**が必要 | **Global Accelerator** | CloudFront：提供されるIPアドレスが変動するため固定できない |
| リージョン全体の障害発生時、**DNSのTTL遅延を待たずに数十秒で別リージョンへトラフィックを切り替えたい** | **Global Accelerator** | Route 53 / CloudFront：クライアント側のDNSキャッシュにより切り替えにタイムラグが発生する |
| リージョン間でトラフィックの比率をパーセンテージで調整したい | Global Accelerator（トラフィックダイヤル機能） | |

**理解確認**：「Webサイトの画像・HTMLの表示速度を上げたい」場合と「リアルタイム対戦ゲームのUDP通信を高速・安定化させたい」場合で選定が分かれる理由は？
→ 前者は**同一のコンテンツを多数のユーザーが繰り返し取得する**ため、エッジでのキャッシュが効果を発揮する CloudFront を選択します。後者は**キャッシュ不可能な双方向のUDPパケット通信**であり、ユーザー端末から最寄りのエッジを経由して高品質なAWS専用ネットワークへ引き込む Global Accelerator を選択します。
