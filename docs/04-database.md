# 第4章 データベース

> **章の一言**：データベースの設問は、「**どのような課題を解決するために**そのコンポーネントを追加するのか」という目的から逆算して判断します。**高可用性（AZ障害時の継続性）にはマルチAZ配置**、**読み取り負荷の分散にはリードレプリカ**、**同一結果の反復読み込みの高速化にはインメモリキャッシュ**、**大量接続によるリソース枯渇にはコネクションプーリング（RDS Proxy）**を選択します。すべて「DBの性能低下や停止」に対する解決策ですが、根本原因がそれぞれ異なります（→第0章 0.1）。

---

## 4.1 Amazon RDS

**概要**：主要なリレーショナルデータベース（MySQL、PostgreSQL、MariaDB、Oracle、Microsoft SQL Server）をAWS上でフルマネージドで提供するサービス。OSや基盤の管理責任はAWSが担うため、ホストOSへのSSHログイン等はできません。単一のプライマリインスタンスに対し、目的に応じて「スタンバイインスタンス（可用性目的）」や「リードレプリカ（読み取りスケール目的）」を追加します。

**マルチAZの2つの構成とリードレプリカの比較**

| 比較項目 | マルチAZ **DBインスタンス**配置 | マルチAZ **DBクラスター**配置 | リードレプリカ |
|---|---|---|---|
| 主な目的 | **高可用性**（AZ障害時にもサービスを停止させない） | **高可用性 ＋ 読み取り負荷分散**の統合 | **読み取り性能**の水平スケーリング |
| インスタンス構成 | プライマリ ＋ スタンバイ1台（別AZ配置） | プライマリ ＋ **読み取り可能なスタンバイ2台**（3AZ配置） | プライマリ ＋ レプリカ（最大15台程度、エンジンによる） |
| レプリケーション方式 | **同期レプリケーション** | **半同期レプリケーション**（2台のうち1台から書き込み確認を受信した時点で完了） | **非同期レプリケーション**（レプリケーションラグが発生し得る） |
| スタンバイ／レプリカの読み取り | **不可**（パッシブ待機専用） | **可能**（リーダーエンドポイント経由で自動分散） | **可能**（レプリカ固有または専用エンドポイント経由） |
| 配置範囲 | 同一リージョン内の別AZ | 同一リージョン内の3つのAZ | 同一AZ、別AZ、**別リージョン（クロスリージョン）**も可能 |
| 障害時の動作 | 自動フェイルオーバー（**DNSエンドポイントの参照先が自動切り替え**。所要時間は通常60〜120秒程度） | 自動フェイルオーバー（**通常35秒未満**で迅速に切り替え） | **手動での昇格操作**（スタンドアロンDB化）。自動フェイルオーバーは行われない |
| 対応エンジン | 主要な全RDSエンジン | MySQL および PostgreSQL のみ | エンジンごとに上限や仕様が異なる |

**選ぶ条件／選ばない条件**
- 「単一AZの障害時でも自動復旧してダウンタイムを最小化したい」→ **マルチAZ DBインスタンス配置**。スタンバイインスタンスはパッシブ待機であり読み取りクエリは受け付けないため、読み取り負荷軽減の目的では選択しません。
- 「参照系の重いクエリでプライマリDBの負荷が高騰している」→ **リードレプリカ**。ただし、**アプリケーション側で読み取りクエリの接続先をレプリカのエンドポイントに向ける改修が必要**です。非同期レプリケーションのため、更新直後の最新データを確実に読み取る必要がある処理には適しません。
- 「高可用性と読み取り負荷分散を、シンプルな単一構成で両立させたい（MySQL/PostgreSQL）」→ **マルチAZ DBクラスター配置**。設問に「35秒未満の迅速なフェイルオーバー」「読み取り可能なスタンバイ」とあればこちらを選択します。
- 「災害対策（DR）として別リージョンに待機系を構築したい、または遠隔地のユーザーに対して低遅延で読み取りを提供したい」→ **クロスリージョンリードレプリカ**。なお、リージョン間の切り替えをより高速化（RTO 1分未満）したい場合は、後述の Aurora グローバルデータベースを検討します（※いずれの場合も、リージョン障害時の昇格・切り替えは自動では行われず、手動または自動化スクリプトによるトリガーが必要です）。
- 「高可用性と読み取り性能の両立（既存エンジン全般）」→ マルチAZ DBインスタンス配置 ＋ リードレプリカの併用構成をとります。

**条件違いの例**

| 設問の要件 | 適切な判断 | 他の選択肢を除外する理由 |
|---|---|---|
| AZ障害時にダウンタイムを最小化して自動復旧させたい。参照クエリの性能は現行で十分 | マルチAZ DBインスタンス配置 | リードレプリカ：非同期であり、障害時に手動昇格が必要なため自動復旧要件を満たさない |
| 月次の集計バッチ処理が本番業務の参照を圧迫している。数秒程度のデータ遅延は許容される | リードレプリカを作成し、集計処理の接続先を向ける | マルチAZ DBインスタンス配置：スタンバイは待機専用であり読み取り分散には使えない |
| 高可用性と読み取り分散を1つのクラスターで実現し、フェイルオーバー時間も短縮したい（PostgreSQL） | マルチAZ DBクラスター配置 | インスタンス配置＋レプリカ：要件は満たせるが、構成と管理対象が2重になる |
| ユーザーによるデータ更新の直後に、必ず最新の反映結果を画面に表示する必要がある | プライマリインスタンスから直接読み取る | リードレプリカ：非同期複製のため、レプリケーション遅延により古い値が返されるリスクがある |

**理解確認**：「マルチAZ DBインスタンス配置のRDSにおいて、参照クエリをスタンバイインスタンスにルーティングして負荷分散を図る」ことは可能か？
→ **不可**。DBインスタンス配置のスタンバイは待機専用であり、クライアントからの接続を受け付けません。読み取り負荷を分散させるには、リードレプリカを追加するか、読み取り可能なスタンバイを備えたマルチAZ DBクラスター配置（またはAmazon Aurora）を採用する必要があります。

**その他の重要機能・設計ポイント**
- **自動バックアップとポイントインタイムリカバリ（PITR）**：バックアップ保持期間（1〜35日）を指定可能で、トランザクションログと併せて過去の任意の秒単位の時点へ新規インスタンスとして復元できます。手動スナップショットは明示的に削除するまで無期限に保持されます。
- **暗号化の適用**：保存時の暗号化（AWS KMS）は**インスタンス作成時にのみ有効化可能**です。既存の未暗号化DBを暗号化するには、「スナップショット作成 → 暗号化を有効にしてスナップショットをコピー → 暗号化スナップショットから新規DBを復元」の手順を実行します。
- **Amazon RDS Proxy**：サーバーレスアーキテクチャや大量接続環境向けのフルマネージド・データベースプロキシ（接続プーリング）。「Lambdaからの急激な同時アクセスによる接続数枯渇（Too many connections）」「接続確立に伴うCPUオーバーヘッド」を解消します。フェイルオーバー時の接続切り替え時間を短縮し、IAM認証の強制やSecrets Managerとの自動連携も可能です。
- **監視と診断**：OSレイヤーのCPU・メモリ詳細メトリクスは **拡張モニタリング（Enhanced Monitoring）** で収集します。データベース内部の実行計画や高負荷クエリの特定には **Performance Insights** を使用します。
- 認証情報の安全な管理には **AWS Secrets Manager** を併用し、パスワードの自動ローテーションを設定します。

## 4.2 Amazon Aurora

**概要**：クラウドネイティブに再設計されたMySQL/PostgreSQL互換の高性能リレーショナルデータベース。3つのAZにまたがって6つのデータコピーを自動保持する分散共有ストレージアーキテクチャが最大の特徴です。

**試験での要点**
- ストレージは10GB単位で**自動的にスケール**し、最大サイズまでの事前プロビジョニングが不要です。上限容量はエンジンバージョンに依存し、**128 TiB**（従来バージョン全般）または**256 TiB**（Aurora PostgreSQL 17.5/16.9/15.13以降、Aurora MySQL 3.10以降）に対応しています（→付録B）。
- クォーラムモデルによる書き込みと読み取り：書き込みは**6コピー中4つ**、読み取りは**3つ**のノードの応答で成立します。1つのAZ全体が停止（2コピー喪失）しても書き込みを継続でき、2つのAZに障害（3コピー喪失）が発生しても読み取りを維持できる自己修復機能を備えています。
- リードレプリカは**最大15台**まで追加可能で、プライマリとストレージ層を共有しているためレプリケーション遅延が極めて小さく（通常ミリ秒単位）、フェイルオーバーも**通常30秒以内**で完了します。
- エンドポイントの種類：**クラスターエンドポイント（書き込み用プライマリ宛て）**／**リーダーエンドポイント（複数リードレプリカへの読み取り負荷分散用）**／カスタムエンドポイント（特定のインスタンス群グループ用）。
- **バックトラック（Backtrack）**：Aurora MySQLにおいて、バックアップからの復元作業を行わずに、巻き戻したい過去の時点へ数分以内にデータベースの状態を即座に戻せる機能（人為的ミスからの超高速リカバリ）。
- **高速データベースクローニング**：書き込み時コピー（Copy-on-Write）プロトコルにより、本番ストレージのデータを物理コピーすることなく、数分で開発・検証用の独立したクローンDBを作成できます。

**派生機能・構成の選び分け**
| 設問の要件・特徴 | 最適な選択肢 |
|---|---|
| 利用頻度が断続的・予測不能、夜間やアイドル時は自動停止してコストを削減したい | **Aurora Serverless v2**（ACU単位で細粒度に自動スケール） |
| **複数リージョン間**で1秒未満のデータ複製を実現し、リージョン規模の災害時にRTO 1分未満で復旧したい | **Aurora グローバルデータベース** |
| Microsoft SQL Server用に開発されたアプリケーションを、**コード改変を最小限に抑えて**PostgreSQLへ移行したい | **Babelfish for Aurora PostgreSQL** |
| 読み書きのI/Oリクエストが膨大で、従量制のI/Oコストが予測困難・高額になっている | **Aurora I/O-Optimized**（固定料金制ストレージ構成） |

**標準RDSとの選び分け**：Oracle、SQL Server、MariaDB等のエンジンが必須、または既存オンプレミスのライセンス持ち込み（BYOL）が必要な場合 → RDS。**圧倒的な高可用性・スループット・高速フェイルオーバー**を求め、MySQL/PostgreSQL互換で運用可能な場合 → Aurora。

## 4.3 Amazon DynamoDB

**概要**：任意の規模で一桁ミリ秒台の応答性能を提供するフルマネージド・サーバーレスのキーバリュー型／ドキュメント型NoSQLデータベース。ただし、水平スケールを十分に活かすには、アクセスが特定キーに集中（ホットパーティション化）しないようパーティションキーの設計でカーディナリティ（分散度）を高める必要があります。

**試験での要点**
- **読み込み整合性**：既定では**結果整合性読み込み（Eventually Consistent Reads）**。設定により**強い整合性読み込み（Strongly Consistent Reads）**を指定可能ですが、**消費する読み込みキャパシティユニット（RCU）は2倍**になります。
- キャパシティモード：**オンデマンドモード**（リクエスト数に応じた完全従量課金、急激なスパイクやトラフィックが読めないワークロード向け）／**プロビジョンドモード**（事前にRCU/WCUを指定、Auto Scalingと併用して安定した負荷を最安コストで運用）。
- キャパシティ計算基準：**1 RCU ＝ 最大4 KBの項目に対し、強い整合性で毎秒1回読み込み（結果整合性なら毎秒2回）**。**1 WCU ＝ 最大1 KBの項目に対し、毎秒1回書き込み**。
- 1項目の最大データサイズは **400 KB**。画像や大容量ドキュメントはS3に配置し、**DynamoDBにはS3のオブジェクトURLやキー情報のみを保存**する設計パターン（Claim Checkパターン）をとります。
- セカンダリインデックスの使い分け：
  - **ローカルセカンダリインデックス（LSI）**：テーブルと同じパーティションキーで、異なるソートキーを定義（**テーブル作成時のみ設定可能**、後からの追加・削除不可。強い整合性読み込みに対応）。
  - **グローバルセカンダリインデックス（GSI）**：テーブルと異なるパーティションキーおよびソートキーを定義（**テーブル作成後も自由に追加・削除可能**。結果整合性読み込みのみ）。
- **DynamoDB Streams**：テーブル内のデータの変更履歴（挿入・更新・削除）を時系列のストリームとして最大24時間保持し、Lambda関数等をトリガーして外部連携（イベント駆動処理、集計、異種DBへの同期）を行います。
- **有効期限（TTL）**：タイムスタンプ属性を指定することで、期限切れとなった項目を追加コストなしで自動削除する機能（セッション情報管理や一時データ破棄に最適）。
- **グローバルテーブル**：複数リージョン間でテーブルを完全双方向同期させる**マルチアクティブ（マルチマスター）**データベース。各リージョンでローカルに読み書きが可能です。

**見分けポイント**
| 設問の要件・特徴 | 最適な選択肢 |
|---|---|
| 一桁ミリ秒の低遅延、**キーに基づくアクセスパターンが事前に明確に定義されている**、スキーマレス、運用管理不要 | **Amazon DynamoDB**（テーブル間の複雑なJOINやアドホック集計が要件ならRDS/Redshiftへ） |
| DynamoDBの応答速度をさらに高め、**マイクロ秒単位のインメモリ読み込み**を実現したい | **Amazon DynamoDB Accelerator（DAX）** |
| 複数テーブルにまたがる複雑なJOIN、GROUP BY、アドホックなBI分析クエリ | Amazon RDS ／ Aurora、または Amazon Redshift |
| Webセッションの保存、ショッピングカート、IoT機器からの超大量の時系列書き込み | Amazon DynamoDB |

## 4.4 Amazon ElastiCache

**概要**：インメモリ型のデータストア／キャッシュサービス（RedisおよびMemcached互換）。同一クエリ結果やセッション情報の反復読み込みにおいて、マイクロ秒単位の低遅延応答とバックエンドDBの負荷軽減を実現します。ただし、キャッシュの有効期限（TTL）や更新反映戦略（遅延読み込み、書き込みスルー）を考慮しないと、古いデータが返されるリスクがあります。

**Redis（ElastiCache for Redis） vs Memcached（ElastiCache for Memcached）の選び分け**

| 要件・機能 | 最適なエンジン |
|---|---|
| **データの永続化、リードレプリカ、マルチAZ配置、自動フェイルオーバー**による耐障害性が必須 | **Redis** |
| ソート済みセット（Sorted Sets）、Pub/Subメッセージング、地理空間データ、リアルタイムランキング・リーダーボード | **Redis** |
| バックアップと復元（スナップショット取得）が必要 | **Redis** |
| **シンプルなオブジェクトキャッシュ**を**マルチスレッド**で並列処理し、キャッシュノードを水平にスケールさせるだけで十分 | **Memcached** |

- キャッシュ戦略：
  - **遅延読み込み（Lazy Loading）**：キャッシュミス時にバックエンドDBから取得してキャッシュに書き込む方式。必要なデータのみがキャッシュされるが、初回アクセス遅延とデータの陳腐化（古いデータ）が発生し得る。
  - **書き込みスルー（Write-Through）**：アプリケーションがDBに書き込む際、同時にキャッシュにも書き込む方式。キャッシュは常に最新に保たれるが、一度も読み取られないデータも書き込まれる。
  - いずれの方式でも、適切な**TTL（有効期限）**を設定して古いデータの滞留を防ぐのが標準設計です。
- **キャッシュを採用してはならない要件**：在庫引当の最終確認や口座残高照会のように、1ミリ秒の遅延もなく最新状態の整合性が求められる処理では、キャッシュを経由せずプライマリDBから直接読み取ります。また、ユーザーごとに結果が完全に異なる集計クエリなどはキャッシュヒット率が低いため不適です。
- なお、「Redis互換のマイクロ秒応答を持ちつつ、キャッシュではなく**プライマリデータベースとして完全な耐久性（トランザクションログのマルチAZ永続化）**が求められる」場合は、**Amazon MemoryDB for Redis** を選択します。

## 4.5 「データベースの性能問題」を原因別に切り分ける

**困りごと**：「DBの応答が遅い」「処理が詰まる」という設問に対し、リードレプリカ、ElastiCache、RDS Proxy、インスタンスのスケールアップのどれを提案すべきかは、**ボトルネックとなっている根本原因**によって決まります。

| ボトルネックの原因 | 設問における典型的な症状 | 効果的な解決策 | 不適切な選択肢とその理由 |
|---|---|---|---|
| **参照（SELECT）クエリの総量** | 参照アクセスが集中、月次レポート実行でCPU使用率が高騰 | **リードレプリカ**の追加、またはAuroraリーダーエンドポイントの活用（アプリの接続先変更が必須） | RDS Proxy：接続確立を効率化するだけであり、実行されるクエリの総量は減らない |
| **同一結果の反復読み込み** | 人気商品ページへのアクセス集中、設定情報やマスタデータの頻繁な参照 | **Amazon ElastiCache** または **DynamoDB DAX** によるキャッシュ | リードレプリカ：同一の重いクエリがレプリカ側で繰り返し実行されるだけになり根本解決にならない |
| **接続数（コネクション）の急増** | Lambda関数からのスパイクアクセス、接続エラー（Too many connections）、接続確立のオーバーヘッド | **Amazon RDS Proxy** によるコネクションプーリング | リードレプリカ：書き込みを伴う接続はプライマリに向かうため接続数は減らない。キャッシュ：接続数そのものは解消しない |
| **書き込み（INSERT/UPDATE）の集中** | 書き込み処理の遅延、行ロック・テーブルロック待ちの発生 | DBインスタンスの垂直スケール（スケールアップ）、Auroraへの移行、**キュー（SQS）による書き込みの非同期バッファリング**、DynamoDBへの移行 | リードレプリカ：書き込みは常に単一のプライマリインスタンスで処理されるため効果がない |
| **大規模な分析クエリの混在** | 全表スキャンを伴う集計クエリが本番OLTP業務のトランザクションを阻害 | OLAP専用基盤へのデータ退避・分離（**Amazon Redshift**、S3＋Athena、分析専用リードレプリカ） | キャッシュ：実行ごとに条件が異なるアドホックな集計クエリはキャッシュにヒットしない |

## 4.6 その他の特化型データベースサービス

| サービス | データベースの種別 | 試験での判断ポイント |
|---|---|---|
| **Amazon Neptune** | フルマネージド・グラフデータベース | SNSの友人関係ネットワーク、不正アクセス・詐欺検知パターン分析、ナレッジグラフなど、**高度に相互関連した複雑なデータの関連性をたどるクエリ** |
| **Amazon DocumentDB** | MongoDB互換のドキュメントデータベース | 「既存のMongoDBワークロードやJSONドキュメント構造を、AWSのマネージド基盤へ移行・運用したい」 |
| **Amazon Keyspaces** | Apache Cassandra互換のワイドカラム型DB | 「オンプレミスのCassandraアプリケーションを、コード改変なしにサーバーレスで運用したい」 |
| **Amazon QLDB** | フルマネージド台帳データベース（Ledger） | **暗号学的に検証可能で、一度書き込んだら管理者であっても変更・削除できない完全な履歴（イミュータブルな監査証跡）**。※中央集権型の単一管理組織が存在する場合 |
| **Amazon Managed Blockchain** | フルマネージド・ブロックチェーン基盤 | **複数の異なる組織・企業が中央管理者を置かずに分散型ネットワークを構築し**、取引履歴を相互検証・合意形成する場合 |
| **Amazon Timestream** | サーバーレス時系列データベース | IoTセンサーからの継続的な測定値データ、システムログ・メトリクスなど、**時間経過に伴う膨大な時系列イベントの高速書き込みと分析** |
| **Amazon Redshift** | ペタバイト規模のクラウドデータウェアハウス（DWH） | 列指向ストレージと超並列処理（MPP）による、大規模データの複合的な集計・BIダッシュボード分析（→第7章） |
