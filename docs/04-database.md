# 第4章 データベース

> **章の一言**：「結合・トランザクションのあるSQL」＝RDS/Aurora、「一桁ミリ秒・無限スケール・キー検索」＝DynamoDB、「マイクロ秒・使い回すだけ」＝ElastiCache。**可用性のマルチAZ**と**性能のリードレプリカ**を混同させる問題が定番。

---

## 4.1 Amazon RDS

**一言で**：MySQL/PostgreSQL/MariaDB/Oracle/SQL Server などをマネージドで動かす。OSへのSSHはできない。

**マルチAZ vs リードレプリカ（最頻出の対比）**
| | マルチAZ配置 | リードレプリカ |
|---|---|---|
| 目的 | **可用性・災害対策** | **読み取り性能のスケール** |
| レプリケーション | 同期 | 非同期（レプリケーションラグあり） |
| 読み取り | スタンバイは**読めない** | 読める |
| 配置 | 別AZ | 同一AZ/別AZ/**別リージョン**も可 |
| 障害時 | 自動フェイルオーバー（**エンドポイントのDNSが切り替わる**） | 手動で昇格（スタンドアロン化） |

- 「読み取りが重くて遅い」→リードレプリカ。「AZ障害でも止めたくない」→マルチAZ。「**両方**」→マルチAZ＋リードレプリカ。
- **マルチAZ DBクラスター**は読み取り可能なスタンバイ2台を持ち、フェイルオーバーがより速い（通常のマルチAZインスタンスとの差を問われる）。

**その他の核心**
- **自動バックアップ（保持1〜35日）でポイントインタイムリカバリ（PITR）**。手動スナップショットは明示的に消すまで残る。
- **暗号化は作成時に指定**。既存の未暗号化DBは「スナップショット→暗号化コピー→復元」。
- **RDS Proxy**＝コネクションプーリング。**Lambdaからの大量接続で枯渇**、フェイルオーバー時間の短縮、IAM認証の強制、が決め手。
- 拡張モニタリング＝OSレベルのメトリクス（CloudWatchの標準メトリクスはハイパーバイザー視点）。遅いクエリの特定は **Performance Insights**。
- 認証情報は **Secrets Manager** で自動ローテーション、DBユーザーは **IAMデータベース認証**も可。
- スキーマ変更のリスクを下げるなら **Blue/Greenデプロイ**。

## 4.2 Amazon Aurora

**一言で**：MySQL/PostgreSQL互換のAWS製DB。**3AZに6コピー**を保持するストレージ層が本体。

**試験の核心**
- ストレージは10GB単位で**自動拡張**（事前のサイズ指定が不要）。上限はエンジンバージョンで異なり、**128 TiB**（従来の全バージョン）または**256 TiB**（Aurora PostgreSQL 17.5/16.9/15.13以降、Aurora MySQL 3.10以降）（→付録B）。
- 書き込みは**6つのうち4つ**、読み取りは**3つ**の応答で成立。2コピー喪失でも書き込み継続、3コピー喪失でも読み取り継続＝自己修復。
- リードレプリカ**最大15台**、フェイルオーバーは**通常30秒以内**。
- エンドポイントは3つ：**クラスター（書き込み）／リーダー（読み取りを自動分散）／カスタム**。アプリの読み取りは必ずリーダーエンドポイントへ。
- **バックトラック**＝MySQL互換で、復元なしに時間を巻き戻す（誤操作の即時復旧）。
- **高速クローン**＝本番データをコピーせず短時間で検証環境を作る。

**派生形の見分け**
| 要件 | 答え |
|---|---|
| 利用が断続的・予測不能、停止中は課金を抑えたい | **Aurora Serverless v2**（ACU単位で細かく自動増減） |
| **複数リージョン**へ1秒未満でレプリケーション、DRでRTO1分未満 | **Aurora グローバルデータベース** |
| SQL Serverのアプリを**コード改変を最小に**PostgreSQLへ | **Babelfish** |
| I/Oが非常に多く課金が読めない | Aurora **I/O-Optimized** |

**RDSとの見分け**：Oracle/SQL Server/MariaDBが要る、ライセンス持ち込み＝RDS。**性能・可用性・スケールを最優先**、MySQL/PostgreSQL互換で良い＝Aurora。

## 4.3 Amazon DynamoDB

**一言で**：サーバーレスのKey-Value NoSQL。**一桁ミリ秒**、事実上無制限にスケール。

**試験の核心**
- **既定は結果整合性の読み取り**。強い整合性の読み取りは指定でき、**消費キャパシティは2倍**。
- キャパシティ：**オンデマンド**（予測不能・スパイク・運用ゼロ）／**プロビジョンド＋Auto Scaling**（安定した負荷で最安）。
- 計算式：**1 RCU＝4KBを強い整合性で1回/秒（結果整合性なら2回/秒）、1 WCU＝1KBを1回/秒**。
- 1項目**最大400KB**。大きいデータはS3に置き、**DynamoDBにはポインタ（キー）だけ**入れる。
- インデックス：**LSI＝同じパーティションキーで別のソートキー（テーブル作成時のみ）／GSI＝別のパーティションキー（後から追加可、結果整合性のみ）**。
- **DynamoDB Streams**＝項目変更をイベント化しLambdaへ（集計、通知、レプリケーション）。
- **TTL**＝期限切れ項目の自動削除（セッション管理）。
- **グローバルテーブル**＝マルチリージョン・**マルチアクティブ**（書き込みも各リージョンで可能）。
- バックアップはPITR（35日）＋オンデマンドバックアップ。

**見分けポイント**
| 問題文のキーワード | 答え |
|---|---|
| 一桁ミリ秒、キーで引く、スキーマレス、無限スケール、サーバーレス | DynamoDB |
| さらに**マイクロ秒**の読み取りが必要 | **DAX**（DynamoDB専用インメモリキャッシュ） |
| 複雑な結合・集計・レポート | RDS/Aurora、または Redshift |
| セッション/カート/IoTの大量書き込み | DynamoDB |

## 4.4 Amazon ElastiCache

**一言で**：インメモリキャッシュ。DBの負荷軽減とレイテンシ改善（マイクロ秒）。

**Redis vs Memcached（頻出）**
| 要件 | 答え |
|---|---|
| **永続化・レプリケーション・マルチAZ・自動フェイルオーバー**が必要 | **Redis** |
| ソート済みセット、Pub/Sub、地理空間、ランキング、リーダーボード | **Redis** |
| バックアップ・スナップショットが要る | **Redis** |
| **単純なキャッシュ**を**マルチスレッド**で、水平に増減するだけ | **Memcached** |

- 典型ユースケース：DBのクエリ結果キャッシュ、**セッションストア**（ステートレスなWeb層を実現）、レートリミット、ランキング。
- キャッシュ戦略：**遅延読み込み（Lazy Loading）**＝必要時に格納、古いデータが残り得る／**書き込みスルー**＝常に最新だが未参照データも書く。TTLの併用が定石。
- 「Redis互換で**キャッシュではなくプライマリDB**として耐久性が必要」→ **Amazon MemoryDB for Redis**。

## 4.5 その他のデータベースサービス

| サービス | 一言で | 試験での決め手 |
|---|---|---|
| Amazon Neptune | グラフDB | **SNSの友達関係・レコメンド・不正検知・ナレッジグラフ**、関係性をたどるクエリ |
| Amazon DocumentDB | MongoDB互換のドキュメントDB | 「既存のMongoDBワークロードをマネージドに」 |
| Amazon Keyspaces | Cassandra互換 | 「Cassandraを運用ごとやめたい」 |
| Amazon QLDB | 台帳DB | **変更不可・暗号学的に検証可能な完全な履歴**（監査証跡）。※中央管理者あり |
| Amazon Managed Blockchain | 分散台帳 | **複数の組織が対等に**取引を検証 |
| Amazon Timestream | 時系列DB | IoTセンサー、メトリクスの時系列分析 |
| Amazon Redshift | データウェアハウス | 大規模な分析・BI（→第7章） |

**QLDB vs Managed Blockchain**：単一の信頼された所有者が履歴を保全＝QLDB／**複数の参加者が分散して**検証＝Managed Blockchain。
