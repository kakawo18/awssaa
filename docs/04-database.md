# 第4章 データベース

> **章の一言**：DBの設問は「**何のために**その構成を足すのか」で決まる。**可用性（止まらない）にはマルチAZ**、**読み取り負荷にはリードレプリカ**、**同じ結果の反復にはキャッシュ**、**接続数の増加には接続の再利用（RDS Proxy）**。全部「DBが遅い／落ちる」への対策だが、解決する原因が違う。サービス選びは「結合・トランザクション」「キーで引く・アクセスパターンが固定」「更新直後の最新が要るか」の条件で決める（→第0章 0.1 障害・性能・データ軸）。

---

## 4.1 Amazon RDS

**困りごと**：「マルチAZにしたのに読み取りが速くならない」「リードレプリカを作ったのにアプリが速くならない」。構成の**目的**（可用性か性能か）と、**アプリ側の接続先**を変えたかを分けていないのが原因。

**仕組み**：MySQL/PostgreSQL/MariaDB/Oracle/SQL Server などをマネージドで動かす。OSへのSSHはできない。1台のプライマリに対して、目的別に「スタンバイ」か「レプリカ」を足す。

**マルチAZの2種類とリードレプリカ（最頻出の対比）**

| | マルチAZ **DBインスタンス**配置 | マルチAZ **DBクラスター**配置 | リードレプリカ |
|---|---|---|---|
| 目的 | **可用性**（AZ障害で止めない） | **可用性＋読み取り分散** | **読み取り性能**のスケール |
| 構成 | プライマリ＋スタンバイ1台（別AZ） | プライマリ＋**読み取り可能なスタンバイ2台**（3AZ） | プライマリ＋レプリカ（最大数台） |
| レプリケーション | **同期** | **半同期**（2台のうち1台の書き込み確認で完了） | **非同期**（レプリケーションラグあり） |
| スタンバイ／レプリカで読める？ | **読めない**（待機専用） | **読める**（リーダーエンドポイント） | 読める |
| 配置 | 別AZ | 3AZ | 同一AZ／別AZ／**別リージョン**も可 |
| 障害時 | 自動フェイルオーバー（**エンドポイントのDNSが切り替わる**。通常60〜120秒程度） | 自動フェイルオーバー（**通常35秒未満**、より速い） | **手動で昇格**（スタンドアロン化）。自動ではない |
| 対応エンジン | 主要エンジン | MySQL／PostgreSQLのみ | エンジンによる |

**選ぶ条件／選ばない条件**
- 「AZ障害でも止めたくない」→マルチAZ DBインスタンス配置。**スタンバイは読めない**ので、読み取り性能の目的では選ばない。
- 「読み取りが重くて遅い」→リードレプリカ。ただし**アプリの読み取りクエリをレプリカのエンドポイントへ向けないと効かない**。作っただけでは自動で分散しない。**非同期なので更新直後の最新を読む用途には向かない**。
- 「可用性も読み取り分散も、1つの構成で」→マルチAZ DBクラスター配置（MySQL/PostgreSQL）。設問で「読み取り可能なスタンバイ」「35秒未満のフェイルオーバー」とあればこちら。
- 「別リージョンでも読みたい／DR」→クロスリージョンリードレプリカ（手動昇格）。自動フェイルオーバーが要るなら Aurora グローバルデータベース（4.2）。
- 「両方」→マルチAZ＋リードレプリカの組み合わせ。**マルチAZ DBインスタンス配置のスタンバイで読み取り分散はできない**。

**条件違いの例**

| 条件 | 判断 | 外す候補と理由 |
|---|---|---|
| AZ障害時に自動で復旧、読み取りは今のままで十分 | マルチAZ DBインスタンス配置 | リードレプリカ：手動昇格で自動復旧にならない |
| レポート処理が本番の読み取りを圧迫。数秒の遅延は許容 | リードレプリカ（＋アプリの読み取り先を変更） | マルチAZ：スタンバイは読めない |
| 可用性と読み取り分散を両方、MySQL | マルチAZ DBクラスター配置 | インスタンス配置＋レプリカ：可能だが構成が2つになる |
| 更新直後に必ず最新を読む必要がある | プライマリから読む（レプリカやキャッシュを無条件に使わない） | リードレプリカ：非同期なので古い値を返し得る |

**理解確認**：「マルチAZ配置のRDSで、読み取りをスタンバイに振り分けて負荷を下げたい」は成立するか？→ **DBインスタンス配置なら不可**（スタンバイは読めない）。**DBクラスター配置なら可**（リーダーエンドポイント経由）。設問が「マルチAZ」としか書いていなければ、既定のDBインスタンス配置と読み、読み取り分散にはリードレプリカを選ぶ。

**その他の核心**
- **自動バックアップ（保持1〜35日）でポイントインタイムリカバリ（PITR）**。手動スナップショットは明示的に消すまで残る。
- **暗号化は作成時に指定**。既存の未暗号化DBは「スナップショット→暗号化コピー→復元」。
- **RDS Proxy**＝コネクションプーリング。**「遅い」の原因が接続数（Lambdaからの大量接続で枯渇、接続確立のオーバーヘッド）**のときに効く。読み取りクエリの重さには効かない。フェイルオーバー時間の短縮、IAM認証の強制も決め手。
- 拡張モニタリング＝OSレベルのメトリクス（CloudWatchの標準メトリクスはハイパーバイザー視点）。遅いクエリの特定は **Performance Insights**。
- 認証情報は **Secrets Manager** で自動ローテーション、DBユーザーは **IAMデータベース認証**も可。
- スキーマ変更のリスクを下げるなら **Blue/Greenデプロイ**。

## 4.2 Amazon Aurora

**一言で**：MySQL/PostgreSQL互換のAWS製DB。**3AZに6コピー**を保持するストレージ層が本体。

**試験の核心**
- ストレージは10GB単位で**自動拡張**（事前のサイズ指定が不要）。上限はエンジンバージョンで異なり、**128 TiB**（従来の全バージョン）または**256 TiB**（Aurora PostgreSQL 17.5/16.9/15.13以降、Aurora MySQL 3.10以降）（→付録B）。
- 書き込みは**6つのうち4つ**、読み取りは**3つ**の応答で成立。2コピー喪失でも書き込み継続、3コピー喪失でも読み取り継続＝自己修復。
- リードレプリカ**最大15台**、フェイルオーバーは**通常30秒以内**。
- エンドポイントは3つ：**クラスター（書き込み）／リーダー（読み取りを自動分散）／カスタム**。アプリの読み取りは必ずリーダーエンドポイントへ。
- **バックトラック**＝MySQL互換で、復元なしに時間を巻き戻す（誤操作の即時復旧）。
- **高速クローン**＝本番データをコピーせず短時間で検証環境を作る。

**派生形の見分け**
| 要件 | 答え |
|---|---|
| 利用が断続的・予測不能、停止中は課金を抑えたい | **Aurora Serverless v2**（ACU単位で細かく自動増減） |
| **複数リージョン**へ1秒未満でレプリケーション、DRでRTO1分未満 | **Aurora グローバルデータベース** |
| SQL Serverのアプリを**コード改変を最小に**PostgreSQLへ | **Babelfish** |
| I/Oが非常に多く課金が読めない | Aurora **I/O-Optimized** |

**RDSとの見分け**：Oracle/SQL Server/MariaDBが要る、ライセンス持ち込み＝RDS。**性能・可用性・スケールを最優先**、MySQL/PostgreSQL互換で良い＝Aurora。

## 4.3 Amazon DynamoDB

**一言で**：サーバーレスのKey-Value NoSQL。**一桁ミリ秒**でスケールする。ただし「無制限」は**パーティションキーが分散している前提**で、ホットキーがあればスロットリングする。

**試験の核心**
- **既定は結果整合性の読み取り**。強い整合性の読み取りは指定でき、**消費キャパシティは2倍**。
- キャパシティ：**オンデマンド**（予測不能・スパイク・運用ゼロ）／**プロビジョンド＋Auto Scaling**（安定した負荷で最安）。
- 計算式：**1 RCU＝4KBを強い整合性で1回/秒（結果整合性なら2回/秒）、1 WCU＝1KBを1回/秒**。
- 1項目**最大400KB**。大きいデータはS3に置き、**DynamoDBにはポインタ（キー）だけ**入れる。
- インデックス：**LSI＝同じパーティションキーで別のソートキー（テーブル作成時のみ）／GSI＝別のパーティションキー（後から追加可、結果整合性のみ）**。
- **DynamoDB Streams**＝項目変更をイベント化しLambdaへ（集計、通知、レプリケーション）。
- **TTL**＝期限切れ項目の自動削除（セッション管理）。
- **グローバルテーブル**＝マルチリージョン・**マルチアクティブ**（書き込みも各リージョンで可能）。
- バックアップはPITR（35日）＋オンデマンドバックアップ。

**見分けポイント**
| 問題文のキーワード | 答え |
|---|---|
| 一桁ミリ秒、**キーで引くアクセスパターンが決まっている**、スキーマレス、サーバーレス | DynamoDB（結合や柔軟なアドホッククエリが要件なら外れる） |
| さらに**マイクロ秒**の読み取りが必要 | **DAX**（DynamoDB専用インメモリキャッシュ） |
| 複雑な結合・集計・レポート | RDS/Aurora、または Redshift（DynamoDBはトランザクションもあるが、結合は苦手） |
| セッション/カート/IoTの大量書き込み | DynamoDB |

## 4.4 Amazon ElastiCache

**一言で**：インメモリキャッシュ。**同じ結果を繰り返し読む**ときにDBの負荷とレイテンシ（マイクロ秒）を下げる。**鮮度**（TTLの間は古い値を返す）と**更新の反映方法**を確認せずに「マイクロ秒」だけで選ばない。

**Redis vs Memcached（頻出）**
| 要件 | 答え |
|---|---|
| **永続化・レプリケーション・マルチAZ・自動フェイルオーバー**が必要 | **Redis** |
| ソート済みセット、Pub/Sub、地理空間、ランキング、リーダーボード | **Redis** |
| バックアップ・スナップショットが要る | **Redis** |
| **単純なキャッシュ**を**マルチスレッド**で、水平に増減するだけ | **Memcached** |

- 典型ユースケース：DBのクエリ結果キャッシュ、**セッションストア**（ステートレスなWeb層を実現）、レートリミット、ランキング。
- キャッシュ戦略：**遅延読み込み（Lazy Loading）**＝必要時に格納、古いデータが残り得る／**書き込みスルー**＝常に最新だが未参照データも書く。TTLの併用が定石。
- **選ばない条件**：更新直後の最新値が必須（在庫の最終確認、残高）→キャッシュを経由せずDBを読む、または書き込みスルー＋短いTTL。結果が毎回違うクエリ（ユーザー固有の集計）→キャッシュヒットしないので効果がない。
- 「Redis互換で**キャッシュではなくプライマリDB**として耐久性が必要」→ **Amazon MemoryDB for Redis**。

## 4.5 「DBが遅い」を原因で分ける（性能対策の選び方）

**困りごと**：「DBが遅い」に対してリードレプリカ・ElastiCache・RDS Proxy・スケールアップのどれを選ぶかは、**何が遅いのか**で決まる。対策名を暗記しても、原因を分解できなければ設問で選べない。

**仕組み**：読み取り処理が集中しているなら、読み取り先の分散を検討する。同じ結果を繰り返し取得するなら、キャッシュが候補になる。接続数の増加が問題なら、まず接続の再利用を検討する。いずれも「DBが遅い」への対策だが、解決する原因が異なる。

| 原因 | 症状の書かれ方 | 効く対策 | 効かない対策と理由 |
|---|---|---|---|
| **読み取りクエリの量** | 読み取りが多い、レポート、CPU高 | リードレプリカ／Auroraリーダーエンドポイント（＋アプリの接続先変更） | RDS Proxy：接続を再利用するだけでクエリは減らない |
| **同じ結果の反復** | 同じ商品ページ、ランキング、設定値 | ElastiCache／DAX（TTLと更新反映を設計） | リードレプリカ：同じクエリをレプリカでも実行するだけ |
| **接続数の増加** | Lambdaから大量接続、接続エラー、too many connections | **RDS Proxy**（接続プーリング） | リードレプリカ：接続はプライマリにも来る。キャッシュ：接続数は減らない |
| **書き込みの量** | 書き込みで詰まる、ロック待ち | スケールアップ、Aurora、シャーディング、書き込みのバッファ（SQS/Kinesis）、アクセスパターン次第でDynamoDB | リードレプリカ：書き込みはプライマリ1台に集中したまま |
| **分析クエリの混在** | 集計・全件スキャンが本番を圧迫 | 分析基盤へ分離（Redshift、S3＋Athena、専用レプリカ） | キャッシュ：毎回違う集計にはヒットしない |

**条件違いの例**

| 条件 | 候補と確認点 | 外す候補と理由 |
|---|---|---|
| 読み取りが集中している | リードレプリカ。**アプリの接続先変更**と**複製遅延の許容**を確認 | RDS Proxy：クエリ量は減らない |
| 同じ検索結果が繰り返し返っている | ElastiCache。**TTL**と**更新時の反映方法**を確認 | リードレプリカ：同じクエリを実行し続ける |
| Lambdaが大量に接続してDBが枯渇 | RDS Proxy。**接続再利用の適合**（短命な接続が多いか）を確認 | スケールアップ：接続上限は上がるが根本の再利用にならない |
| 更新直後の最新状態が必須 | キャッシュや非同期レプリカを無条件に使わず、**整合性を満たす読み取り先**（プライマリ、書き込みスルー）を選ぶ | Lazy Loading のキャッシュ：TTLの間は古い |

**理解確認**：「Lambdaから RDS への接続が増えて接続エラーが出る。リードレプリカを追加すべきか？」→ **いいえ**。原因は**接続数**であり読み取り量ではない。RDS Proxy で接続を再利用する。レプリカを足しても各Lambdaがプライマリへ接続する構成は変わらない。

## 4.6 その他のデータベースサービス

| サービス | 一言で | 試験での決め手 |
|---|---|---|
| Amazon Neptune | グラフDB | **SNSの友達関係・レコメンド・不正検知・ナレッジグラフ**、関係性をたどるクエリ |
| Amazon DocumentDB | MongoDB互換のドキュメントDB | 「既存のMongoDBワークロードをマネージドに」 |
| Amazon Keyspaces | Cassandra互換 | 「Cassandraを運用ごとやめたい」 |
| Amazon QLDB | 台帳DB | **変更不可・暗号学的に検証可能な完全な履歴**（監査証跡）。※中央管理者あり |
| Amazon Managed Blockchain | 分散台帳 | **複数の組織が対等に**取引を検証 |
| Amazon Timestream | 時系列DB | IoTセンサー、メトリクスの時系列分析 |
| Amazon Redshift | データウェアハウス | 大規模な分析・BI（→第7章） |

**QLDB vs Managed Blockchain**：単一の信頼された所有者が履歴を保全＝QLDB／**複数の参加者が分散して**検証＝Managed Blockchain。
