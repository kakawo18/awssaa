# 第5章 セキュリティ、アイデンティティ、コンプライアンス

> **章の一言**：「誰が何をできるか」＝IAM、「守る」＝WAF/Shield/KMS、「見つける」＝GuardDuty/Inspector/Macie。**検出系4兄弟（GuardDuty・Inspector・Macie・Config）の役割分担**が最大の得点源。

---

## 5.1 AWS IAM

**一言で**：AWSの認証・認可の中核。リージョンをまたぐグローバルサービス。

**試験の核心**
- **ポリシー評価ロジック**：**明示的なDeny ＞ 明示的なAllow ＞ 暗黙のDeny**。どこか1箇所でもDenyがあれば拒否。
- **EC2・Lambda・ECSにはアクセスキーを置かず、IAMロール**。キーのハードコードを見たら即「ロールに変更」が正解。
- クロスアカウントアクセス＝相手アカウントでロールを作り、`sts:AssumeRole`。第三者（外部ベンダー）には**外部ID**を必須にして混乱した代理問題を防ぐ。
- ルートユーザーは初期設定後は使わない。**MFA必須**、アクセスキーは削除。

**ポリシーの種類の見分け**
| 要件 | 答え |
|---|---|
| ユーザー/ロールに権限を与える | アイデンティティベースポリシー |
| S3バケット・SQS・KMSなど**リソース側**で許可（クロスアカウントの定番） | リソースベースポリシー |
| 委譲した管理者が**与えられる権限の上限**を決める | **アクセス許可境界（Permissions Boundary）** |
| 組織・OU・アカウント全体で**使えるサービスを制限**（ルートにも効く） | **SCP**（Organizations、許可は与えない・上限のみ） |
| 一時的な認証情報にさらに絞りを入れる | セッションポリシー |

**関連機能**：IAM Access Analyzer（**外部公開されているリソースの検出**、未使用アクセスの検出）、認証情報レポート、Access Advisor（最終アクセス日時で権限を削る）、条件キー（`aws:MultiFactorAuthPresent`, `aws:SourceIp`, `aws:PrincipalOrgID`）。

## 5.2 AWS IAM Identity Center（旧 AWS SSO）

**一言で**：複数AWSアカウント＋外部IdPをまとめたシングルサインオン。

- 決め手は「**多数のAWSアカウント**に対し、**既存のID基盤（Active Directory / Okta / Entra ID）**で一元ログインしたい」。
- **許可セット（Permission Set）**をアカウント×グループに割り当てる。アカウントごとにIAMユーザーを作る運用は不正解の典型。
- Organizations と組み合わせて使うのが前提。

---

## 5.3 AWS Directory Service

| 要件 | 答え |
|---|---|
| AWS上に**本格的なMicrosoft AD**が要る（信頼関係、グループポリシー、FSx/RDS SQL Serverと統合） | **AWS Managed Microsoft AD** |
| 認証は**オンプレADのまま**。AWSにはディレクトリを置かず、そのまま転送したい | **AD Connector**（プロキシ） |
| 小規模・低コスト、Linux中心の簡易なLDAP | **Simple AD**（Samba互換、信頼関係は不可） |

## 5.4 Amazon Cognito

**一言で**：**アプリのエンドユーザー（顧客）**向けの認証基盤。IAMは「AWSを操作する人」、Cognitoは「アプリを使う人」。

- **ユーザープール**＝サインアップ/サインインとトークン（JWT）発行。ソーシャルログイン、SAML連携、MFA。API GatewayやALBのオーソライザーとして直接使える。
- **IDプール（フェデレーティッドID）**＝認証済みユーザーに**AWSリソースへの一時認証情報**を渡す（例：S3の自分専用フォルダに直接アップロード）。
- 「数百万ユーザーのモバイルアプリのログイン」＝Cognito、「社内の管理者アクセス」＝IAM Identity Center。

---

## 5.5 AWS WAF

**一言で**：L7（HTTP）のファイアウォール。**SQLインジェクション・XSS・不正Bot**を止める。

- 適用先は **CloudFront / ALB / API Gateway / AppSync / Cognitoユーザープール**。**NLBやEC2には直接付けられない**。
- **レートベースルール**＝特定IPからの大量リクエスト（ブルートフォース、L7 DDoS）を遮断。
- AWSマネージドルール（OWASP Top 10、既知の不正IP）で即導入。
- 地理的ブロックはWAF／CloudFrontの地理制限／Route 53位置情報のいずれでも可（**問題文の制御層で選ぶ**）。

## 5.6 AWS Shield

| | Shield Standard | Shield Advanced |
|---|---|---|
| 料金 | 無料・自動適用 | 月額課金（$3,000〜） |
| 防御 | L3/L4のDDoS | L3/L4/L7、より高度な検出 |
| 付帯 | なし | **DDoSレスポンスチーム(SRT)**、**スケーリング費用の補償**、WAF/Firewall Managerの利用料込み |

「大規模DDoSが来ても専門家の支援と**急増した料金の返金**が欲しい」＝Advanced。

## 5.7 AWS Certificate Manager (ACM)

- **パブリック証明書は無料**、**自動更新**。失効切れの運用事故を無くすのが価値。
- 統合先：**ELB / CloudFront / API Gateway / Cognito**。**EC2に直接インストールはできない**（EC2で使いたいなら自前 or ACM Private CA）。
- **CloudFrontで使う証明書は us-east-1 で発行**。ALB用はALBと同じリージョン。
- 社内向けのプライベート証明書は **AWS Private CA**（有料）。

## 5.8 AWS KMS

**一言で**：暗号鍵の生成・管理・監査。ほぼ全AWSサービスの暗号化がここに繋がる。

**試験の核心**
- **エンベロープ暗号化**：データはデータキーで暗号化し、そのデータキーをKMSキーで暗号化する（4KB超のデータを直接KMSで暗号化はしない）。
- キーの種類：**AWS所有**（不可視）／**AWS管理**（`aws/s3`など、ローテーション自動・ポリシー変更不可）／**カスタマー管理**（自分で作成、**ポリシー・ローテーション・無効化・削除が可能**）。
- **キーポリシー**が必須。IAMポリシーだけでは使えない（クロスアカウント利用はキーポリシーで許可）。
- 自動ローテーション（年1回）は**カスタマー管理キー**のみ設定可。古い鍵は保持され過去データも復号できる。
- キーの削除は**7〜30日の待機期間**あり（取り消せる）。
- **リージョン固有**。別リージョンで使うには**マルチリージョンキー**、またはスナップショットのコピー時に再暗号化。
- **CloudHSMとの違い**：KMS＝マネージド・共有HSM／**CloudHSM＝専有HSM、FIPS 140-2 レベル3、鍵をAWSにも触らせない**規制要件。

## 5.9 Amazon Macie

**一言で**：**S3内の個人情報（PII）・機密データを機械学習で発見**し、公開状態や暗号化状況も評価する。

- キーワード：「クレジットカード番号」「マイナンバー/社会保障番号」「個人情報がS3に紛れていないか」。
- **対象はS3**。EC2やDBの中身はスキャンしない。

---

## 5.10 AWS Secrets Manager

| 要件 | 答え |
|---|---|
| DBパスワード等を**自動ローテーション**したい（RDS/Aurora/Redshift/DocumentDBと統合） | **Secrets Manager**（有料） |
| 設定値やパラメータを**無料で**安全に保管（SecureStringはKMS暗号化） | **SSM Parameter Store** |
| 階層管理・バージョン管理・変更通知だけで十分 | Parameter Store |
| クロスアカウント共有、複数リージョンへのレプリケーション | Secrets Manager |

**決め手は「自動ローテーションが要件にあるか」**。あればSecrets Manager、なければParameter Store（コスト最適解）。

---

## 5.11 Amazon GuardDuty

**一言で**：**脅威検知**。有効化するだけで、CloudTrail・VPCフローログ・DNSログ・S3/EKS/RDSのログを機械学習で分析する。

- 検知例：ビットコインマイニング、既知の不正IPとの通信、通常と違う地域からのAPI呼び出し、認証情報の流出疑い。
- **ログを自分で有効化・保存する必要がない**（裏で読む）のが特徴。
- 検出結果は EventBridge → Lambda/SNS で自動対応につなげる。

---

## 5.12 Amazon Inspector

**一言で**：**脆弱性（CVE）診断**。EC2・ECRのコンテナイメージ・Lambda関数を継続的にスキャン。

- 「OSやライブラリに既知の脆弱性がないか」「意図せず外部から到達可能になっていないか（ネットワーク到達性）」。
- SSM エージェント経由でEC2をスキャン。

## 5.13 その他のセキュリティ、アイデンティティ、コンプライアンスのサービス

| サービス | 一言で | 決め手 |
|---|---|---|
| AWS Security Hub | 各種検出結果の**集約ダッシュボード**＋ベストプラクティス自動チェック | 「GuardDuty/Inspector/Macieの結果を一元管理」 |
| Amazon Detective | 検出結果の**根本原因の深掘り**（グラフ分析） | 「なぜ起きたのかを調査」 |
| AWS Artifact | **第三者監査レポート（SOC、ISO、PCI）のダウンロード** | 「コンプライアンス証明書が欲しい」 |
| AWS Audit Manager | 監査用の証跡収集を自動化 | 「監査レポート作成の工数削減」 |
| AWS Firewall Manager | 複数アカウントのWAF/Shield/SG/Network Firewallを**一括適用** | Organizations全体にルールを強制 |
| AWS CloudHSM | 専有ハードウェアセキュリティモジュール | FIPS 140-2 レベル3、鍵の完全な自己管理 |
| Amazon Verified Permissions / Cedar | アプリ内の認可 | アプリ側の細かい権限判定 |

**検出系の見分け（丸暗記推奨）**
| 目的 | サービス |
|---|---|
| 「誰が」APIを呼んだかの**記録** | CloudTrail |
| リソース設定の**変更履歴とルール準拠の評価** | AWS Config |
| **不審な振る舞い**の検知 | GuardDuty |
| **脆弱性（CVE）**の検知 | Inspector |
| **S3内の機密データ**の検出 | Macie |
| 検出結果の**集約** | Security Hub |
| 検出結果の**原因調査** | Detective |
