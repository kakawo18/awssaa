# 第5章 セキュリティ、アイデンティティ、コンプライアンス

> **章の一言**：セキュリティ分野は「認証・認可（IAM/Identity Center）」、「防御（WAF/Shield/KMS）」、「検出・監査（GuardDuty/Inspector/Macie/Config）」の3つの柱で整理します。特に**脅威検知・脆弱性診断・機密データ検出・構成監査（GuardDuty／Inspector／Macie／Config）の役割の明確な区別**が最頻出のポイントです。

---

## 5.1 AWS IAM

**概要**：AWSリソースへのアクセス認証（Authentication）および権限認可（Authorization）を一元管理するグローバルサービス。

**試験での要点**
- **ポリシー評価ロジックの優先順位**：**明示的な拒否（Explicit Deny） ＞ 明示的な許可（Explicit Allow） ＞ 暗黙の拒否（Implicit Deny）**。評価チェーン内のいずれか1箇所でも明示的なDenyがあれば、すべてのAllowを上書きしてアクセスは拒否されます。
- **一時的な認証情報の活用**：EC2インスタンス、Lambda関数、ECSタスクなどにアクセスキーをハードコードしてはならず、**IAMロール**を割り当てて動的に認証情報を自動ローテーションさせます。
- **クロスアカウントアクセス**：ターゲットアカウント側でIAMロールを作成し、信頼ポリシーで接続元アカウントを許可した上で、接続元から `sts:AssumeRole` を呼び出します。第三者（外部ベンダーやSaaS等）に自社アカウントへのアクセスを委譲する場合は、**外部ID（ExternalId条件）を必須化して「混乱した代理問題（Confused Deputy Problem）」を防止**します。
- **ルートユーザーの保護**：アカウント初期作成後の日常的な運用にはルートユーザーを使用しません。**多要素認証（MFA）を必須化**し、アクセスキーが存在する場合は削除します。

**IAMポリシーの種類の選び分け**
| ポリシーの種類 | 主な用途・特徴 |
|---|---|
| **アイデンティティベースのポリシー** | IAMユーザー、グループ、ロールに直接アタッチし、そのアイデンティティが「何を実行できるか」を定義 |
| **リソースベースのポリシー** | S3バケット、SQSキュー、KMSキーなど**リソース側に直接アタッチ**し、「誰がこのリソースに何を実行できるか」を定義（クロスアカウントアクセスの簡素化に頻出） |
| **アクセス許可境界（Permissions Boundary）** | 特権を委譲された開発者管理者が、他のユーザーやロールを作成する際に**付与できる権限の最大上限**を制限する安全策 |
| **サービスコントロールポリシー（SCP）** | AWS Organizationsの組織・OU・アカウント全体に適用され、**利用可能なAPIの上限ガードレール**を設定（直接許可を与えるものではなく、メンバーアカウントのルートユーザーを含む全員に適用される） |
| **セッションポリシー** | AssumeRole等で一時セッションを作成する際、渡された権限をさらに一時的に絞り込むために使用 |

**関連機能**：IAM Access Analyzer（外部アカウントやパブリックに公開されているリソースの自動検出、未使用アクセスの可視化）、IAM認証情報レポート（全ユーザーのパスワード・アクセスキー・MFA状況の監査）、IAM Access Advisor（各ユーザーの最終アクセス日時を確認し最小権限への絞り込みを支援）、条件キー（`aws:MultiFactorAuthPresent`［MFA必須］、`aws:SourceIp`［IP制限］、`aws:PrincipalOrgID`［特定組織内のみ許可］）。

## 5.2 AWS IAM Identity Center（旧 AWS SSO）

**概要**：マルチアカウント環境およびビジネスクラウドアプリに対するシングルサインオン（SSO）と一元的なアクセス権限管理を提供するサービス。

- 採用の決め手：「**多数のAWSアカウント**に対し、**社内の既存ID基盤（Active Directory、Okta、Microsoft Entra IDなど）**を用いて一元ログイン・統合認証を実現したい」。
- **許可セット（Permission Set）**を作成し、AWS Organizationsのアカウントおよびグループに対して一括で割り当てます。アカウントごとに個別のIAMユーザーを作成する運用はアンチパターンとなります。
- AWS Organizationsとの連携を前提として設計されています。

---

## 5.3 AWS Directory Service

| 要件・特徴 | 最適なサービス |
|---|---|
| AWS上に**本格的なMicrosoft Active Directory**が必要（オンプレADとの信頼関係構築、グループポリシーの適用、FSx for WindowsやRDS SQL Serverとのドメイン統合） | **AWS Managed Microsoft AD** |
| 認証自体は**オンプレミスのADに委譲**し、AWS上にはディレクトリデータを保持せずプロキシとしてリクエストを転送したい | **AD Connector** |
| 小規模環境・低コスト優先、Linuxクライアント中心の簡易なSambaベースLDAPディレクトリ | **Simple AD**（オンプレADとの信頼関係は構築不可。※2026年6月30日にメンテナンス（新規受付終了）へ移行） |

## 5.4 Amazon Cognito

**概要**：Web／モバイルアプリケーションのエンドユーザー（一般顧客）向けCIAM（顧客ID・アクセス管理）サービス。AWS基盤の管理者を対象とするIAM / IAM Identity Centerとは対象が異なります。

- **ユーザープール（User Pools）**：エンドユーザーのサインアップ／サインイン機能と認証トークン（JWT）の発行。ソーシャルログイン（Google、Apple、Facebookなど）やSAML/OIDC連携、MFAを提供。API GatewayやALBの認証オーソライザーとして直接統合可能。
- **IDプール（Identity Pools / Federated Identities）**：認証済み（またはゲスト）ユーザーに対し、**AWSリソースへ直接アクセスするためのIAM一時認証情報（STSトークン）**を発行（例：Cognitoでログインしたユーザーに、S3の自分専用プレフィックスへの直接アップロード権限を付与する）。
- 「一般顧客向けモバイルアプリの会員登録・ログイン」＝Amazon Cognito、「社内エンジニアのAWSマネジメントコンソールアクセス」＝IAM Identity Center。

## 5.5 AWS WAF

**概要**：レイヤー7（HTTP/HTTPS）で動作するWebアプリケーションファイアウォール。SQLインジェクション、クロスサイトスクリプティング（XSS）、不正BotなどのWebエクスプロイトから保護します。

- 適用対象サービス：**CloudFront ／ Application Load Balancer（ALB） ／ Amazon API Gateway ／ AWS AppSync ／ Amazon Cognitoユーザープール**。（※Network Load BalancerやEC2インスタンスには直接アタッチできません）。
- **レートベースルール**：同一送信元IPアドレスからの指定期間内のリクエスト数が閾値を超えた場合に自動遮断（ブルートフォース攻撃やL7 DDoS攻撃への防御）。
- **AWSマネージドルール（AMR）**：OWASP Top 10脆弱性対策や既知の不正IPリストなど、AWSが事前定義したルールセットを即座に適用可能。
- 地理的ブロッキング：要件に応じて、AWS WAF（ルールによる制御）、CloudFront（エッジでの地理的制限）、Route 53（位置情報ルーティング）を使い分けます。

## 5.6 AWS Shield

| 比較項目 | Shield Standard | Shield Advanced |
|---|---|---|
| 利用料金 | **無料（すべてのAWS利用者に自動適用）** | **月額固定料金（$3,000〜） ＋ データ転送量課金** |
| 防御レイヤー | レイヤー3およびレイヤー4（ネットワーク／トランスポート層）の一般的なDDoS攻撃 | L3／L4／L7のより高度で大規模なDDoS攻撃 |
| 付帯サポート | なし | **AWS Shield レスポンスチーム（SRT）**による24時間365日の直接支援、**DDoS攻撃によるスケーリング費用の補償**、AWS WAFおよびFirewall Managerの追加利用料が内包 |

「大規模なDDoS攻撃に対して専任チームの直接支援を求めたい」「攻撃によるスパイクで発生したAuto Scaling等の予期せぬインフラ費用を補償してほしい」という要件では **Shield Advanced** を選択します。

## 5.7 AWS Certificate Manager (ACM)

- **AWS統合サービス向けのパブリック証明書は無料**で提供され、**自動更新**されます。証明書の有効期限切れによるサービス停止事故を防止できる点が大きな価値です。
- 統合対象：**ELB、CloudFront、API Gateway、Cognito** など。証明書のプロビジョニングから更新・バインドまでAWS側で自動処理されるため、ユーザーが秘密鍵を直接操作・管理することはできません。
- **エクスポート可能なパブリック証明書**：EC2インスタンス内やオンプレミスサーバーに秘密鍵ごと持ち出して配置することが可能ですが、**有料**であり、**更新後の証明書を各サーバーへ再配置するプロセスはユーザー自身で管理**する必要があります。「EC2上でTLSを終端したい」「オンプレミスと同一の証明書を使いたい」という要件に対応します。
- **リージョン要件の重要規則**：**CloudFrontディストリビューションに関連付けるACM証明書は、必ずバージニア北部リージョン（us-east-1）で発行**する必要があります。ALBやAPI Gatewayで使用する場合は、各リソースと同一のリージョンで発行します。
- 社内イントラネット等で利用するプライベート証明書の一元発行には **AWS Private CA**（有料）を使用します。

## 5.8 AWS Key Management Service (KMS)

**概要**：データの暗号化に使用される暗号鍵の作成・管理・ライフサイクル制御・アクセス監査を行うフルマネージドサービス。

**試験での要点**
- **エンベロープ暗号化**：プレーンテキストデータを直接KMSキーで暗号化するのではなく、暗号化専用の「データキー（Data Key）」をKMSから生成してローカルでデータを暗号化し、そのデータキー自体をKMSキーで暗号化してデータと共に保存する方式（4 KBを超えるデータはエンベロープ暗号化が必須）。
- キーの種類：
  - **AWS所有のキー（AWS Owned Keys）**：AWSの内部利用キー（利用者からは見えず、利用料無料）。
  - **AWS管理のキー（AWS Managed Keys）**：サービスごとに自動生成（例：`aws/s3`）。キーポリシーの編集は不可で、1年ごとの自動ローテーションが固定適用。
  - **カスタマー管理のキー（Customer Managed Keys: CMK）**：ユーザーが明示的に作成。**キーポリシーの編集、手動・自動ローテーションの制御、無効化、削除が可能**。
- **キーポリシー**：KMSキーへのアクセス制御には**キーポリシーが必須**です。IAMポリシーで権限が付与されていても、キーポリシー側で許可されていない限りアクセスは拒否されます（クロスアカウントアクセスではキーポリシーでの委譲が必須）。
- **自動ローテーション**：カスタマー管理キー（AWS KMS生成の対称暗号化キー）で設定可能。ローテーション周期は **90日〜2,560日（既定は365日）** の範囲で指定可能です。過去の鍵マテリアルは安全に保持されるため、過去に暗号化されたデータの復号は引き続き可能です。
- **キーの削除保護**：即時削除はできず、**7日〜30日間の待機期間（デフォルト30日）**が強制されます（待機期間中であれば削除の取り消しが可能）。
- **リージョン制約**：KMSキーは**リージョン固有**のリソースです。別リージョンで共通の鍵を使用したい場合は**マルチリージョンキー**を作成するか、リージョン間コピー時に復号と再暗号化を実行します。
- **AWS CloudHSMとの違い**：KMSは共有マルチテナント基盤のマネージドサービス（HSMは現在FIPS レベル3の認証を取得）。**AWS CloudHSM は顧客専用のシングルテナント専有ハードウェアであり、AWSの管理者であっても鍵マテリアルに一切アクセスできない**厳格なコンプライアンス要件を満たします。

## 5.9 Amazon Macie

**概要**：機械学習とパターンマッチングを活用し、**Amazon S3内の個人情報（PII）や機密データを自動的に検出・分類・保護**するフルマネージドセキュリティサービス。

- 典型キーワード：「クレジットカード番号」「マイナンバー・社会保障番号」「知的財産」「S3バケット内の機密データの意図しない露出検出」。
- **検査対象はAmazon S3に特化**しています（EC2やリレーショナルデータベースの内部はスキャン対象外）。

---

## 5.10 AWS Secrets Manager vs AWS Systems Manager Parameter Store

| 比較項目 | AWS Secrets Manager | SSM Parameter Store（Standard） |
|---|---|---|
| 主な用途 | データベース認証情報、APIキー、OAuthトークン | 設定値、環境変数、ライセンスコード、秘密情報 |
| **自動ローテーション** | **標準対応（Lambda関数と統合し、RDS/Aurora/DocumentDB/Redshift等で自動更新）** | 標準では非対応（自作のLambda等のスクリプトが必要） |
| 暗号化 | AWS KMSと統合（必須） | KMS暗号化（SecureString）または平文（String/StringList） |
| 利用料金 | シークレットごとの月額料金 ＋ APIリクエスト課金（有料） | 標準パラメータは**無料**（アドバンストパラメータは有料） |
| マルチリージョンレプリケーション | 標準サポート（クロスリージョンでの自動同期） | 標準では非対応 |

**選定の決め手**：「**データベースパスワード等の自動ローテーションが要件にあるか**」。ローテーションが必要であれば **Secrets Manager**、静的な設定値やコストを最小限に抑えたい機密情報管理であれば **Parameter Store** を選択します。

## 5.11 Amazon GuardDuty

**概要**：機械学習、異常検知アルゴリズム、統合された脅威インテリジェンスを活用した**インテリジェントな脅威検知サービス**。

- 収集・分析ソース：AWS CloudTrailイベントログ、VPCフローログ、Route 53 DNSクエリログ、Amazon S3データイベント、EKS監査ログ、RDSログインイベントなど。
- **運用上の大きな特徴**：**各種ログを手動で有効化・収集・保管する必要がなく、裏側でAWS基盤から直接ストリーミング分析される**ため、既存のインフラ性能やログ保存コストに影響を与えません。
- 主な検知内容：暗号通貨の不正マイニング、既知のC&Cサーバーとの通信、普段と異なる地理的場所からのAPI実行、IAM認証情報の漏洩疑いなど。
- 検知後の自動修復：EventBridge と連携し、Lambda関数をトリガーしてセキュリティグループの遮断やIAMポリシーの無効化を自動化します。

## 5.12 Amazon Inspector

**概要**：ワークロードの**ソフトウェア脆弱性（CVE）および意図しないネットワーク到達性**を自動的かつ継続的にスキャン・評価する脆弱性管理サービス。

- スキャン対象：**Amazon EC2インスタンス、Amazon ECR内のコンテナイメージ、AWS Lambda関数（コードおよび依存関係）**。
- EC2のスキャンには AWS Systems Manager（SSM）エージェントを利用し、OSパッケージやアプリケーションライブラリの既知の脆弱性を自動検出します。

## 5.13 その他のセキュリティ・ガバナンスサービスと検出系の整理

| サービス | 概要と主な役割 | 試験での判断ポイント |
|---|---|---|
| **AWS Security Hub** | セキュリティアラートの**集約・統合ダッシュボード** ＋ ベストプラクティス自動チェック | 「GuardDuty、Inspector、Macie等の検出結果を1つの画面で一元管理し、CISベンチマークの準拠状況を評価したい」 |
| **Amazon Detective** | セキュリティインシデントの**根本原因分析・フォレンジック調査** | グラフモデルを活用し、「インシデントがなぜ起きたのか、影響範囲はどこまで及んでいるかを詳細に追跡・調査したい」 |
| **AWS Firewall Manager** | 複数アカウントにわたるセキュリティルール（WAF/Shield/SG/Network Firewall）の**一括集中管理** | 「AWS Organizations配下の全アカウントに共通のWAFルールやセキュリティグループポリシーを一律適用・強制したい」 |
| **AWS Artifact** | AWSの**コンプライアンスレポートおよび各種認証アグリーメントのセルフサービスポータル** | 「AWSのSOCレポート、PCI-DSS証明書、ISO認証書類を監査機関へ提出するためにダウンロードしたい」 |
| **AWS Audit Manager** | 規制コンプライアンス（HIPAA、GDPR等）の監査証跡収集を自動化。※2026年4月30日に新規顧客の受付を終了 | 「監査対応のための証拠収集作業を自動化し、監査レポートの作成工数を削減したい」 |

**検出・監査系サービスの目的別整理**

| 目的・課題 | 最適なサービス |
|---|---|
| 「誰が、いつ、どのAPIを呼び出したか」の**監査証跡ログの記録** | **AWS CloudTrail** |
| AWSリソースの設定状態の**変更履歴の追跡と、コンプライアンスルールの評価** | **AWS Config** |
| ログ分析と機械学習による**不審な振る舞いや脅威の検知** | **Amazon GuardDuty** |
| EC2／コンテナ／Lambdaの**既知のソフトウェア脆弱性（CVE）診断** | **Amazon Inspector** |
| S3バケット内の**機密情報・個人情報（PII）の検出** | **Amazon Macie** |
| 複数のセキュリティサービスからのアラートの**一元集約とスコアリング** | **AWS Security Hub** |
| セキュリティインシデント発生時の**根本原因の深掘り調査・因果関係の分析** | **Amazon Detective** |
