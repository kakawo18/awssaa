# 第6章 アプリケーション統合

> **章の一言**：疎結合アーキテクチャの本質は「システムコンポーネント間の直接的な依存を排除し、一方の障害や負荷スパイクが他方に波及しない状態を作ること」です。**非同期キューイングと負荷のバッファリング＝SQS、Pub/Subモデルによる一対多の同報配信＝SNS、詳細なルールによるイベントのルーティング＝EventBridge、複数ステップの状態遷移とワークフロー制御＝Step Functions**という役割分担を明確に整理します。

---

## 6.1 Amazon SQS

**困りごと**：リクエストの受信速度がバックエンドの処理速度を上回ると、同期処理の構成では待機時間の増大やタイムアウトが発生します。SQSを介して処理要求をキューに保持することで、受付と処理を切り離し、ワーカーが処理可能なペースで順次取り出せるようになります。ただし、キューに仕事を蓄積するだけで後段の処理能力そのものが向上するわけではありません。

**仕組み：1つのメッセージのライフサイクル**

「受信したら即座にキューから消える」わけではありません。**受信 → 一時的に不可視化 → 処理実行 → 処理成功後にワーカーが明示的に削除**という流れをたどります。削除しない限り、メッセージはキューに残り続けます。

| 時刻 | 発生するイベント | メッセージの状態 |
|---|---|---|
| t0 | プロデューサーがメッセージを送信（`SendMessage`） | キューに永続化。メッセージ保持期間（既定4日、最大14日）のカウントダウンが開始 |
| t1 | ワーカーAがメッセージを受信（`ReceiveMessage`） | **不可視（In Flight）**状態になる。他のワーカーからは一時的に見えなくなる（可視性タイムアウト、既定30秒） |
| t2 | ワーカーAが処理を正常完了し、キューから**削除**（`DeleteMessage`） | キューから完全に削除される。**ここで初めて「処理完了」となる** |
| t2' | （失敗時）ワーカーAが削除前にクラッシュした／タイムアウト時間内に処理が終わらなかった | 可視性タイムアウトが切れると**再び可視状態に戻る**。ワーカーBが同一メッセージを受信＝**再配信** |
| t3 | 再配信の試行回数が `maxReceiveCount` を超過した | **DLQ（デッドレターキュー）へ自動隔離**され、他の正常なメッセージの処理を阻害しない |
| t4 | メッセージ保持期間を経過した | 削除されずに残っていた場合でも**自動的に破棄**される（DLQ側でも同様に保持期間が適用される） |

**混同しやすい4つの時間パラメータ**

| パラメータ名 | 制御する動作 | 既定値／設定可能範囲 | 短すぎる場合／長すぎる場合の影響 |
|---|---|---|---|
| **可視性タイムアウト** | メッセージ受信後、他のワーカーから隠しておく時間 | 既定30秒、最大12時間 | 短すぎる：処理中に別ワーカーが同一メッセージを重複受信し**二重処理**が発生／長すぎる：処理失敗時の再配信までの待機時間が長期化 |
| **メッセージ保持期間** | 削除されない未処理メッセージをキュー内に保持する期間 | 既定4日、60秒〜最大14日 | 短すぎる：後段の障害復旧が遅れた際にメッセージが消失／長すぎる：滞留した古い不要ジョブが残存 |
| **遅延秒数（遅延キュー）** | メッセージ送信後、最初にワーカーから見えるようになるまでの待機時間 | 既定0秒、最大15分 | 送信から一定時間経過後に処理を開始させたいワークロードに使用（可視性タイムアウトとは無関係） |
| **ロングポーリング** | メッセージ受信要求時、キューが空の場合にメッセージの到着を待機する時間 | 0秒〜最大20秒 | 0秒（ショートポーリング）：空応答の頻度が増加しAPI費用とCPU負荷が増大／20秒：空応答を劇的に削減しコストとレイテンシを最適化 |

処理時間が想定よりも長引きそうな場合は、ワーカーから **`ChangeMessageVisibility` API を定期的に呼び出して可視性タイムアウトを動的に延長**します（ハートビート処理）。

**標準キュー vs FIFOキューの選び分け**

| 比較項目 | 標準キュー（Standard Queue） | FIFOキュー（First-In-First-Out） |
|---|---|---|
| スループット | **ほぼ無制限** | 既定モードは**APIアクションごと・パーティションごとに300 TPS**（バッチ10件なら3,000メッセージ/秒）。**高スループットモード**を有効化すると数千〜数万TPSまで拡張可能（→付録B） |
| 配信順序 | ベストエフォート（**順序の保証なし**） | **厳密な先入れ先出し順序を保証**（メッセージグループID単位） |
| 重複の排除 | **最低1回配信（At-Least-Once）**：まれに重複配信される可能性あり | **1回のみの配信（Exactly-Once）**：重複排除IDに基づき、5分間の重複排除ウィンドウで同一送信をブロック |
| 適した用途 | 順序が問われない大量トランザクション処理、ログ転送、画像変換など | 口座振替、在庫引当、発注受付など順序と重複防止が業務上必須の処理 |

**FIFOの「1回のみの配信」と、業務処理の1回限りの成立は別問題**
- FIFOキューの重複排除機能は、「**送信側が同一メッセージを5分以内に二重送信することを防止する**」仕組みです。
- **受信側の再配信は FIFO キューであっても発生します**。ワーカーが処理完了後にメッセージを削除する前にクラッシュした場合、可視性タイムアウトの経過により同一メッセージが別のワーカーへ再配信されます。
- したがって、**業務処理が厳密に1回のみ実行される保証は、ワーカー側の「冪等性（べきとうせい）」の設計によって担保**します。

**冪等性（Idempotency）の重要性**：例えば、決済処理自体は完了したものの、SQSメッセージを削除する直前にワーカーが障害で停止した場合を想定します。可視性タイムアウト経過後に同一メッセージが再配信された際、二重決済を実行しない仕組みが不可欠となります。これが冪等性です。具体的には注文IDなどの一意の識別子を用いて処理済みかを判定し、DynamoDBの条件付き書き込み（Conditional Writes）やトランザクション処理と組み合わせて安全に制御します。

**デッドレターキュー（DLQ）の運用設計**
- DLQを作成・設定しただけでは、異常メッセージが隔離されるだけであり、**自動的に再処理されるわけでも、永続的に保存されるわけでもありません**（DLQにも保持期間が存在します）。
- 運用としては、「**DLQのメッセージ滞留を検知（CloudWatchアラーム） → 管理者への通知 → バグや障害原因の修正 → DLQ Redrive（元のキューへメッセージを戻して安全に再実行）**」という運用フローまでを含めてアーキテクチャを設計します。

**ワーカーの並行処理：仕事の「分担」と「同報」の違い**

| アーキテクチャ構成 | 動作の仕組み | 主なユースケース |
|---|---|---|
| **単一キューを複数ワーカーで受信** | 各メッセージは**いずれか1台のワーカーのみ**が受信して処理（タスクの分担）。ワーカー台数を増やすことで処理能力がスケール | バックグラウンドジョブ処理。**キューの滞留数（`ApproximateNumberOfMessagesVisible`）に基づきワーカーをAuto Scaling** |
| **SNS ＋ 複数SQS（ファンアウト）** | 1回のメッセージ発行が**すべての購読キューへ複製・並列配信**される（同報）。各処理系は独立したキューを持つ | 同一の注文イベントに対し、「決済処理」「出荷準備」「分析基盤転送」を互いに影響を与えずに並列実行 |

キューを配置するだけでは、バックエンド全体の処理能力そのものが向上するわけではありません。**恒常的にリクエスト流入量が処理能力を上回る場合は、ワーカーの水平スケール（Auto Scaling）やAPI Gateway等でのスロットリング（流量制限）が必要**です。SQSはあくまで一時的な負荷スパイクを吸収するためのバッファとして機能します。

**SQS と Amazon Kinesis Data Streams の違い**：SQSは「**処理完了後にメッセージを削除するタスクキュー**」であり、1つのメッセージは1台のワーカーが消費します。Kinesisは「**保持期間内であれば複数の異なるコンシューマーが何度でも独立して読み直せるデータストリーム**」です。「複数の分析システムが同一データを異なるタイミングで読み取る」「障害時に過去の時点から再処理したい」場合は Kinesis、「独立したワーカー群でタスクを分担して1回ずつ確実に処理したい」場合は SQS を選択します（→第7章）。

**選ぶ条件／選ばない条件**
- リクエスト受付とバックエンド処理を疎結合にしてスパイクを吸収したい、処理側の能力に応じたペースで取り出したい → **SQS**。
- 同一のイベント通知を複数の異なるサブシステムへ並列に届けたい → **SNS（＋SQSファンアウト）**。SQS単体では複数の独立したコンシューマーに同一メッセージを配ることはできません。
- 処理順序が業務上クリティカルである → **SQS FIFOキュー**。なお、並行度を維持するために**メッセージグループID**を適切に設計します。
- 数分〜数日間にわたる**一連のワークフロー（条件分岐、待機、人の承認ステップなど）を制御したい** → **Step Functions**。SQSは個別のメッセージを蓄積するのみで、手順全体のオーケストレーションは行いません。
- 既存オンプレミスアプリケーションのJMSやAMQPプロトコルをコード変更なしに移行したい → **Amazon MQ**。

**条件違いの例**

| 設問の前提条件 | 適切な判断 | 他の選択肢を除外する理由 |
|---|---|---|
| 処理所要時間に60秒かかるが、可視性タイムアウトが30秒に設定されている | 可視性タイムアウトを60秒以上に延長、または処理中に `ChangeMessageVisibility` で動的延長 | DLQの追加：二重処理が発生する根本原因は解決されない |
| 決済処理完了後、キューからの削除直前にワーカーが障害停止する可能性がある | ワーカー側に冪等性を実装（注文IDによる処理済みチェック＋条件付き書き込み） | FIFOキューへの変更：送信側の二重投入は防げるが、受信側の障害による再配信は防止できない |
| 1つの注文イベントを「決済」「配送」「メール通知」の全システムが確実に受信したい | SNSトピック ＋ 各システム用の3つのSQSキュー（ファンアウト構成） | 1つのSQSを全システムでポーリング：いずれか1つのシステムにしかメッセージが届かない |
| 決済処理ワーカーを複数台起動し、大量の注文を並列に分散処理したい | 1つのSQSキューを複数台のワーカーインスタンスで並列受信 | SNSファンアウト：全ワーカーに同じ注文が重複して届いてしまう |
| 特定のフォーマット異常メッセージがエラーとなり、キューの先頭を塞ぎ続けている | `maxReceiveCount` を設定してDLQへ自動隔離し、アラームで通知 | 保持期間の延長：処理不能なメッセージがキューに残り続ける問題は解決しない |

**理解確認**
1. メッセージ処理に60秒を要するのに対し、可視性タイムアウトが30秒に設定されている場合、どのような問題が発生するか？
   → 30秒が経過した時点で該当メッセージが再びキュー内で可視化され、**別のワーカーが同一メッセージを受信して重複処理（二重実行）が発生**します。最初のワーカーが後から削除を実行しても、2台目のワーカーの処理は停止しません。対処法は可視性タイムアウトの延長です。
2. FIFOキューを採用すれば、ワーカー停止に伴う二重処理を完全に防止できるか？
   → **防止できない**。FIFOの重複排除機能は送信側の5分以内の重複送信をブロックするものであり、受信後に削除されなかったメッセージの再配信はFIFOであっても発生します。処理を1回のみ成立させるにはワーカー側の冪等性設計が必要です。
3. 同一の注文イベントを「決済」と「通知」の双方が受け取る場合と、複数の決済ワーカーで処理を分担する場合の構成の違いは？
   → 前者は**同報配信**であるため SNSトピック → 2つのSQSキュー によるファンアウト構成をとります。後者は**負荷分担**であるため 1つのSQSキュー を複数ワーカーがポーリングする構成をとります。

## 6.2 Amazon SNS

**概要**：完全マネージド型の**プッシュ型Pub/Sub（パブリッシュ／サブスクライブ）**メッセージングサービス。1つのトピックに発行されたメッセージを、多数のサブスクライバーへ即座に並列配信します。

- 主なサブスクライバー：**Amazon SQSキュー、AWS Lambda関数、HTTPSエンドポイント、Eメール、SMS、モバイルプッシュ通知、Amazon Kinesis Data Firehose**。
- **SNS ＋ SQS ファンアウトパターン**：トピックへの1回の発行で複数のSQSキューへメッセージを同時配信。各サブシステムは独立したキューから独自のペースでメッセージを取得・処理でき、個別にリトライやDLQを設定可能です。
- **メッセージフィルタリング**：サブスクリプションごとに属性フィルターポリシーを定義し、各サブスクライバーが必要とする条件に合致するメッセージのみを選択的に受信させることができます。
- **SNS FIFOトピック**：厳密なメッセージ順序の保持と重複排除をサポート（※サブスクライバーは SQS FIFOキュー に限定されます）。

## 6.3 Amazon EventBridge

**概要**：AWSサービス、自社アプリケーション、およびサードパーティSaaSから発生するイベントを、**きめ細かなフィルタリングルールに基づいて複数のターゲットへルーティングする**サーバーレスのイベントバス。

**試験での要点**
- AWSリソースの状態変化（EC2インスタンスの停止、RDSフェイルオーバー、CodePipelineの成功/失敗、GuardDutyの脅威検知など）をリアルタイムで検知し、Lambda、SNS、SQS、Step Functions等を自動起動します。
- **スケジュール式（cron / rate）**：従来のCloudWatch Eventsと同様、「平日毎朝9時にLambdaを定期実行する」といったジョブスケジューリングの標準機能です。
- イベントバスの種類：デフォルトイベントバス（AWSサービス発）、カスタムイベントバス（自社アプリ独自イベント用）、パートナーイベントバス（Datadog、Zendesk、PagerDuty等のSaaSから直接イベント受信）。
- **イベントのアーカイブとリプレイ**：過去に発生したイベントを指定期間記録・保存し、障害復旧時や新機能のテスト時に過去のイベントを再送信（リプレイ）して検証できます。
- **EventBridge Pipes**：イベントプロデューサーとコンシューマーを直結し、途中でフィルタリングや入力変換、Step Functions等によるデータエンリッチメントをノーコードで挟み込む機能。
- **EventBridge Scheduler**：数百万件規模のワンタイムまたは定期的なスケジュールタスクを柔軟なタイムゾーン指定で管理する専用スケジューラー。

**SNS と EventBridge の選び分け**
- **送り先が固定されており、極めて高いスループットと低レイテンシで単純同報配信したい場合** → **Amazon SNS**。
- **JSONイベントの中身（ペイロードの特定フィールド）に基づいて動的にルーティング先を分岐させたい、AWSサービスの状態変化をトリガーにしたい、スケジュール実行を行いたい場合** → **Amazon EventBridge**。

## 6.4 AWS Step Functions

**概要**：分散コンポーネントやサーバーレス機能を、**視覚的なステートマシン（ワークフロー）**として定義・実行・監視できるオーケストレーションサービス。

- 採用の決め手：「複数のLambda関数をつなぎ合わせた処理において、**順序制御、条件分岐、並列実行、エラーハンドリング、指数バックオフによる再試行のロジックが複雑化**してきた」。
- **長期間の実行と人手による承認**：タスクの完了を最大1年間待機可能。コールバックタスク（タスクトークン）を用いることで、「管理者が承認メールのリンクをクリックするまでワークフローを中断・待機する」といった人手介入ステップを簡単に構築できます。
- ワークフロータイプの比較：
  - **標準ワークフロー（Standard Workflows）**：最大1年間実行可能、すべてのステップの詳細な実行履歴を保持、**厳密に1回（Exactly-Once）の実行**。監査や決済などの基幹ビジネストランザクション向け。
  - **Expressワークフロー（Express Workflows）**：最大実行時間5分、超高スループット（毎秒10万イベント以上）、**最低1回（At-Least-Once）の実行**。IoTデータ取り込みやストリーミング変換向け。
- 200以上のAWSサービスとの直接統合に対応しており、単純なCRUD操作や別サービスの起動のためにLambda関数を仲介役として作成する必要がありません（Lambdaのコード保守と実行コストを削減）。

## 6.5 Amazon MQ

**概要**：オープンソースの標準メッセージブローカーである **Apache ActiveMQ** および **RabbitMQ** のマネージドサービス。

- 採用の決め手：**既存オンプレミスアプリケーションのクラウド移行**。「**AMQP、JMS、MQTT、STOMP、OpenWire**といった業界標準プロトコルやAPIに依存している既存システムを、アーキテクチャやコードを変更せずにそのまま移行したい」。
- 新規クラウドネイティブ開発において無限のスケーラビリティとサーバーレス運用を求める場合は、**Amazon SQS / SNS** を優先します（Amazon MQはプロビジョンドインスタンス上で稼働するため、キャパシティに上限があり手動サイジングが必要です）。
- 高可用性の確保には、マルチAZのアクティブ／スタンバイ構成（共有ストレージまたはレプリケーション）を採用します。

## 6.6 Amazon AppFlow

**概要**：Salesforce、Slack、ServiceNow、Zendeskなどの主要SaaSアプリケーションと、AWSサービス（Amazon S3、Amazon Redshiftなど）との間で、**コードを書くことなく安全に双方向データ転送**を実行するフルマネージド統合サービス。

- 実行トリガー：スケジュール実行、イベント駆動（SaaS側でのオブジェクト作成等）、オンデマンド実行。
- 転送時にデータのフィルタリング、マスキング（個人情報の秘匿化）、フィールドマッピングをGUI上で設定可能。
- AWS PrivateLink と統合されており、インターネットを経由させずにプライベートネットワーク内で安全にデータを同期できます。
- 「SaaSのデータを分析のためにS3やRedshiftへ取り込みたいが、自前でLambdaやGlueのETLコードを開発・保守したくない」という要件に対する最適解です。

## アプリケーション統合サービスの横断まとめ

| アーキテクチャの要件 | 最適なサービス |
|---|---|
| 処理要求をキューに蓄積して非同期化し、後段のワーカー群でタスクを**分散・消化**（バッファリング。1メッセージは1台が処理して削除） | **Amazon SQS** |
| 1つのイベント通知を、複数の独立したサブシステムへ**一斉同報配信**（Pub/Sub） | **Amazon SNS**（＋SQSファンアウト） |
| イベントのJSON中身に応じた動的ルーティング、AWSリソースの状態変化検知、cron式定期実行 | **Amazon EventBridge** |
| 複数ステップの処理順序、条件分岐、並列実行、長時間の待機、エラー再試行の**ワークフローオーケストレーション** | **AWS Step Functions** |
| **大量の時系列ストリーミングデータ**を順序を維持して取り込み、**複数の分析アプリケーションが保持期間内に何度でも再読み込み**可能 | **Amazon Kinesis Data Streams**（→第7章） |
| 既存オンプレミスで利用中の**JMS／AMQP等の標準プロトコルをそのまま**利用して移行 | **Amazon MQ** |
| サードパーティSaaS（Salesforce等）とAWSサービス間の**ノーコードデータ連携** | **Amazon AppFlow** |
