# 第6章 アプリケーション統合

> **章の一言**：疎結合＝「相手が落ちても壊れない」。**1対1でためる＝SQS、1対多で配る＝SNS、ルールで振り分ける＝EventBridge、順番に処理を進める＝Step Functions**。

---

## 6.1 Amazon SQS

**困りごと**：受付の速度が処理の速度を上回ると、その場で処理する構成では待ち時間やタイムアウトが増えます。SQSに仕事を預けると、受付と処理を分離し、ワーカーが処理できるペースで取り出せます。ただし、仕事をためること自体で後段の処理能力が増えるわけではありません。

**仕組み：1つのメッセージのライフサイクル**

「受信したら消える」ではない。**受信→一時的に不可視→処理→成功したらワーカーが削除**。削除しない限りメッセージはキューに残る。

| 時刻 | 起きること | メッセージの状態 |
|---|---|---|
| t0 | プロデューサーが送信（SendMessage） | キューに保存。保持期間（既定4日、最大14日）のカウント開始 |
| t1 | ワーカーAが受信（ReceiveMessage） | **不可視**になる。他のワーカーからは見えない（可視性タイムアウト、既定30秒） |
| t2 | ワーカーAが処理を完了し**削除**（DeleteMessage） | キューから消える。**ここで初めて「完了」** |
| t2' | （失敗系）ワーカーAが削除前に落ちた／タイムアウト内に終わらなかった | 可視性タイムアウトが切れると**再び見える**。ワーカーBが同じメッセージを受信＝**再配信** |
| t3 | 再配信が maxReceiveCount 回を超えた | **DLQ（デッドレターキュー）へ隔離**。正常なメッセージの処理を止めない |
| t4 | 保持期間を超えた | 削除されずに残っていても**自動で消える**（DLQ側も同じ） |

**4つの「時計」を混同しない**

| 時計 | 何を決めるか | 既定／上限 | 短すぎると／長すぎると |
|---|---|---|---|
| **可視性タイムアウト** | 受信後、他のワーカーから隠す時間 | 既定30秒、最大12時間 | 短い：処理中に他のワーカーが同じメッセージを受信＝**二重処理**／長い：失敗時の再配信が遅れる |
| **保持期間** | 削除されないメッセージをキューに置く期間 | 既定4日、60秒〜14日 | 短い：処理が追いつかないと消える／長い：古い仕事が残る |
| **配信遅延（遅延キュー）** | 送信後、最初に見えるまで待つ時間 | 既定0秒、最大15分 | 「送ってから n 分後に処理」に使う。可視性タイムアウトとは別物 |
| **ロングポーリング** | 受信要求で、メッセージがないとき待つ時間 | 0〜20秒 | 0（ショートポーリング）：空応答が増えAPI料金が上がる／20秒：空応答が減りコストと遅延が下がる |

処理時間が可視性タイムアウトより長くなりそうなら、**ChangeMessageVisibility で延長**する（ハートビート）。

**標準キュー vs FIFOキュー**

| | 標準 | FIFO |
|---|---|---|
| スループット | ほぼ無制限 | 既定モードは**APIアクションごと・パーティションごとに300 TPS**（バッチ10件なら3,000メッセージ/秒）。**高スループットモード**を有効にするとリージョンにより数千〜数万TPSまで上がる。TPS（API呼び出し数）とメッセージ/秒を混同しない（→付録B） |
| 順序 | ベストエフォート（**保証なし**） | **厳密な順序**（メッセージグループID単位） |
| 重複 | **最低1回配信**（重複あり得る） | **送信の重複排除**（重複排除ID、5分間の窓） |
| 選ぶ場面 | 大量・順不同で良い処理 | 銀行取引、在庫更新など順序が意味を持つ処理 |

**FIFOの「正確に1回」と、業務処理が1回だけ成立することは別**
- FIFOの重複排除は「**同じ送信を5分以内に2回受け付けない**」仕組み。**送信側の重複**を防ぐ。
- **受信側の再配信は FIFO でも起こる**。ワーカーが削除前に落ちれば、同じメッセージが再び配信される。
- したがって、**業務処理が1回だけ成立する保証は、ワーカー側の冪等性で作る**。

**冪等性（べきとうせい）**：決済は完了したが、SQSのメッセージを削除する前にワーカーが落ちたとします。メッセージが再配信されたとき、同じ決済をもう一度実行しない仕組みが必要です。これが冪等性です。例えば注文ID等を使い、既に処理済みかを判定します。ただし単純な「確認→実行」だけでは同時実行の競合があるため、条件付き更新（DynamoDBの条件式）やトランザクション等も考慮します。

**DLQは「隔離」であって「復旧」ではない**
- DLQを作るだけでは、失敗したメッセージは**自動では再処理されない**し、**永久に保存されるわけでもない**（DLQにも保持期間がある）。
- 運用は「**DLQに溜まったら通知（CloudWatchアラーム）→原因を直す→再処理（DLQ redrive で元のキューへ戻す）**」まで含めて設計する。
- 「メッセージが失われないように」＝DLQ、ではなく「失敗したメッセージを**見失わず、後で処理し直せる**ように」＝DLQ＋再処理の手順。

**ワーカーは1台ではない：仕事の分担と同報の違い**

| 構成 | 何が起きるか | 使う場面 |
|---|---|---|
| **1つのキューを複数ワーカーが受信** | 各メッセージは**どれか1台**が受け取る（仕事の分担）。ワーカーを増やせば処理能力が上がる | 画像変換、注文処理。**キューの滞留数（ApproximateNumberOfMessagesVisible）でワーカーをAuto Scaling** |
| **SNS＋複数のSQS（ファンアウト）** | 1回の発行が**全部のキュー**に届く（同報）。各キューは独立に再試行できる | 同じ注文を「決済」と「通知」と「分析」が別々に処理 |

キューを置くだけでは後段の処理能力は増えない。**持続的に流入が処理を上回るなら、ワーカーの増強か流量制御（スロットリング）**が要る。キューは一時的なスパイクを吸収するバッファ。

**SQS と Kinesis Data Streams の違い**：SQSは「**処理したら削除する仕事のキュー**」で、1メッセージは1つのワーカーが処理する。Kinesisは「**保持期間内なら何度でも読み直せるストリーム**」で、複数のアプリが同じデータを独立に読める（→第7章）。「複数の分析システムが同じデータを読む」「後から再処理したい」＝Kinesis、「仕事を分担して1回ずつ処理」＝SQS。

**選ぶ条件／選ばない条件**
- 受付と処理を分離してスパイクを吸収したい、処理側のペースで取り出したい→SQS。
- 同じイベントを複数の処理系に届けたい→SNS（＋SQSでファンアウト）。SQS単体では1つの処理系にしか渡らない。
- 順序が業務的に意味を持つ→FIFO。ただし順序が要るのは**同じグループ内**だけなので、メッセージグループIDで並列度を確保する。
- 数分〜数時間の**手順の制御**（分岐・待機・人の承認）→Step Functions。キューは手順を管理しない。
- 既存のJMS/AMQPアプリをそのまま→Amazon MQ。

**条件違いの例**

| 条件 | 判断 | 外す候補と理由 |
|---|---|---|
| 処理に60秒かかるが可視性タイムアウトが30秒 | タイムアウトを処理時間より長く設定、または処理中に延長 | DLQ追加：二重処理の原因は解決しない |
| 決済完了後・削除前にワーカーが落ちる可能性がある | ワーカーに冪等性（注文IDで処理済み判定＋条件付き更新） | FIFOへ変更：送信の重複は防ぐが、受信側の再配信は防げない |
| 同じ注文を「決済」と「通知」の両方が受け取りたい | SNS＋SQS×2（ファンアウト） | 1キューを2ワーカー：どちらか1台にしか届かない |
| 決済ワーカーを複数台で分担したい | 1つのSQSを複数ワーカーで受信 | SNSファンアウト：全ワーカーに同じ注文が届き重複する |
| 失敗が続くメッセージが正常処理を塞ぐ | maxReceiveCount＋DLQ、DLQ監視と再処理手順 | 保持期間の延長：塞いでいる原因は残る |

**理解確認**
1. 処理に60秒、可視性タイムアウトが30秒の場合に何が起こり得るか。→ 30秒経過時点でメッセージが再び見えるようになり、**別のワーカーが同じメッセージを受信して二重処理**になる。最初のワーカーが後で削除しても、2台目は処理を続ける。対策はタイムアウトの延長か、処理中の ChangeMessageVisibility。
2. FIFOに変えれば、決済完了後・削除前の障害にも自動的に対応できるか。→ **できない**。FIFOの重複排除は送信側の重複（5分以内の同じ内容）を防ぐもので、受信後に削除されなかったメッセージの再配信は FIFO でも起こる。業務処理を1回にするのはワーカーの冪等性。
3. 同じ注文を「決済」と「通知」の両方が受け取りたい場合と、複数の決済ワーカーで分担したい場合はどう違うか。→ 前者は**同報**なので SNS→SQS×2 のファンアウト（各キューが全注文を受ける）。後者は**分担**なので 1つのSQS を複数ワーカーがポーリング（各注文はどれか1台が処理）。取り違えると、前者では通知が届かず、後者では同じ注文が複数回決済される。

## 6.2 Amazon SNS

**一言で**：**プッシュ型**のPub/Sub。1つのメッセージを多数のサブスクライバーへ同報。

- サブスクライバー：SQS、Lambda、HTTP/S、Eメール、SMS、モバイルプッシュ、Data Firehose。
- **ファンアウト（SNS＋複数SQS）**が最重要パターン：1回の発行を複数の処理系へ配り、**各処理系はキューで独立に再試行できる**。「S3にアップされた画像をサムネイル生成と解析の両方へ」など。
- **メッセージフィルタリング**＝サブスクリプションごとに属性で絞り、不要な配信をなくす。
- FIFOトピックあり（サブスクライバーはSQS FIFOのみ）。配信失敗は再試行＋DLQ。

**SQSとの見分け**：**1つの処理系**（ワーカーは複数台でよい）が**自分のペースで取り出して分担**＝SQS。**複数の処理系に同じメッセージを同時に**届ける＝SNS。両方（同報したうえで各処理系が自分のペースで処理）＝ファンアウト。

## 6.3 Amazon EventBridge（旧 CloudWatch Events）

**一言で**：AWSサービス・自作アプリ・SaaSのイベントを**ルールで振り分ける**サーバーレスのイベントバス。

**試験の核心**
- AWSサービスの状態変化（EC2の起動、RDSの障害、CodePipelineの成功、GuardDutyの検出）をトリガーにLambda/SNS/SQS/Step Functionsを起動。
- **cron/rate式でのスケジュール実行**＝「毎晩3時にLambdaを実行」の定番解。
- **カスタムイベントバス**でアプリ独自イベント、**パートナーイベントバス**でSaaS（Datadog、Zendeskなど）から直接受信。
- スキーマレジストリ、アーカイブと**リプレイ**（過去イベントの再処理）。
- EventBridge **Pipes**＝ソースとターゲットを直結（フィルタ・変換付き）。**Scheduler**＝大規模なスケジュール管理。

**SNSとの見分け**：**送り先が固定で単純な同報**＝SNS（低レイテンシ・高スループット）。**イベントの内容（JSON）でルーティング先を分岐、AWSサービスのイベントを拾う、スケジュール実行**＝EventBridge。

## 6.4 AWS Step Functions

**一言で**：複数の処理を**状態遷移図（ワークフロー）**として定義・実行する。分岐・並列・リトライ・待機を宣言的に書ける。

- 「Lambdaを複数つないだ処理の**エラー処理と再試行が複雑になってきた**」＝Step Functions。
- **人手の承認待ち**や長時間の待機（コールバックパターン、最大1年）も可能。
- **標準ワークフロー**＝最大1年、実行履歴あり、**正確に1回**、監査向き。**Expressワークフロー**＝最大5分、大量・高速（**最低1回**）、IoTやストリーム処理向き。
- 200以上のAWSサービスを直接呼べる（Lambdaを挟まなくて良い＝コスト削減）。

**見分け**：手順・順序・分岐の**制御**＝Step Functions／単なるイベント配送＝EventBridge・SNS／計算ジョブの**キューイングと実行**＝AWS Batch。

## 6.5 Amazon MQ

**一言で**：ApacheActiveMQ / RabbitMQ のマネージドサービス。

- 決め手は**既存アプリの移行**。「**AMQP、MQTT、STOMP、OpenWire、JMS**といった標準プロトコルを使っている」「コードを書き換えずにオンプレのメッセージブローカーをクラウドへ」＝Amazon MQ。
- 新規開発でスケールが必要なら **SQS/SNS**（MQはブローカーのサイズに上限があり、スケールは手動）。
- マルチAZのアクティブ/スタンバイ構成で可用性を確保。

---

## 6.6 Amazon AppFlow

**一言で**：SaaSとAWSの間でデータを**ノーコード**で転送。

- 例：Salesforce → S3/Redshift、Slack → S3、S3 → Salesforce。
- スケジュール実行・イベント駆動・オンデマンド、転送時のフィルタとマッピング、PrivateLink経由も可。
- 「SaaSのデータを分析基盤に取り込みたいが、コードもインフラも書きたくない」＝AppFlow（Glue/Lambdaで自作するのは不正解の型）。

## メッセージング横断まとめ

| 要件 | 答え |
|---|---|
| 処理をためて非同期に、処理側のペースで取り出して**分担**（バッファリング。1メッセージは1ワーカーが処理して削除） | SQS |
| 1つのイベントを複数の処理系へ同報 | SNS（＋SQSでファンアウト） |
| イベントの中身でルーティング、AWSイベント、定期実行 | EventBridge |
| 手順・分岐・リトライを可視化して制御 | Step Functions |
| **大量のストリーミングデータ**を順序付きで、**複数コンシューマーが保持期間内に何度でも読み直せる**形で | **Kinesis Data Streams**（→第7章） |
| 既存のJMS/AMQPアプリをそのまま | Amazon MQ |
