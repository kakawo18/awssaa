# 第7章 アナリティクス

> **章の一言**：アナリティクス分野は、データパイプラインのライフサイクルである「**収集（Kinesis）→ 変換・カタログ化（Glue）→ 蓄積（S3データレイク）→ 分析・クエリ（Athena / Redshift / EMR）→ 可視化（QuickSight）**」という位置関係と役割分担を軸に整理します。

---

## 7.1 Amazon Kinesis

**概要**：大規模なリアルタイム・ストリーミングデータを低遅延で収集・処理・分析するためのフルマネージドサービス群。

| サービス | 主な用途・特徴 | データの保持と再処理 |
|---|---|---|
| **Amazon Kinesis Data Streams** | **順序保証・複数コンシューマーによる並行読み出し・データの再処理**が必要なリアルタイム処理基盤（レイテンシ200ミリ秒未満） | **1日〜最大365日間保持可能**。期間内であれば何度でも再読み込みが可能 |
| **Amazon Data Firehose**（旧 Kinesis Data Firehose） | 収集したデータを **Amazon S3、Redshift、OpenSearch、Splunk** 等へコードレスで自動配信・ロードするフルマネージド配信サービス | **保持機能なし（バッファリングのみ）**。宛先へ書き込み後はFirehose内にデータは残らない |
| **Amazon Managed Service for Apache Flink**（旧 Kinesis Data Analytics） | ストリーミングデータに対し、標準SQLやApache Flinkを用いてリアルタイムに時系列集計（移動平均、スライディングウィンドウ、異常検知）を実行 | ストリームをインラインでリアルタイム処理 |
| **Amazon Kinesis Video Streams** | IPカメラ、IoTデバイス、スマートフォン等からの映像・音声ストリーミングの安全な取り込みと機械学習連携 | 暗号化して永続化・再生可能 |

**試験での要点**
- **Kinesis Data Streams のスケーリング**：キャパシティの単位は**シャード（Shard）**（1シャードあたり書き込み1 MB/秒または1,000レコード/秒、読み取り2 MB/秒）。スループット不足時は**シャード分割（リシャーディング）**で対応します。プロビジョニング管理を不要にしたい場合は**オンデマンドモード**を選択します。
- **順序保証とパーティションキー**：同一のパーティションキーを持つレコードは同一のシャードへ割り当てられ、**シャード内での厳密な処理順序が保証**されます。偏ったキー設計によるホットシャード（特定シャードのスロットリング）を回避するため、十分なカーディナリティを持つキーを指定します。
- **Data Firehose の配信遅延と機能**：ニアリアルタイム配信であり、バッファサイズ（1〜128 MB）またはバッファ間隔（0〜900秒、既定300秒）のいずれかに達した時点で配信されます。配信途中で AWS Lambda によるデータ形式変換や、**Apache Parquet / ORC への列指向自動変換**が可能です。
- **SQS と Kinesis の本質的な違い**：SQSは「タスクをワーカー間で分散し、処理成功後に削除するキュー」です。Kinesisは「保持期間内であれば複数の異なるコンシューマーが同一のストリームを各自のオフセットから何度でも繰り返し読み取れるストリーム」です。

## 7.2 AWS Glue

**概要**：サーバーレスのデータ統合・ETL（抽出・変換・ロード）サービス、およびデータレイクのメタデータを一元管理する **AWS Glue データカタログ** を提供。

- **Glue クローラー（Crawler）**：S3やRDS等のデータストアを自動スキャンし、ファイル形式やスキーマ定義を推論して**Glue データカタログにテーブル定義としてメタデータを登録**します。このカタログは **Amazon Athena、Amazon Redshift Spectrum、Amazon EMR** から共通のスキーマ定義として透過的に参照されます。
- **ETLジョブ**：Apache Spark または Python Shell ベースのサーバーレス分散処理基盤。インフラの管理なしに大量データ変換を実行でき、**ジョブブックマーク**により過去に処理済みのデータを自動識別して差分のみを再処理できます。
- **Glue DataBrew**：アナリスト向けノーコードデータ準備ツール。GUI操作でデータのプロファイリング、欠損値の穴埋め、クレンジングを自動化します。
- **Amazon EMR との使い分け**：サーバー管理を行わずETLジョブをスケジュール実行したい場合 → **AWS Glue**。Hadoop/Sparkのクラスタ構成やミドルウェアを細部までチューニングしたい、または既存のビッグデータ基盤をそのまま移行したい場合 → **Amazon EMR**。

## 7.3 Amazon Athena

**概要**：Amazon S3上のデータに対して、標準SQLを用いて直接アドホッククエリを実行できるサーバーレスの対話型分析サービス。スキャンしたデータ量（TB単位）に基づく完全従量課金制。

**試験での要点（コスト最適化の定石）**
- **スキャンデータ量の削減がそのままコスト削減と高速化に直結**します。以下の3つの最適化手法が頻出です：
  1. **列指向フォーマット（Apache Parquet / ORC）へのデータ変換**（必要な列のみをスキャンするため、CSV/JSONと比較してスキャン量を大幅削減）。
  2. **データの圧縮（Snappy、GZIP等）**。
  3. **パーティション分割（年/月/日などの日付階層）**（`WHERE` 句で指定したパーティション以外の読み込みをスキップ）。
- 最適なユースケース：Application Load Balancer、CloudFront、CloudTrail、VPCフローログなどのログ分析、およびS3データレイクに対するアドホックな探索的クエリ。
- 定常的に複雑な集計クエリを繰り返し実行する大規模なBIレポート基盤としては、データウェアハウスである Amazon Redshift の方が適しています。

---

## 7.4 Amazon Redshift

**概要**：ペタバイト規模の構造化・半構造化データを高速に集計・分析できる、クラウド向けフルマネージド・データウェアハウス（DWH）。列指向ストレージアーキテクチャと大規模超並列処理（MPP）により、複雑なBIクエリや結合処理を高速化。

- **OLTP（オンライントランザクション処理）ではなくOLAP（オンライン分析処理）**向け。「複数の巨大テーブルを結合した複雑な集計クエリを、BIツールから定常的に高頻度で実行する」要件に適します。
- **Redshift Spectrum**：S3上のデータレイクにあるオープンフォーマットデータを、Redshiftクラスタ内にロードすることなく、外部テーブルとして直接SQLで結合・クエリ実行できる機能。
- **コンピュートとストレージの分離**：**RA3インスタンス**を採用することで、Redshift マネージドストレージ（RMS）を利用し、計算ノード数とストレージ容量を独立してスケーリング可能です。
- **同時実行スケーリング（Concurrency Scaling）**：クエリリクエストが急増した際、バックグラウンドでクラスタキャパシティを自動追加し、待機時間を発生させずに同時実行性能を担保。
- **Redshift Serverless**：データウェアハウスのインフラをプロビジョニングすることなく、クエリ実行時間とデータ処理量（RPU）に応じた従量課金で利用可能。

## 7.5 Amazon QuickSight

**概要**：クラウドネイティブでサーバーレスのフルマネージド・ビジネスインテリジェンス（BI）およびデータ可視化サービス。

- **SPICE（Super-fast, Parallel, In-memory Calculation Engine）**：QuickSight内蔵の超高速インメモリ並列計算エンジン。Redshift、Athena、RDS、S3、外部SaaSなど多様なソースからデータを事前に取り込み、ダッシュボードの描画や集計応答をミリ秒単位で高速化します。
- **行レベルセキュリティ（RLS）**：ユーザーやグループの属性に応じて、閲覧可能なデータ行を自動フィルタリングし、単一のダッシュボードで部署ごとの適切なデータアクセス制御を実現。
- 埋め込みダッシュボード（Embedded Analytics）により、自社のポータルサイトやSaaSアプリケーション内にインタラクティブな分析グラフをシームレスに組み込み可能。

---

## 7.6 Amazon OpenSearch Service

**概要**：オープンソースの検索・分析エンジン（OpenSearchおよび従来のElasticsearch互換）を提供するフルマネージドサービス。

- 主な用途：**大規模なテキストデータの全文検索**、および**システムログやメトリクスのリアルタイム集約・可視化（OpenSearch Dashboards）**。
- 典型的なログ分析パイプライン：アプリケーションログ → **Amazon Data Firehose**（または CloudWatch Logsサブスクリプション） → **Amazon OpenSearch Service** → OpenSearch Dashboards によるリアルタイムな障害分析・可視化。
- 「ログを検索して直近のエラー原因を即座に調査したい」場合は OpenSearch、「S3に長期保存されたログを必要に応じてSQLで抽出・監査したい」場合は Athena を選択します。

---

## 7.7 AWS Lake Formation

**概要**：Amazon S3を中心とした安全なデータレイクの構築・管理・セキュリティ制御を一元化するガバナンスサービス。

- 採用の決め手：「S3データレイク上のデータに対し、**テーブル単位、列（カラム）単位、行単位、セル単位のきめ細かなアクセス制御ポリシー**を定義し、複数の分析エンジン（Amazon Athena、Amazon Redshift Spectrum、Amazon EMR）に横断的・統一的に適用したい」。
- 単なるS3バケットポリシーやIAMポリシーだけでは管理が極めて煩雑になる、複数ユーザー・複数サービス間でのマルチテナントなデータレイク運用を簡素化します。

---

## 7.8 Amazon EMR

**概要**：Apache Hadoop、Apache Spark、Apache Hive、Presto、HBaseなどのオープンソース・ビッグデータフレームワークをAWS上で大規模に実行するためのフルマネージドクラスター基盤。

- ノード構成と耐障害性：
  - **マスターノード**：クラスター全体の管理とジョブ調整を担当（単一障害点を防ぐマルチマスター構成も可能）。
  - **コアノード**：データ処理を実行し、クラスター内部ストレージである **HDFS（Hadoop Distributed File System）のデータを保持**。障害時のデータ損失を避けるため、通常はオンデマンドインスタンスまたはリザーブドインスタンスで運用。
  - **タスクノード**：HDFSデータを保持せず、**計算処理のみを実行**。途中で停止してもジョブ全体が破損しないため、**スポットインスタンスを適用して大幅なコスト削減**を図るのが定石。
- **EMRFS（EMR File System）**：HDFSの代わりに Amazon S3 を永続ストレージとして直接マウント・利用するアーキテクチャ。クラスターを常時稼働させる必要がなくなり、**バッチ処理完了後にクラスター自体を破棄（一時クラスター運用）**することで運用コストを劇的に最適化できます。

## 7.9 その他のアナリティクスサービスと分析サービスの選び分け

| サービス | 概要と主な役割 | 試験での判断ポイント |
|---|---|---|
| **Amazon MSK** | Apache Kafka のフルマネージドサービス | 「**既存のオンプレミス Kafka アプリケーション**を、プロトコルやクライアントライブラリを変更せずにAWSへ移行したい」 |
| **AWS Data Exchange** | サードパーティが提供するデータセットの安全な検索・購読・利用 | 「外部の市場データ、気象データ、統計データを自社の分析基盤に取り込みたい」 |
| **Amazon DataZone** | 組織全体のデータ発見、ガバナンス、共有を一元化するデータ管理ポータル | 「社内のドメイン間でデータカタログを共有し、ビジネスユーザーが安全にデータを検索・利用申請できるようにしたい」 |

**分析クエリサービスの最終見分け表**

| 設問の要件・分析ワークロード | 最適なサービス |
|---|---|
| S3上の大量ファイルに対して、サーバー管理不要で**アドホック（単発・探索的）に標準SQLクエリ**を実行したい | **Amazon Athena** |
| 構造化データを集約し、**複雑な結合や大規模集計を伴うBIレポート・DWH環境**を構築したい（数十TB〜PB規模） | **Amazon Redshift** |
| **既存のHadoop / Sparkジョブ資産**を活用し、高度な分散データ処理・機械学習パイプラインを実行したい | **Amazon EMR** |
| アプリケーションログの**リアルタイム全文検索・インデックス化、およびダッシュボード分析** | **Amazon OpenSearch Service** |
| 異種データソース間のデータ抽出・変換・ロード処理、および**メタデータカタログの中央管理** | **AWS Glue** |
