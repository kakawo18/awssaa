# 第7章 アナリティクス

> **章の一言**：データの流れ「**集める（Kinesis）→ 整える（Glue）→ 貯める（S3）→ 問い合わせる（Athena / Redshift）→ 見せる（QuickSight）**」の位置関係で覚える。

---

## 7.1 Amazon Kinesis

**一言で**：リアルタイムのストリーミングデータを受け止める入口。**4兄弟の使い分けが頻出**。

| 要件 | サービス |
|---|---|
| **順序保証・複数のコンシューマー・再処理（保持1〜365日）**、カスタム処理、リアルタイム（〜200ms） | **Kinesis Data Streams** |
| **S3 / Redshift / OpenSearch / Splunk へ「ただ配送」したい**。管理ゼロ、コード不要 | **Data Firehose**（ニアリアルタイム、**最短60秒のバッファ**） |
| ストリームに対する**SQLやApache Flink**でのリアルタイム集計（移動平均、異常検知） | **Managed Service for Apache Flink**（旧 Kinesis Data Analytics） |
| 映像ストリームの取り込みと分析 | Kinesis Video Streams |

**試験の核心**
- Data Streamsの単位は**シャード**（1シャード＝書き込み1MB/秒・1,000レコード/秒、読み取り2MB/秒）。スループット不足＝**シャード追加（リシャーディング）**。管理したくないなら**オンデマンドモード**。
- **パーティションキーで順序が決まる**。同じキーは同じシャード＝順序保証。ホットキーに偏るとスロットリング。
- Firehoseは**サーバーレスで自動スケール、保持しない（再処理できない）**。途中でLambda変換、Parquet変換が可能。
- **SQSとの違い**：SQSは**1メッセージを1回消費して消える**／Kinesisは**同じデータを複数のアプリが何度でも読める**。「複数の分析システムが同じストリームを読む」＝Kinesis。

---

## 7.2 AWS Glue

**一言で**：**サーバーレスのETL**＋**データカタログ**（メタデータの中央管理）。

- **クローラー**がS3などをスキャンしてスキーマを推論し、**Glueデータカタログ**に登録。**Athena・Redshift Spectrum・EMRが同じカタログを参照**する。
- ETLジョブはSpark（またはPython Shell）。サーバー管理不要、ジョブブックマークで差分処理。
- **Glue DataBrew**＝ノーコードでデータクレンジング・前処理（アナリスト向け）。
- **EMRとの違い**：クラスターを管理したくない・ETLが主目的＝Glue／**Hadoop/Spark/Hiveを細かく制御**したい、既存のビッグデータ基盤を移す＝EMR。

---

## 7.3 Amazon Athena

**一言で**：**S3上のデータにそのままSQL**。サーバーレス、**スキャンしたデータ量（TB単位）で課金**。

**試験の核心（コスト最適化がそのまま出る）**
- **列指向フォーマット（Parquet / ORC）に変換**＋**圧縮**＋**パーティション分割（年/月/日）**でスキャン量を減らす＝そのままコスト削減。
- ログ分析（ALB、CloudFront、CloudTrail、VPCフローログ）のアドホック調査の定番解。
- ETL不要・インフラ不要。**定常的な大量BIワークロードには不向き**（→Redshift）。

---

## 7.4 Amazon Redshift

**一言で**：ペタバイト級の**データウェアハウス**。列指向・MPP（並列処理）でBI/レポートを高速化。

- **OLTPではなくOLAP**。「複雑な集計・結合を継続的に、BIツールから」＝Redshift。単発・低頻度ならAthena。
- **Redshift Spectrum**＝S3上のデータを**ロードせずに**直接クエリ（Redshiftとデータレイクの橋渡し）。
- **同時実行スケーリング**＝クエリ集中時に自動でクラスターを追加。**RA3＋マネージドストレージ**＝コンピューティングとストレージを分離。
- **Redshift Serverless**＝使った分だけ、断続的な分析に。
- 可用性：スナップショットはS3に自動保存、**クロスリージョンコピー**でDR。マルチAZ構成も可。
- 分散スタイル（KEY/EVEN/ALL）とソートキーで性能が決まる。

---

## 7.5 Amazon QuickSight

**一言で**：サーバーレスのBI（可視化）ツール。

- **SPICE**＝インメモリ高速計算エンジン。データソース（Redshift、Athena、RDS、S3、SaaS）から取り込んで高速表示。
- **行レベルセキュリティ**で部署ごとに見えるデータを制限、**埋め込み分析**でアプリに組み込み。
- 「経営層にダッシュボードを見せたい」＝QuickSight（データを取ってくるのはAthena/Redshift側の役割）。

---

## 7.6 Amazon OpenSearch Service（旧 Elasticsearch Service）

**一言で**：**全文検索**と**ログのリアルタイム分析・可視化（Dashboards/Kibana）**。

- 定番パターン：アプリのログ → **Data Firehose** or Lambda → OpenSearch → ダッシュボードで即時検索。
- 「**アプリケーションログを検索して障害を即座に調べたい**」＝OpenSearch／「S3に貯めたログをたまにSQLで分析」＝Athena。
- 商品検索・オートコンプリートなどの検索機能にも使う。

---

## 7.7 AWS Lake Formation

**一言で**：データレイク（S3＋Glueカタログ）の構築と**きめ細かなアクセス制御**を一元化。

- 決め手は「**テーブル・列・行・セル単位**の権限を、複数の分析サービス（Athena、Redshift、EMR、QuickSight）に**横断で**効かせたい」。
- S3バケットポリシーやIAMだけでは列単位の制御が煩雑になる、という問題文が来たらこれ。

---

## 7.8 Amazon EMR（旧 Elastic MapReduce）

**一言で**：Hadoop・Spark・Hive・Presto・HBaseを動かすマネージドクラスター。

- ノード構成：**マスター／コア（HDFS保持）／タスク（計算のみ）**。**タスクノードにスポットを使う**のがコスト最適化の定番（コアノードにスポットは危険）。
- **EMRFS**でS3を直接データストアにすると、クラスターを落としてもデータが残る（**一時クラスター＝処理が終わったら削除**でコスト削減）。
- 「既存のHadoop/Sparkジョブをそのまま」「何時間もかかる大規模な分散処理」＝EMR。

---

## 7.9 その他のアナリティクスのサービス

| サービス | 一言で | 決め手 |
|---|---|---|
| Amazon MSK | マネージドApache Kafka | 「**既存のKafka**アプリをそのまま移行」（新規ならKinesis） |
| AWS Data Exchange | サードパーティデータの購読 | 「外部の統計データを取り込みたい」 |
| AWS Data Pipeline | 旧世代のバッチオーケストレーション | 新規はStep Functions/Glueが推奨 |
| Amazon DataZone | データカタログとガバナンスのポータル | 「組織横断でデータを発見・共有」 |

**分析クエリの最終見分け**
| 問題文 | 答え |
|---|---|
| S3のデータに**たまに**SQL、インフラ管理なし | Athena |
| 継続的・大規模なBI、複雑な結合、数十TB〜 | Redshift |
| Hadoop/Sparkのコード資産、カスタム分散処理 | EMR |
| ログの**全文検索**とリアルタイム可視化 | OpenSearch |
| ETLとスキーマ管理 | Glue |
