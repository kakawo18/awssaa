# 第8章 管理、モニタリング、ガバナンス

> **章の要点**：**CloudWatchは性能・稼働状況（メトリクス・ログ）**、**CloudTrailは操作履歴（誰が・いつ・何を）**、**AWS Configは構成の変更履歴とルール準拠性（どう設定されているか）**を担う。この3大サービスの役割分担と連携パターンの整理が本章の核心となる。

---

## 8.1 Amazon CloudWatch

**概要**：メトリクスの収集、ログの一元管理、しきい値監視と自動アクションを提供する統合監視基盤。

**試験対策のポイント**
- **メトリクスの収集間隔**：標準モニタリングは**5分間隔**、詳細モニタリングを有効にすると**1分間隔**（追加料金）で収集される。カスタムメトリクスでは最短1秒間隔の高解像度メトリクスも利用可能。
- **標準メトリクスの収集範囲**：ハイパーバイザー側から取得できるCPU使用率、ネットワークトラフィック、ディスクI/Oなどは標準で収集される。一方、**メモリ使用率やOS内部のディスク空き容量は標準では取得できない**。これらを監視するには、インスタンス内に**CloudWatchエージェント（Unified Agent）**を導入し、カスタムメトリクスとして送信する必要がある（頻出の論点）。
- **ログ管理（CloudWatch Logs）**：EC2インスタンスのOS・アプリケーションログの収集にもCloudWatchエージェントが必要（LambdaやECS Fargateなどは標準でログを送信可能）。ログの**保持期間はデフォルトで無期限**に設定されているため、コスト最適化の観点から「保持期間の適切な設定」や「S3へのエクスポート」が求められる。
- **アラームのアクション**：しきい値超過時にSNS通知、**EC2アクション（再起動・復旧・停止）**、Auto Scalingのトリガーを実行できる。欠落データの処理方法（見つからない、適正、しきい値超過など）も定義可能。
- **分析と連携機能**：
  - **CloudWatch Logs Insights**：収集したログに対して対話型クエリを実行し、迅速なトラブルシューティングを行う。
  - **メトリクスフィルタ**：ログ内の特定文字列（「ERROR」や不正ログインパターンなど）を検出し、その発生回数を数値メトリクス化してアラームのトリガーとする。
  - **サブスクリプションフィルタ**：ログイベントをリアルタイムにKinesis Data Streams、Kinesis Data Firehose、Lambda、OpenSearch Service等へ転送する。
- **外形監視・ユーザー体験監視**：
  - **CloudWatch Synthetics（Canary）**：エンドポイントやUIフローをスクリプトで定期実行し、外部からの可用性やレイテンシを監視する。
  - **CloudWatch RUM**：Webアプリケーションのエンドユーザー側のパフォーマンス情報を直接収集・分析する。

## 8.2 AWS CloudTrail

**概要**：**誰が・いつ・どのリソースに対して・どのAPIを呼び出したか**の操作ログを記録する監査・ガバナンス基盤。

- **イベント履歴と証跡（Trail）**：コンソールの「イベント履歴」は直近90日間の管理イベントのみを保持する。**90日以上の長期保存、複数リージョンの集約、組織（Organizations）全体の証跡収集を行う場合は「証跡（Trail）」を作成してS3バケットへ出力**する。
- **イベントの種類**：
  - **管理イベント（Management events）**：リソースの作成・変更・削除など、コントロールプレーンの操作を記録（デフォルトで有効）。
  - **データイベント（Data events）**：**S3のオブジェクトレベル操作（GetObject, PutObject等）**や**Lambda関数の実行**など、データプレーンの高頻度操作を記録（デフォルトは無効、追加料金が必要）。「特定オブジェクトの削除者を特定したい」といった要件ではデータイベントの有効化が必須。
- **ログの保護とセキュリティ**：
  - **ログファイル検証（Log File Validation）**：ダイジェストファイルを用いてログファイルの改ざんや削除を暗号学的に検知する。
  - ログ保存先S3バケットでのバージョニング、オブジェクトロック（WORM）、KMS暗号化の併用、および**集中ログ管理専用アカウントへの保管**がベストプラクティスとなる。
- **リアルタイム検知**：CloudTrailのログをCloudWatch Logsへ配信し、メトリクスフィルタとアラームを組み合わせることで、ルートユーザーのログインやセキュリティグループの不正変更などを即座に検知・通知できる。

## 8.3 AWS CloudFormation

**概要**：インフラストラクチャを宣言型のテンプレート（YAML/JSON）で定義し、自動的かつ再現可能にリソースをプロビジョニングするIaC（Infrastructure as Code）サービス。基本料金は無料（作成されたAWSリソースの料金のみ）。

- **変更セット（Change Sets）**：テンプレートの更新を適用する前に、既存リソースにどのような追加・変更・再作成（中断）が発生するかを事前にプレビューする。
- **ドリフト検出（Drift Detection）**：コンソールやCLIからの手動変更によって、実際のインフラ構成がCloudFormationテンプレートの定義と乖離した箇所を特定する。
- **AWS CloudFormation StackSets**：単一の操作で、**複数のAWSアカウントおよび複数のリージョン**にまたがってスタックを一括展開・管理する（AWS Organizationsと緊密に統合）。
- **DeletionPolicy**：スタック削除時に特定のリソースを削除せず保持する（`Retain`）か、スナップショットを取得してから削除する（`Snapshot`）かを指定し、RDSやS3のデータ意図しない消失を防止する。
- **スタックのモジュール化**：
  - **ネストされたスタック**：共通コンポーネント（VPCネットワークなど）を子スタックとして再利用する設計。
  - **クロススタック参照**：あるスタックの出力値（Export）を別のスタックでインポート（`Fn::ImportValue`）して参照する設計。
- **関連サービス**：
  - **AWS CDK**：TypeScriptやPython等のプログラミング言語でインフラを定義し、CloudFormationテンプレートを生成するフレームワーク。
  - **AWS Service Catalog**：組織で承認されたCloudFormationテンプレートをカタログ化し、利用者に必要なリソースのみをセルフサービスで安全に展開させる仕組み。

## 8.4 AWS Systems Manager (SSM)

**概要**：ハイブリッドクラウド環境におけるサーバー群の可視化、設定管理、パッチ適用、リモート操作を一元化する運用ハブ。多くの基本機能が無料で提供される。

| 機能 | 特徴とユースケース |
|---|---|
| **Session Manager** | **SSHキーの配布や踏み台（踏み台サーバー）の設置、インバウンド22番ポートの開放を一切行わず**、ブラウザやCLIからセキュアにシェル接続する。全セッションの操作ログをS3やCloudWatch Logsに記録可能。 |
| **Patch Manager** | OSやアプリケーションのセキュリティパッチ適用を自動化する。メンテナンスウィンドウと連携し、業務影響のない時間帯に準拠ルールに基づきパッチを適用・レポート出力する。 |
| **Run Command** | SSH接続を行わずに、フリート（数千台のEC2やオンプレミスサーバー）に対してコマンドやスクリプトを一括かつ並列に安全実行する。 |
| **Parameter Store** | アプリケーションの設定値やシークレット（平文・SecureString）を一元管理する階層型ストレージ（標準パラメータは無料、KMSと連携）。 |
| **State Manager** | サーバーが常に定義された望ましい状態（アンチウイルスソフトの稼働、ドメイン参加状態など）を維持するよう自動構成・追跡する。 |
| **Automation** | AMIの定期作成や障害復旧手順などをランブック（手順書）としてコード化し自動化する。AWS Configの修復アクションの実行主体としても利用される。 |
| **Inventory / Fleet Manager** | OSバージョン、導入済みソフトウェア、ネットワーク設定などの構成情報を自動収集し、GUI上でフリートの状態を一括管理する。 |

**運用の前提条件**：管理対象インスタンスに**SSM Agent**が導入されており、適切なIAMロール（`AmazonSSMManagedInstanceCore` 等）がインスタンスプロファイルとして付与されていること。また、プライベートサブネットのインスタンスからSSMへ到達するために、**NAT Gateway**経由の送信経路、または**インターフェース型VPCエンドポイント**（`ssm`／`ssmmessages`／`ec2messages`）が必要となる（プライベートサブネットからインターネットゲートウェイへは直接出られない）。

## 8.5 AWS Organizations

**概要**：複数のAWSアカウントを階層的にグループ化し、一括請求とポリシーベースのガバナンスを一元適用する管理サービス。

- **一括請求（Consolidated Billing）**：
  - 組織内の全アカウントの使用量が合算されるため、**ボリュームディスカウントの閾値を満たしやすくなる**。
  - アカウントをまたいで**リザーブドインスタンス（RI）やSavings Plansの割引枠を共有適用**できる。
- **組織単位（OU: Organizational Unit）とSCP**：
  - アカウントを用途（本番、ステージング、開発など）ごとにOUに分類し、**サービスコントロールポリシー（SCP）**を適用する。
  - **SCPの本質**：SCPは**アクセス権限を「付与」するものではなく、メンバーアカウント内で実行可能な操作の「最大の境界（上限ガードレール）」を制限するポリシー**である。
  - **制約とスコープ**：SCPはメンバーアカウントの**ルートユーザーを含むすべてのIAMユーザー・ロールに強制適用**される。ただし、**組織の管理アカウント（Management Account）には適用されない**。
- **マルチアカウント戦略の狙い**：請求の明確な分離、コンプライアンス要件の隔離、および**障害やセキュリティ侵害の影響範囲（ブラストラディウス）の極小化**。
- **AWS Control Tower**：
  - Organizations、SCP、AWS Config、CloudTrail、IAM Identity Centerなどを組み合わせ、AWSのベストプラクティスに基づいたマルチアカウント環境（**ランディングゾーン**）を自動構築・運用するオーケストレーションサービス。
  - 事前定義された**ガードレール（予防的・発見的統制）**を迅速に適用できる。

## 8.6 AWS Trusted Advisor

**概要**：AWS環境を継続的にスキャンし、ベストプラクティスに照らし合わせた改善推奨事項を自動提示するアドバイザリーサービス。

- **5つの柱**：**コスト最適化**、**パフォーマンス**、**セキュリティ**、**耐障害性**、**サービスクォータ（サービス制限）**の観点から診断を行う。
- **サポートプランによる違い**：Basic/Developerサポートでは基本的なチェック項目のみが提供される。**全チェック項目の利用およびCloudWatch・EventBridge連携には、BusinessサポートまたはEnterpriseサポートの契約が必須**となる。
- **代表的な診断例**：「使用されていないElastic IP」「アイドル状態のRDSインスタンス」「使用率の極めて低いEC2インスタンス」「パブリックアクセス可能なS3バケット」「サービスクォータの上限到達リスク」などの検知。
- **AWS Compute Optimizerとの違い**：
  - **Trusted Advisor**：環境全体を多角的に点検し、大まかな過剰プロビジョニングや設定の不備を報告する。
  - **AWS Compute Optimizer**：機械学習アルゴリズムを用いて過去のメトリクス（CPU、メモリ、ストレージ等）を詳細に分析し、**EC2、EBS、Lambda、ECS on Fargateの具体的な最適インスタンスタイプやサイズを推奨**する。

## 8.7 AWS Config

**概要**：AWSリソースの**構成変更履歴を継続的に記録**し、事前に定義した**コンプライアンスルール（あるべき状態）に準拠しているかを自動評価・監査**する構成管理サービス。

- **主なユースケースと自動修復**：
  - 「S3バケットがパブリックアクセス不可になっているか」「EBSボリュームが暗号化されているか」「セキュリティグループで不要なインバウンドポート（例：0.0.0.0/0 からのポート22）が開放されていないか」などを自動評価。
  - ルール違反を検知した場合、EventBridge通知や**Systems Manager Automationと連携した修復アクション（Remediation Action）による自動修復**が可能。
- **CloudTrailとConfigの明確な役割分担**：
  - **CloudTrail**：API呼び出しの履歴（「**誰が・いつ・何のリクエストを実行したか**」の操作ログ）。
  - **AWS Config**：リソースの構成状態そのものの時系列履歴（「**リソースがどのような設定状態にあり、ルールに適合していたか**」の構成ログ）。
- **大規模統制**：
  - **コンフォーマンスパック（Conformance Packs）**：特定のセキュリティ標準（CIS、PCI DSSなど）に準拠するためのConfigルールと修復アクションをパッケージ化して一括適用する。
  - **アグリゲータ（Aggregator）**：複数アカウント・複数リージョンの構成情報やコンプライアンス準拠状況を単一のアカウントに集約して可視化する。

## 8.8 その他の管理、監視、ガバナンスサービス一覧

| サービス | 概要 | 主な選定ポイント・キーワード |
|---|---|---|
| **AWS Service Catalog** | 承認済み製品のセルフサービス提供 | 組織で承認されたインフラ構成をエンドユーザーが必要に応じて安全にデプロイできる環境を整備する。 |
| **AWS Control Tower** | マルチアカウント基盤の自動展開 | ベストプラクティスに基づいたランディングゾーンの構築、マルチアカウントの統制とガードレール適用。 |
| **AWS License Manager** | ソフトウェアライセンスの一元管理 | EC2やオンプレミスにおけるBYOLライセンス（コア数・ソケット数・vCPU数）の準拠監視と制限（Dedicated Hostと連携）。 |
| **AWS Health Dashboard** | AWS側のインフラ障害・メンテナンス通知 | 自社のアカウントが利用している特定のリソースに影響を及ぼすイベントや定期メンテナンス情報を確認する。 |
| **AWS Compute Optimizer** | 機械学習による適正リソース推奨 | 過去の負荷履歴を分析し、EC2・EBS・Lambda・ECSの最適なサイジングを提案してコストと性能を両立させる。 |
| **AWS Well-Architected Tool** | クラウドアーキテクチャの設計診断 | 6つの柱（卓越性、セキュリティ、信頼性、性能、コスト、持続可能性）に沿った質問に回答し、リスクを可視化・改善する。 |
| **AWS Resource Groups / Tag Editor** | リソースの一括検索とタグ管理 | 複数リージョンにまたがるリソースをタグベースでグループ化し、一括設定やコスト配分タグの管理を行う。 |
| **AWS AppConfig** | アプリケーション設定・機能フラグの安全な配信 | コードの再デプロイを行わずに設定値やフィーチャーフラグを段階的かつ安全に動的反映・ロールバックする。 |
