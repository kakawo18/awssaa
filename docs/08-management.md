# 第8章 管理、モニタリング、ガバナンス

> **章の一言**：**CloudWatch＝性能（メトリクス・ログ）／CloudTrail＝誰が操作したか／Config＝設定はどうなっていたか**。この3つの役割分担は毎回出る。

---

## 8.1 Amazon CloudWatch

**一言で**：メトリクス・ログ・アラームの監視基盤。

**試験の核心**
- 標準メトリクスは**5分間隔**、**詳細モニタリングで1分間隔**（有料）。カスタムメトリクスは高解像度（1秒）も可。
- **メモリ使用率・ディスク使用量（OS内部の情報）は標準では取れない**。**CloudWatchエージェント**を入れてカスタムメトリクスとして送る＝超頻出のひっかけ。
- **ログも標準では送られない**。エージェントが必要（Lambda・ECS Fargateなどは自動）。ログの**保持期間は既定で無期限**＝コスト削減の設問では期間設定やS3エクスポートが答え。
- アラームのアクション：SNS通知、**EC2アクション（再起動・復旧・停止）**、Auto Scalingアクション。データ不足時の扱いも設定できる。
- **Logs Insights**＝ログへのクエリ。**メトリクスフィルタ**＝ログ中の文字列（例：ERROR、不正ログイン）を数値メトリクス化してアラーム。**サブスクリプションフィルタ**＝ログをリアルタイムにKinesis/Lambda/OpenSearchへ流す。
- **CloudWatch Synthetics（Canary）**＝外形監視（ユーザー目線での死活・レイテンシ）。RUMは実ユーザー計測。

## 8.2 AWS CloudTrail

**一言で**：**誰が・いつ・どのAPIを呼んだか**の記録。監査・追跡の答えは常にこれ。

- **イベント履歴は直近90日**のみ、かつ管理イベント中心。**長期保存・全リージョン・組織横断なら「証跡（Trail）」を作成してS3へ**。
- **管理イベント**（既定で記録）＝リソースの作成・変更・削除。**データイベント**（既定オフ・追加料金）＝**S3のオブジェクトレベル操作、Lambdaの実行**。「誰がこのオブジェクトを削除したか」＝データイベントを有効化。
- **ログファイル検証**＝改ざん検知。S3にはバージョニング＋オブジェクトロック、KMS暗号化、**ログ専用アカウントへ集約**が定石。
- CloudWatch Logsに送ると、メトリクスフィルタ＋アラームで**リアルタイム検知**（ルートログイン、SG変更など）。

## 8.3 AWS CloudFormation

**一言で**：インフラをテンプレート（YAML/JSON）で定義し、再現可能にする（IaC）。追加料金なし。

- **変更セット**＝適用前に差分を確認。**ドリフト検出**＝手動変更でテンプレートとズレた箇所を検出。
- **StackSets**＝**複数アカウント・複数リージョン**へ同じスタックを一括展開（Organizations統合）。
- **DeletionPolicy: Retain / Snapshot**＝スタック削除時にDBやS3を残す（データ消失事故の防止）。
- ネストされたスタック＝共通部品の再利用、クロススタック参照（Export/Import）。
- 関連：**CDK**（プログラミング言語で書きCloudFormationを生成）、**Service Catalog**（承認済みテンプレートを利用者に配布し、使えるものを制限）、**Elastic Beanstalk**（アプリ中心の自動構築）。

## 8.4 AWS Systems Manager

**一言で**：サーバー群の運用（構成・パッチ・操作）を一元化。**無料の機能が多く、正解になりやすい**。

| 機能 | 決め手になるキーワード |
|---|---|
| **Session Manager** | **SSHキー・踏み台サーバー・22番ポート開放が不要**でシェル接続、操作ログを残す（監査） |
| **Patch Manager** | OSパッチ適用の自動化・準拠レポート、メンテナンスウィンドウで実行 |
| **Run Command** | 多数のEC2/オンプレへ一斉にコマンド実行（エージェント経由） |
| **Parameter Store** | 設定値・シークレットの保管（無料、SecureStringはKMS） |
| State Manager | あるべき状態を維持（エージェント設定、ドメイン参加） |
| Automation | 運用手順（AMI作成、復旧）のランブック自動化。Configの修復アクションにも使う |
| Inventory / Fleet Manager | インストール済みソフトの棚卸し、GUIでのサーバー管理 |

**前提**：SSM Agent＋インスタンスプロファイル（IAMロール）。プライベートサブネットからはVPCエンドポイントで到達可能にする。

## 8.5 AWS Organizations

**一言で**：複数アカウントの一元管理。**一括請求とSCP**の2点が試験の本丸。

- **一括請求**：使用量を合算して**ボリュームディスカウント**、**RI/Savings Plansをアカウント間で共有**。
- **OU（組織単位）**で環境ごと（本番/開発）に分け、**SCP**で「使えるサービス・リージョンの上限」を定義。
  - SCPは**許可を与えない。上限を絞るだけ**。管理アカウントには効かない。**メンバーアカウントのルートユーザーにも効く**のが強み。
- アカウント分離の目的：請求の分離、**障害・権限の影響範囲（ブラストラディウス）の限定**、環境の完全分離。
- **AWS Control Tower**＝Organizations＋SCP＋ログ集約＋アカウント発行を**ベストプラクティス構成で自動化**（ランディングゾーン、ガードレール）。「マルチアカウント環境をゼロから素早く安全に」＝Control Tower。

---

## 8.6 AWS Trusted Advisor

**一言で**：アカウントを5観点（**コスト最適化・パフォーマンス・セキュリティ・耐障害性・サービスクォータ**）で自動点検。

- 無料枠では一部のチェックのみ。**全チェックはビジネス/エンタープライズサポート**が必要。
- 「使っていないEIP・アイドル状態のRDS・低使用率のEC2を見つけたい」「サービス上限に近づいていないか」＝Trusted Advisor。
- **Compute Optimizerとの違い**：Trusted Advisor＝広く浅い点検／**Compute Optimizer＝機械学習でEC2/EBS/Lambdaの適正サイズを推奨**。

---

## 8.7 AWS Config

**一言で**：**リソース設定の変更履歴**を記録し、**あるべき状態（ルール）に準拠しているか**を継続評価する。

- 典型：「S3バケットが公開されていないか」「EBSが暗号化されているか」「SGが0.0.0.0/0で22番を開けていないか」を**継続的にチェックし、違反を自動修復**（SSM Automationによる修復アクション）。
- **CloudTrailとの違い**：CloudTrail＝**APIコールの記録（誰が）**／Config＝**設定そのものの時系列（どうなっていたか・準拠しているか）**。
- コンフォーマンスパック（ルールの詰め合わせ）、アグリゲータで**マルチアカウント・マルチリージョンの準拠状況を集約**。
