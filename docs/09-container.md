# 第9章 コンテナ

> **章の要点**：コンテナワークロードの選定では、オーケストレーターとして「AWSネイティブで運用負荷の低い**ECS**」か「Kubernetesエコシステムとの互換性・移植性を重視する**EKS**」か、実行基盤として「サーバーレス運用の**Fargate**」か「ホスト制御や特殊ハードウェアが利用可能な**EC2**」か、という2つの評価軸で判断する。

---

## 9.1 Amazon ECS (Elastic Container Service)

**概要**：AWS独自の高可用性・スケーラブルなコンテナオーケストレーションサービス。Kubernetesの深い専門知識を必要とせず、AWSの他サービスと密接に連携できる点が特徴。

**試験対策のポイント**
- **主要な構成要素**：
  - **タスク定義（Task Definition）**：コンテナイメージ、必要なCPU/メモリ、環境変数、ポートマッピング、IAMロールなどを定義するブループリント（設計図）。
  - **タスク（Task）**：タスク定義に基づいて実行されるコンテナの実行単位。
  - **サービス（Service）**：指定された数のタスクを維持・監視し、Application Load Balancer (ALB) と連携してトラフィックを分散する仕組み。
  - **クラスター（Cluster）**：タスクやサービスが実行される論理的なグループ。
- **2つのIAMロールの違い（最頻出）**：
  - **タスクロール（Task Role）**：**コンテナ内で稼働するアプリケーション**が、S3やDynamoDBなどのAWSリソースへアクセスするために使用するIAM権限。
  - **タスク実行ロール（Task Execution Role）**：**ECSエージェントおよびFargate基盤**が、ECRからのコンテナイメージのプルや、CloudWatch Logsへのログ送信、Secrets Managerからの秘匿情報取得を行うために使用するIAM権限。
- **ALBとの連携**：
  - **動的ポートマッピング**：EC2起動タイプにおいて、タスク定義のホストポートを `0` に設定することで、同一EC2インスタンス上で同一ポートを使用する複数のコンテナタスクを競合なく稼働させ、ALBのターゲットグループへ自動登録できる。
- **スケーリング**：Service Auto Scalingにより、タスク数をCPU/メモリ使用率やALBのリクエスト数に応じて動的にスケールアウト/スケールインさせる。
- **ECS Anywhere**：オンプレミスの物理サーバーやVMをECSクラスターのノードとして登録し、AWSとオンプレミスで統一的にコンテナを管理する。

---

## 9.2 Amazon EKS (Elastic Kubernetes Service)

**概要**：標準のKubernetes環境をAWS上で実行できるマネージドサービス。

- **選定の基準**：設問に**「Kubernetes」「kubectl」「Helmチャート」「既存のKubernetesマニフェスト資産の移行」「オンプレミスや他クラウドとの共通運用（マルチクラウド）」**といった要件が含まれる場合は、EKSが第一候補となる。
- **コントロールプレーンとデータプレーン**：
  - **コントロールプレーン**：AWSがマルチAZ構成で高可用性を担保して管理する（クラスターごとに時間単位の課金が発生）。
  - **データプレーン（ワーカーノード）**：**マネージド型ノードグループ（AWSがプロビジョニング・パッチ適用を支援）**、セルフマネージド型EC2ノード、または**Fargate**から選択可能。
- **ハイブリッド展開**：
  - **EKS Anywhere**：オンプレミス環境にEKS互換のKubernetesクラスターを構築・運用する。
  - **EKS Distro**：AWS EKSで使用されているオープンソースKubernetesディストリビューション。
- **ECSとEKSの使い分け**：
  - **EKS**：Kubernetesエコシステム、オープンソースツールとの互換性、他環境への移植性を重視する場合。
  - **ECS**：運用の簡素化、AWS他サービスとのネイティブな統合、学習コストおよび管理コストの最小化を重視する場合。

---

## 9.3 AWS Fargate

**概要**：Amazon ECSおよびAmazon EKS向けに提供される**サーバーレスのコンテナ実行基盤**。基盤となるEC2インスタンスのプロビジョニング、OSパッチ適用、クラスターのサイジング管理が不要。

- **課金体系**：タスク（またはPod）に割り当てた**vCPUおよびメモリのリソース量×実行時間**に基づいて課金される。アイドル状態のサーバー費用が発生しないため、トラフィックの変動が大きいワークロードに適する。
- **コスト最適化**：**Fargate Spot**を利用することで、予備キャパシティを活用し最大70%の割引が適用される（中断耐性のあるバッチ処理等に最適）。
- **特徴と制限事項**：
  - 基盤サーバーへのSSH接続は不可（対話型操作には**ECS Exec**を利用）。
  - 特権（privileged）コンテナの実行やデーモンセット形式の常駐管理には制限がある。
  - エフェメラル（一時）ストレージはタスクごとにデフォルト20GB（最大200GBまで拡張可能）。永続データが必要な場合は**Amazon EFS**をマウントして利用する。
- **EC2起動タイプを選択すべきケース**：
  - GPUインスタンスが必要な機械学習ワークロード。
  - 特殊なカーネルパラメータの調整やカスタムAMIが必要な場合。
  - 既存のEC2リザーブドインスタンスやSavings Plansの割引枠を最大限に流用したい場合。
  - 極めて高密度にコンテナを集約し、インフラコストを限界まで最適化したい場合。

## 9.4 Amazon ECR (Elastic Container Registry)

**概要**：高可用性・高耐久性を備えたフルマネージド型のDocker/OCIコンテナイメージプライベートレジストリ。

- **イメージ脆弱性スキャン**：
  - **基本スキャン（Basic Scanning）**：イメージプッシュ時にCVE（共通脆弱性識別子）データベースと照合してスキャンを実施。
  - **拡張スキャン（Enhanced Scanning）**：**AWS Inspector**と統合し、プッシュ時だけでなく継続的な脆弱性検出を行う。
- **ライフサイクルポリシー**：古いタグなしイメージや特定世代を超えた古いイメージを自動削除し、ストレージコストを削減する。
- **マルチリージョン展開**：クロスリージョンおよびクロスアカウントのイメージレプリケーションに対応し、各リージョンのコンテナ起動時のプル遅延を最小化する。
- **ネットワークセキュリティ**：IAMポリシーおよびリポジトリポリシーによるアクセス制御に対応。VPC内からは**インターフェース型VPCエンドポイント（PrivateLink）**を経由して、インターネットに出ることなくセキュアにイメージを取得できる。

## コンピューティングサービスの選定フロー

| 要件・特徴 | 最適なコンピューティングサービス |
|---|---|
| イベント駆動、実行時間数秒〜15分以内、インフラ管理不要、リクエスト数連動 | **AWS Lambda** |
| コンテナ化されたワークロード、Kubernetes固有機能は不要、運用負荷を最小化 | **Amazon ECS on AWS Fargate** |
| コンテナワークロード、**Kubernetes/kubectl/Helm資産の流用**、マルチクラウド前提 | **Amazon EKS** |
| コンテナワークロード、**GPU利用・特殊なカーネル設定・RI適用によるコスト追求** | **Amazon ECS / EKS on EC2** |
| コンテナ化されたWebアプリ・APIを、ロードバランサーやSSL証明書を含め迅速に公開 | **AWS App Runner**（※2026年4月30日に新規受付終了。後継はECS Express Mode） |
| OSへのフルアクセス権限、レガシーバイナリ、特定ハードウェア依存、ライセンス持ち込み | **Amazon EC2** |
| 15分を超える長時間の並列バッチ計算、キューイングとEC2/Spotの自動スケール | **AWS Batch** |
