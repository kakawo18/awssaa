# 第9章 コンテナ

> **章の一言**：**「Kubernetesという単語があるか」でECSとEKSが決まり、「サーバー管理をしたくない」でFargateが決まる。**この2問だけで大半が解ける。

---

## 9.1 Amazon ECS

**一言で**：AWS独自のコンテナオーケストレーション。**Kubernetesの知識が不要**でAWSサービスとの統合が密。

**試験の核心**
- 構成：**タスク定義**（コンテナの設計図：イメージ、CPU/メモリ、ポート、ロール）→**タスク**（実行単位）→**サービス**（タスク数を維持し、ALBと連携）→**クラスター**。
- **2つのIAMロールの違いが頻出**：
  - **タスクロール**＝コンテナ内のアプリがS3やDynamoDBにアクセスするための権限。
  - **タスク実行ロール**＝ECSエージェントがECRからイメージを取得し、CloudWatch Logsへ出力するための権限。
- 起動タイプ：**EC2**（自分でインスタンス群を管理、コスト最適化やGPU・特殊要件向け）／**Fargate**（サーバー管理なし）。
- ALBの**動的ポートマッピング**で1つのEC2に同じコンテナを複数配置可能。
- サービスAuto ScalingでタスクをCPU/メモリ/ALBリクエスト数に応じて増減。
- **ECS Anywhere**＝オンプレのサーバーをECSで管理。

---

## 9.2 Amazon EKS

**一言で**：マネージドKubernetes。

- 決め手は**「Kubernetes」「kubectl」「Helm」「既存のK8sマニフェスト」「マルチクラウド/オンプレと同じ方法で運用したい」**という記述。
- コントロールプレーンはAWSがマルチAZで管理（**時間課金がかかる**）。データプレーンは**マネージドノードグループ／セルフマネージドノード／Fargate**。
- **EKS Anywhere**＝オンプレで同じEKSを、**EKS Distro**＝AWSが使うK8sディストリビューション。
- ECSとの比較：移植性・エコシステム＝EKS／**シンプルさ・AWS統合・運用コストの低さ＝ECS**。

---

## 9.3 AWS Fargate

**一言で**：ECS/EKSの**サーバーレス実行環境**。EC2インスタンスの管理・パッチ・スケーリングが不要。

- 課金は**タスクに割り当てたvCPU・メモリ×実行時間**。アイドルなEC2の無駄がない。
- **Fargate Spot**で最大70%削減（中断可のバッチ向け）。
- 制約：インスタンスへのSSH不可（→ECS Exec）、特権コンテナやデーモンセット的な使い方が不可、GPUは不可、インスタンスストア相当は一時ストレージ（20〜200GB）。
- **EC2起動タイプを選ぶ理由**：GPU、特殊なカーネル設定、既存のRI/Savings Plansの活用、極端に高密度でのコスト最適化。

---

## 9.4 Amazon ECR

**一言で**：コンテナイメージのプライベートレジストリ。

- **イメージスキャン**（基本＝プッシュ時、拡張＝Inspector連携で継続スキャン）。
- **ライフサイクルポリシー**で古いイメージを自動削除＝ストレージコスト削減。
- **クロスリージョン/クロスアカウントレプリケーション**でマルチリージョン展開を高速化。
- アクセス制御はIAM（＋リポジトリポリシー）。VPC内からはインターフェースエンドポイント経由でプライベートに取得。

## コンピューティング全体の選択フロー（頻出）

| 問題文のキーワード | 答え |
|---|---|
| イベント駆動、数秒〜数分、運用ゼロ、実行時間分だけ課金 | **Lambda** |
| コンテナ、Kubernetesの記述なし、AWS統合、運用を軽く | **ECS on Fargate** |
| コンテナ、**Kubernetes/kubectl/Helm**、既存資産、マルチクラウド | **EKS** |
| コンテナだが**GPU・特殊要件・RI活用でコスト最適化** | ECS/EKS on **EC2** |
| コンテナ化済みのWebアプリを**URLまで最速で** | **App Runner** |
| OSレベルの制御、レガシーアプリ、ライセンス | **EC2** |
| 15分を超える大量のバッチ計算 | **AWS Batch** |
