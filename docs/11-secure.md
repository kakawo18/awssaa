# 第11章 第1分野：セキュアなアーキテクチャの設計（出題比率 30%）

> **章の要点**：本章では第1部で習得したセキュリティ知識を、「ビジネス・セキュリティ要件から最適な構成を導く判断フロー」へと統合する。設計上の判断基準としては、**「静的認証情報を排除する」「保管時および転送時の暗号化を徹底する」「パブリック露出を排除する」「最小権限の原則を適用する」**という4大原則を常に基準とする。章末の設計ケースを通じて、ネットワーク経路・IAM・リソースベースポリシー・暗号鍵（KMS）の各レイヤーにおける認可を明確に分離して考察する力を養う。

**設計ケースの読み方（第11〜14章共通）**：要件 → 前提となる絶対条件 → 検討候補 → 不採用候補とその理由 → 採用アーキテクチャ → 運用上の留意点・制約 → 条件変更時の再評価、の順序で論理展開を追う。各サービスの基本仕様については第1部の該当章を参照すること。

## 11.1 アクセス管理

### 認証主体の種別に応じたサービス選定
| 認証の対象（主体） | 最適なサービス・方式 |
|---|---|
| AWS環境を操作する従業員・運用者 | **IAM Identity Center**（既存の企業IdPとSAML/OIDC連携） |
| AWS上で稼働するアプリケーション（EC2/ECS/Lambda） | **IAMロール**（永続的なアクセスキーを排除し、一時認証情報を使用） |
| アプリケーションのエンドユーザー（一般消費者） | **Amazon Cognito ユーザープール** |
| AWSリソースへ直接一時アクセスを行うモバイル・Webクライアント | **Amazon Cognito IDプール（フェデレーションID）** |
| オンプレミスActive Directoryのドメインユーザー | **AD Connector** または **AWS Directory Service for Microsoft AD** |
| 外部委託先や別アカウントからのアクセス | **クロスアカウントIAMロール**（なりすまし防止のため**外部ID（External ID）**を併用） |

### 認可制御と権限境界の設計
| 要件・ガバナンス目的 | 採用すべき方式・機能 |
|---|---|
| 組織（Organizations）全体で利用可能なサービスやリージョンを強制制限 | **サービスコントロールポリシー（SCP）** |
| 委譲された開発者が自身の権限を超える強力なIAMを作成することを防止 | **アクセス許可境界（Permissions Boundary）** |
| 自アカウント内の特定リソース（S3、KMS等）へのアクセスを他アカウントに直接許可 | **リソースベースポリシー** |
| 意図せず外部（別アカウントやインターネット）に公開されているリソースの特定 | **IAM Access Analyzer** |
| 付与された過剰な権限を棚卸しし、最小権限に最適化するための根拠データ取得 | **IAM Access Advisor**（サービスごとの最終アクセス日時を確認） |
| 特権操作や特定APIの実行時にMFA認証を強制 | IAMポリシーの条件キー `aws:MultiFactorAuthPresent: true` |

**アクセス管理の設計原則**：
- ルートユーザーは初期セットアップ後に施錠（MFA必須、アクセスキー削除）し、日常業務では使用しない。
- 人間のアクセスにはIAM Identity Centerによるシングルサインオン、システムにはIAMロールを徹底する。
- 永続的な認証情報（APIキー、DBパスワード）はコードに埋め込まず、Secrets ManagerまたはParameter Storeに格納する。
- ポリシー評価ロジックにおいて、**「明示的な拒否（Explicit Deny）」はすべての許可に優先する**特性を理解する。

## 11.2 データ保護

### 保管時の暗号化（Encryption at Rest）
| 暗号化要件 | 推奨される方式・キータイプ |
|---|---|
| 追加料金やキー管理の手間をかけずに標準的な暗号化を適用 | **SSE-S3**（S3の既定。KMSを使うSSE-KMSは、AWSマネージドキー `aws/s3` でもKMSのリクエスト料金がかかる） |
| キーのアクセス権限、自動ローテーション、CloudTrailでの利用監査を自社で厳密に制御 | **カスタマー管理キー（CMK）によるSSE-KMS** |
| 他の利用者と共有しない**専用（シングルテナント）HSM**で、鍵を顧客が専有管理することが必須 | **AWS CloudHSM**（FIPSのレベル3は現在KMSも満たすため、それだけでは決め手にならない） |
| 既存の非暗号化リソース（EBS、RDS等）を暗号化 | **スナップショット取得 → 暗号化を有効にしてコピー → 新規ボリューム/インスタンスへ復元** |
| 複数リージョンにまたがる暗号化データを同一の鍵で復号・レプリケーション | **KMSマルチリージョンキー** |

### 転送時の暗号化（Encryption in Transit）
- **Web通信の保護**：AWS Certificate Manager (ACM) でパブリック証明書を発行し、CloudFrontやALBにアタッチしてTLS暗号化を終端する。
- **ハイブリッド接続の保護**：
  - AWS Site-to-Site VPN（IPsec暗号化）を利用する。
  - AWS Direct Connectは**標準状態では平文通信**であるため、トラフィックの暗号化が必要な場合はDirect Connect経由でVPN（IPsec）を構築するか、MACsec対応ポートを利用する。
- **ストレージアクセスの保護**：S3バケットポリシーで `"aws:SecureTransport": "false"` の通信を明示的にDenyし、HTTPS接続のみを強制する。

### データのライフサイクル保護と耐改ざん性
| 要件・脅威 | 推奨される対策 |
|---|---|
| 意図しない削除や誤操作からのオブジェクト保護 | S3バージョニング ＋ **MFA Delete**、CloudFormation `DeletionPolicy: Retain` |
| 法的規制に基づく変更・削除防止（WORM要件） | **S3 オブジェクトロック（コンプライアンスモード）**、**AWS Backup Vault Lock** |
| ストレージ内に個人情報（PII）や機密データが散在していないかの網羅的調査 | **Amazon Macie** |
| ランサムウェア感染やアカウント全体の侵害への対策 | バックアップデータを**別アカウントの隔離されたBackup Vault**へクロスアカウントレプリケーション |

## 11.3 多層防御（Defense in Depth）

### 階層別のセキュリティ統制
| 防御層 | 導入すべきセキュリティ手段 |
|---|---|
| **エッジ（エッジロケーション）** | **AWS Shield**（DDoS防御）、**AWS WAF**（SQLi、XSS、レート制限）、**CloudFront**（オリジンの隠蔽、地理的制限） |
| **ネットワーク境界** | パブリック/プライベートサブネットの完全分離、**ステートレスなNACL（L3/L4 IP遮断）**、**ステートフルなセキュリティグループ**、AWS Network Firewall（ドメイン名フィルタリング） |
| **ホスト・OS** | Systems Manager Patch Managerによるパッチ適用、**Session Managerによる踏み台・SSHキーの排除**、**Amazon Inspector**による脆弱性スキャン |
| **アプリケーション** | CognitoユーザープールやLambdaオーソライザーによるJWT検証、API Gatewayのスロットリング制限 |
| **データ** | KMSによるデータ暗号化、S3ブロックパブリックアクセス、最小権限のリソースベースポリシー |
| **検知・分析** | **CloudTrail**（操作履歴監査）、**AWS Config**（構成変化の監視・修復）、**GuardDuty**（脅威インテリジェンス検知）、**Security Hub**（一元集約とスコアリング） |

**多層防御におけるベストプラクティス構成（3層アーキテクチャ）**：
- ALBをパブリックサブネット、アプリケーションサーバー（EC2/ECS）をプライベートサブネット、データベース（RDS）を独立したデータベース専用プライベートサブネットに配置する。
- セキュリティグループのインバウンドルールにはCIDRブロックではなく、**上位レイヤーのセキュリティグループIDを送信元（Source）として指定（連鎖）**させる（例：DBのSGは「AppのSGからの通信のみ許可」）。

## 11.4 責任共有モデル（Shared Responsibility Model）

**AWSは「クラウドのセキュリティ（Security OF the Cloud）」、利用者は「クラウドにおけるセキュリティ（Security IN the Cloud）」を担う。**

| 責任対象項目 | 責任主体 |
|---|---|
| データセンターの物理的セキュリティ、サーバーハードウェア、ハイパーバイザー | **AWS** |
| フルマネージドサービス（S3、DynamoDB、Lambda等）のホストOS、パッチ適用 | **AWS** |
| **EC2インスタンスのゲストOS、ミドルウェア、アプリケーションのパッチ適用** | **利用者** |
| **RDSのDBエンジンパッチの適用スケジュール管理と判断**（自動適用の設定は利用者） | **利用者**（保守の実行自体はAWS） |
| **データの暗号化設定（保管時・転送時）、データ分類、機密性管理** | **利用者** |
| **IAMのユーザー・権限設計、セキュリティグループやNACLのルール設定** | **利用者** |
| グローバルインフラストラクチャ（リージョン、AZ、エッジ）の物理的冗長性 | **AWS** |
| **独自アプリケーションのコード脆弱性対策（SQLインジェクション、XSS等）** | **利用者** |

**判断の原則**：
- サービスのマネージドレベルが高くなるほど、基盤管理に関するAWS側の責任範囲が広がる（EC2 → RDS → ECS Fargate → Lambda / S3）。
- ただし、**「データそのものの保護」と「アクセス権限（IAM/ネットワーク）の設定責任」は、どのようなサービスを利用していても常に利用者に帰属する**。

## 11.5 設計ケーススタディ：機密データへの安全な内部アクセス

### 要件定義
- Amazon S3上に格納された機密データを、プライベートサブネット内のEC2インスタンス上で動作する業務アプリケーションからのみ読み書きする。
- 通信経路は一切パブリックインターネットを経由させない。
- 社内管理者や他のインスタンスを含む第三者による直接的なデータアクセスを遮断する。

### 前提・制約条件（絶対条件）
1. 通信経路がAWSバックボーンネットワーク内に閉じており、インターネットを経由しないこと。
2. 対象アプリケーション専用の実行主体以外からの読み書きを厳密に拒絶すること。
3. 保存データがカスタマー管理キーにより暗号化されていること。

### 検討候補と不採用理由
- **NAT Gateway 経由でのアクセス**：S3のパブリックIPへインターネット経由で通信するため「閉域通信」の要件を満たさない。またデータ転送料金が発生する。
- **IAMアクセスキーをアプリケーションに直接埋め込む**：認証情報の漏洩リスクが高く、ローテーション運用が困難であるため不適。
- **セキュリティグループによるS3アクセス制御**：S3はVPC外のマネージドサービスであり、EC2のセキュリティグループで直接S3の認可を制御することはできない。

### 採用アーキテクチャ（階層別アプローチ）

| 防御層 | 採用技術・設定内容 | 遮断・防止するリスク |
|---|---|---|
| **ネットワーク経路** | **S3用ゲートウェイ型VPCエンドポイント**をVPCに設定し、ルートテーブルを更新 | インターネットを経由するデータ転送の排除 |
| **主体の認証** | EC2インスタンスプロファイルに**IAMロール**を関連付け | 静的認証情報の漏洩リスクの排除 |
| **主体の認可** | IAMロールのポリシーで、当該S3バケットに対する最小限のAPI（`s3:GetObject`, `s3:PutObject` 等）のみ許可 | アプリケーションの侵害時における過剰権限行使の防止 |
| **リソース側の認可（経路制限）** | S3バケットポリシーで、条件キー `aws:sourceVpce` が指定したVPCエンドポイントIDと一致しない通信をすべて明示的Deny | 外部ネットワークや別VPCからの不正なアクセス経路の遮断 |
| **リソース側の認可（主体制限）** | バケットポリシーで、`aws:PrincipalArn` が指定のEC2用IAMロール以外からのアクセスをDeny。同時に適切なKMS暗号化ヘッダーを伴わないPutObjectをDeny | 同一エンドポイントを経由する他インスタンスや管理者コンソールからの不正アクセス防止 |
| **暗号鍵の認可** | **AWS KMS カスタマー管理キー（CMK）**によるSSE-KMS。キーポリシーにて、指定のIAMロールにのみ `kms:Decrypt`（読み取り時）および `kms:GenerateDataKey`（書き込み時）を許可 | 暗号化データの漏洩時における第三者による無断復号の防止 |

### 運用上の留意点と制約
- S3バケットポリシーで `aws:sourceVpce` による拒否条件を設定すると、AWSマネジメントコンソールからの直接閲覧も遮断される。運用監視やデータ確認が必要な場合は、同一VPC内の踏み台環境を経由するか、除外条件（管理ロールのARN等）を慎重に定義する必要がある。
- KMSキーポリシーにおいて、書き込み処理には `kms:GenerateDataKey`、読み取り処理には `kms:Decrypt` の権限が必須となる（`kms:Decrypt` のみではオブジェクトの書き込みに失敗する点に留意）。

### 条件変更時の再評価

| 変更された要件 | 設計変更点 | 技術的根拠 |
|---|---|---|
| オンプレミス環境のバッチサーバーからも同一バケットへ閉域アクセスを行いたい | **インターフェース型VPCエンドポイント（S3 on PrivateLink）**を導入し、Direct Connect/VPN経由で接続 | ゲートウェイ型VPCエンドポイントはオンプレミスから直接到達できないため（→第3章 3.3）。 |
| 外部のビジネスパートナーへ特定オブジェクトを安全に一時共有したい | 有効期限付きの**S3事前署名URL（Presigned URL）**を発行して受け渡す。※共有対象ファイルは閉域バケットポリシーが適用されない専用の共有バケットへ配置 | 永続的なIAMロールやバケットポリシーを外部に開放することは最小権限に反するため。事前署名URLであってもバケットポリシーの明示的Denyは回避できない。 |
| 通信は届いているが「HTTP 403 Access Denied」が発生する | ネットワーク経路ではなく、**認可層（IAMポリシー、バケットポリシー、KMSキーポリシー）**の権限設定を切り分けて確認する | 403エラーはネットワーク到達が成立した上で認可が失敗したことを意味するため（→第0章 0.4）。 |
