# 第11章 第1分野：セキュアなアーキテクチャの設計（出題比率 30%）

> **この章の使い方**：第1部の知識を「要件 → 選ぶもの」の**判断フロー**に組み替える。迷ったら**「認証情報を置かない」「暗号化する」「公開しない」「最小権限」**の4原則に合う選択肢を選ぶ。章末の**設計ケース**で、経路・IAM・リソースポリシー・暗号鍵の権限を分けて考える練習をする。

**設計ケースの読み方（第11〜14章共通）**：要件→絶対条件→候補→条件を満たさない候補と理由→採用構成→残る制約→条件を1つ変えた再検討、の順で読む。1ケースに新しいサービスを詰め込まず、詳しいサービス説明は第1部の該当章を参照する。

## 11.1 アクセス管理

**誰の認証か、で使うサービスが決まる**
| 主体 | サービス |
|---|---|
| AWSを操作する人（社員） | IAM Identity Center（＋既存IdP） |
| AWS上で動くプログラム（EC2/Lambda/ECS） | **IAMロール**（アクセスキーは使わない） |
| アプリを使う一般ユーザー（顧客） | Cognito ユーザープール |
| 一時的にAWSリソースへ触るモバイルアプリ | Cognito IDプール（一時認証情報） |
| オンプレのWindowsユーザー | AD Connector / Managed Microsoft AD |
| 別アカウント／外部ベンダー | クロスアカウントロール（**外部ID**を必須に） |

**権限をどう絞るか**
| 要件 | 答え |
|---|---|
| 組織全体で「使えるサービス／リージョン」を強制的に制限 | **SCP**（Organizations） |
| 委譲した開発者が自分より強い権限を作らないようにする | **アクセス許可境界** |
| 特定のリソースへのアクセスを相手アカウントに許す | リソースベースポリシー |
| 意図せず外部公開されているリソースを洗い出す | IAM Access Analyzer |
| 与えすぎた権限を削る根拠が欲しい | Access Advisor（最終アクセス日時） |
| 特定操作にMFAを必須にする | 条件キー `aws:MultiFactorAuthPresent` |

**チェックリスト（正解の型）**：ルートユーザーは封印＋MFA／人にはIAM Identity Center／システムにはロール／キーは Secrets Manager／権限は最小＋定期棚卸し／**明示的Denyは誰にも覆せない**。

## 11.2 データ保護

**保管時の暗号化（At Rest）**
| 要件 | 答え |
|---|---|
| 標準的な暗号化（運用の手間なし） | AWSマネージドキー（`aws/s3` など） |
| キーの権限・ローテーション・監査を自分で制御 | **カスタマー管理キー（CMK）** |
| 鍵をAWSにすら触らせない／FIPS 140-2 レベル3 | **CloudHSM** |
| 既存の未暗号化リソースを暗号化 | スナップショット → **暗号化コピー** → 復元（EBS/RDS共通の型） |
| 複数リージョンで同じ鍵を使いたい | KMSマルチリージョンキー |

**転送時の暗号化（In Transit）**：ACM証明書＋ELB/CloudFrontでTLS終端、VPN（IPsec）、Direct Connectは**そのままでは暗号化されない**ためVPN/MACsecを重ねる、S3は`aws:SecureTransport: false`をDenyするバケットポリシーでHTTPを禁止。

**データのライフサイクルと保全**
| 要件 | 答え |
|---|---|
| 誤削除対策 | バージョニング＋MFA削除、DeletionPolicy: Retain |
| 規制で**改変不可の保管**（WORM） | S3 オブジェクトロック（コンプライアンスモード）、Backup Vault Lock |
| 機密データがどこにあるか分からない | **Macie** |
| ランサムウェア・アカウント侵害への備え | クロスアカウント／クロスリージョンのバックアップ（別アカウントのVaultへ） |

## 11.3 多層防御（Defense in Depth）

**層ごとに「何を置くか」を言えるようにする**
| 層 | 守る手段 |
|---|---|
| エッジ | Shield（DDoS）、**WAF**（SQLi/XSS/レート制限）、CloudFront（オリジン隠蔽・地理制限） |
| ネットワーク境界 | パブリック/プライベートサブネット分離、**特定IPの遮断はL3/L4ならNACL・HTTPならWAF**、SGで最小ポート、Network Firewall（ドメイン制御） |
| ホスト | パッチ（Patch Manager）、**Session Managerで踏み台とSSHキーを廃止**、Inspectorで脆弱性検査 |
| アプリ | Cognito/Lambdaオーソライザー、API Gatewayのスロットリング |
| データ | KMS暗号化、バケットポリシー、ブロックパブリックアクセス |
| 検知・監査 | CloudTrail（誰が）、Config（設定）、GuardDuty（振る舞い）、Security Hub（集約） |

**典型の3層構成**：ALBはパブリックサブネット、EC2/ECSはプライベートサブネット、RDSは**さらに別のプライベートサブネット**。SGはチェーンで参照（ALBのSG → WebのSG → DBのSG）し、CIDRではなく**SGを送信元に指定**するのが定石。

## 11.4 責任共有モデル

**AWSは「クラウド“の”セキュリティ」、利用者は「クラウド“における”セキュリティ」**

| 項目 | 責任者 |
|---|---|
| データセンターの物理セキュリティ、ハードウェア、ハイパーバイザー | AWS |
| マネージドサービス（S3/DynamoDB/Lambda）のOS・パッチ | AWS |
| **EC2のゲストOS・ミドルウェアのパッチ** | **利用者** |
| **RDSのDBエンジンのマイナーパッチ適用タイミング**（自動適用の設定は利用者） | 利用者（実行はAWS） |
| **データの暗号化の有無・分類** | 利用者 |
| **IAMの設定、SG/NACLの設定** | 利用者 |
| ネットワークインフラの冗長性 | AWS |
| **アプリケーションの脆弱性** | 利用者 |

**覚え方**：**マネージドの度合いが上がるほどAWS側の責任が増える**（EC2 → RDS → Lambda/S3）。ただし**データとアクセス制御は常に利用者の責任**。

## 11.5 設計ケース：非公開データへ、アプリだけがアクセスする

**要件**：S3にある顧客データを、プライベートサブネットのEC2上のアプリだけが読み書きする。インターネットには一切出さない。運用担当者も直接は触れない。

**絶対条件**：(1) 通信がインターネットを経由しない、(2) アプリ以外の主体（他のEC2、外部、コンソール操作）からは読めない、(3) 保管時に暗号化。

**候補**：ゲートウェイVPCエンドポイント／NAT Gateway／IAMロール／バケットポリシー／KMS カスタマー管理キー。

**条件を満たさない候補と理由**
- NAT Gateway 経由：S3のパブリックエンドポイントへ出るので (1) を満たさない。料金もかかる。
- アクセスキーをアプリに埋め込む：認証情報を置かない原則に反する。ローテーションもできない。
- SGで制御しようとする：S3はVPC内のリソースではないので、SGでは「誰が読めるか」を決められない。

**採用構成（層ごとに1つずつ）**

| 層 | 設定 | 何を防ぐか |
|---|---|---|
| 経路 | S3 ゲートウェイエンドポイント（→第3章 3.3） | インターネット経由の通信 |
| 主体の認証 | EC2にIAMロール（アプリはSDKで自動取得） | キーの埋め込み・漏えい |
| 主体側の認可 | ロールのポリシーで対象バケットの Get/Put のみ許可 | 過剰権限 |
| リソース側の認可（経路） | バケットポリシーで `aws:sourceVpce` がそのエンドポイント以外なら Deny、パブリックアクセスブロック | 別経路からのアクセス。**主体は絞れない**（同じエンドポイントを通る同一アカウントの別ロールは通る） |
| リソース側の認可（主体） | バケットポリシーで `aws:PrincipalArn` がアプリのロール以外なら Deny。あわせて `s3:x-amz-server-side-encryption` が `aws:kms`（かつ指定キー）でない PutObject を Deny | 別ロールによる読み書き。**SSE-S3 で上書きして KMS の権限を迂回**すること |
| 暗号鍵 | SSE-KMS（カスタマー管理キー）。キーポリシーでアプリのロールだけに `kms:Decrypt`（読み取り）と `kms:GenerateDataKey`（書き込み時のデータキー生成） | 暗号化されたデータを別主体が復号すること。**書き込みには GenerateDataKey が要る**（Decrypt だけだと PutObject が AccessDenied） |

**残る制約**：バケットポリシーの `aws:sourceVpce` Deny はコンソールからのアクセスも拒否するので、運用時の閲覧は別経路（踏み台からエンドポイント経由、または一時的な例外）を設計する。KMS のキーポリシーとIAMポリシーの**両方**で許可が要る。

**条件を1つ変えると**

| 変えた条件 | 変わる判断 | 理由 |
|---|---|---|
| オンプレのバッチからも同じバケットを読む | インターフェースエンドポイント（＋VPN/DX）を追加し、バケットポリシーの条件も追加 | ゲートウェイ型はオンプレから使えない（→第3章 3.3） |
| 外部パートナーに特定ファイルを一時的に渡す | 事前署名URL（有効期限付き）。ただし**このバケットの `aws:sourceVpce` Deny は事前署名URLにも効く**ので、共有用の別バケット（またはプレフィックス単位で Deny を除外）に置いて署名する | ロールやポリシーを恒久的に開けるのは最小権限に反する。署名はバケットポリシーの明示的 Deny を回避しない |
| 「通信は届くのに403」という症状 | 経路ではなく認可（IAM／バケットポリシー／キーポリシー）を見る | 403 は到達している証拠（→第0章 0.4） |

**理解確認**：エンドポイントもロールも正しいのに、オブジェクトの取得だけ「KMS AccessDenied」になる。何を見るか。→ **KMSキーポリシー**（とIAMポリシーの `kms:Decrypt`）。S3の認可は通っているが、復号の権限が別の層にある。
