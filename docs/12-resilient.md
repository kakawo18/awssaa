# 第12章 第2分野：弾力性に優れたアーキテクチャの設計（出題比率 26%）

> **この章の使い方**：「壊れても止まらない／増えても耐える」構成を、**単一障害点（SPOF）をどう潰すか**の一問一答にする。

---

## 12.1 スケーリング

**スケールアップかスケールアウトか**
| 状況 | 答え |
|---|---|
| 負荷が変動し、可用性も欲しい | **スケールアウト（ASG＋ELB＋マルチAZ）**＝基本の正解 |
| リレーショナルDBの書き込みが重い | スケールアップ（インスタンスタイプ変更）／Aurora／シャーディング |
| DBの読み取りが重い | リードレプリカ、ElastiCache、DAX |
| スパイクが急激でインスタンス起動が間に合わない | ウォームプール、予測スケーリング、Lambda/Fargateへ移行 |

**各層のスケール手段**：Web/App＝Auto Scaling／コンテナ＝サービスAuto Scaling／Lambda＝自動（同時実行の上限に注意）／DynamoDB＝オンデマンド or Auto Scaling／Aurora＝Auto Scalingレプリカ、Serverless v2。

**ステートレス化が前提**：セッションは **ElastiCache/DynamoDB** へ、共有ファイルは **EFS/S3** へ、ローカルディスクに状態を持たない。これができて初めて自由にスケールできる。

---

## 12.2 疎結合

| 症状 | 処方 |
|---|---|
| 後段の処理が詰まると前段まで落ちる | 間に **SQS** を挟んでバッファリング |
| 1つのイベントを複数システムが必要とする | **SNSファンアウト**／EventBridge |
| サーバーのIPを直接参照している | **ELB／Route 53／サービスディスカバリ**を挟む |
| 処理の順序と再試行が複雑 | **Step Functions** |
| 同期呼び出しでタイムアウトが多発 | 非同期化（キュー＋ワーカー、ポーリングまたは通知で結果取得） |
| 巨大なモノリスの一部だけスケールしたい | マイクロサービス化（ECS/EKS/Lambda＋API Gateway） |

**キーワード**：「コンポーネント間の依存を減らす」「一方の障害が他方に波及しないように」＝**キュー／トピックを挟む**選択肢を選ぶ。

---

## 12.3 サーバーレステクノロジ

**サーバーレスの構成要素（この組み合わせが答えになりやすい）**
- 入口：**API Gateway / ALB / CloudFront**
- 処理：**Lambda / Step Functions / Fargate**
- 保存：**S3 / DynamoDB / Aurora Serverless**
- 連携：**SQS / SNS / EventBridge / Kinesis**
- 認証：**Cognito**

**選ぶ理由になる記述**：「サーバーの管理をしたくない」「使った分だけ」「アクセスが読めない／断続的」「小さなチームで運用負荷を最小に」。
**選べない理由になる記述**：「15分を超える処理」「常時高負荷で定常的（EC2のRI/SPの方が安い）」「OSレベルの制御」「特殊なライセンス」。

---

## 12.4 イベント駆動型アーキテクチャ

**トリガー元 → 典型の受け手**
| イベント | 典型構成 |
|---|---|
| S3にファイルが置かれた | S3イベント通知 → Lambda（軽い処理）／SQS（大量・順序不問）／SNS（複数宛先） |
| DynamoDBの項目が変わった | DynamoDB Streams → Lambda |
| EC2/RDSの状態が変わった、GuardDutyが検出した | EventBridge → Lambda/SNS/SSM Automation |
| 毎日決まった時刻に実行 | EventBridge Scheduler → Lambda/Step Functions/ECSタスク |
| 大量のストリーミングデータが届いた | Kinesis Data Streams → Lambda/Flink/Firehose |
| SaaSで何かが起きた | パートナーイベントバス → EventBridge |

**再試行と失敗の受け皿**：Lambda非同期は**2回リトライ＋DLQ/Destinations**、SQSは**maxReceiveCount超過でDLQ**、Step Functionsは**Retry/Catch**。「メッセージが失われないように」＝DLQを含む選択肢。ただしDLQは隔離であり、**監視して原因を直し、再処理する手順**まで含めて設計する。

## 12.5 高可用性と耐障害性

**まずSPOFを消す定型**
- 単一AZ → **マルチAZ**（ASG＋ELB、RDSマルチAZ、EFS、NAT GatewayをAZごとに）
- 単一リージョン → **マルチリージョン**（Route 53フェイルオーバー、Auroraグローバル、S3 CRR、DynamoDBグローバルテーブル）
- 単一インスタンス → ASG（min=2以上）
- 手作業の復旧 → CloudFormationで再現可能に

**DR戦略の4類型（RTO は復旧手順で、RPO は複製方式で決まる）**

| 戦略 | 中身（代表例） | RTO（復旧までの時間）を決めるもの | RPO（失うデータの幅）を決めるもの | コスト |
|---|---|---|---|---|
| バックアップ＆リストア | バックアップのみ別リージョンに保管し、被災後に構築 | 構築と復元の手順（**時間〜日**が目安） | **バックアップ間隔**（時間〜日） | 最安 |
| パイロットライト | **DBなど中核だけ複製して起動**、アプリ層は停止状態で準備（代表例） | アプリ層の起動とスケール（**数十分**が目安） | DBの複製方式（非同期なら**秒〜分**） | 安い |
| ウォームスタンバイ | **縮小版の本番が常時稼働**、被災時にスケールアップ | スケールアップとDNS切替（**数分**が目安） | 複製方式（非同期なら秒〜分） | 中 |
| マルチサイト（アクティブ/アクティブ） | 両リージョンで本番稼働 | ルーティング切替のみ（**秒〜分**） | 複製方式（同期に近いほど**ほぼゼロ**） | 最高 |

- **RPO＝失ってよいデータの時間幅**。決めるのは**バックアップの頻度**か、**レプリケーションの方式（同期／非同期）とその遅延**。**RTO＝復旧までに許容できる時間**。決めるのは**復旧手順の長さ**（起動済みか、構築が要るか、切替が自動か）。
- 戦略名だけで数値は保証されない。「パイロットライトなら RTO 10分」のような固定値ではなく、**実際の起動手順と複製方式**で決まる（→第0章 0.3）。表の時間は目安であって SLA ではない。
- 設問の「数分以内に復旧」は RTO、「データ損失は許されない」「直近数秒まで」は RPO の要件。両方短い要件ほど右の戦略（高コスト）になる。**要件を満たす中で最も左（安い）を選ぶ**。
- リージョン切り替えは **Route 53フェイルオーバー**（DNS、TTL分の遅れ）か **Global Accelerator**（数十秒、静的IP）。

**その他の耐障害性パターン**：ELBヘルスチェック＋ASGの自動入れ替え、複数AZへのインスタンス均等配置、EBSスナップショットとAMIの定期取得（DLM／AWS Backup）、指数バックオフによる再試行、冪等性の確保（SQSの再配信は標準でもFIFOでも起こる前提で、ワーカー側が同じ処理を2回実行しないようにする→第6章 6.1）。

## 12.6 設計ケース：障害の種類ごとに何を変えるか

**要件**：ALB＋ASG（EC2）＋RDS の3層Webアプリ。「インスタンス障害」「AZ障害」「リージョン障害」「誤削除」のそれぞれに備えたい。RTO 1時間、RPO 15分。コストは要件を満たす範囲で最小。

**絶対条件**：どの障害でも1時間以内に再開し、失うデータは15分以内。

**候補と、障害の種類ごとに効くもの／効かないもの**

| 障害 | 効く対策 | 効かない対策と理由 |
|---|---|---|
| インスタンス障害 | ASG（min 2以上、複数AZ）＋ELBヘルスチェック | RDSマルチAZ：DBではなくアプリ層の話 |
| AZ障害 | 複数AZのASG、**RDSマルチAZ**、AZごとのNAT | リードレプリカ：手動昇格で自動復旧しない |
| リージョン障害 | 別リージョンへのバックアップコピー or クロスリージョンレプリカ、Route 53 フェイルオーバー | マルチAZ：同じリージョン内の対策 |
| **誤削除・誤更新** | **バックアップ／PITR／スナップショット**、S3バージョニング | マルチAZ・レプリカ：**削除も複製される**（→第0章 0.2） |

**採用構成**：複数AZの ASG＋ALB、RDS マルチAZ（AZ障害の自動復旧）、自動バックアップで PITR（誤削除に備える。RPO 15分は PITR の連続バックアップで満たせる）、スナップショットの別リージョンコピー（リージョン障害時はバックアップ＆リストアで RTO 1時間以内に構築できるか手順で確認）。

**残る制約**：リージョン障害時の RTO 1時間は「構築手順を自動化（CloudFormation）してあること」が前提。手作業なら満たせない。リージョン障害時の RPO は**スナップショットコピーの間隔**で決まり、15分を満たすには**クロスリージョンリードレプリカ**か **Aurora グローバルデータベース**に上げる必要がある。

**条件を1つ変えると**

| 変えた条件 | 変わる判断 | 理由 |
|---|---|---|
| RTO 5分・RPO 1分（リージョン障害でも） | ウォームスタンバイ以上＋Aurora グローバルデータベース | バックアップからの構築では RTO/RPO とも満たせない |
| 誤削除への備えだけでよい（可用性要件なし） | 単一AZ＋自動バックアップ＋バージョニング | マルチAZは誤削除に効かず、要件がなければ費用だけ増える |
| データ損失は一切許されない（RPO 0） | 同期レプリケーション（マルチAZ）＋リージョン間はグローバルデータベースでも RPO 0 は保証されないと明記 | 非同期の複製方式では RPO 0 にならない |

**理解確認**：「マルチAZにしてあるので、誤ってテーブルを DROP しても即座に復旧できる」は正しいか。→ **誤り**。DROP はスタンバイにも同期される。復旧はバックアップからの PITR で、DROP 直前の時点へ戻す。
