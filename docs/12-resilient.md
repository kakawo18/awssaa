# 第12章 第2分野：弾力性に優れたアーキテクチャの設計（出題比率 26%）

> **この章の使い方**：「壊れても止まらない／増えても耐える」構成を、**単一障害点（SPOF）をどう潰すか**の一問一答にする。

---

## 12.1 スケーリング

**スケールアップかスケールアウトか**
| 状況 | 答え |
|---|---|
| 負荷が変動し、可用性も欲しい | **スケールアウト（ASG＋ELB＋マルチAZ）**＝基本の正解 |
| リレーショナルDBの書き込みが重い | スケールアップ（インスタンスタイプ変更）／Aurora／シャーディング |
| DBの読み取りが重い | リードレプリカ、ElastiCache、DAX |
| スパイクが急激でインスタンス起動が間に合わない | ウォームプール、予測スケーリング、Lambda/Fargateへ移行 |

**各層のスケール手段**：Web/App＝Auto Scaling／コンテナ＝サービスAuto Scaling／Lambda＝自動（同時実行の上限に注意）／DynamoDB＝オンデマンド or Auto Scaling／Aurora＝Auto Scalingレプリカ、Serverless v2。

**ステートレス化が前提**：セッションは **ElastiCache/DynamoDB** へ、共有ファイルは **EFS/S3** へ、ローカルディスクに状態を持たない。これができて初めて自由にスケールできる。

---

## 12.2 疎結合

| 症状 | 処方 |
|---|---|
| 後段の処理が詰まると前段まで落ちる | 間に **SQS** を挟んでバッファリング |
| 1つのイベントを複数システムが必要とする | **SNSファンアウト**／EventBridge |
| サーバーのIPを直接参照している | **ELB／Route 53／サービスディスカバリ**を挟む |
| 処理の順序と再試行が複雑 | **Step Functions** |
| 同期呼び出しでタイムアウトが多発 | 非同期化（キュー＋ワーカー、ポーリングまたは通知で結果取得） |
| 巨大なモノリスの一部だけスケールしたい | マイクロサービス化（ECS/EKS/Lambda＋API Gateway） |

**キーワード**：「コンポーネント間の依存を減らす」「一方の障害が他方に波及しないように」＝**キュー／トピックを挟む**選択肢を選ぶ。

---

## 12.3 サーバーレステクノロジ

**サーバーレスの構成要素（この組み合わせが答えになりやすい）**
- 入口：**API Gateway / ALB / CloudFront**
- 処理：**Lambda / Step Functions / Fargate**
- 保存：**S3 / DynamoDB / Aurora Serverless**
- 連携：**SQS / SNS / EventBridge / Kinesis**
- 認証：**Cognito**

**選ぶ理由になる記述**：「サーバーの管理をしたくない」「使った分だけ」「アクセスが読めない／断続的」「小さなチームで運用負荷を最小に」。
**選べない理由になる記述**：「15分を超える処理」「常時高負荷で定常的（EC2のRI/SPの方が安い）」「OSレベルの制御」「特殊なライセンス」。

---

## 12.4 イベント駆動型アーキテクチャ

**トリガー元 → 典型の受け手**
| イベント | 典型構成 |
|---|---|
| S3にファイルが置かれた | S3イベント通知 → Lambda（軽い処理）／SQS（大量・順序不問）／SNS（複数宛先） |
| DynamoDBの項目が変わった | DynamoDB Streams → Lambda |
| EC2/RDSの状態が変わった、GuardDutyが検出した | EventBridge → Lambda/SNS/SSM Automation |
| 毎日決まった時刻に実行 | EventBridge Scheduler → Lambda/Step Functions/ECSタスク |
| 大量のストリーミングデータが届いた | Kinesis Data Streams → Lambda/Flink/Firehose |
| SaaSで何かが起きた | パートナーイベントバス → EventBridge |

**再試行と失敗の受け皿**：Lambda非同期は**2回リトライ＋DLQ/Destinations**、SQSは**maxReceiveCount超過でDLQ**、Step Functionsは**Retry/Catch**。「メッセージが失われないように」＝DLQを含む選択肢。

---

## 12.5 高可用性と耐障害性

**まずSPOFを消す定型**
- 単一AZ → **マルチAZ**（ASG＋ELB、RDSマルチAZ、EFS、NAT GatewayをAZごとに）
- 単一リージョン → **マルチリージョン**（Route 53フェイルオーバー、Auroraグローバル、S3 CRR、DynamoDBグローバルテーブル）
- 単一インスタンス → ASG（min=2以上）
- 手作業の復旧 → CloudFormationで再現可能に

**DR戦略の4類型（RTO/RPOで一意に決まる）**
| 戦略 | 中身 | RTO/RPO | コスト |
|---|---|---|---|
| バックアップ＆リストア | バックアップのみ保管し、被災後に構築 | 数時間〜数日 | 最安 |
| パイロットライト | **DBだけ複製して起動**、その他は停止状態で準備 | 数十分 | 安い |
| ウォームスタンバイ | **縮小版の本番が常時稼働**、被災時にスケールアップ | 数分 | 中 |
| マルチサイト（アクティブ/アクティブ） | 両リージョンで本番稼働 | ほぼゼロ | 最高 |

- **RPO＝どこまでのデータ損失を許容できるか**（バックアップ間隔）、**RTO＝どれだけ早く復旧するか**（構築時間）。問題文の「数分以内に復旧」「データ損失は許されない」を拾って戦略を決める。
- リージョン切り替えは **Route 53フェイルオーバー**（DNS、TTL分の遅れ）か **Global Accelerator**（数十秒、静的IP）。

**その他の耐障害性パターン**：ELBヘルスチェック＋ASGの自動入れ替え、複数AZへのインスタンス均等配置、EBSスナップショットとAMIの定期取得（DLM／AWS Backup）、指数バックオフによる再試行、冪等性の確保（SQS標準の重複対策）。
