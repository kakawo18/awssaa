# 第13章 第3分野：高パフォーマンスなアーキテクチャの設計（出題比率 24%）

> **この章の使い方**：性能問題は「**遅いのはどこか（ストレージ/CPU/DB/ネットワーク）**」を特定し、**キャッシュ・並列化・適材適所のサービス**のどれで解くかを選ぶ。

---

## 13.1 ストレージとパフォーマンス

| 症状・要件 | 打ち手 |
|---|---|
| EC2のディスクIOPSが足りない | gp3でIOPS増、io2 Block Express、**EBS最適化インスタンス**、インスタンスストア（一時データ・キャッシュ・バッファ） |
| 一時ファイル・スクラッチ領域が超高速に必要 | **インスタンスストア（NVMe）** |
| 複数サーバーで同じファイルを共有しつつ高速に | EFS（Elastic/プロビジョンドスループット） |
| HPC・機械学習で数百GB/sのスループット | **FSx for Lustre**（S3連携） |
| S3へのアップロードが遅い（海外から） | **S3 Transfer Acceleration**、マルチパートアップロード |
| S3の同一プレフィックスでスロットリング | プレフィックスを分散（3,500 PUT/5,500 GET 毎秒/プレフィックス） |
| 大量の小さなオブジェクトの読み取りが遅い | CloudFrontでキャッシュ、まとめて格納（Parquet化） |
| アーカイブなのに即時取り出しが必要 | Glacier **Instant Retrieval**（Deep Archiveは12時間） |

---

## 13.2 コンピューティングとパフォーマンス

| 要件 | 打ち手 |
|---|---|
| CPU負荷が高い／バースト枯渇（T系のCPUクレジット切れ） | **コンピューティング最適化（C系）へ変更**、または T系のアンリミテッドモード |
| メモリ大量（インメモリDB、ビッグデータ処理） | **メモリ最適化（R系、X系）** |
| 機械学習の学習・推論、グラフィック処理 | 高速コンピューティング（**P/G/Inf系**） |
| コストあたりの性能を上げたい | **Graviton（ARM）インスタンス**へ移行 |
| ノード間通信のレイテンシが性能を決める（HPC） | **クラスタープレイスメントグループ＋EFA＋拡張ネットワーキング** |
| Lambdaの処理が遅い | **メモリ割り当てを増やす（CPUも比例して増える）** |
| Lambdaの初回応答が遅い | **プロビジョニング済み同時実行**、SnapStart（Java）、VPC設定の見直し |
| 負荷に応じて自動で最適な台数に | Auto Scaling（ターゲット追跡） |
| インスタンスサイズが適正か分からない | **Compute Optimizer** |

---

## 13.3 データベースとパフォーマンス

「DBが遅い」は原因で分ける（→第4章 4.5）。対策は原因にしか効かない。

| 症状 | 原因 | 打ち手 | 効かないもの |
|---|---|---|---|
| 読み取りクエリが集中して遅い | 読み取り量 | **リードレプリカ**（アプリの読み取りを向ける）、Auroraリーダーエンドポイント | RDS Proxy（クエリ量は減らない） |
| 同じクエリが繰り返される | 同一結果の反復 | **ElastiCache**（遅延読み込み＋TTL、鮮度要件を確認） | レプリカ（同じクエリを実行し続ける） |
| DynamoDBの読み取りをさらに速く（マイクロ秒） | レイテンシ | **DAX**（結果整合性の読み取りに限る） | 強い整合性が要件なら不可 |
| 書き込みが限界 | 書き込み量 | シャーディング、Aurora、アクセスパターン次第でDynamoDB、書き込みのバッファ（SQS/Kinesis） | リードレプリカ（書き込みはプライマリのまま） |
| Lambdaからの接続でDBの接続数が枯渇 | 接続数 | **RDS Proxy** | リードレプリカ（接続は減らない） |
| 分析クエリが本番DBを圧迫している | 分析負荷の混在 | 分析基盤へ分離（Redshift、Athena＋S3、専用リードレプリカ） | キャッシュ（毎回違う集計にはヒットしない） |
| DynamoDBでスロットリング | ホットパーティション／容量不足 | パーティションキーの設計見直し（**ホットパーティションの解消**）、オンデマンド、GSIの追加 | DAX（書き込みのスロットリングには効かない） |
| 全文検索が遅い（LIKE検索） | クエリの種類がDBに不向き | **OpenSearch Service** | インデックス追加（部分一致には効きにくい） |
| 遅いクエリの原因が分からない | 原因未特定 | **Performance Insights** で待機イベントとSQLを特定してから対策を選ぶ | いきなりレプリカやキャッシュを足す |

## 13.4 ネットワークアーキテクチャ

| 要件 | 打ち手 |
|---|---|
| 世界中のユーザーへの配信が遅い | **CloudFront**（キャッシュ）／オリジンは1か所のままでよい |
| 非HTTPのグローバル低遅延、静的IP | **Global Accelerator** |
| 特定地域のユーザーを最寄りリージョンへ | Route 53 **レイテンシーベースルーティング** |
| オンプレとの帯域が不安定 | **Direct Connect**（＋VPNバックアップ） |
| VPC間の通信をインターネットに出したくない | VPCピアリング／**Transit Gateway**／PrivateLink |
| VPC内からS3への大量通信のデータ転送料と遅延 | **ゲートウェイVPCエンドポイント**（追加料金なし、インターネットを経由しない）。**オンプレからならインターフェース型**（有料） |
| 同一AZ内の通信を増やしてレイテンシと転送料を下げる | AZを意識した配置、クラスタープレイスメントグループ |
| 高スループットが必要なEC2 | 拡張ネットワーキング（ENA）、EFA、ジャンボフレーム（VPC内9001 MTU） |
| ユーザー近くで処理したい | Local Zones、Wavelength、CloudFront Functions／Lambda@Edge |

**キャッシュの階層（性能問題のチェック順）**：CloudFront（エッジ）→ API Gatewayキャッシュ → ElastiCache/DAX（DB手前）→ アプリ内。「まずキャッシュできないか」を疑うのが試験の思考順序。

## 13.5 設計ケース：「DBが遅い」を原因で切り替える

**要件**：ECサイトの商品ページが遅い。DBは RDS for MySQL（単一インスタンス）。ページ表示の遅延を下げたい。

**絶対条件**：在庫数は購入時に必ず最新を見る（古い在庫で売り越さない）。

**候補**：リードレプリカ／ElastiCache／RDS Proxy／スケールアップ。

**まず原因を特定する**（Performance Insights、CloudWatch の DatabaseConnections・ReadIOPS・CPU）。原因によって採用が変わる（→第4章 4.5）。

| 判明した原因 | 採用 | 条件を満たさない候補と理由 | 残る制約 |
|---|---|---|---|
| 商品一覧の**読み取りクエリが集中**（CPU 高、ReadIOPS 高） | リードレプリカを追加し、**アプリの一覧取得だけをレプリカへ向ける** | RDS Proxy：クエリ量は減らない。キャッシュ：一覧が頻繁に変わるならヒットしない | レプリカは非同期。在庫の最終確認はプライマリから読む |
| **同じ商品詳細**が繰り返し読まれている | ElastiCache（Lazy Loading＋TTL 数分） | リードレプリカ：同じクエリを実行し続ける | TTL の間は古い。在庫数はキャッシュ対象から外すか、書き込みスルーで更新 |
| Lambda（API）からの**接続数**が増えて接続エラー | RDS Proxy | リードレプリカ：接続は減らない。スケールアップ：上限は上がるが根本解決でない | Proxy 経由の接続はプライマリ向け。読み取り分散は別途 |

**条件を1つ変えると**

| 変えた条件 | 変わる判断 | 理由 |
|---|---|---|
| 在庫の最終確認も含めて全部速くしたい | 在庫の読み取りだけはプライマリ、他はレプリカ／キャッシュに分ける | 更新直後の最新が要るデータに非同期複製やキャッシュは使えない |
| DBが DynamoDB でマイクロ秒が欲しい | DAX（結果整合性の読み取りに限る） | 強い整合性の読み取りは DAX を通らない |
| 原因が「集計レポートの実行」だった | 分析を Athena/Redshift へ分離 | キャッシュもレプリカも本番の集計負荷の根本解決にならない |

**理解確認**：「遅いのでとりあえずリードレプリカを追加した」が効かないのはどんなとき？→ 原因が**接続数**（Proxy が要る）、**同一結果の反復**（キャッシュが要る）、**書き込み**（プライマリの負荷）、または**アプリの接続先を変えていない**とき。
