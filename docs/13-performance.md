# 第13章 第3分野：高パフォーマンスなアーキテクチャの設計（出題比率 24%）

> **章の要点**：システム全体の性能ボトルネックを「ストレージ」「コンピュート」「データベース」「ネットワーク」の各階層で正確に特定し、適切なスケーリング、多段キャッシング、並列化、および専用サービスの適材適所な配置によって最適化する設計手法を習得する。

---

## 13.1 ストレージとパフォーマンス

| 性能要件・課題 | 推奨される最適化アプローチ |
|---|---|
| EC2接続のEBSボリュームでディスクIOPSが不足している | **Amazon EBS gp3**（容量と独立してIOPS/スループットをプロビジョニング）、**io2 Block Express**（最高クラスのIOPS/低遅延）、**EBS最適化インスタンス**の有効化。 |
| 超低レイテンシ・高IOPSの一時ファイル領域やスクラッチ領域が必要 | ホスト直付けの**NVMeインスタンスストア**（揮発性一時ストレージ）を採用する。 |
| 複数サーバーから同時に共有マウントし、高スループットを維持したい | **Amazon EFS**（Elasticスループットまたはプロビジョンドスループット）。 |
| HPC（ハイパフォーマンスコンピューティング）や機械学習で数百GB/s規模のスループットが必要 | **Amazon FSx for Lustre**（Amazon S3バケットとリンクした並列ファイルシステム）。 |
| 海外や遠隔地からAmazon S3への大容量アップロードが遅い | **S3 Transfer Acceleration**（CloudFrontエッジロケーション経由の高速転送）および**マルチパートアップロード**の並列実行。 |
| Amazon S3の特定プレフィックスに対するリクエスト集中でスロットリングが発生 | オブジェクトキーの**プレフィックスを分散**させる（プレフィックスごとに毎秒3,500 PUT / 5,500 GETのリクエストを処理可能）。 |
| 多数の小さなオブジェクトに対する個別読み取りがボトルネック | **Amazon CloudFront**によるエッジキャッシュ、または複数ファイルをParquet等の列指向フォーマットに集約して保存。 |
| コストを抑えたアーカイブストレージでありながら、必要時にミリ秒単位での即時取り出しが必要 | **S3 Glacier Instant Retrieval**（S3 Glacier Flexible / Deep Archiveは取り出しに数時間以上要するため不適）。 |

## 13.2 コンピューティングとパフォーマンス

| ワークロード要件 | 推奨される最適化アプローチ |
|---|---|
| 常時CPU負荷が高い、またはバースト枯渇（T系インスタンスのCPUクレジット切れ） | **コンピューティング最適化インスタンス（Cファミリー）**への変更、またはT系における無制限（Unlimited）モードの有効化。 |
| インメモリキャッシュ、ビッグデータ分散処理など大量のメモリを消費 | **メモリ最適化インスタンス（Rファミリー、Xファミリー）**の採用。 |
| 機械学習のモデル学習・推論、グラフィックレンダリング | **高速コンピューティングインスタンス（GPU搭載のP/G系、AWS Trainium/Inferentia搭載系）**の採用。 |
| コストパフォーマンス（ワットパフォーマンス・価格対性能比）の最大化 | **AWS Gravitonプロセッサ（ARMアーキテクチャ）**搭載インスタンスへの移行。 |
| ノード間の超低レイテンシ通信がワークロード全体の性能を決定づける（HPC等） | **クラスタープレイスメントグループ ＋ Elastic Fabric Adapter (EFA) ＋ 拡張ネットワーキング（ENA）**の組み合わせ。 |
| AWS Lambda関数の処理速度を向上させたい | **Lambdaのメモリ割り当てを増やす**（メモリ設定に比例してCPUパワー・ネットワーク帯域が自動的に割り当てられる）。 |
| AWS Lambdaの初回起動時レイテンシ（コールドスタート）を抑えたい | **プロビジョニング済み同時実行（Provisioned Concurrency）**の設定、Java関数の場合は**SnapStart**の有効化。 |
| 負荷変動に対して過不足なく最適なインスタンス数を自動維持したい | EC2 Auto Scalingにおける**ターゲット追跡スケーリングポリシー**（CPU使用率やALBリクエスト数等）。 |
| 稼働中のインスタンスサイズが過剰または不足していないか検証したい | **AWS Compute Optimizer**による機械学習ベースの適正サイジング推奨の確認。 |

## 13.3 データベースとパフォーマンス

データベースの性能劣化は根本原因によって対処法が完全に異なる（→第4章 4.5）。誤った対策を講じてもボトルネックは解消しない。

| 性能課題・症状 | 根本原因 | 適切な対処法 | 不適切な対策とその理由 |
|---|---|---|---|
| SELECTクエリが集中し、CPU・ディスク読み取りI/Oが逼迫 | 読み取りトラフィック過多 | **リードレプリカの追加**（アプリの参照先をレプリカへ分散）、Auroraリーダーエンドポイントの活用 | **RDS Proxy**：接続をプーリングするものであり、クエリ実行負荷そのものは軽減されない。 |
| 同一のSELECTクエリ結果が頻繁に反復実行されている | 静的・準静的データの反復取得 | **Amazon ElastiCache**（Redis/Memcached）によるインメモリキャッシング（Cache-Aside / 遅延読み込み） | **リードレプリカ**：毎回DBエンジンでSQLが再実行されるため、根本的な負荷軽減にならない。 |
| Amazon DynamoDBの読み取りでマイクロ秒単位の極めて低い応答速度が必要 | ミリ秒レイテンシの限界 | **Amazon DynamoDB Accelerator (DAX)** の導入（インメモリキャッシュ） | **強い整合性の読み取り**：DAXは結果整合性のみ対応しており、強整合性クエリはDAXをバイパスする。 |
| INSERT / UPDATE処理が限界に達し、マスターDBのCPU・I/Oが飽和 | 書き込みトラフィック過多 | アプリケーションのシャーディング、**Amazon Aurora**への移行、DynamoDBへの移行、**SQS/Kinesisによる書き込みバッファリング** | **リードレプリカ**：書き込みは常にプライマリ（マスター）インスタンスで行われるため無効。 |
| サーバーレス（Lambda）からのスパイクアクセスでDBの最大接続数（Max Connections）が枯渇 | 急激なコネクション急増 | **Amazon RDS Proxy**の導入（コネクションプーリングと接続再利用） | **リードレプリカ**：レプリカを増やしてもプライマリへの接続数は削減できない。 |
| 大規模な分析・集計バッチクエリが本番トランザクションを圧迫 | OLTPとOLAPの混在 | 分析ワークロードの完全分離（**Amazon Redshift**、**Amazon Athena ＋ S3**、または分析専用リードレプリカの割り当て） | **キャッシュ**：分析クエリは条件や集計期間が毎回異なるためキャッシュヒットしない。 |
| DynamoDBで特定キーへのアクセス集中によるスロットリング | ホットパーティション | **パーティションキーの設計見直し**（ランダムサフィックスの付与等）、オンデマンドキャパシティへの変更、GSIの活用 | **DAX**：書き込みスロットリングの解消には寄与しない。 |
| 部分一致（LIKE検索）やテキスト検索クエリが極めて遅い | RDBMSの全文検索の限界 | **Amazon OpenSearch Service**への検索ワークロードオフロード | **B-treeインデックスの追加**：中間一致やあいまい検索にはインデックスが効かない。 |
| ボトルネックとなっているSQLや待機理由が特定できない | 原因の未分析 | **Amazon RDS Performance Insights**を有効化し、負荷の要因（待機イベント・クエリ）を可視化 | 原因を特定せずに安易なインスタンス増強を行うこと。 |

## 13.4 ネットワークパフォーマンスの最適化

| 要件・課題 | 推奨されるネットワーク構成 |
|---|---|
| 世界中に分散するエンドユーザーへのコンテンツ配信レイテンシを短縮 | **Amazon CloudFront**によるエッジキャッシュ（オリジンサーバーは単一リージョンに配置したままで対応可能）。 |
| 非HTTPプロトコル（TCP/UDP、ゲーム、VoIP等）でのグローバル低遅延接続、静的Anycast IP | **AWS Global Accelerator**（AWSグローバルバックボーン経由で最寄りのエッジからルーティング）。 |
| 地理的に近い最寄りのリージョンへユーザーを動的に誘導 | **Amazon Route 53 レイテンシーベースルーティング**。 |
| オンプレミスとAWS間のネットワーク遅延・帯域の安定化 | **AWS Direct Connect**（専用線接続。冗長化としてVPNバックアップを構成）。 |
| 多数のVPC間およびオンプレミス間のメッシュ通信を高速・セキュアに集約 | **AWS Transit Gateway**（ハブ＆スポーク構造で最大50Gbps/アタッチメント）。 |
| VPC内からAmazon S3への大容量データ転送の帯域確保と転送料金削減 | **ゲートウェイ型VPCエンドポイント**（NAT Gatewayを経由せずAWS内部バックボーンで高速通信、通信費無料）。 |
| 同一VPC内のインスタンス間通信で最高スループット・最低レイテンシを実現 | **クラスタープレイスメントグループ**（同一AZ内の物理的に近接したハードウェアに配置）。 |
| EC2インスタンスのネットワーク帯域（最大100Gbps〜）の最大化 | **拡張ネットワーキング（ENA）**の有効化、同一VPC内での**ジャンボフレーム（MTU 9001）**の適用。 |

**多段キャッシングアーキテクチャの階層構造**：
1. **エッジ層**：Amazon CloudFront（ユーザーの物理的最寄りで静的・動的コンテンツをキャッシュ）
2. **APIゲートウェイ層**：Amazon API Gateway キャッシュ（バックエンド呼び出しを抑止）
3. **データアクセス層**：Amazon ElastiCache / DynamoDB DAX（データベース前段でクエリ結果やセッションをインメモリ保持）
4. **アプリケーション層**：インスタンスローカルメモリ / ローカルNVMeストレージ

## 13.5 設計ケーススタディ：データベースボトルネックの原因別切り分けと対処

### 要件定義
- ECサイトの商品カタログ・購入システム（Amazon RDS for MySQL 単一インスタンス）。
- アクセス増加に伴い、商品ページおよびチェックアウト処理の応答遅延が顕著化している。
- 根本的な原因を特定し、最小限のアーキテクチャ変更で最大のレスポンス向上を図る。

### 前提・制約条件
- 商品詳細ページの閲覧は数秒程度のキャッシュ遅延を許容できる。
- ただし、**注文確定時の「在庫確認・在庫引き落とし」処理においては、絶対に古いキャッシュや遅延レプリカを参照せず、最新の確定データを参照・更新すること（売り越しの防止）**。

### 原因別の診断と最適なアーキテクチャ選定

| 診断された根本原因 | 採用するアーキテクチャ | 不採用候補とその理由 | 運用上の留意点・制約 |
|---|---|---|---|
| **商品一覧・検索の読み取りクエリ集中**（CPU使用率高、ReadIOPS高、書き込み負荷は低い） | **Amazon RDSリードレプリカを追加**し、アプリケーションの一覧表示処理のみをレプリカのエンドポイントへ向ける | **RDS Proxy**：クエリの処理量そのものは削減できないため不適。<br>**ElastiCache**：一覧のソート・絞り込み条件が多岐にわたる場合、キャッシュヒット率が低下する。 | リードレプリカは非同期複製の遅延が生じる。在庫確定処理などの整合性がクリティカルなトランザクションは必ずプライマリDBに向ける。 |
| **特定の大人気商品の詳細情報が繰り返しアクセスされている**（同一クエリの反復） | **Amazon ElastiCache（Redis）**を導入し、Lazy Loading（遅延読み込み）＋TTL設定で商品詳細をキャッシュ | **リードレプリカ**：同一の重いクエリがレプリカ側で繰り返し実行されるため、リソース消費が抑えられない。 | キャッシュ有効期限（TTL）中は商品情報の変更が即時反映されない場合がある。商品価格や在庫の変更時にキャッシュを無効化（Write-Through等）する設計が必要。 |
| **AWS Lambdaからの急激な同時呼び出しによる接続数枯渇**（`Too many connections` エラー） | **Amazon RDS Proxy**を導入し、LambdaとRDS間にコネクションプールを介在させる | **リードレプリカ**：接続先を分散しても、各インスタンスの最大接続数制限に達するため根本解決にならない。<br>**垂直スケールアップ**：メモリ増量で接続上限は増えるが、費用対効果が悪くスパイクに追従できない。 | RDS Proxy経由での接続確立により、コネクション枯渇を完全に防止できる。 |

### 条件変更時の再評価

| 変更された要件 | 設計変更点 | 技術的根拠 |
|---|---|---|
| 在庫確認も含め、ミリ秒未満（マイクロ秒）の極めて低い応答レイテンシが必須 | **Amazon DynamoDB ＋ DAX**への移行、またはElastiCacheでの在庫管理と悲観的ロック/条件付き書き込みの組み合わせ | RDBMSのディスクI/Oベースの構造ではマイクロ秒の応答を保証できないため。 |
| 夜間の日次集計レポート処理が本番DBのCPUを100%消費してサービス遅延を引き起こしている | **レポート専用のリードレプリカ**を1台配置して集計専用エンドポイントとする。データ量が増大している場合は**Amazon Redshift**へのETLを構成 | 集計クエリは毎回異なる条件で全表スキャンを伴うためキャッシュは無効。本番OLTPのプライマリDBから分析処理を完全に物理隔離する必要がある。 |
