# 第14章 第4分野：コストを最適化したアーキテクチャの設計（出題比率 20%）

> **この章の使い方**：コスト問題の正解は、ほぼ**「使った分だけ」「安いクラスへ移す」「無駄を止める」「コミットして割引」**の4パターンに収まる。**要件（性能・可用性）を落とす選択肢は不正解**であることに注意。

---

## 14.1 コスト管理

| 要件 | 答え |
|---|---|
| 何にいくらかかっているか分析、将来予測、RI/SP推奨 | **Cost Explorer** |
| 予算超過を**事前に**アラート、超過時に自動アクション | **AWS Budgets** |
| 時間単位・リソース単位の**最も詳細な**データを自分で分析 | **CUR**（S3 → Athena/QuickSight） |
| 部門・プロジェクト別に按分したい | **コスト配分タグ**（＋タグポリシーで統制） |
| 複数アカウントの請求をまとめ、割引を共有 | **Organizations 一括請求** |
| 無駄なリソース（未使用EIP、アイドルRDS、低使用率EC2）の発見 | **Trusted Advisor** |
| インスタンスの適正サイズの推奨 | **Compute Optimizer** |
| 異常な支出の自動検知 | AWS Cost Anomaly Detection |

---

## 14.2 ストレージとコスト最適化

| 状況 | 打ち手 |
|---|---|
| アクセス頻度が下がっていくデータ | **ライフサイクルポリシー**でIA→Glacier→Deep Archiveへ自動移行 |
| アクセスパターンが読めない | **S3 Intelligent-Tiering**（監視料金のみ、取り出し料金なし） |
| 再生成可能なデータ | One Zone-IA |
| 完了しなかったマルチパートアップロードの残骸 | ライフサイクルルールで中止・削除 |
| 古いバージョンやスナップショットが溜まる | 非現行バージョンの失効、**DLM/AWS Backup**の保持期間設定 |
| EBSが過剰にプロビジョニングされている | gp2→**gp3**、サイズ/IOPSの見直し、未アタッチボリュームの削除 |
| EFSのコスト | ライフサイクル管理でIAへ、One Zone |
| データ転送料が高い | CloudFrontでオフロード、**VPC内からのS3/DynamoDBはゲートウェイエンドポイント（追加料金なし、NAT処理料も不要）**、同一AZ内通信、**AZ間・リージョン間転送を減らす** |
| ログの保管費用 | CloudWatch Logsの保持期間設定、S3へエクスポートしてGlacierへ |

**覚え方**：**AWSへの受信（イン）は原則無料、送信（アウト）とAZ/リージョン間が有料**。

---

## 14.3 コンピューティングとコスト最適化

| 状況 | 打ち手 |
|---|---|
| 中断できるバッチ、CI、ビッグデータ | **スポットインスタンス**（最大90%引き、EMRのタスクノード、Fargate Spot、Batch） |
| 常時稼働が1年以上確実 | **Savings Plans**（柔軟）／**RI**（特定条件でさらに安い） |
| 開発環境が夜間・休日も動いている | **スケジュールされたスケーリング／Instance Schedulerで停止** |
| 使用率が低いインスタンスが多い | 適正サイズ変更（Compute Optimizer）、**Gravitonへ移行** |
| リクエストが断続的・少量 | **Lambda / Fargate / Aurora Serverless**（アイドル課金をなくす） |
| ライセンス費用が重い | Dedicated HostでBYOL、Linuxへの移行、Babelfish |
| 冗長化しすぎ | 可用性要件に応じたAZ数・台数の見直し（**要件を下回らない範囲で**） |

**組み合わせの定番**：ベース負荷はRI/Savings Plans、変動分はオンデマンド、バースト分はスポット。

---

## 14.4 データベースとコスト最適化

| 状況 | 打ち手 |
|---|---|
| DBが常時稼働・長期利用 | **リザーブドインスタンス（RDS/ElastiCache/Redshift/OpenSearch）** |
| 開発・検証DBが夜間も起動 | RDSの停止（最大7日で自動起動する点に注意）、Aurora Serverless v2 |
| 読み取り負荷にレプリカを増やし続けている | **ElastiCacheで肩代わり**（レプリカより安くなることが多い） |
| DynamoDBの負荷が安定している | プロビジョンドキャパシティ＋Auto Scaling（オンデマンドより安い） |
| DynamoDBに古いデータが溜まる | **TTL**で自動削除、S3へアーカイブ |
| 大きなオブジェクトをDBに入れている | **S3に本体、DBにはポインタ** |
| 分析のためだけに大きなDBを維持 | S3＋Athena、Redshift Serverless、Spectrum |
| スナップショットが増え続ける | 保持ポリシーの設定、不要な手動スナップショットの削除 |

---

## 14.5 その他のコスト削減策

- **サーバーレス・マネージドへの移行**：運用人件費まで含めた「総コスト」が下がる、という選択肢は正解になりやすい。
- **アーキテクチャでの削減**：API Gatewayから**AWSサービスを直接統合**してLambdaを省く、Step FunctionsからSDK直接呼び出し、CloudFrontのキャッシュヒット率向上、SQSの**ロングポーリング**でAPIコール削減。
- **リージョンの選択**：料金はリージョンで異なる。レイテンシ・法規制の要件がなければ安いリージョンを選ぶ。
- **Snowball vs ネットワーク転送**：大容量かつ回線が細い場合は物理移送の方が安く速い。
- **削除し忘れの回収**：未使用のEIP（アタッチされていないと課金）、古いスナップショット、停止中インスタンスに紐づくEBS、アイドルのNAT Gateway/ELB。
- **タグ付けの徹底**：可視化できないコストは削減できない。タグポリシー＋コスト配分タグ。

**試験での注意**：「最もコスト効率が高いのはどれか」の設問でも、**要件（可用性・RTO・レイテンシ）を満たさない選択肢は不正解**。まず要件を満たす候補に絞ってから、その中で最も安いものを選ぶ。
