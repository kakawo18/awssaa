# 第14章 第4分野：コストを最適化したアーキテクチャの設計（出題比率 20%）

> **章の要点**：コスト最適化は「リソースの適正サイジング（Right Sizing）」「最適な購入オプション（Savings Plans / スポット）の選択」「データライフサイクルに応じた階層化」「遊休資産の停止・削除」を軸に推進する。最も重要な原則は、**「設問で提示された要件（可用性・パフォーマンス・耐障害性・RTO/RPO）を損なう選択肢は、いくら安価であっても不正解である」**という点である。必ず要件を満たす選択肢に絞り込んだ上で、最も経済的な構成を導き出す。

---

## 14.1 コスト管理ツールの使い分け

| 管理要件・課題 | 最適なツール・機能 |
|---|---|
| 過去の利用実績分析、将来予測、リザーブドインスタンス（RI）/Savings Plansの購入推奨 | **AWS Cost Explorer** |
| 予算（コスト額・使用量・RI/SP利用率）のしきい値監視と超過時の自動アクション | **AWS Budgets**（Budgets Actionsによる通知やリソース停止） |
| 時間単位・リソース単位の**最も詳細なメタデータを含む課金ログ**をS3に出力して独自分析 | **AWS Cost and Usage Reports (CUR)**（Athena / QuickSightと連携） |
| コストを部門、プロジェクト、環境（本番/検証）ごとに正確に配賦・追跡 | **コスト配分タグ**（AWS Organizationsのタグポリシーで統制） |
| 複数アカウントの利用量を合算し、ボリュームディスカウントの適用やRI/SP割引枠の共有 | **AWS Organizations 一括請求（Consolidated Billing）** |
| 未使用のElastic IP、アイドル状態のDB、低使用率のEC2など遊休リソースの検出 | **AWS Trusted Advisor**（コスト最適化チェック項目） |
| 機械学習を用いてEC2、EBS、Lambda、ECSの過剰プロビジョニングを分析し適正サイズを推奨 | **AWS Compute Optimizer** |
| 通常と異なる予期せぬ費用の急増（スパイク）を自動検知してアラート通知 | **AWS Cost Anomaly Detection** |

## 14.2 ストレージのコスト最適化

| ストレージの利用状況・課題 | 推奨されるコスト削減策 |
|---|---|
| 時間経過とともにアクセス頻度が低下するログやデータ | **S3ライフサイクルポリシー**を設定し、S3 Standard → Standard-IA → Glacier Flexible → Glacier Deep Archiveへ自動移行。 |
| アクセスパターンが予測困難、または不規則に変化するデータ | **S3 Intelligent-Tiering**（データ取り出し料金なし、監視・自動階層化料金のみで最適な層へ自動移動）。 |
| 障害時に再生成可能な中間処理データやサムネイル画像 | **S3 One Zone-IA**（単一AZ配置による保管料金の削減）。 |
| 途中で失敗・中断したマルチパートアップロードの不完全なパーツデータが蓄積 | S3ライフサイクルルールで**不完全なマルチパートアップロードの自動破棄**（数日後）を設定。 |
| 古い世代のオブジェクトや不要なスナップショットによる容量圧迫 | S3の非現行バージョンの失効ルール、**Amazon Data Lifecycle Manager (DLM)** や **AWS Backup** によるスナップショット保持期限の自動適用。 |
| EBSボリュームのストレージおよびIOPSコストの見直し | **Amazon EBS gp2からgp3への移行**（容量を増やさずにベースラインIOPS/スループットを確保可能で最大20%安価）、未アタッチの孤立EBSボリュームの削除。 |
| Amazon EFSのストレージコスト削減 | **EFSライフサイクル管理**を有効化し、一定期間アクセスのないファイルを低頻度アクセス（IA）ストレージクラスへ自動移行、単一AZ利用ならOne Zoneストレージクラスを採用。 |
| インターネットおよびリージョン間のデータ転送料金が過大 | **Amazon CloudFront**によるエッジキャッシュ、**VPC内からS3/DynamoDBへのアクセスにはゲートウェイ型VPCエンドポイントを採用**（通信料・NAT Gatewayデータ処理料が無料）、同一AZ内通信の徹底。 |
| CloudWatch Logsの長期保管による課金増大 | ロググループの**保持期間（Retention Period）を無期限から適切な日数に設定**、長期保管が必要なログはS3へエクスポートしてGlacierへ退避。 |

> [!NOTE]
> **データ転送料金の原則**：AWSへの**インバウンドデータ転送（外部からAWS内への受信）は原則無料**。一方、**アウトバウンドデータ転送（AWSからインターネットへの送信）および異なるAZ間・異なるリージョン間のデータ転送は有料**となる。

## 14.3 コンピューティングのコスト最適化

| ワークロード特性 | 最適なコンピューティング購入オプション・設計 |
|---|---|
| **中断耐性のあるバッチ処理、CI/CD環境、ビッグデータ分散計算（EMR等）** | **EC2 スポットインスタンス**（オンデマンド比で最大90%割引、Fargate SpotやAWS Batchでの活用）。※「中断されても処理を再試行・継続できるか」が選定の必須前提。 |
| 1年または3年間にわたり継続的かつ安定して稼働する定常ワークロード | **Compute Savings Plans** または **EC2 Instance Savings Plans**（高い柔軟性とコミット割引）、**リザーブドインスタンス（RI）**。 |
| 開発・検証環境が夜間や休日もアイドル稼働している | **スケジュールスケーリング**または**AWS Instance Scheduler**を用いた営業時間外の自動停止。 |
| 低負荷なEC2インスタンスの過剰サイジング | **AWS Compute Optimizer**に基づくダウンサイジング、**AWS Gravitonプロセッサ搭載インスタンス**への移行（優れた価格性能比）。 |
| トラフィックが断続的、またはアクセス頻度が極めて低いワークロード | **AWS Lambda**（リクエストがないアイドル時は課金ゼロ）。※Fargateはタスクが1台でも起動していれば時間課金が継続する点に留意。 |
| 商用ソフトウェアのコア数課金ライセンス費用が過大 | **Amazon EC2 Dedicated Host** を採用し、BYOL（ライセンス持ち込み）でソケット数・コア数を固定管理。 |

**購入オプションの組み合わせベストプラクティス**：
- ベースライン負荷（24時間365日定常稼働する最小構成）：**Savings Plans / リザーブドインスタンス**
- 予測可能な日中の負荷増加分：**オンデマンドインスタンス**（または変動に追従するAuto Scaling）
- 突発的で中断耐性のある処理・キュー滞留の消化：**スポットインスタンス**

## 14.4 データベースのコスト最適化

| データベース運用の課題 | 推奨されるコスト最適化策 |
|---|---|
| 長期的に常時稼働する本番リレーショナルDB | **RDS / Aurora リザーブドインスタンス**（1年または3年コミットによる大幅割引）。 |
| 開発・テスト環境のDBインスタンス費用 | 夜間・休日の手動停止（最大7日間で自動再起動される点に注意）、または**Amazon Aurora Serverless v2**による動的スケーリング。 |
| 読み取り性能向上のためにリードレプリカを追加し続けている | **Amazon ElastiCache**によるクエリ結果のインメモリキャッシング（高価なDBインスタンスを追加するよりも費用対効果が高い場合が多い）。 |
| Amazon DynamoDBのトラフィックが安定的かつ予測可能 | オンデマンドモードから**プロビジョンドキャパシティモード ＋ Auto Scaling**への切り替え（定常利用ではプロビジョンドの方が安価）。 |
| DynamoDBテーブルに古い時系列ログデータが蓄積 | **Time to Live (TTL)** を有効化して不要データを無料自動削除、または定期的にS3へエクスポートしてテーブルサイズを圧縮。 |
| 数十MB〜数GBの大容量BLOBデータがデータベースを圧迫 | **実体データをAmazon S3に格納し、データベースにはそのS3オブジェクトURL（メタデータ）のみを保持**するアーキテクチャへの分離。 |
| データ分析・集計のためだけに巨大なRDBMSを稼働 | **S3データレイク ＋ Amazon Athena**（スキャンデータ量課金）や**Amazon Redshift Serverless**への移行。 |

## 14.5 コスト削減における「3つの観点」の区別

設問が「何を最小化したいのか」によって、正解となる選択肢が異なる。

| 設問の要件表現 | 最小化の対象 | 選択すべきアーキテクチャの方向性 |
|---|---|---|
| **「運用負荷（管理工数）を最小化したい」** | 人件費・サーバー保守作業・パッチ適用工数 | **フルマネージドサービス、サーバーレスアーキテクチャ**（AWSの利用料自体はEC2自作構成より高くなる場合があっても正解となる）。 |
| **「AWS利用料（請求額）を最小化したい」** | AWSインフラへの月額支払額 | **Savings Plans / スポットインスタンス、ストレージ階層化、適正サイジング**。 |
| **「総所有コスト（TCO）を最小化したい」** | インフラ利用料 ＋ 人的運用工数 ＋ 機会損失 | サーバーレスへの移行による運用工数削減とアイドルコスト排除の組み合わせ。 |

> [!WARNING]
> **試験における最重要ルール**：
> 「最もコスト効率の良い構成を選べ」という設問であっても、**「可用性」「耐障害性」「RTO/RPO」「性能要件」を満たせない選択肢はすべて不正解（誤答）**となる。例えば、「マルチAZをシングルAZに変更する」「バックアップ頻度を減らしてRPOを満たせなくする」といった選択肢はコストが下がっても選んではならない。

## 14.6 設計ケーススタディ：昼夜で負荷が大きく変動するWebアプリケーションの費用比較

### 要件定義
- 社内向け業務Webアプリケーション。
- 平日の日中（9:00〜18:00）は多数のリクエストが発生するが、夜間および休日はリクエストがほぼゼロになる。
- 営業時間中はアベイラビリティゾーン（AZ）障害が発生してもサービスを停止させない（マルチAZ要件）。
- 専任のインフラ運用担当者は1名であり、管理負荷を極力抑えたい。

### 前提・制約条件
1. 営業時間内は単一AZ障害に耐えられる高可用性を備えていること。
2. 営業時間外は停止または最小構成へのスケールインが許容される。

### 候補となるアーキテクチャと課金モデルの比較

| 候補アプローチ | 課金単位と特性 | 夜間・休日（アイドル時）の費用 | 運用保守の工数 |
|---|---|---|---|
| **候補A：EC2 Auto Scaling（複数AZ） ＋ Savings Plans** | インスタンス稼働時間単位。Savings Plans（SP）は一定額のコミットに対して常時課金が発生。 | 夜間に最小インスタンス数へスケールインしても、**コミットしたSPの基本料金は発生し続ける**。 | ゲストOSのパッチ適用、AMI更新、セキュリティ運用が必要。 |
| **候補B：Amazon ECS on AWS Fargate ＋ スケジュールスケーリング** | タスクに割り当てたvCPU・メモリ×秒単位。 | **夜間にスケジュールスケーリングでタスク数を0（または1）にスケールインすることで、コンピュート費用を極小化可能**。 | サーバーホストの管理は不要。コンテナイメージの管理のみ。 |
| **候補C：AWS Lambda ＋ Amazon API Gateway** | リクエスト数 ＋ 実行ミリ秒×メモリ量。 | **リクエストが完全にゼロであれば、コンピュート費用は1円も発生しない**。 | サーバー管理・OSパッチは完全不要。15分の実行時間制限やコールドスタート対策を考慮。 |
| **候補D：単一EC2インスタンス（夜間停止スクリプト）** | 起動時間課金。停止中はEBSストレージ費用のみ。 | 停止中はインスタンス料金ゼロ。 | **単一障害点（SPOF）が存在し、営業時間中のマルチAZ可用性要件を満たせない**ため不採用。 |

### 採用判断
- 既存のアプリケーションがすでにコンテナ化されている場合、**候補B（ECS on Fargate ＋ スケジュールスケーリング）**が最適解となる。日中はマルチAZで最小2タスクを維持し、夜間はタスク数を0または1へスケールインすることで、可用性要件と運用負荷軽減、コスト最適化を同時に達成できる。
- 新規開発でステートレスな軽量APIとして実装可能であれば、**候補C（Lambda ＋ API Gateway）**が夜間アイドルコスト完全ゼロかつ運用負荷最小を達成できる。

### 条件変更時の再評価

| 変更された要件 | 設計変更点 | 技術的根拠 |
|---|---|---|
| 24時間365日、昼夜を問わず高負荷なトラフィックが一定して発生する | **候補A（EC2 Auto Scaling ＋ Compute Savings Plans）**を採用 | 定常的な連続高負荷環境では、従量課金型のサーバーレス（Lambda/Fargate）よりも、リソースを固定して長期コミット割引（最大72%）を適用したEC2の方が大幅に安価となるため。 |
| 開発・ステージング環境であり、可用性要件（マルチAZ）が不要 | **候補D（単一EC2 ＋ AWS Instance Schedulerによる夜間自動停止）**を採用 | 業務影響がない環境であれば、冗長構成を排除して稼働時間を絞ることが最大のコスト削減となるため。 |
