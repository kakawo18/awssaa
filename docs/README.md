## 使い方

2. 週末など時間が取れるときに **第2部（分野別）** で判断フローを通す。

### 全体を貫く4つの判断軸
1. **運用負荷**：「オーバーヘッドを最小限に」＝マネージド／サーバーレス。
2. **可用性**：単一AZ・単一インスタンスの選択肢は原則外す。
3. **コスト**：要件を満たす候補に絞ってから、その中の最安を選ぶ。
4. **セキュリティ**：認証情報を置かない・暗号化する・公開しない・最小権限。

## 編集方針（執筆者向け）

### 数値・上限・料金・時間の書き方（出典方針）

数字は「現行仕様」であって「試験の正解」ではない。読者が根拠を追えて、保守時に古い値を見つけられる形で書く。

**原則**
1. 主要な数値は **付録B「数字で覚えるもの」の表に集約**し、章本文からは「（→付録B）」で参照する。同じ上限表を複数の章に重複させない。
2. 付録Bの表は次の4列で書く。

   | 項目 | 値・種類 | 条件 | 根拠・確認日 |
   |---|---|---|---|
   | SQS メッセージ最大サイズ | 1,048,576 bytes（1 MiB）・上限 | 送信するメッセージ本体。S3参照方式（拡張クライアント、最大2GB）とは別 | [公式クォータ](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html)・2026-09-13 |

3. 「値・種類」の**種類**は次のいずれかを必ず付ける。
   - **既定**：設定を変えなければこの値（例：可視性タイムアウト30秒）
   - **上限（調整可）**：Service Quotas 等で引き上げられる（例：Lambda 同時実行1,000）
   - **上限（固定）**：引き上げ不可のハード上限（例：Lambda 15分）
   - **目安**：AWSが「通常〜」と示す値で保証ではない（例：Aurora フェイルオーバー30秒以内）
   - **SLA**：契約上の値。設計目標と混同しない
4. **条件**には、値が変わる要因を書く：リージョン、エンジン/バージョン、構成（モード・オプション）、単位（MiB か MB か、TPS か メッセージ/秒か）、周辺料金の有無。
5. **根拠・確認日**は、実際にそのページを開いて値を確かめた日を書く。推測で埋めない。確認できなかった項目は「未確認」と書き、暗記必須の扱いにしない。
6. 「無料」と書くときは、サービス本体と周辺料金（データ転送、リクエスト、監視）を分ける。時間は「保証値」か「構成依存の目安」かを示す。
7. 章本文で数字に触れるときは、**その数字がなぜ設計判断に効くのか**（例：可視性タイムアウトが処理時間より短いと二重処理になる）を添え、値だけを並べない。

**現行仕様と試験の関係**
- 仕様変更（上限の引き上げなど）は現行値を正とし、必要なら「従来は〜」と併記する。ただし最新機能が必ず出題されるとは扱わない。
- 設問文に条件が明示されている場合はそちらを優先する、と読者に案内する。
