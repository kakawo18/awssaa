# AWS SAA 試験ポイント集（隙間時間用）

**サービス間の違いを「問題文のキーワード → 答え」で引けること**に特化した要点集です。各節は2〜3分で読み切れる分量に構成しています。

## 使い方
1. 最初に **[第0章 設計の基礎と問題の読み方](./00-foundations.md)** を読み、6つの判断軸・可用性と耐久性・RTO/RPO・設問を解く順序の基礎を固めます。
2. 移動中は **第1部（章別）** を1節ずつ読み、各サービスの仕組みと「選ぶ条件／選ばない条件」を押さえます。
3. 週末などまとまった時間が取れるときに **第2部（分野別）** の設計ケースを読み、前提条件が1つ変わった際に答えがどう変化するかを理解します。
4. 試験直前は **付録A・B** を総復習用の対照表として活用します。候補を思い浮かべたあと、右端の「確認する条件」をチェックします。

### 全体を貫く4つの判断軸
1. **運用負荷**：「運用のオーバーヘッドを最小限に」という表現はマネージドサービスやサーバーレスを示唆しますが、実行時間の制限、OSレベルの制御要件、常時稼働といった制約によっては対象外となることがあります。
2. **可用性**：設問で高可用性が求められている場合、単一AZや単一インスタンスの構成は要件を満たしません。逆に可用性要件が特に指定されていない場合は、最もコストの低い構成が正解となるケースがあります。
3. **コスト**：要件（可用性・RTO・性能など）を確実に満たす候補を洗い出した上で、その中から最も安価な構成を選びます。
4. **セキュリティ**：認証情報をハードコードしない、暗号化を徹底する、不要な公開を避ける、最小権限を適用する、が基本です。また「ネットワーク的に到達できること」と「リソースへの操作が認可されること」は別のレイヤーとして切り分けて考えます。

より詳細な6つの軸（通信・障害・データ・処理・性能・費用）については [第0章](./00-foundations.md) を参照してください。

## 編集方針（執筆者向け）

### 到達基準（何ができれば「理解した」と言えるか）

「キーワードから候補サービスを思い浮かべられる」ことは学習の入り口にすぎず、最終目標ではありません。各節では次の3つの到達基準を目指します。

1. 設問の条件から**適切な候補を挙げられる**
2. **他の候補を除外できる理由を論理的に説明できる**（例：「AではなくBを選ぶのは、〜という条件があるため」）
3. **前提条件が一部変更されても適切に判断できる**（例：「接続元がオンプレミス環境であれば答えが変わる」）

### 節の共通形式

主要な節（各章の中心となるサービス、比較表の対象）は次の構成で統一します。全項目が必須ではありませんが、**2・3・4・5 を欠くと単なる「暗記表」になってしまう**ため、原則としてこれらは省略しません。

| # | 見出し | 記載内容 | 分量の目安 |
|---|---|---|---|
| 1 | **困りごと** | そのサービスがないとどのような課題が生じるか。読者が既に知っている構成の弱点から解説する | 1〜2文 |
| 2 | **仕組み** | 入力→処理→出力の流れ。データがどこに配置され、いつ削除されるか。必要に応じて簡易表や時系列図を用いる | 3〜6行 |
| 3 | **選ぶ条件** | どのような要件をどう満たすために採用するのか。単なるキーワードではなく要件ベースで記載する | 箇条書き2〜4個 |
| 4 | **選ばない条件** | 他のサービスを選択すべき制約条件。「〜の場合は X ではなく Y」の形式で記載する | 箇条書き2〜4個 |
| 5 | **条件違いの例** | 条件を一部変えた2〜3のケース。各ケースにおける「正解」と「他候補を除外する理由」を示す | 表1つ |
| 6 | **理解確認** | 他候補を除外する理由を読者自身が説明できるかを問う。必ず模範解答を併記する | 問い1〜3個 |
| 7 | **公式出典** | 数値や仕様の根拠となるURL・適用条件・確認日（付録Bの表と同一形式） | 必要なもののみ |

**記入例（6.1 SQS の「困りごと」「仕組み」の冒頭）**

> **困りごと**：リクエストの受信速度がバックエンドの処理速度を上回ると、同期処理の構成では待機時間の増大やタイムアウトが発生します。SQSを介して処理要求をキューに保持することで、受付と処理を切り離し、ワーカーが処理可能なペースで順次取り出せるようになります。ただし、キューに仕事を蓄積するだけで後段の処理能力そのものが向上するわけではありません。
>
> **仕組み**：メッセージ送信 → キューへ保存 → ワーカーによる受信（この間、該当メッセージは他のワーカーから一時的に不可視化＝可視性タイムアウト） → 処理実行 → **処理成功後にワーカー自身がメッセージを削除**。削除されないまま可視性タイムアウトが経過すると、メッセージは再び可視状態に戻り、別のワーカーによって再受信されます。

完全な適用例は [第6章 6.1 Amazon SQS](./06-integration.md) を参照してください。

### 教材の粒度

- コアとなる解説は**2〜3分程度で読める**分量を目安とします。ただし、分量制限のために必要な前提条件を削ることは避け、前提が複雑な場合は「基礎」と「発展」に切り分けます。
- 各節の内容を **基礎**（仕組みと選定要件）／**選び分け**（他候補との比較、条件変化のパターン）／**発展・仕様確認**（詳細なクォータや新機能）に整理し、初回通読時に細かな上限値の暗記を強いません。
- 「9割決まる」「頻出」「一択」「即決」といった、客観的根拠のない出題頻度の誇張や断定的な表現は避け、「〜という条件が提示されている場合は」と論理的な根拠を明示します。
- 「不正解」と解説する際は、なぜその選択肢が要件を満たさないのかという理由を必ず併記します。サービス名のみを根拠なく不正解扱いしません。

### 数値・上限・料金・時間の記載方針（出典の扱い）

数値は「現時点の公式仕様」であり、それ自体の丸暗記が試験の目的ではありません。読者が根拠を確認でき、仕様変更時にも古い記述を特定できるように記述します。

**原則**
1. 主要な数値は **付録B「数字で覚えるもの」の表に集約**し、各章の本文からは「（→付録B）」として参照します。同一の上限表を複数の章で重複して記載しません。
2. 付録Bの表は次の4列で構成します。

   | 項目 | 値・種類 | 条件 | 根拠・確認日 |
   |---|---|---|---|
   | SQS メッセージ最大サイズ | 1,048,576 bytes（1 MiB）・上限 | 送信するメッセージ本体。S3参照方式（拡張クライアント、最大2GB）とは別 | [公式クォータ](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html)・2026-09-13 |

3. 「値・種類」の**種類**には、以下の区分のいずれかを必ず明記します。
   - **既定**：明示的に変更しない場合のデフォルト値（例：可視性タイムアウト30秒）
   - **上限（調整可）**：Service Quotas 等を通じて引き上げ可能な上限値（例：Lambda 同時実行数1,000）
   - **上限（固定）**：原則として引き上げられないハードリミット（例：Lambda 実行時間15分）
   - **目安**：AWS公式が「通常〜」と案内している値であり、保証値ではないもの（例：Aurora フェイルオーバー時間30秒以内）
   - **SLA**：契約上保証されるサービスレベル目標。設計目標値と混同しないよう注意する
4. **条件**の列には、値が変動する要因（リージョン、エンジン/バージョン、モードやオプション、単位区分［MiB/MB、TPS/メッセージ毎秒］、周辺料金の有無など）を明記します。
5. **根拠・確認日**には、実際にドキュメントを参照して仕様を確認した日付を記載します。推測で補うことはせず、確認できなかった項目は「未確認」と明記し、暗記必須の事項としては扱いません。
6. 「無料」と表記する場合は、サービス自体の基本料金と周辺で発生する料金（データ転送料、リクエスト料、監視メトリクス料など）を明確に区別します。時間についても「SLA等の保証値」なのか「環境に依存する目安値」なのかを区別します。
7. 各章の本文で数値に言及する際は、**その数値がなぜアーキテクチャの選定・設計判断に影響を与えるのか**（例：可視性タイムアウトが処理所要時間より短いと二重処理が発生する、など）という背景を併記し、単なる数値の羅列にならないようにします。

**現行仕様と試験との関係**
- 仕様変更（クォータの引き上げなど）が生じた場合は現行の仕様を正とし、必要に応じて「従来の仕様では〜」と補足を加えます。ただし、最新機能が試験で必ず問われるわけではない点にも留意します。
- 設問文に前提条件が明記されている場合は、そちらの指示が常に優先される旨を読者に案内します。
