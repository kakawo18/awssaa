# AWS SAA 試験ポイント集（隙間時間用）

**サービス間の違いを「問題文のキーワード → 答え」で引けること**に特化した要点集。各節は2〜3分で読み切れる分量にしてあります。

## 使い方
1. 最初に **[第0章 設計の基礎と問題の読み方](./00-foundations.md)** を読み、6つの判断軸・可用性と耐久性・RTO/RPO・設問を解く順序を固める。
2. 移動中は **第1部（章別）** を1節ずつ読み、各サービスの仕組みと「選ぶ条件／選ばない条件」を押さえる。
3. 週末など時間が取れるときに **第2部（分野別）** の設計ケースで、条件を1つ変えたときに答えがどう変わるかを練習する。
4. 試験直前は **付録A・B** を復習表として使う。候補を思い出したら、最後の列の「確認する条件」に戻る。

### 全体を貫く4つの判断軸
1. **運用負荷**：「オーバーヘッドを最小限に」はマネージド／サーバーレスを示すが、実行時間・OS制御・常時稼働の要件で外れることがある。
2. **可用性**：設問に可用性要件があるなら、単一AZ・単一インスタンスは満たさない。要件がなければ最安の構成が正解になり得る。
3. **コスト**：要件（可用性・RTO・性能）を満たす候補に絞ってから、その中の最安を選ぶ。
4. **セキュリティ**：認証情報を置かない・暗号化する・公開しない・最小権限。到達できることと操作が許可されることは別。

より細かい6軸（通信・障害・データ・処理・性能・費用）は [第0章](./00-foundations.md) を参照。

## 編集方針（執筆者向け）

### 到達基準（何ができれば「分かった」とするか）

「キーワードを見て候補を思い出せる」は入口であって到達点ではない。各節の到達基準は次の3つ。

1. 設問の条件から**候補を挙げられる**
2. **別候補を外す理由を言える**（「Aではなく B なのは、〜という条件があるから」）
3. **条件を1つ変えられても対応できる**（「接続元がオンプレなら答えが変わる」）

### 節の共通形式

主要な節（各章の中心サービス、比較表の対象）は次の並びで書く。すべての節に一括適用はせず、改訂する節から順に揃える。全項目が必須ではないが、**2・3・4・5 を欠いた節は「暗記表」に戻ってしまう**ので、それらは省かない。

| # | 見出し | 書くこと | 分量の目安 |
|---|---|---|---|
| 1 | **困りごと** | このサービスがないと何に困るか。読者が既に知っている構成の弱点から入る | 1〜2文 |
| 2 | **仕組み** | 入力→処理→出力。データはどこに置かれ、いつ消えるか。必要なら小さな表や時系列 | 3〜6行 |
| 3 | **選ぶ条件** | どの要件をどう満たすから選ぶのか。キーワードではなく要件で書く | 箇条書き2〜4個 |
| 4 | **選ばない条件** | 別候補になる制約。「〜なら X ではなく Y」の形で | 箇条書き2〜4個 |
| 5 | **条件違いの例** | 条件を1つ変えた2〜3ケース。各ケースに「答え」と「他候補を外す理由」 | 表1つ |
| 6 | **理解確認** | 他候補を外す理由を読者に説明させる問い。解答例を必ず添える | 問い1〜3個 |
| 7 | **公式出典** | 数字や仕様を支えるURL・適用条件・確認日（付録Bの表と同じ形式） | 必要なものだけ |

**記入例（6.1 SQS の「困りごと」「仕組み」の冒頭）**

> **困りごと**：受付の速度が処理の速度を上回ると、その場で処理する構成では待ち時間やタイムアウトが増えます。SQSに仕事を預けると、受付と処理を分離し、ワーカーが処理できるペースで取り出せます。ただし、仕事をためること自体で後段の処理能力が増えるわけではありません。
>
> **仕組み**：送信→キューに保存→ワーカーが受信（この間メッセージは他のワーカーから見えなくなる＝可視性タイムアウト）→処理→**成功したらワーカーが削除**。削除されずにタイムアウトが切れると、再び見えるようになり別のワーカーが受信する。

完全な適用例は [第6章 6.1 Amazon SQS](./06-integration.md) を参照。

### 教材の粒度

- コアの説明は**2〜3分で読める**分量を目安にする。ただし、分量に合わせるために前提条件を削らない。前提が長いなら「基礎」と「発展」に分ける。
- 各節の内容を **基礎**（仕組みと選ぶ条件）／**選び分け**（別候補との違い、条件違いの例）／**発展・仕様確認**（細かい上限、新機能）に区別し、初読で上限の暗記を強制しない。
- 「9割決まる」「毎回出る」「一択」「即決」など、根拠のない出題頻度や断定は書かない。代わりに「〜という条件があれば」と条件を書く。
- 「不正解」と書くときは、なぜ要件を満たさないかを添える。サービス名だけを不正解扱いしない。

### 数値・上限・料金・時間の書き方（出典方針）

数字は「現行仕様」であって「試験の正解」ではない。読者が根拠を追えて、保守時に古い値を見つけられる形で書く。

**原則**
1. 主要な数値は **付録B「数字で覚えるもの」の表に集約**し、章本文からは「（→付録B）」で参照する。同じ上限表を複数の章に重複させない。
2. 付録Bの表は次の4列で書く。

   | 項目 | 値・種類 | 条件 | 根拠・確認日 |
   |---|---|---|---|
   | SQS メッセージ最大サイズ | 1,048,576 bytes（1 MiB）・上限 | 送信するメッセージ本体。S3参照方式（拡張クライアント、最大2GB）とは別 | [公式クォータ](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html)・2026-09-13 |

3. 「値・種類」の**種類**は次のいずれかを必ず付ける。
   - **既定**：設定を変えなければこの値（例：可視性タイムアウト30秒）
   - **上限（調整可）**：Service Quotas 等で引き上げられる（例：Lambda 同時実行1,000）
   - **上限（固定）**：引き上げ不可のハード上限（例：Lambda 15分）
   - **目安**：AWSが「通常〜」と示す値で保証ではない（例：Aurora フェイルオーバー30秒以内）
   - **SLA**：契約上の値。設計目標と混同しない
4. **条件**には、値が変わる要因を書く：リージョン、エンジン/バージョン、構成（モード・オプション）、単位（MiB か MB か、TPS か メッセージ/秒か）、周辺料金の有無。
5. **根拠・確認日**は、実際にそのページを開いて値を確かめた日を書く。推測で埋めない。確認できなかった項目は「未確認」と書き、暗記必須の扱いにしない。
6. 「無料」と書くときは、サービス本体と周辺料金（データ転送、リクエスト、監視）を分ける。時間は「保証値」か「構成依存の目安」かを示す。
7. 章本文で数字に触れるときは、**その数字がなぜ設計判断に効くのか**（例：可視性タイムアウトが処理時間より短いと二重処理になる）を添え、値だけを並べない。

**現行仕様と試験の関係**
- 仕様変更（上限の引き上げなど）は現行値を正とし、必要なら「従来は〜」と併記する。ただし最新機能が必ず出題されるとは扱わない。
- 設問文に条件が明示されている場合はそちらを優先する、と読者に案内する。
