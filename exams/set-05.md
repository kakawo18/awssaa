### Q1 ｜ マルチアカウント統制 ｜ ★★

企業が新規事業ごとにAWSアカウントを発行する方針を決めました。各アカウントには、ログの集約、ガードレールの適用、標準的なネットワーク構成が最初から備わっている必要があります。アカウント発行のたびに手作業で設定する運用は避けたいと考えています。適切なサービスはどれですか。

- **A.** AWS Control Towerでランディングゾーンを構築し、Account Factoryでアカウントを発行する
- **B.** AWS Organizationsを有効化し、アカウント作成後にSCPを手動で適用する
- **C.** AWS CloudFormation StackSetsのみで各アカウントへリソースを展開する
- **D.** AWS Service Catalogで承認済みのアカウント設定を配布する

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：「**マルチアカウント基盤をベストプラクティス構成で自動的に立ち上げる**」のがControl Towerです。Organizations、SCP、ログ集約、アカウント発行（Account Factory）を一括で用意します。

**他の選択肢を外す理由**
- **B**：Organizations単体では請求統合とSCPの適用まで。ログ集約やネットワークの標準化、発行の自動化は自前で組む必要があります。
- **C**：StackSetsはリソースの展開手段であり、アカウントそのものの発行やガードレールの枠組みは提供しません（Control Towerの内部でも使われます）。
- **D**：Service Catalogは利用者に承認済みの構成テンプレートを配布する仕組みで、アカウント基盤の構築とは目的が異なります。

**参照**：[第8章 8.5 AWS Organizations](../docs/08-management.md) ／ [第11章 11.1 アクセス管理](../docs/11-secure.md)

</details>

### Q2 ｜ オンプレミス接続 ｜ ★★★

本社データセンターとAWS間を、**帯域が安定した専用線**で接続しています。監査部門から「経路上のデータはすべて暗号化されていること」という指摘を受けました。既存の接続方式は維持したまま、最小の変更で対応する方法はどれですか。

- **A.** Direct Connectの上にIPsec VPN（またはMACsec）を構成し、通信を暗号化する
- **B.** Direct Connectを解約し、Site-to-Site VPNのみに切り替える
- **C.** Direct Connect Gatewayを追加する
- **D.** 転送するデータをアプリケーション側でS3へアップロードしてから処理する

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**Direct Connectは既定では暗号化されません**。専用線の帯域特性を保ったまま暗号化要件を満たすには、その上にIPsec VPNを重ねるか、対応回線でMACsecを使います。

**他の選択肢を外す理由**
- **B**：VPNはインターネット経由のため、専用線の「安定した帯域・低レイテンシ」という前提を失います。
- **C**：DX Gatewayは複数リージョン・複数VPCへ接続を広げる仕組みで、暗号化とは無関係です。
- **D**：経路の暗号化要件に対する回答になっておらず、アプリケーションの作り替えも必要になります。

**参照**：[第3章 3.3 VPCの外部接続](../docs/03-network.md) ／ [第11章 11.2 データ保護](../docs/11-secure.md)

</details>

### Q3 ｜ 暗号鍵の管理 ｜ ★★★

金融機関のシステムで、規制により「**暗号鍵は専有のハードウェアで管理し、FIPS 140-2 レベル3の検証を受けていること**」「鍵素材はクラウド事業者にも一切触らせないこと」が求められています。適切なサービスはどれですか。

- **A.** AWS CloudHSM
- **B.** AWS KMSのカスタマー管理キー（自動ローテーション有効）
- **C.** AWS KMSのAWSマネージドキー
- **D.** AWS Secrets Manager

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**専有HSM・FIPS 140-2 レベル3・鍵素材の完全な自己管理**という要件はCloudHSMです（KMSのカスタムキーストアと組み合わせることもできます）。

**他の選択肢を外す理由**
- **B**：KMSはマネージドな共有HSM基盤で、専有ハードウェアの要件を満たしません。
- **C**：AWSマネージドキーはポリシーの変更もできず、要件から最も遠い選択肢です。
- **D**：Secrets Managerは資格情報の保管とローテーションのサービスで、暗号鍵のハードウェア要件とは関係ありません。

**参照**：[第5章 5.8 AWS KMS](../docs/05-security.md) ／ [第11章 11.2 データ保護](../docs/11-secure.md)

</details>

### Q4 ｜ API設計 ｜ ★★

社内向けのモノリシックなアプリケーションから、参照系の機能だけを切り出してAPIとして外部パートナーへ公開することになりました。パートナーごとに**呼び出し回数の上限**を設け、超過分は遮断する必要があります。バックエンドはLambda関数で実装します。適切な構成はどれですか。

- **A.** Amazon API Gatewayで公開し、APIキーと使用量プランでパートナーごとの上限を設定する
- **B.** Application Load BalancerのターゲットにLambdaを登録し、WAFのレートベースルールで制限する
- **C.** Lambda関数URLを発行し、関数内で呼び出し回数をカウントする
- **D.** CloudFrontを前段に置き、キャッシュのTTLを長くする

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**利用者ごとの流量制御（APIキー＋使用量プラン）**はAPI Gatewayの標準機能です。スロットリングでバックエンドも保護できます。

**他の選択肢を外す理由**
- **B**：WAFのレートベースルールは主にIP単位の制限で、パートナー単位の契約上限を管理する仕組みとしては粗すぎます。
- **C**：カウント処理を自前で実装・保守することになり、超過時の遮断やプラン管理も作り込みが必要です。
- **D**：キャッシュは負荷軽減には効きますが、契約上の呼び出し回数の上限管理にはなりません。

**参照**：[第10章 10.1 Amazon API Gateway](../docs/10-others.md) ／ [第12章 12.2 疎結合アーキテクチャ](../docs/12-resilient.md)

</details>

### Q5 ｜ コンテナ移行 ｜ ★★

オンプレミスで稼働するDockerアプリケーションをAWSへ移行します。開発チームにKubernetesの運用経験はなく、**EC2インスタンスの管理も避けたい**と考えています。既存のDockerfileはそのまま使う方針です。適切な構成はどれですか。

- **A.** Amazon ECS on AWS Fargate
- **B.** Amazon EKS on Amazon EC2（マネージドノードグループ）
- **C.** Amazon EC2上にDockerを導入して直接実行する
- **D.** AWS Lambdaのコンテナイメージサポートを利用する

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**Kubernetesの記述がない＋サーバー管理をしたくない**＝ECS on Fargateです。AWSサービスとの統合が容易で、運用負荷が最も低くなります。

**他の選択肢を外す理由**
- **B**：Kubernetesの学習・運用コストが発生し、EC2ノードの管理も残ります。要件と逆方向です。
- **C**：OSのパッチ適用、スケーリング、障害対応をすべて自前で担うことになります。
- **D**：Lambdaは15分の実行時間制限とイベント駆動の実行モデルが前提です。常時稼働するWebアプリケーションの移行先としては制約が大きすぎます。

**参照**：[第9章 9.3 AWS Fargate](../docs/09-container.md) ／ [第12章 12.3 サーバーレステクノロジーの活用](../docs/12-resilient.md)

</details>

### Q6 ｜ 高可用性 ｜ ★★★

単一AZのEC2インスタンス1台とRDSシングルAZ構成で動いているアプリケーションを、**AZ障害が起きてもサービスを継続できる**構成に変更します。実施すべき対策はどれですか。**2つ選択してください。**

- **A.** EC2をAuto Scalingグループに入れ、複数AZのサブネットにまたがってALB配下で最低2台稼働させる
- **B.** RDSをマルチAZ配置に変更する
- **C.** EC2のインスタンスタイプを1つ大きいサイズへ変更する
- **D.** EBSのスナップショットを1時間おきに取得する
- **E.** RDSのリードレプリカを同一AZに1台追加する

<details>
<summary>解答と解説</summary>

**正解：A・B**

**決め手**：AZ障害への耐性は「**複数AZに冗長化する**」ことでしか得られません。アプリ層はASG＋ELB＋マルチAZ、DB層はマルチAZ配置が定型です。

**他の選択肢を外す理由**
- **C**：スケールアップは処理能力の話で、AZ障害時には同じように停止します。
- **D**：スナップショットは復旧の材料であり、障害時にサービスを継続させるものではありません（RPOの改善にとどまります）。
- **E**：同一AZにレプリカを置いても、そのAZが落ちれば同時に失われます（別AZへ置けば可用性にも寄与しますが、自動フェイルオーバーはマルチAZ配置の役割です）。

**参照**：[第12章 12.5 高可用性と耐障害性](../docs/12-resilient.md) ／ [第0章 0.2 可用性と耐久性](../docs/00-foundations.md)

</details>

### Q7 ｜ データ取り込み ｜ ★★

数万台のIoTデバイスから送られるテレメトリを、**追加のコードを書かずに**S3へ集約し、Parquet形式に変換して保存したいと考えています。取り込みは数分程度の遅延が許容されます。運用負荷を最小にする構成はどれですか。

- **A.** Amazon Data Firehose（旧 Kinesis Data Firehose）でS3へ配信し、形式変換を有効にする
- **B.** Kinesis Data Streamsで受け、独自のコンシューマーアプリケーションでS3へ書き出す
- **C.** Amazon SQSで受け、Lambdaで変換してS3へ書き出す
- **D.** Amazon EMRクラスターを常時稼働させ、デバイスから直接書き込ませる

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：「**S3などへ配送するだけ**」「**コード不要・完全マネージド**」「数分の遅延が許容」はFirehoseの適用条件です。Parquetへの形式変換も組み込み機能で行えます。

**他の選択肢を外す理由**
- **B**：Data Streamsはコンシューマーを自分で実装・運用する前提で、順序保証や再処理が必要な場合に選びます。今回は要件に含まれていません。
- **C**：実装と運用が必要になり、「追加のコードを書かずに」という要件に反します。
- **D**：常時稼働のEMRはコストが高く、取り込みの入口としても適しません。

**参照**：[第7章 7.1 Amazon Kinesis](../docs/07-analytics.md) ／ [第13章 13.1 ストレージとパフォーマンス](../docs/13-performance.md)

</details>

### Q8 ｜ データ変換と分析 ｜ ★★

S3に蓄積した生ログに対し、**スキーマを自動的に推論してカタログ化**し、ETL処理を行ったうえで、アナリストがSQLでアドホックに分析できるようにしたいと考えています。サーバーの管理は避けたい方針です。適切な組み合わせはどれですか。

- **A.** AWS Glue（クローラーとETLジョブ）＋ Amazon Athena
- **B.** Amazon EMR（Spark）＋ Amazon Redshift
- **C.** AWS Lambda（変換）＋ Amazon RDS
- **D.** Amazon Kinesis Data Streams ＋ Amazon QuickSight

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**スキーマ推論とカタログ化＝Glueクローラー／サーバーレスETL＝Glueジョブ／S3への直接SQL＝Athena**。いずれもサーバー管理が不要です。

**他の選択肢を外す理由**
- **B**：EMRはクラスターの構成管理が必要で、Redshiftも常時稼働のクラスター運用を伴います。「サーバー管理を避けたい」に反します。
- **C**：Lambdaでの大規模ETLは実行時間の制約があり、RDSはアドホックな大規模分析の基盤には適しません。
- **D**：Data Streamsはリアルタイム取り込みの仕組みで、蓄積済みデータのカタログ化・変換は行いません。QuickSightは可視化であり、データを取得する層が別途必要です。

**参照**：[第7章 7.2 AWS Glue](../docs/07-analytics.md) ／ [第7章 7.3 Amazon Athena](../docs/07-analytics.md)

</details>

### Q9 ｜ ロードバランサーの選択 ｜ ★★

サードパーティ製の仮想ファイアウォールアプライアンスを導入し、VPCへ出入りするトラフィックをすべて検査したうえで転送する構成を作ります。アプライアンスは複数台で冗長化し、スケールさせる必要があります。適切なサービスはどれですか。

- **A.** Gateway Load Balancer
- **B.** Application Load Balancer
- **C.** Network Load Balancer
- **D.** Amazon Route 53の加重ルーティング

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**サードパーティの仮想アプライアンス（ファイアウォール、IDS/IPS）を透過的に挟み込み、冗長化・スケールさせる**のがGateway Load Balancerの役割です（GENEVEプロトコルでカプセル化します）。

**他の選択肢を外す理由**
- **B**：ALBはL7のHTTP/HTTPS向けで、すべてのトラフィックを透過的に検査する用途には使えません。
- **C**：NLBはL4の負荷分散で、アプライアンスへの透過的な引き込み（ミラーではなくインライン挿入）の仕組みは持ちません。
- **D**：Route 53はDNSレベルの振り分けで、パケットの検査経路を構成するものではありません。

**参照**：[第3章 3.5 負荷分散（ELB）](../docs/03-network.md) ／ [付録A ネットワーク](../docs/90-comparison.md)

</details>

### Q10 ｜ ストレージのコスト ｜ ★★

数百台のEC2インスタンスで、汎用SSD（gp2）のEBSボリュームを使用しています。現在のIOPS使用状況を調べたところ、多くのボリュームで割り当てIOPSを持て余している一方、一部のボリュームではIOPS不足のためにサイズだけを大きくして対応していました。コストと性能の両面で最も適切な対処はどれですか。

- **A.** gp3へ変更し、必要なIOPSとスループットを容量とは独立に設定する
- **B.** すべてのボリュームをio2 Block Expressへ変更する
- **C.** IOPS不足のボリュームだけをさらに大きなサイズへ拡張する
- **D.** スループット最適化HDD（st1）へ変更する

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：gp3は**IOPSとスループットを容量から切り離して設定**できます。容量を増やしてIOPSを稼ぐ必要がなくなり、gp2より単価も安くなります。

**他の選択肢を外す理由**
- **B**：io2 Block Expressは最高水準の性能を要するDB向けで、単価が高くコスト最適化に反します。
- **C**：容量課金が増え続けるうえ、余っているボリュームの無駄は解消されません。
- **D**：st1はシーケンシャルなスループット向けのHDDで、ブートボリュームにも使えず、ランダムIOPSを要する用途には不適です。

**参照**：[第2章 2.2 Amazon EBS](../docs/02-storage.md) ／ [第14章 14.2 ストレージのコスト最適化](../docs/14-cost.md)

</details>
