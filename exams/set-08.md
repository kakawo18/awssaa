# 問題セット08 ｜ 頻出②：ストレージの選択とデータ移行

> 全10問・目安15分。各問の「解答と解説」を開くと正解が表示されます。
> 本試験の問題は含みません。出題形式に沿ったオリジナル問題です。
>
> **このセットのねらい**：共有ストレージの選び分けと、移行・転送サービス（Storage Gateway／DataSync／Snow／DMS／Transfer Family）は
> **毎回問われるうえに取り違えやすい**領域です。「使い続けるのか、移すのか」「オンラインか、物理輸送か」で切り分けます。

### Q1 ｜ 共有ストレージの選択 ｜ ★★

Linux上で動くコンテンツ管理システムを、複数のEC2インスタンスへスケールアウトします。各インスタンスは**同じディレクトリを同時に読み書き**する必要があり、容量は使用量に応じて自動的に増減してほしいと考えています。適切なストレージはどれですか。

- **A.** Amazon S3をファイルシステムとしてマウントする
- **B.** Amazon EBS（gp3）を各インスタンスにアタッチする
- **C.** Amazon EBS Multi-Attach（io2）
- **D.** Amazon EFS

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：**「複数のインスタンスから同時にマウント」「Linux／NFS」「容量の自動拡張」＝EFS**。マルチAZに分散配置されるため可用性も高まります。

**他の選択肢を外す理由**
- **A**：S3はオブジェクトストレージで、POSIXのファイルロックや部分更新を前提とするCMSの用途には向きません。
- **B**：EBSは単一インスタンスにアタッチするブロックストレージで、別々のボリュームになるため内容を共有できません。
- **C**：Multi-Attachは**io1/io2かつ同一AZ限定**で、さらにクラスタ対応ファイルシステムの導入が前提です。一般的なファイル共有には適しません。

**参照**：[第2章 2.3 Amazon EFS](../docs/02-storage.md) ／ [付録A ストレージ](../docs/90-comparison.md)

</details>

### Q2 ｜ 共有ストレージの選択 ｜ ★★

社内の**Windowsファイルサーバー**をAWSへ移行します。要件は (1) SMBプロトコルで既存のクライアントからそのまま接続できる、(2) **Active Directoryのユーザー権限（NTFS ACL）をそのまま使う**、(3) サーバーの運用をやめたい、の3つです。適切なサービスはどれですか。

- **A.** Amazon FSx for Lustre
- **B.** Amazon EFS
- **C.** Amazon FSx for Windows File Server
- **D.** EC2にWindows Serverを構築してファイルサーバーにする

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：**Windows・SMB・Active Directory統合・NTFS ACL**というキーワードが揃えばFSx for Windows File Serverです。

**他の選択肢を外す理由**
- **A**：FSx for LustreはHPC・機械学習向けの高スループット並列ファイルシステムで、用途が異なります。
- **B**：EFSはLinux向けのNFSで、SMBやNTFS ACLには対応しません。
- **D**：OSのパッチ適用やバックアップなど運用が残り、要件(3)に反します。

**参照**：[第2章 2.4 Amazon FSx](../docs/02-storage.md) ／ [付録A ストレージ](../docs/90-comparison.md)

</details>

### Q3 ｜ ハイブリッドストレージ ｜ ★★★

オンプレミスのバックアップソフトウェアが、物理テープライブラリへバックアップを書き出しています。テープ装置を廃止したいものの、**バックアップソフトウェアは変更したくありません**。適切なサービスはどれですか。

- **A.** AWS DataSync
- **B.** AWS Storage Gateway の S3 File Gateway
- **C.** AWS Storage Gateway の Tape Gateway（仮想テープライブラリ）
- **D.** AWS Backup

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：**「既存のバックアップソフトのテープ装置をそのまま置き換える」＝Tape Gateway（VTL）**。バックアップソフトからは従来のテープ装置に見え、実体はS3／Glacierに保管されます。

**他の選択肢を外す理由**
- **A**：DataSyncはファイルの転送サービスで、テープ装置としては振る舞いません。
- **B**：File GatewayはNFS/SMBのファイル共有として見せる方式で、テープインターフェースは提供しません。
- **D**：AWS BackupはAWSリソースのバックアップを一元管理するサービスで、オンプレのバックアップソフトのテープ出力先にはなりません。

**参照**：[第2章 2.6 AWS Storage Gateway](../docs/02-storage.md)

</details>

### Q4 ｜ 移行方式の選択 ｜ ★★★

オンプレミスのNASに蓄積された**300 TB**のデータをS3へ移行します。拠点のインターネット回線は実効 **100 Mbps** で、業務時間帯は帯域を空けられません。移行はできるだけ短期間で完了させたい考えです。適切な方法はどれですか。

- **A.** S3 Transfer Acceleration を有効化してアップロードする
- **B.** AWS DataSync でインターネット経由の転送をスケジュール実行する
- **C.** AWS Transfer Family のSFTPエンドポイントへアップロードする
- **D.** AWS Snowball Edge を利用して物理デバイスで移送する

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：**回線容量と転送量の比**で判断します。100 Mbps で 300 TB は、理論値でも **270日以上**（300 TB ÷ 100 Mbps ≒ 6,600時間超）かかります。**回線が細い／データが大きい／期限がある**ならSnow Familyの物理移送です。※Snowball Edgeは2025年11月7日から既存顧客のみの提供です（新規にはDataSyncやAWS Data Transfer Terminalが案内されています）。試験では今も「帯域が足りない大容量移送＝Snowball」の対応で出るため、判断の手順として押さえます。

**他の選択肢を外す理由**
- **A**：Transfer Accelerationは遠距離のレイテンシを改善する機能で、帯域そのものを増やすわけではありません。
- **B**：DataSyncは転送を効率化しますが、**物理的な回線容量の上限は超えられません**。
- **C**：Transfer Familyは既存のSFTP運用を維持するためのサービスで、大容量の一括移行手段ではありません。

**参照**：[第10章 10.15 その他の移行サービス](../docs/10-others.md) ／ [第10章 10.13 AWS DataSync](../docs/10-others.md)

</details>

### Q5 ｜ 移行方式の選択 ｜ ★★

オンプレミスのNFSサーバーにある **2 TB** のファイルを、毎晩Amazon EFSへ同期します。差分のみを効率よく転送し、転送後にデータの整合性も検証したいと考えています。適切なサービスはどれですか。

- **A.** AWS DataSync
- **B.** AWS Storage Gateway の S3 File Gateway
- **C.** rsync を cron で実行するスクリプトをEC2上に構築する
- **D.** AWS Snowcone

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**「オンプレ↔AWSの定期的なファイル同期」「増分転送」「整合性チェック」＝DataSync**。NFS/SMB/HDFSからS3・EFS・FSxへ転送できます。

**他の選択肢を外す理由**
- **B**：Storage Gatewayは**オンプレから使い続ける**ためのハイブリッド運用の仕組みで、同期ジョブの管理は行いません。
- **C**：自前実装は保守・監視・再試行・整合性検証をすべて自分で担うことになります。
- **D**：Snowconeは物理デバイスによる少量データの移送用で、毎晩の同期には使えません（2024年11月に提供終了済み）。

**参照**：[第10章 10.13 AWS DataSync](../docs/10-others.md) ／ [第2章 2.6 AWS Storage Gateway](../docs/02-storage.md)

</details>

### Q6 ｜ データベース移行 ｜ ★★★

オンプレミスのOracleデータベース（4 TB）をAmazon Aurora PostgreSQLへ移行します。要件は (1) **停止時間を数分以内**に抑える、(2) スキーマとストアドプロシージャを変換する、の2つです。適切な組み合わせはどれですか。

- **A.** AWS DMSのフルロードのみを実行し、完了後にアプリケーションを切り替える
- **B.** AWS SCT（Schema Conversion Tool）でスキーマを変換し、AWS DMSの継続的レプリケーション（CDC）で差分同期してから切り替える
- **C.** Oracleのデータポンプでエクスポートし、S3経由でインポートする
- **D.** AWS DataSyncでデータファイルを転送する

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：**異種DB移行＝SCT（スキーマ変換）＋DMS（データ移行）**、**停止時間の最小化＝CDCによる継続的レプリケーション**。この組み合わせが定番です。

**他の選択肢を外す理由**
- **A**：フルロードのみでは、ロード中の更新が反映されず、停止時間もデータ量に比例して長くなります。
- **C**：データポンプは同種DB間の手段で、PostgreSQLへの異種移行ではスキーマ変換の問題が残り、停止時間も長くなります。
- **D**：DataSyncはファイル転送サービスで、稼働中のDBの論理的な移行には使えません。

**参照**：[第10章 10.12 AWS Database Migration Service](../docs/10-others.md)

</details>

### Q7 ｜ 外部連携 ｜ ★★

取引先30社が、毎日**SFTPクライアント**でファイルを送信してきます。現在はEC2上にSFTPサーバーを構築して運用していますが、パッチ適用と可用性の確保が負担です。取引先の接続方法は変更できません。適切な移行先はどれですか。

- **A.** AWS Transfer Family のSFTPエンドポイントを作成し、保存先をS3にする
- **B.** S3の事前署名URLを毎日発行して取引先へ配布する
- **C.** AWS DataSyncのエージェントを取引先に導入してもらう
- **D.** Amazon AppFlowで取引先のシステムと連携する

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**「取引先の既存SFTPクライアントを変えられない」「サーバー運用をやめたい」＝Transfer Family**。認証はIAM・Active Directory・カスタムIDプロバイダーと連携でき、保存先はS3またはEFSです。

**他の選択肢を外す理由**
- **B**：接続方法の変更を取引先に強いることになり、前提に反します。
- **C**：取引先側にエージェント導入を求めるのは現実的でなく、DataSyncの用途とも異なります。
- **D**：AppFlowはSaaS（SalesforceやZendeskなど）との連携用で、SFTPの受け口にはなりません。

**参照**：[第10章 10.14 AWS Transfer Family](../docs/10-others.md)

</details>

### Q8 ｜ S3のデータ保護 ｜ ★★★

コンプライアンス要件により、S3バケットのオブジェクトを**別リージョンへ複製**することになりました。設定後に確認すると、**既存のオブジェクトが複製されていません**。原因と対処として正しいものはどれですか。**2つ選択してください。**

- **A.** レプリケーションは設定後に作成・更新されたオブジェクトが対象のため、既存分はS3バッチレプリケーションで複製する
- **B.** 既存オブジェクトを複製するには、バケットのリージョンを変更する必要がある
- **C.** レプリケーション先のストレージクラスをGlacierにすれば既存オブジェクトも複製される
- **D.** レプリケーションはライフサイクルポリシーで設定するため、移行日数を0日にすれば既存分も対象になる
- **E.** レプリケーションにはソースと宛先の両方のバケットで**バージョニングの有効化**が必要である

<details>
<summary>解答と解説</summary>

**正解：A・E**

**決め手**：レプリケーションの前提は**バージョニング**、対象は**設定後の変更分**。既存オブジェクトは**バッチレプリケーション**で別途複製します。

**他の選択肢を外す理由**
- **B**：バケットのリージョンは作成後に変更できません。
- **C**：宛先のストレージクラスは複製対象の範囲とは無関係です。
- **D**：レプリケーションとライフサイクルは別の機能で、ライフサイクルで複製を起こすことはできません。

**参照**：[第2章 2.1 Amazon S3](../docs/02-storage.md) ／ [第12章 12.5 高可用性と耐障害性](../docs/12-resilient.md)

</details>

### Q9 ｜ EC2のストレージ ｜ ★★

動画のトランスコード処理を行うEC2インスタンスで、**処理中の一時ファイル**を最速のディスクに置きたいと考えています。一時ファイルは処理が終われば不要で、インスタンスの停止・終了時に失われても構いません。適切なストレージはどれですか。

- **A.** EBS gp3
- **B.** インスタンスストア（NVMe SSD）
- **C.** EBS st1
- **D.** Amazon EFS

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：**インスタンスストアは物理サーバー直結で最速**。**停止・終了でデータが消える**（再起動では消えない）という性質が、一時ファイルの用途と一致します。

**他の選択肢を外す理由**
- **A**：gp3は永続ストレージで十分高速ですが、ネットワーク越しのためインスタンスストアのレイテンシには及びません。
- **C**：st1はHDDでシーケンシャルなスループット向け、ランダムI/Oの多い一時領域には不適です。
- **D**：EFSはネットワーク共有ファイルシステムで、一時ファイル用途では遅く、コストも無駄になります。

**参照**：[第2章 2.2 Amazon EBS](../docs/02-storage.md) ／ [第13章 13.1 ストレージとパフォーマンス](../docs/13-performance.md)

</details>

### Q10 ｜ 大容量アップロード ｜ ★★

海外の拠点から、**1ファイルあたり20 GB**の測定データをS3（東京リージョン）へ毎日アップロードしています。アップロードの失敗が多く、完了までの時間も長いという問題があります。適切な対処はどれですか。**2つ選択してください。**

- **A.** ストレージクラスをS3 Standard-IAに変更する
- **B.** アップロード先のバケットでバージョニングを有効化する
- **C.** マルチパートアップロードを使い、分割して並列にアップロードする
- **D.** S3 Transfer Accelerationを有効化し、最寄りのエッジロケーション経由で転送する
- **E.** ファイルをGlacier Deep Archiveへ直接アップロードする

<details>
<summary>解答と解説</summary>

**正解：C・D**

**決め手**：**単一PUTの上限は5 GB**であり、20 GBのファイルは**マルチパートアップロードが必須**です（分割・並列・再試行が可能になり、失敗にも強くなります）。加えて**遠距離からの転送はTransfer Acceleration**で改善します。

**他の選択肢を外す理由**
- **A**：ストレージクラスは保管コストの話で、アップロードの速度や成功率には影響しません。
- **B**：バージョニングは誤削除・上書き対策で、転送の問題には関係しません。
- **E**：アーカイブクラスへ直接置いても転送は速くならず、取り出しにも時間がかかるようになります。

**参照**：[第2章 2.1 Amazon S3](../docs/02-storage.md) ／ [第13章 13.1 ストレージとパフォーマンス](../docs/13-performance.md)

</details>
