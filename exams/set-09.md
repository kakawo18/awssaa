### Q1 ｜ 認証の主体 ｜ ★★★

3つのID管理の要件があります。それぞれに最も適したサービスの組み合わせはどれですか。

1. モバイルアプリの**エンドユーザー数百万人**のサインアップ・サインインを実装したい
2. 社員が**50個のAWSアカウント**へ、既存のIdP（Okta）のIDでログインできるようにしたい
3. AWS上のWindows Serverを、**オンプレミスのActive Directory**のユーザーで認証させたい（AWS側にディレクトリを置かない）

- **A.** 1: IAM Identity Center ／ 2: Amazon Cognito ／ 3: AWS Managed Microsoft AD
- **B.** 1: Amazon Cognito ／ 2: IAM Identity Center ／ 3: AD Connector
- **C.** 1: Amazon Cognito ／ 2: IAMユーザーとグループ ／ 3: Simple AD
- **D.** 1: AWS Directory Service ／ 2: IAM Identity Center ／ 3: Amazon Cognito

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：**アプリの利用者＝Cognito／AWSを操作する社員＝IAM Identity Center／Windowsのドメイン認証＝Directory Service**。さらにDirectory Serviceの中では「**AWS側にディレクトリを置かず、オンプレADへ転送する＝AD Connector**」です。

**他の選択肢を外す理由**
- **A**：1と2が逆です。Identity Centerは社内の管理者・開発者向けで、一般消費者のサインアップには使いません。
- **C**：50アカウントに個別のIAMユーザーを作る運用は破綻します。Simple ADはオンプレADとの信頼関係を張れず、要件3を満たしません（Simple ADは2026年6月30日に新規受付を終了しています）。
- **D**：Directory Serviceは消費者向けのサインアップ基盤ではなく、Cognitoはドメイン参加の認証を提供しません。

**参照**：[第5章 5.2 IAM Identity Center](../docs/05-security.md) ／ [第5章 5.3 AWS Directory Service](../docs/05-security.md) ／ [第5章 5.4 Amazon Cognito](../docs/05-security.md)

</details>

### Q2 ｜ ポリシー評価 ｜ ★★★

あるIAMロールには`AmazonS3FullAccess`が付与されています。しかし、そのアカウントが所属するOUに適用されたSCPで、`s3:DeleteObject`が明示的に拒否されています。さらに対象バケットのバケットポリシーでは、当該ロールに対して`s3:*`が明示的に許可されています。このロールは対象バケットのオブジェクトを削除できますか。

- **A.** できる。SCPはルートユーザーにのみ適用されるため
- **B.** できる。バケットポリシーでの明示的な許可が、SCPの拒否を上書きするため
- **C.** できる。IAMポリシーとバケットポリシーの両方で許可されているため
- **D.** できない。SCPによる明示的な拒否は、他のどの許可よりも優先されるため

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：**明示的な拒否（Deny）はすべての許可に優先**します。SCP・IAMポリシー・リソースポリシーのどこか1つでも拒否があれば、その操作は実行できません。

**他の選択肢を外す理由**
- **A**：SCPはメンバーアカウント内のすべてのプリンシパル（ルートユーザーを含む）に適用されます。管理アカウントには効かない、という点との混同に注意します。
- **B**：リソースポリシーの許可がSCPの拒否を上書きすることはありません。評価順の理解を問う典型的な誤答です。
- **C**：「複数箇所で許可されている＝実行できる」ではありません。拒否の有無が先に効きます。

**参照**：[第5章 5.1 AWS IAM](../docs/05-security.md) ／ [第11章 11.1 アクセス管理](../docs/11-secure.md)

</details>

### Q3 ｜ 資格情報の管理 ｜ ★★

アプリケーションの設定値と資格情報をAWSで管理します。要件は (1) RDSのマスターパスワードを**30日ごとに自動でローテーション**する、(2) アプリの機能フラグなど**数百件の設定値を無料で**保管する、の2つです。適切な組み合わせはどれですか。

- **A.** 1: AWS KMS ／ 2: Amazon S3
- **B.** 1: AWS Systems Manager Parameter Store ／ 2: AWS Secrets Manager
- **C.** 1: AWS Secrets Manager ／ 2: AWS Systems Manager Parameter Store
- **D.** 1: AWS Secrets Manager ／ 2: AWS Secrets Manager

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：**自動ローテーションが要件にあるか**で決まります。あればSecrets Manager（RDS等と統合済み・有料）、なければParameter Store（標準パラメータは無料、SecureStringでKMS暗号化）。

**他の選択肢を外す理由**
- **A**：KMSは鍵の管理サービスで、資格情報そのものの保管・ローテーションは行いません。S3に平文で置くのは論外です。
- **B**：Parameter Storeの標準機能には、RDSと統合した自動ローテーションはありません。
- **D**：Secrets Managerはシークレット1件あたりの月額課金があるため、数百件の一般的な設定値には割高です。

**参照**：[第5章 5.10 Secrets Manager vs Parameter Store](../docs/05-security.md)

</details>

### Q4 ｜ 監視 ｜ ★★

EC2インスタンスの**メモリ使用率**と**ディスクの空き容量**が、CloudWatchのメトリクス一覧に表示されず、しきい値アラームを設定できません。適切な対処はどれですか。

- **A.** CloudWatchエージェントをインスタンスに導入し、カスタムメトリクスとして送信する
- **B.** 詳細モニタリングを有効化し、取得間隔を1分にする
- **C.** インスタンスにIAMロールを付与すれば、標準メトリクスとして自動的に収集される
- **D.** VPCフローログを有効化する

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：CloudWatchの標準メトリクスは**ハイパーバイザー視点**で取得されるため、**OSの内部情報であるメモリ使用率やディスク空き容量は含まれません**。エージェントの導入が必要です（試験の頻出ポイント）。

**他の選択肢を外す理由**
- **B**：詳細モニタリングは取得**間隔**を5分から1分にするもので、取得できる**種類**は増えません。
- **C**：IAMロールはエージェントがメトリクスを送信するために必要ですが、ロールだけでは収集されません。
- **D**：フローログはネットワーク通信の記録で、OSのリソース使用率とは無関係です。

**参照**：[第8章 8.1 Amazon CloudWatch](../docs/08-management.md) ／ [第13章 13.2 コンピューティングとパフォーマンス](../docs/13-performance.md)

</details>

### Q5 ｜ 監視と統制 ｜ ★★★

セキュリティ監査の指摘に対応します。要件は (1) **ルートユーザーによるログインが発生したら即座に通知**する、(2) **S3バケットが公開設定になっていないかを継続的に評価し、違反を自動修復**する、の2つです。適切な組み合わせはどれですか。

- **A.** 1: AWS Config ルール ／ 2: CloudTrail のデータイベント
- **B.** 1: CloudTrail → CloudWatch Logs のメトリクスフィルタ＋アラーム → SNS ／ 2: AWS Config ルール＋修復アクション
- **C.** 1: Amazon GuardDuty ／ 2: Amazon Macie
- **D.** 1: AWS Trusted Advisor ／ 2: Amazon Inspector

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：**「特定のAPI操作をリアルタイムに検知」＝CloudTrail＋メトリクスフィルタ＋アラーム**、**「設定が基準に沿っているかを継続評価し直す」＝Config ルール＋修復アクション（SSM Automation）**。

**他の選択肢を外す理由**
- **A**：Configは設定状態の評価であり、ログイン操作そのものの通知には向きません。データイベントはS3オブジェクト操作等の記録で、公開設定の評価はしません。
- **C**：GuardDutyは脅威検知、Macieは機密データの発見で、いずれも設定の準拠評価や自動修復の仕組みではありません。
- **D**：Trusted Advisorは定期的な点検、Inspectorは脆弱性診断で、要件の即時通知・自動修復には対応しません。

**参照**：[第8章 8.2 AWS CloudTrail](../docs/08-management.md) ／ [第8章 8.7 AWS Config](../docs/08-management.md)

</details>

### Q6 ｜ イベント駆動 ｜ ★★

次の2つの自動化を実装します。それぞれに適したサービスはどれですか。

1. **毎日深夜2時**に、未使用リソースを棚卸しするLambda関数を実行する
2. **RDSインスタンスの障害イベントが発生したら**、運用チームのSlackへ通知する

- **A.** 1: Amazon EventBridge（スケジュール式） ／ 2: Amazon EventBridge（イベントパターン）
- **B.** 1: Amazon SQSの遅延キュー ／ 2: Amazon SNS
- **C.** 1: AWS Lambdaのタイマー機能 ／ 2: AWS CloudTrail
- **D.** 1: Amazon EventBridge（スケジュール式） ／ 2: Amazon SQS

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**EventBridgeは「cron/rate式による定期実行」と「AWSサービスの状態変化をルールで振り分ける」の両方を担います**。どちらも試験の定番パターンです。

**他の選択肢を外す理由**
- **B**：SQSの遅延キューは配信を最大15分遅らせる機能で、毎日のスケジュール実行はできません。
- **C**：Lambda自体にスケジュール実行の機能はなく（EventBridgeが起動します）、CloudTrailは記録であって通知の振り分けは行いません。
- **D**：SQSはキューであり、イベントの内容に応じた振り分けや通知の役割は担いません。

**参照**：[第6章 6.3 Amazon EventBridge](../docs/06-integration.md) ／ [第12章 12.4 イベント駆動型アーキテクチャ](../docs/12-resilient.md)

</details>

### Q7 ｜ ワークフロー ｜ ★★★

保険金請求の処理を自動化します。処理は「書類のOCR → 内容の検証 → **金額が100万円を超える場合は管理者の承認を待つ** → 支払い」という流れで、各ステップの失敗時には再試行と補償処理が必要です。承認待ちは数日に及ぶことがあります。適切なサービスはどれですか。

- **A.** AWS Step Functions（標準ワークフロー、コールバックパターンで承認を待つ）
- **B.** 単一のAWS Lambda関数にすべての処理を実装する
- **C.** Amazon SQS FIFOキューで各ステップをつなぐ
- **D.** Amazon EventBridgeのイベントバスで各Lambdaを連鎖させる

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**分岐・再試行・補償処理・長時間の待機**を宣言的に管理できるのがStep Functionsです。標準ワークフローは**最大1年**実行でき、タスクトークンによるコールバックで人の承認を待てます。

**他の選択肢を外す理由**
- **B**：Lambdaの実行時間は**最大15分**で、数日の承認待ちは不可能です。エラー処理も自前実装になります。
- **C**：キューは処理の受け渡しはできますが、条件分岐・状態管理・補償処理の枠組みは提供しません。
- **D**：EventBridgeでの連鎖は、全体の状態把握と再試行・巻き戻しが困難で、長時間の待機状態を管理できません。

**参照**：[第6章 6.4 AWS Step Functions](../docs/06-integration.md) ／ [第12章 12.2 疎結合アーキテクチャ](../docs/12-resilient.md)

</details>

### Q8 ｜ コンテナの権限 ｜ ★★★

Amazon ECS on Fargateで動くアプリケーションが、S3バケットへのアクセスで`AccessDenied`になります。一方、**ECRからのイメージ取得とCloudWatch Logsへのログ出力は正常**に動作しています。修正すべき対象はどれですか。

- **A.** サービスにアタッチされたセキュリティグループでHTTPSのアウトバウンドを許可する
- **B.** タスク実行ロール（task execution role）にS3へのアクセス許可を追加する
- **C.** EC2インスタンスプロファイルにS3へのアクセス許可を追加する
- **D.** タスクロール（task role）にS3へのアクセス許可を追加する

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：**タスクロール＝コンテナ内のアプリが他のAWSサービスを呼ぶための権限**、**タスク実行ロール＝ECSエージェントがイメージ取得とログ出力を行うための権限**。イメージ取得とログが正常なので、実行ロールは正しく機能しています。

**他の選択肢を外す理由**
- **A**：通信が遮断されていればタイムアウトになります。`AccessDenied`は**到達したうえで認可が拒否された**ことを示します。
- **B**：実行ロールはアプリケーションのAPI呼び出しには使われません（症状からも正常に機能していると分かります）。
- **C**：Fargateではインスタンスプロファイルは存在しません（EC2起動タイプの概念です）。

**参照**：[第9章 9.1 Amazon ECS](../docs/09-container.md) ／ [第0章 0.4 通信経路と認可の区別](../docs/00-foundations.md)

</details>

### Q9 ｜ Lambdaの同時実行 ｜ ★★★

同一アカウント内に複数のLambda関数があります。次の2つの問題が発生しました。**それぞれに対する適切な対処を2つ選択してください。**

1. 大量に起動されるバッチ用の関数が同時実行数を占有し、**決済APIの関数がスロットリング**された
2. 決済APIの関数で、**コールドスタートによる初回応答の遅延**が問題になっている

- **A.** 決済APIの関数のタイムアウト値を15分に延長する
- **B.** バッチ用の関数に**予約済み同時実行数**を設定し、使用できる上限を制限する
- **C.** 決済APIの関数に**プロビジョニング済み同時実行数**を設定する
- **D.** バッチ用の関数のメモリ割り当てを減らす
- **E.** 決済APIの関数をVPC内に配置する

<details>
<summary>解答と解説</summary>

**正解：B・C**

**決め手**：**予約済み同時実行＝その関数の上限を固定し、他の関数への影響を隔離する**（スロットリング対策）。**プロビジョニング済み同時実行＝あらかじめ実行環境を温めておく**（コールドスタート対策）。名前が似ているため役割の取り違えが頻出します。

**他の選択肢を外す理由**
- **A**：タイムアウトは1回の実行時間の上限で、同時実行数の枯渇にも初回遅延にも効きません。
- **D**：メモリを減らすとCPUも比例して下がり処理が遅くなるため、占有時間はむしろ延びます。
- **E**：VPC配置はネットワーク到達性のための設定で、コールドスタートはむしろ不利になる場合があります。

**参照**：[第1章 1.6 AWS Lambda](../docs/01-compute.md) ／ [第13章 13.2 コンピューティングとパフォーマンス](../docs/13-performance.md)

</details>

### Q10 ｜ 運用の自動化 ｜ ★★

数百台のEC2インスタンスに対し、OSのセキュリティパッチを**定期的に適用し、適用状況をレポート**したいと考えています。インスタンスへのSSH接続は禁止されています。適切なサービスはどれですか。

- **A.** AWS Config
- **B.** Amazon Inspector
- **C.** AWS Systems Manager Patch Manager（メンテナンスウィンドウで実行）
- **D.** Amazon EventBridge＋Lambdaで各インスタンスへSSH接続してパッチを適用する

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：**パッチ適用の自動化と準拠レポート＝Patch Manager**。SSMエージェント経由で動作するためSSHは不要で、メンテナンスウィンドウで実行時間帯も制御できます。

**他の選択肢を外す理由**
- **A**：Configは設定の記録と準拠評価で、OSのパッチ適用の実行者ではありません。
- **B**：Inspectorは脆弱性を**検出**するサービスで、パッチの適用は行いません（検出→Patch Managerで適用、という組み合わせになります）。
- **D**：SSH接続が禁止されている前提に反し、自前実装の保守負担も大きくなります。

**参照**：[第8章 8.4 AWS Systems Manager](../docs/08-management.md) ／ [第5章 5.12 Amazon Inspector](../docs/05-security.md)

</details>
