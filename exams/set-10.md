### Q1 ｜ スケーリングポリシー ｜ ★★

ECサイトのアクセスは、毎日**朝9時と夜20時に大きく増える**という明確な周期があります。現在はターゲット追跡スケーリングのみを設定していますが、増加の立ち上がりでインスタンスの起動が追いつかず、数分間レスポンスが悪化します。適切な対処はどれですか。

- **A.** クールダウン期間を0秒に設定する
- **B.** ステップスケーリングに変更し、しきい値を細かく刻んで早めに増やす
- **C.** 予測スケーリングを有効にして事前に台数を増やす
- **D.** スケールイン保護をすべてのインスタンスに設定する

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：**周期的な負荷パターンがあり、事後の反応では間に合わない**場合は予測スケーリングです。機械学習で需要を予測し、**負荷が来る前に**容量を用意します（時刻が固定で読めるならスケジュールされたスケーリングでも可）。

**他の選択肢を外す理由**
- **A**：クールダウンを詰めても、しきい値を超えてから起動する点は変わらず、立ち上がりの遅れは解消しません。
- **B**：ステップスケーリングも実測値に反応する方式のため、起動時間そのものは埋められません。
- **D**：スケールイン保護は縮小を止める設定で、増加への追随とは無関係です。

**参照**：[第1章 1.2 EC2 Auto Scaling](../docs/01-compute.md) ／ [第12章 12.1 スケーリング戦略](../docs/12-resilient.md)

</details>

### Q2 ｜ ライフサイクルフック ｜ ★★★

Auto Scalingグループのスケールインでインスタンスが終了する際、**ローカルに残っているアプリケーションログをS3へ退避**してから終了させたいと考えています。退避には最大3分かかります。適切な方法はどれですか。

- **A.** 終了ポリシーを「最も古いインスタンス」に変更する
- **B.** 終了時のライフサイクルフックを設定する
- **C.** ターゲットグループの登録解除の遅延を180秒に設定する
- **D.** インスタンスのシャットダウンスクリプトに、ログをS3へ退避する処理を書く

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：**終了・起動の途中で処理を差し込みたいときはライフサイクルフック**です。インスタンスを待機状態（Terminating:Wait）で止め、処理完了を通知するまで終了を保留できます。

**他の選択肢を外す理由**
- **A**：終了ポリシーは「どのインスタンスを選ぶか」の設定で、終了処理の内容には関与しません。
- **C**：登録解除の遅延は**処理中のリクエストを完了させる**ための待機で、任意の後処理の完了を保証するものではありません。
- **D**：シャットダウンスクリプトは確実な完了を保証できず（強制終了され得る）、失敗時の検知もできません。

**参照**：[第1章 1.2 EC2 Auto Scaling](../docs/01-compute.md)

</details>

### Q3 ｜ Elastic Beanstalk ｜ ★★★

Elastic Beanstalkで運用するアプリケーションのデプロイ要件は、(1) **ダウンタイムを発生させない**、(2) 既存インスタンスの容量を落とさない、(3) 新バージョンに問題があれば**即座に切り戻せる**、の3つです。追加インスタンスのコストは許容できます。適切なデプロイポリシーはどれですか。

- **A.** All at once
- **B.** Rolling
- **C.** Rolling with additional batch
- **D.** Immutable

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：Immutableは**新しいインスタンス群を別に立ち上げてから入れ替える**方式です。既存環境には触れないため容量が落ちず、失敗時は新しい群を破棄するだけで**即座に元に戻せます**。

**他の選択肢を外す理由**
- **A**：全インスタンスを同時に入れ替えるためダウンタイムが発生します。
- **B**：入れ替え中は稼働インスタンスが減り、要件(2)に反します。切り戻しにも再デプロイが必要です。
- **C**：容量は維持できますが、既存インスタンスを段階的に更新するため、切り戻しには再デプロイを要し要件(3)を満たしにくくなります。

**参照**：[第1章 1.3 AWS Elastic Beanstalk](../docs/01-compute.md)

</details>

### Q4 ｜ AMIの管理 ｜ ★★

セキュリティ部門から「**毎月、最新のOSパッチとセキュリティエージェントを適用したゴールデンAMIを作成し、各アカウントへ配布する**」よう求められました。手作業を避けたいと考えています。適切なサービスはどれですか。

- **A.** EC2 Image Builder
- **B.** AWS Systems Manager Patch Manager
- **C.** Amazon Inspector
- **D.** AWS Backup

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**AMIの作成・テスト・配布をパイプラインとして自動化**するのがEC2 Image Builderです。スケジュール実行と他アカウントへの共有まで扱えます。

**他の選択肢を外す理由**
- **B**：Patch Managerは**稼働中のインスタンス**へパッチを適用する仕組みで、AMIの生成・配布は行いません（併用はします）。
- **C**：Inspectorは脆弱性の検出であり、イメージの作成はしません。
- **D**：AWS Backupはバックアップの管理で、ゴールデンイメージの継続的な生成には使いません。

**参照**：[第1章 1.7 その他のコンピューティングサービス](../docs/01-compute.md) ／ [第8章 8.4 AWS Systems Manager](../docs/08-management.md)

</details>

### Q5 ｜ EC2の停止と再開 ｜ ★★★

科学計算アプリケーションは、起動時に**メモリ上へ大きなデータセットを読み込むのに15分**かかります。日中しか使わないため夜間は停止したいのですが、翌朝の起動に毎回15分待たされるのは避けたいと考えています。適切な方法はどれですか。

- **A.** インスタンスを停止せず、夜間はインスタンスタイプを小さく変更する
- **B.** EC2 Hibernate（休止）で停止し、翌朝に再開する
- **C.** 夜間にAMIを作成し、翌朝そのAMIから新しいインスタンスを起動する
- **D.** インスタンスストアにデータセットを保存しておく

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：**Hibernateはメモリの内容をEBSルートボリュームに保存**し、再開時に復元します。長い初期化処理をやり直さずに済みます（対応インスタンスタイプ・暗号化されたルートボリュームなどの条件があります）。

**他の選択肢を外す理由**
- **A**：タイプ変更にも停止が必要なうえ、稼働し続ける分の課金が残ります。
- **C**：AMIから起動しても**メモリの状態は復元されない**ため、15分の読み込みは再度発生します。
- **D**：インスタンスストアは**停止で内容が失われます**。加えてディスクからの読み込み自体は発生します。

**参照**：[第1章 1.1 Amazon EC2](../docs/01-compute.md) ／ [第14章 14.3 コンピューティングのコスト最適化](../docs/14-cost.md)

</details>

### Q6 ｜ Lambdaの起動時間 ｜ ★★★

Java製のLambda関数で、**初回呼び出しの遅延（コールドスタート）が1秒を超える**ことが問題になっています。呼び出しは断続的で、常時ウォームな状態を維持するとコストが見合いません。適切な対処はどれですか。

- **A.** 共通ライブラリをLambdaレイヤーへ移動する
- **B.** プロビジョニング済み同時実行数を常時100に設定する
- **C.** 関数のタイムアウト値を延長する
- **D.** Lambda SnapStartを有効化する

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：**SnapStartは初期化済みの実行環境のスナップショットから復元**するため、追加コストなしでコールドスタートを短縮できます（Javaで顕著に効きます）。

**他の選択肢を外す理由**
- **A**：レイヤーはデプロイパッケージの共通化・管理のための機能で、初期化時間の短縮を保証するものではありません。
- **B**：効果はありますが、常時ウォームな環境を確保する分の料金がかかり「コストが見合わない」という前提に反します。
- **C**：タイムアウトは処理の上限時間で、起動の遅延とは無関係です。

**参照**：[第1章 1.6 AWS Lambda](../docs/01-compute.md) ／ [第13章 13.2 コンピューティングとパフォーマンス](../docs/13-performance.md)

</details>

### Q7 ｜ API Gatewayの種別 ｜ ★★

モバイルアプリ向けのシンプルなプロキシAPI（Lambda統合のみ）を新規に公開します。要件は**可能な限り低コスト・低レイテンシ**で、APIキーや使用量プラン、リクエスト検証、レスポンスキャッシュは不要です。適切な選択はどれですか。

- **A.** HTTP APIを作成する
- **B.** REST APIを作成し、キャッシュを無効化する
- **C.** WebSocket APIを作成する
- **D.** Application Load BalancerにLambdaを直接登録する

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**HTTP APIはREST APIより安価で低レイテンシ**な代わりに機能が絞られています。設問は「絞られた機能が不要」と明示しているため、HTTP APIが最適です。

**他の選択肢を外す理由**
- **B**：REST APIは高機能ですが、使わない機能の分だけ単価が高くなります。
- **C**：WebSocketは双方向通信用で、リクエスト・レスポンス型のAPIには適しません。
- **D**：ALBは時間課金が常時発生し、APIとしての認証・スロットリングなどの機能も別途必要になります。

**参照**：[第10章 10.1 Amazon API Gateway](../docs/10-others.md)

</details>

### Q8 ｜ メッセージング基盤 ｜ ★★

オンプレミスで稼働する社内システム群が、**Apache ActiveMQ（JMS／AMQP）**を介して連携しています。この仕組みをAWSへ移行しますが、**アプリケーションのコードは変更できません**。適切なサービスはどれですか。

- **A.** Amazon MQ
- **B.** Amazon SNS
- **C.** Amazon SQS
- **D.** Amazon Kinesis Data Streams

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：**既存のJMS／AMQPなど標準プロトコルのアプリをコード変更なしで移行するならAmazon MQ**（ActiveMQ／RabbitMQのマネージド版）です。新規開発ならSQS/SNSを選びます。

**他の選択肢を外す理由**
- **B**：SNSもAWS独自のPub/Subで、プロトコル互換性がありません。
- **C**：SQSはAWS独自のAPIで、JMSクライアントからそのまま利用することはできません（コード変更が必要）。
- **D**：Kinesisはストリーミングデータの取り込み基盤で、メッセージブローカーの置き換えではありません。

**参照**：[第6章 6.5 Amazon MQ](../docs/06-integration.md) ／ [付録A アプリケーション統合](../docs/90-comparison.md)

</details>

### Q9 ｜ 通知の振り分け ｜ ★★★

1つのSNSトピックに、注文イベント（`type=order`）と在庫イベント（`type=stock`）の両方が発行されています。在庫管理チームのキューには**在庫イベントだけ**を届けたいと考えています。アプリケーションの発行側は変更できません。適切な方法はどれですか。

- **A.** トピックを用途ごとに分割し、発行側で宛先を送り分ける
- **B.** 在庫チームのキュー側で、不要なメッセージを受信後にLambdaで判定して破棄する
- **C.** サブスクリプションにフィルターポリシーを設定する
- **D.** SQSの可視性タイムアウトを調整する

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：**SNSのフィルターポリシーは、サブスクリプションごとにメッセージ属性で配信を絞り込みます**。発行側に手を入れずに、必要な通知だけを届けられます。

**他の選択肢を外す理由**
- **A**：発行側の変更が必要で、「発行側は変更できない」という前提に反します。
- **B**：不要なメッセージも配信・受信されるため、リクエスト料金と処理の無駄が残ります。
- **D**：可視性タイムアウトは処理中の再配信を防ぐ設定で、配信内容の絞り込みとは無関係です。

**参照**：[第6章 6.2 Amazon SNS](../docs/06-integration.md)

</details>

### Q10 ｜ 起動の遅いワークロード ｜ ★★★

Auto Scalingグループで使うAMIは、アプリケーションの初期化に**約5分**かかります。トラフィックの増加は毎朝ほぼ同じ時間帯に起こりますが、スケールアウトが間に合わず、その間エラー率が上がります。**適切な対策を2つ選択してください。**

- **A.** ウォームプールを構成し、初期化済みのインスタンスを待機状態で確保しておく
- **B.** ヘルスチェックの猶予期間（グレースピリオド）を0秒に短縮する
- **C.** 予測スケーリングを有効にし、需要の増加前に容量を追加する
- **D.** Auto Scalingグループの最大容量を2倍に引き上げる
- **E.** スケールイン時のクールダウンを延長する

<details>
<summary>解答と解説</summary>

**正解：A・C**

**決め手**：**起動に時間がかかる**ことが原因なので、対処は「**あらかじめ用意しておく（ウォームプール）**」か「**早めに増やし始める（予測スケーリング）**」のどちらかです。

**他の選択肢を外す理由**
- **B**：グレースピリオドを短くすると、初期化中のインスタンスが異常と判定されて置き換えられ、状況が悪化します。
- **D**：最大容量は上限値であり、起動の遅さ（立ち上がりの時間）は変わりません。
- **E**：スケールインのクールダウンは縮小の頻度を抑える設定で、スケールアウトの遅れには効きません。

**参照**：[第1章 1.2 EC2 Auto Scaling](../docs/01-compute.md) ／ [第12章 12.1 スケーリング戦略](../docs/12-resilient.md)

</details>
