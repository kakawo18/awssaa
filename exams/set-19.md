### Q1 ｜ 社内専用API ｜ ★★

社内システム向けのREST APIをAPI Gatewayで提供しています。このAPIは**VPC内のアプリケーションからだけ**呼び出せるようにし、インターネットからは到達できないようにしたいと考えています。最も適切な構成はどれですか。

- **A.** リージョンAPIのまま、AWS WAFで社内のIPアドレス範囲以外を拒否する
- **B.** APIキーを必須にし、キーをVPC内のアプリケーションにだけ配布する
- **C.** エッジ最適化APIにし、CloudFrontの地理的制限で日本以外を拒否する
- **D.** プライベートAPIにし、`execute-api` のインターフェース型VPCエンドポイント経由でのみ呼び出させる

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：プライベートAPIは**インターフェース型VPCエンドポイント経由でしか到達できない**API Gatewayのエンドポイント種別です。リソースポリシーで `aws:SourceVpce` などを条件にすれば、呼び出し元をさらに特定のエンドポイントやVPCに絞れます。

**キーワード**：プライベートAPI／インターフェース型VPCエンドポイント

**他の選択肢を外す理由**
- **A**：APIはインターネットに公開されたままです。IPアドレスによる制限だけでは「インターネットから到達できない」状態になりません。
- **B**：APIキーは利用量の管理のためのもので、認証や到達範囲の制御には使えません。キーが漏れれば外部からも呼び出せます。
- **C**：国単位の制限は到達範囲をVPCに絞る仕組みではありません。

**参照**：[第10章 10.1 Amazon API Gateway](../docs/10-others.md) ／ [第3章 3.3 VPCの外部接続](../docs/03-network.md)

</details>

### Q2 ｜ シークレットのDR ｜ ★★

東京リージョンのアプリケーションがSecrets ManagerからDBの認証情報を取得しています。災害対策として大阪リージョンにも同じ構成を用意しますが、**フェイルオーバー時に同じ認証情報をすぐ取得できる**必要があり、ローテーション後の値も両リージョンでそろえたいと考えています。最も運用負荷が小さい方法はどれですか。

- **A.** シークレットを大阪リージョンへレプリケートする
- **B.** 大阪リージョンにも同じ名前のシークレットを手動で作成し、ローテーションのたびに担当者が値を更新する
- **C.** 認証情報をS3に保存し、クロスリージョンレプリケーションで複製する
- **D.** 認証情報をアプリケーションのAMIに埋め込み、AMIを大阪へコピーする

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：Secrets Managerには**シークレットを別リージョンへ複製する機能**があり、プライマリの値が更新・ローテーションされるとレプリカにも反映されます。DRリージョンのアプリは、自リージョンのレプリカから同じ値を取得できます。

**キーワード**：Secrets Managerのレプリケーション

**他の選択肢を外す理由**
- **B**：手作業の同期は漏れや遅れが起きやすく、フェイルオーバー時に値がずれる危険があります。
- **C**：S3に認証情報を置くと管理が煩雑になり、ローテーションとも連動しません。
- **D**：認証情報をイメージに埋め込むのはアンチパターンで、ローテーションにも追従できません。

**参照**：[第5章 5.10 AWS Secrets Manager vs Parameter Store](../docs/05-security.md) ／ [第12章 12.5 高可用性と耐障害性](../docs/12-resilient.md)

</details>

### Q3 ｜ コンテナへの機密情報の受け渡し ｜ ★★

ECS on Fargateのタスク定義で、DBのパスワードを**環境変数に平文で**書いています。タスク定義を閲覧できる人なら誰でもパスワードを読めてしまう状態です。コードの変更を最小限にして改善したいと考えています。最も適切な方法はどれですか。

- **A.** パスワードをBase64でエンコードしてから環境変数に設定する
- **B.** パスワードをコンテナイメージに埋め込み、ECRのリポジトリを非公開にしてイメージの取得をIAMで制限する
- **C.** Secrets Managerに保存してタスク定義の`secrets`で参照し、実行ロールに取得権限を付ける
- **D.** パスワードをS3に保存し、コンテナの起動スクリプトでダウンロードする

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：タスク定義の `secrets` にSecrets Manager（またはParameter Store）のARNを指定すると、**タスクの起動時に値が取得され、環境変数としてコンテナへ渡されます**。アプリは従来どおり環境変数を読むだけなので、コードの変更は不要です。値を取得するのはECSエージェント側なので、権限は**タスク実行ロール**に付けます。

**キーワード**：タスク定義のsecrets／タスク実行ロール

**他の選択肢を外す理由**
- **A**：Base64は暗号化ではなく、誰でも元に戻せます。
- **B**：イメージを取得できる人なら誰でもパスワードを読めます。変更のたびにイメージを作り直す必要もあります。
- **D**：起動スクリプトの変更が必要になり、S3の権限管理も増えます。

**参照**：[第9章 9.1 Amazon ECS](../docs/09-container.md) ／ [第5章 5.10 AWS Secrets Manager vs Parameter Store](../docs/05-security.md)

</details>

### Q4 ｜ 最小権限への絞り込み ｜ ★★

バッチ処理用のIAMロールに、開発初期に `AdministratorAccess` を付与したままになっています。実際に使っている操作だけを許可するポリシーに置き換えたいのですが、どの操作を使っているか誰も把握していません。最も効率的な方法はどれですか。

- **A.** `AdministratorAccess` を外し、エラーが出た操作を1つずつ追加する
- **B.** IAM Access AnalyzerでCloudTrailの記録からポリシーを生成する
- **C.** IAM認証情報レポートをダウンロードして確認する
- **D.** AWS Configで、ロールの設定変更履歴を確認する

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：IAM Access Analyzerは、指定した期間の**CloudTrailのログからロールが実際に呼び出した操作を洗い出し、ポリシーのひな形を生成**できます。これを確認・調整して置き換えるのが、最小権限へ絞り込む最短の手順です。

**キーワード**：IAM Access Analyzerのポリシー生成

**他の選択肢を外す理由**
- **A**：本番のバッチが失敗するたびに権限を足す運用になり、業務への影響が大きくなります。
- **C**：認証情報レポートはIAMユーザーのパスワードやアクセスキー、MFAの状況を一覧にするもので、ロールが使った操作はわかりません。
- **D**：Configで追えるのはロール自体の設定の変更履歴で、ロールがどの操作を呼んだかはわかりません。

**参照**：[第5章 5.1 AWS IAM](../docs/05-security.md) ／ [第11章 11.1 アクセス管理](../docs/11-secure.md)

</details>

### Q5 ｜ 不正なドメインへの通信の遮断 ｜ ★★★

AWS Organizationsで管理する全アカウントのVPCについて、**既知のマルウェア配布ドメインやボットネットのドメイン**へ名前解決や通信ができないようにしたいと考えています。新しいアカウントやVPCにも自動で適用したいと考えています。**適切な対策を2つ選択してください。**

- **A.** 各VPCのセキュリティグループで、対象ドメインへのアウトバウンドを拒否する
- **B.** ネットワークACLで、対象ドメインのIPアドレス範囲を拒否する
- **C.** Route 53 ResolverのDNS Firewallでブロックする
- **D.** AWS WAFのWeb ACLを各VPCに関連付ける
- **E.** Firewall Managerで組織全体のVPCへ一括適用する

<details>
<summary>解答と解説</summary>

**正解：C・E**

**決め手**：**ドメイン名で止める**にはDNS Firewallが適しています。VPCからの名前解決の段階でブロックでき、AWSが管理する脅威ドメインのリストも使えます。**組織全体への一括適用と、新しいアカウント・VPCへの自動適用**はFirewall Managerの役割です。

**キーワード**：Route 53 ResolverのDNS Firewall／AWS Firewall Manager

**他の選択肢を外す理由**
- **A**：セキュリティグループには拒否ルールがなく、ドメイン名も指定できません。
- **B**：ネットワークACLはIPアドレスでしか指定できず、変わり続ける攻撃者のIPアドレスを追いかけるのは現実的ではありません。
- **D**：WAFはCloudFrontやALBなどに届くHTTPリクエストを検査するもので、VPCからの外向きの名前解決や通信は対象外です。

**参照**：[第3章 3.4 名前解決：Route 53 と Resolver](../docs/03-network.md) ／ [第5章 5.13 その他のセキュリティ・ガバナンスサービス](../docs/05-security.md)

</details>

### Q6 ｜ アカウントをまたぐイベント連携 ｜ ★★

20個のワークロードアカウントで発生する特定のイベント（EC2の状態変化やGuardDutyの検出結果）を、**セキュリティアカウントで一元的に処理**したいと考えています。処理はセキュリティアカウントのLambda関数で行います。最も運用負荷が小さい構成はどれですか。

- **A.** 各アカウントのEventBridgeルールで、セキュリティアカウントのイベントバスへ転送する
- **B.** 各アカウントにLambda関数を配置し、処理結果をセキュリティアカウントのS3バケットに書き込む
- **C.** 各アカウントのCloudTrailログをセキュリティアカウントに集約し、1時間ごとにLambdaで解析する
- **D.** 各アカウントからSNSトピックへ発行し、セキュリティアカウントの担当者がメールで確認する

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：EventBridgeは**別アカウントのイベントバスを直接ターゲットにできます**。各アカウントのルールで対象イベントを転送し、セキュリティアカウントのイベントバスで受けて、そこのルールからLambdaを起動します。処理のロジックを1か所にまとめられ、イベント駆動でほぼリアルタイムに動きます。

**キーワード**：EventBridgeのクロスアカウントのイベントバス

**他の選択肢を外す理由**
- **B**：処理のロジックが20アカウントに分散し、更新や監視の負荷が大きくなります。
- **C**：1時間ごとのバッチ処理では即応できず、ログ解析の実装も必要になります。
- **D**：人手の確認は自動処理の要件を満たしません。

**参照**：[第6章 6.3 Amazon EventBridge](../docs/06-integration.md) ／ [第12章 12.4 イベント駆動型アーキテクチャ](../docs/12-resilient.md)

</details>

### Q7 ｜ ワークフローのエラー処理 ｜ ★★

Step Functionsで、外部の決済APIを呼び出すLambda関数を含むワークフローを動かしています。決済APIは**一時的にタイムアウトする**ことがあり、そのたびにワークフロー全体が失敗しています。一時的な失敗は自動でやり直し、それでも失敗した場合は担当者への通知処理に進めたいと考えています。最も適切な方法はどれですか。

- **A.** Lambda関数の中でループを書き、APIが成功するまで何度も呼び出す
- **B.** 該当ステートにRetryとCatchを定義し、失敗時は通知へ進める
- **C.** ワークフロー全体を毎回最初から手動で再実行する
- **D.** Lambda関数のタイムアウトを15分に延長する

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：Step Functionsは、ステートごとに**Retry（エラーの種類・回数・間隔と倍率）**と**Catch（最終的に失敗したときの遷移先）**を宣言的に書けます。再試行と失敗時の分岐を関数のコードではなくワークフローの定義で管理でき、実行履歴にも残ります。

**キーワード**：Retry／Catch

**他の選択肢を外す理由**
- **A**：実行時間と料金が膨らみ、Lambdaの最大実行時間に達する危険もあります。再試行の状況も見えにくくなります。
- **C**：手作業の再実行は自動化の要件に反し、途中まで進んだ処理を二重に実行する危険もあります。
- **D**：タイムアウトを延ばしても、APIの一時的な失敗は解消しません。

**参照**：[第6章 6.4 AWS Step Functions](../docs/06-integration.md)

</details>

### Q8 ｜ オンプレミスサーバーの災害対策 ｜ ★★

オンプレミスの30台の業務サーバー（物理・仮想の混在）について、AWSを災害対策サイトにしたいと考えています。要件は**RPOが数秒、RTOが数分**で、平常時のAWS側のコストは最小限に抑えたいと考えています。最も適切なサービスはどれですか。

- **A.** Elastic Disaster Recoveryで継続的に複製する
- **B.** AWS DataSyncで、サーバーのファイルを1時間ごとにS3へ同期し、災害時にEC2へ書き戻して起動する
- **C.** AWS Backupで、オンプレミスのサーバーを毎日バックアップする
- **D.** AWS Snowball Edgeで、毎月データを輸送する

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：Elastic Disaster Recoveryは、サーバーのディスクを**ブロックレベルで継続的にAWSへ複製**し（RPOは秒単位）、災害時には数分でEC2として起動できます（RTOは分単位）。平常時は低コストのステージング領域に複製を保つだけなので、本番相当のサーバーを常時動かす必要がありません。

**キーワード**：AWS Elastic Disaster Recovery

**他の選択肢を外す理由**
- **B**：ファイルの同期であり、サーバー全体（OSやアプリケーション）を起動し直せる形にはなりません。RPOも1時間です。
- **C**：日次のバックアップではRPOが最大1日になり、復元にも時間がかかります。
- **D**：物理輸送では秒単位のRPOは実現できません。

**参照**：[第12章 12.5 高可用性と耐障害性](../docs/12-resilient.md) ／ [第10章 10.15 その他の移行サービス](../docs/10-others.md)

</details>

### Q9 ｜ テーブルの誤操作への備え ｜ ★★

DynamoDBのテーブルで、運用担当者の誤ったスクリプトにより**大量の項目が上書き**される事故が起きました。今後は、**誤操作の直前の状態に戻せる**ようにし、**テーブルそのものの誤削除**も防ぎたいと考えています。最も適切な組み合わせはどれですか。

- **A.** グローバルテーブルで別リージョンにレプリカを作成する
- **B.** PITRと削除保護を有効にする
- **C.** DAXを導入し、読み取りをキャッシュ経由にする
- **D.** オンデマンドキャパシティモードに変更する

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：PITRを有効にすると、**過去35日間の任意の時点**へ秒単位でテーブルを復元できます。削除保護を有効にすれば、設定を解除しない限りテーブルを削除できません。誤更新と誤削除の両方に対応する組み合わせです。

**キーワード**：ポイントインタイムリカバリ（PITR）／削除保護

**他の選択肢を外す理由**
- **A**：グローバルテーブルは変更を即座に複製するため、誤った上書きもレプリカへそのまま反映されます（レプリケーションはバックアップではありません）。
- **C**：DAXは読み取りの高速化で、データ保護には関係しません。
- **D**：キャパシティモードは課金とスループットの方式で、誤操作への備えにはなりません。

**参照**：[第4章 4.3 Amazon DynamoDB](../docs/04-database.md) ／ [第0章 0.2 可用性と耐久性、冗長化・レプリケーション・バックアップの区別](../docs/00-foundations.md)

</details>

### Q10 ｜ キャッシュの読み取り負荷 ｜ ★★

ElastiCache for Redis（クラスターモード無効、ノード1台）をセッションとランキングのキャッシュに使っています。データ量はノードのメモリに十分収まっていますが、**読み取り**が急増してCPU使用率が高止まりしています。書き込みは少量です。最も適切な対処はどれですか。

- **A.** リードレプリカを追加し、読み取りをリーダーエンドポイントに向ける
- **B.** クラスターモードを有効にし、データを複数のシャードに分散して負荷を分ける
- **C.** Memcachedへ移行する
- **D.** キャッシュのTTLを短くする

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：データ量ではなく**読み取りの集中**が問題なので、同じデータを持つレプリカを増やして読み取りを分散します。リーダーエンドポイントを使えば、アプリは接続先を1つ指定するだけで複数のレプリカに分散できます。レプリカはマルチAZの自動フェイルオーバーにも使えます。

**キーワード**：リードレプリカ／リーダーエンドポイント

**他の選択肢を外す理由**
- **B**：シャーディングは**メモリ容量や書き込み**の限界を広げる手段です。データがメモリに収まっていて書き込みも少ない状況では、構成の変更に見合いません。
- **C**：Memcachedにはレプリケーションや永続化がなく、ランキング（ソート済みセット）などRedisのデータ構造も使えません。
- **D**：TTLを短くするとキャッシュのミスが増え、バックエンドの負荷がかえって上がります。

**参照**：[第4章 4.4 Amazon ElastiCache](../docs/04-database.md) ／ [第13章 13.3 データベースとパフォーマンス](../docs/13-performance.md)

</details>

### Q11 ｜ ストリーミング基盤の移行 ｜ ★

オンプレミスでApache Kafkaを運用しており、多数のプロデューサーとコンシューマーがKafkaのクライアントライブラリで接続しています。AWSへ移行するにあたり、**アプリケーションのコードを変えずに**、ブローカーの運用負荷をなくしたいと考えています。最も適切なサービスはどれですか。

- **A.** Amazon Kinesis Data Streams
- **B.** Amazon SQS
- **C.** Amazon MSK
- **D.** Amazon MQ

<details>
<summary>解答と解説</summary>

**正解：C**

**キーワード**：Amazon MSK

**他の選択肢を外す理由**

- **B**：SQSはキューで、Kafkaのプロトコルやトピック・パーティションの考え方とは異なります。
- **D**：Amazon MQはActiveMQとRabbitMQのマネージドサービスで、Kafkaには対応していません。

**参照**：[第7章 7.9 その他のアナリティクスサービス](../docs/07-analytics.md) ／ [第6章 6.5 Amazon MQ](../docs/06-integration.md)

### Q12 ｜ 夜間のデータ変換 ｜ ★★

毎晩、S3に置かれた数百GBのCSVファイルを結合・変換し、Parquet形式で別のバケットに書き出しています。現在は常時起動のEMRクラスターで処理していますが、**日中はクラスターが遊んでいる**うえ、クラスターの運用にも手間がかかっています。Sparkのコードは流用したいと考えています。最も適切な方法はどれですか。

- **A.** Athenaのクエリで毎晩変換する
- **B.** Lambda関数で1ファイルずつ変換する
- **C.** EMRクラスターのインスタンスタイプを大きくし、夜間の処理時間を短くする
- **D.** AWS GlueのETLジョブ（Spark）に移す

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：Glue ETLは**サーバーレスのSpark実行環境**で、ジョブが動いている間だけ課金されます。既存のSparkのコードを流用でき、クラスターの管理も不要です。スケジュールやジョブブックマーク（処理済みデータの管理）も備えています。

**キーワード**：AWS GlueのETLジョブ

**他の選択肢を外す理由**
- **A**：AthenaのCTASでも変換はできますが、Sparkのコードを流用できず、複雑な結合・変換ロジックの移植が必要になります。
- **B**：数百GBを結合する処理は、Lambdaの実行時間（最大15分）やメモリの制約に合いません。Sparkのコードも流用できません。
- **C**：常時起動のクラスターである限り、日中の遊休コストと運用の手間は残ります。

**参照**：[第7章 7.2 AWS Glue](../docs/07-analytics.md) ／ [第7章 7.8 Amazon EMR](../docs/07-analytics.md)

</details>

### Q13 ｜ サーバーレス関数のコスト ｜ ★★

数百のLambda関数（Python、x86_64）が毎月大量に実行され、Lambdaの料金が増え続けています。関数の多くは**メモリを3GBに設定したまま**ですが、実際の使用量は500MB程度です。ネイティブの依存ライブラリはありません。コードの変更を最小限にしてコストを下げたいと考えています。最も効果的な対策はどれですか。

- **A.** プロビジョニング済み同時実行数を設定する
- **B.** 関数のタイムアウトを短くし、長い処理を打ち切る
- **C.** すべての関数をEC2上のcronジョブに移行する
- **D.** 関数をarm64に切り替え、メモリを見直す

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：Lambdaの料金は**メモリ量×実行時間**で決まるため、過大なメモリ設定を実測に合わせて下げるのが最も直接的です（Compute Optimizerがメモリの推奨を出します）。さらに**arm64はx86_64より単価が安く**、ネイティブの依存ライブラリがないPythonならコードを変えずに切り替えられます。

**キーワード**：arm64（Graviton）

**他の選択肢を外す理由**
- **A**：プロビジョニング済み同時実行数はコールドスタート対策で、待機中の料金が追加でかかります。
- **B**：正常に終わる処理の料金は変わりません。途中で打ち切られる処理が出れば、再実行でかえってコストが増えます。
- **C**：サーバーの管理が必要になり、処理の量に合わせた伸縮もできなくなります。

**参照**：[第1章 1.6 AWS Lambda](../docs/01-compute.md) ／ [第14章 14.3 コンピューティングのコスト最適化](../docs/14-cost.md)

</details>

### Q14 ｜ I/Oの多いデータベース ｜ ★★

Aurora PostgreSQLの請求を分析したところ、**I/Oリクエストの料金がAuroraの費用全体の約半分**を占めており、月ごとの変動も大きいことがわかりました。アプリケーションやインスタンス構成は変えたくありません。最も適切な対策はどれですか。

- **A.** Aurora Serverless v2に移行する
- **B.** リードレプリカを追加して読み取りを分散する
- **C.** Aurora I/O-Optimizedに変更する
- **D.** 自動バックアップの保持期間を短くする

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：Aurora I/O-Optimizedは、**I/Oリクエストの料金がかからない**代わりにインスタンスとストレージの単価が上がる構成です。I/O料金が費用の大きな割合（目安として25%超）を占めるワークロードでは、総額が下がり、請求も予測しやすくなります。構成の切り替えだけで済み、アプリの変更は不要です。

**キーワード**：Aurora I/O-Optimized

**他の選択肢を外す理由**
- **A**：Serverless v2は容量の伸縮による節約策で、I/O料金の課金方式は変わりません。
- **B**：レプリカを増やしてもI/Oの量は減らず、インスタンス料金が増えます。
- **D**：バックアップの保持期間はI/O料金とは関係ありません。

**参照**：[第4章 4.2 Amazon Aurora](../docs/04-database.md) ／ [第14章 14.4 データベースのコスト最適化](../docs/14-cost.md)

</details>

### Q15 ｜ 費用の見張り ｜ ★★

経営層から、「**月末の請求が予算を超えそうなら早めに知りたい**」「**普段と違う急な費用の増加はすぐに検知したい**」という2つの要望がありました。**適切な対策を2つ選択してください。**

- **A.** AWS Budgetsの予算アラートを設定する
- **B.** AWS Trusted Advisorのコスト最適化チェックを毎月確認する
- **C.** Cost and Usage ReportをS3に出力する
- **D.** AWS Cost Anomaly Detectionで、機械学習による異常な支出の検知と通知を設定する
- **E.** AWS Configで、高額なインスタンスタイプの起動を記録する

<details>
<summary>解答と解説</summary>

**正解：A・D**

**決め手**：「予算を**超えそう**」はBudgetsの**予測値に基づくアラート**、「**普段と違う**急増」はCost Anomaly Detectionの役割です。前者は計画との比較、後者は過去のパターンとの比較で、見張る観点が違います。

**キーワード**：AWS Budgets（予測値のアラート）／AWS Cost Anomaly Detection

**他の選択肢を外す理由**
- **B**：Trusted Advisorは削減の余地を示す点検で、予算の超過見込みや急増を通知する仕組みではありません。
- **C**：CURは詳細な分析用のデータで、自分で集計や通知を作り込まない限り、要望には応えられません。
- **E**：Configは構成の記録で、費用の監視や通知の仕組みではありません。

**参照**：[第10章 10.9〜10.11 コスト管理サービス](../docs/10-others.md) ／ [第14章 14.1 コスト管理ツールの使い分け](../docs/14-cost.md)

</details>
