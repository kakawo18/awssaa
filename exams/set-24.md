### Q1 ｜ 共有ファイルシステムの入り口 ｜ ★★

1つのEFSファイルシステムを、3つのアプリケーションで共有しています。要件は、(1) 各アプリケーションは**自分用のディレクトリ**だけを見られること、(2) アプリケーションごとに**決まったPOSIXユーザー・グループ**として読み書きすること、です。最も管理しやすい方法はどれですか。

- **A.** アプリケーションごとに別のEFSファイルシステムを作成する
- **B.** セキュリティグループでアプリケーションごとにNFSの通信を分ける
- **C.** 各インスタンスでマウント後に `chmod` を実行してディレクトリの権限を調整する
- **D.** アプリケーションごとにEFSアクセスポイントを作成する

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：EFSアクセスポイントは、接続したクライアントに**特定のディレクトリをルートとして見せ**、**POSIXのユーザーとグループを強制**できます。IAMポリシーでアプリごとに使えるアクセスポイントを限定することもでき、1つのファイルシステムを安全に共有できます。

**キーワード**：EFSアクセスポイント

**他の選択肢を外す理由**
- **A**：ファイルシステムが増えて管理が分散し、共有の利点を失います。
- **B**：セキュリティグループはネットワークの到達を制御するもので、ディレクトリ単位の制御はできません。
- **C**：各インスタンスの設定に依存し、設定漏れや、ほかのディレクトリへのアクセスを防げません。

**参照**：[第2章 2.3 Amazon EFS](../docs/02-storage.md)

</details>

### Q2 ｜ LinuxとWindowsで同じデータ ｜ ★★

オンプレミスのNetApp製ストレージで、**同じデータをLinuxからはNFS、WindowsからはSMB**で共有しています。スナップショットや重複排除の機能も使っており、運用手順をできるだけ変えずにAWSへ移したいと考えています。最も適切なサービスはどれですか。

- **A.** Amazon FSx for NetApp ONTAP
- **B.** Amazon FSx for Windows File Server
- **C.** Amazon FSx for Lustre
- **D.** Amazon EFS

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：FSx for NetApp ONTAPは、**NFS・SMB・iSCSIを同じデータに対して同時に提供**でき、スナップショットや重複排除などONTAPの機能もそのまま使えます。「NetApp」「マルチプロトコル」がそろえば ONTAP です。

**キーワード**：Amazon FSx for NetApp ONTAP

**他の選択肢を外す理由**
- **B**：FSx for Windows File ServerはSMB向けで、LinuxからのNFSでは共有できません。
- **C**：FSx for LustreはHPC向けの高速ファイルシステムで、SMBには対応していません。
- **D**：EFSはNFSだけで、WindowsのSMBには対応していません。

**参照**：[第2章 2.4 Amazon FSx](../docs/02-storage.md)

</details>

### Q3 ｜ ブロックストレージの拡張 ｜ ★★

工場の生産管理システムは、**オンプレミスのiSCSIボリューム**を使っています。すべてのデータを**ローカルで低遅延に**読み書きしたまま、クラウドにバックアップを取り、災害時にはAWS上で復元できるようにしたいと考えています。最も適切な構成はどれですか。

- **A.** Volume Gatewayのキャッシュ型ボリュームを使う
- **B.** Volume Gatewayの保管型ボリュームを使う
- **C.** S3 File Gatewayを使う
- **D.** Tape Gatewayを使う

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：保管型ボリュームは**全データをオンプレミスに置き**、その特定時点のスナップショットを非同期でAWSへ保存します（EBSスナップショットとして復元可能）。全データを低遅延で扱いながら、クラウドへのバックアップとDRを実現できます。

**キーワード**：Volume Gatewayの保管型ボリューム

**他の選択肢を外す理由**
- **A**：キャッシュ型は**全データをAWS側に置き**、よく使うデータだけをローカルにキャッシュします。すべてのデータを低遅延で扱うという要件を満たしません。
- **C**：S3 File GatewayはNFS/SMBのファイル共有で、iSCSIのブロックストレージではありません。
- **D**：Tape Gatewayはバックアップソフト向けの仮想テープで、業務システムが直接読み書きするボリュームではありません。

**参照**：[第2章 2.6 AWS Storage Gateway](../docs/02-storage.md)

</details>

### Q4 ｜ 大量オブジェクトの一括処理 ｜ ★★

S3バケットに保存された**約5億個のオブジェクト**すべてに、部署名のタグを付け直す必要があります。自前のスクリプトで1つずつ処理すると、何週間もかかり、失敗したオブジェクトの管理も大変です。最も適切な方法はどれですか。

- **A.** EC2インスタンスを多数起動し、オブジェクトの一覧を分担して並列でタグを付け直す
- **B.** S3 Batch Operationsで、既存オブジェクトのタグを一括で置き換える
- **C.** S3のイベント通知でLambda関数を起動し、オブジェクトごとに新しいタグを付け直す
- **D.** ライフサイクルルールでタグを付ける

<details>
<summary>解答と解説</summary>

**正解：B**

**決め手**：S3 Batch Operationsは、**大量の既存オブジェクト**に対してタグの付け替え・コピー・復元・Lambdaの実行などを**1つのジョブ**で行えます。対象はインベントリなどのマニフェストで指定し、進捗や失敗したオブジェクトのレポートも自動で出力されます。

**キーワード**：S3 Batch Operations

**他の選択肢を外す理由**
- **A**：並列化や再試行、失敗の管理を自前で作る必要があり、運用負荷が大きくなります。
- **C**：イベント通知は**新しく作成・変更された**オブジェクトで動く仕組みで、既存のオブジェクトには働きません。
- **D**：ライフサイクルルールはストレージクラスの移行や削除を行うもので、タグは付けられません。

**参照**：[第2章 2.1 Amazon S3](../docs/02-storage.md)

</details>

### Q5 ｜ 復元直後の性能 ｜ ★★

障害訓練で、EBSスナップショットから大量のボリュームを作成してデータベースを起動しました。しかし、**起動直後のしばらくはディスクの読み取りが非常に遅く**、性能要件を満たせませんでした。本番の復旧時は、**ボリュームの作成直後から本来の性能**を出したいと考えています。最も適切な対策はどれですか。

- **A.** 復元先のAZで、高速スナップショット復元（FSR）を有効にする
- **B.** ボリュームタイプをsc1にする
- **C.** スナップショットの取得頻度を上げ、最新の状態から復元できるようにする
- **D.** スナップショットをEBSスナップショットアーカイブに移し、保管コストを下げる

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：通常、スナップショットから作ったボリュームは、データが**最初にアクセスされたときにS3から読み込まれる**ため、初回の読み取りが遅くなります。FSRを有効にしたスナップショットから作ったボリュームは、**作成時点で完全に初期化**されており、すぐに本来の性能を出せます（AZごとに有効化し、料金がかかります）。

**キーワード**：高速スナップショット復元（FSR）

**他の選択肢を外す理由**
- **B**：sc1はさらに性能の低いHDDです。
- **C**：取得頻度はRPOに関係する設定で、復元直後の性能は変わりません。
- **D**：アーカイブ層からの復元はさらに時間がかかります。

**参照**：[第2章 2.2 Amazon EBS](../docs/02-storage.md)

</details>

### Q6 ｜ 無停止でのボリュームの変更 ｜ ★★

本番のEC2インスタンスで使っているgp3ボリュームの**容量とIOPSが不足**してきました。アプリケーションを止めずに、容量とIOPSを増やしたいと考えています。最も適切な方法はどれですか。

- **A.** スナップショットを取得し、大きなボリュームを作成して付け替える
- **B.** インスタンスを停止してから、ボリュームを変更する
- **C.** Elastic Volumesで、接続したまま容量とIOPSを変更する
- **D.** インスタンスストアを追加し、データを移す

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：Elastic Volumesを使えば、EBSボリュームの**容量・タイプ・IOPS・スループットを、接続したまま変更**できます。容量を増やした場合は、OS側でパーティションとファイルシステムを拡張すれば使えるようになります。

**キーワード**：Elastic Volumes

**他の選択肢を外す理由**
- **A**：付け替えには停止や切り替えの作業が必要で、手間もかかります。
- **B**：停止は不要です。停止すれば要件に反します。
- **D**：インスタンスストアは停止や終了で消える一時領域で、本番データの置き場所に向きません。

**参照**：[第2章 2.2 Amazon EBS](../docs/02-storage.md)

</details>

### Q7 ｜ 共有データレイクの権限 ｜ ★★

1つのS3バケットに全社のデータレイクを置き、**数十のチーム**がそれぞれ異なるプレフィックスと権限でアクセスしています。1つのバケットポリシーにすべてのルールを書いた結果、**ポリシーが巨大で変更しにくく**なっています。最も適切な改善策はどれですか。

- **A.** チームごとにS3アクセスポイントを作成する
- **B.** チームごとにバケットを分け、データを複製する
- **C.** バケットのACLでチームごとに権限を付ける
- **D.** すべてのチームに同じIAMロールを使わせる

<details>
<summary>解答と解説</summary>

**正解：A**

**決め手**：S3アクセスポイントは、1つのバケットに対して**用途ごとの入り口と専用のポリシー**を作れる機能です。チームごとに権限を分けて管理でき、特定のVPCからだけ使えるアクセスポイントも作れます。巨大なバケットポリシーを分割する定番の方法です。

**キーワード**：S3アクセスポイント

**他の選択肢を外す理由**
- **B**：データが重複し、同期の管理とコストが増えます。
- **C**：ACLは細かな条件を表現できず、現在は無効にすることが推奨されています。
- **D**：チームごとに権限を分けるという要件に反します。

**参照**：[第2章 2.1 Amazon S3](../docs/02-storage.md)

</details>

### Q8 ｜ 同じエンジンへのDB移行 ｜ ★★

オンプレミスのMySQL（1 TB）を**Aurora MySQL**へ移行します。移行作業中も業務は止められず、**切り替え時の停止は数分以内**にしたいと考えています。最も適切な方法はどれですか。

- **A.** AWS SCTでスキーマを変換してから、DMSでデータを移して切り替える
- **B.** mysqldumpでエクスポートし、Auroraへインポートしてから切り替える
- **C.** AWS DMSで全ロードとCDCを行い、追いついた時点で切り替える
- **D.** Snowball Edgeでデータを輸送する

<details>
<summary>解答と解説</summary>

**正解：C**

**決め手**：DMSは初期の全体ロードの後、**変更データキャプチャ（CDC）で移行中の更新を継続的に反映**できます。移行元を止めずに同期を続け、差分がなくなった時点で接続先を切り替えれば、停止は切り替えの数分だけで済みます。同じMySQL系のエンジン同士なので、スキーマの変換は不要です。

**キーワード**：AWS DMS（全体ロード＋CDC）

**他の選択肢を外す理由**
- **A**：SCTはエンジンが異なる移行（例：OracleからPostgreSQL）で使うものです。同じエンジン同士では不要です。
- **B**：エクスポートからインポートまでの間の更新が反映されず、長い停止が必要になります。
- **D**：輸送の間に発生した更新を反映できず、1 TBであればネットワーク経由で十分に転送できます。

**参照**：[第10章 10.12 AWS Database Migration Service](../docs/10-others.md)

</details>

### Q9 ｜ 一時的な高速処理 ｜ ★★

ゲノム解析のジョブを**数日間だけ**実行します。入力データはS3にあり、処理中は非常に高いスループットのファイルシステムが必要です。結果はS3に書き戻し、ファイルシステムはジョブ終了後に削除します。**コストを最小**にしたいと考えています。最も適切な構成はどれですか。

- **A.** FSx for Windows File Serverを使う
- **B.** FSx for Lustreのパーシステントデプロイタイプを使う
- **C.** EFSのプロビジョンドスループットモードを使う
- **D.** FSx for Lustreのスクラッチを、S3にリンクして使う

<details>
<summary>解答と解説</summary>

**正解：D**

**決め手**：スクラッチは**データの複製を持たない代わりに安価**で、短期間の処理と一時的なデータに向いたデプロイタイプです。S3にリンクすれば、入力を読み込み、結果をS3へ書き戻せます。元データはS3にあるため、ファイルシステムの障害に備える必要もありません。

**キーワード**：FSx for Lustreのスクラッチ

**他の選択肢を外す理由**
- **A**：Windows向けのファイルサーバーで、HPCの用途に合いません。
- **B**：パーシステントは長期間の利用とデータ保護のためのタイプで、数日間だけの処理には割高です。
- **C**：EFSは汎用の共有ファイルシステムで、HPC並みのスループットを出すにはFSx for Lustreより高くつきます。

**参照**：[第2章 2.4 Amazon FSx](../docs/02-storage.md) ／ [第13章 13.1 ストレージとパフォーマンス](../docs/13-performance.md)

</details>

### Q10 ｜ バックアップの一元管理 ｜ ★★★

EC2、EBS、RDS、EFSのバックアップを、アカウントごと・サービスごとのスクリプトで取得しています。監査から、(1) **全リソースのバックアップ方針を一元管理**すること、(2) **管理者であっても保持期間中のバックアップを削除できない**こと、を求められました。**適切な対策を2つ選択してください。**

- **A.** Amazon Data Lifecycle ManagerでEBSのスナップショットだけを管理する
- **B.** AWS Backupのバックアッププランを作成し、タグで対象のリソースを割り当てる
- **C.** 各サービスの手動スナップショットをS3にエクスポートする
- **D.** バックアップボールトにAWS Backup Vault Lock（コンプライアンスモード）を設定する
- **E.** EC2のインスタンスストアにバックアップを保存する

<details>
<summary>解答と解説</summary>

**正解：B・D**

**決め手**：AWS Backupは複数のサービスのバックアップを**1つのプランで一元管理**でき、タグで対象を自動的に割り当てられます。Vault Lockのコンプライアンスモードを設定すると、**ルートユーザーを含む誰であっても**保持期間中のバックアップを削除したり、保持期間を短くしたりできなくなります。

**キーワード**：AWS Backup／AWS Backup Vault Lock

**他の選択肢を外す理由**
- **A**：Data Lifecycle ManagerはEBS（とAMI）が対象で、RDSやEFSは管理できません。
- **C**：手作業の運用が残り、一元管理にも削除防止にもなりません。
- **E**：インスタンスストアはインスタンスの停止や終了で消える一時領域です。

**参照**：[第2章 2.5 AWS Backup](../docs/02-storage.md) ／ [第11章 11.2 データ保護](../docs/11-secure.md)

</details>
